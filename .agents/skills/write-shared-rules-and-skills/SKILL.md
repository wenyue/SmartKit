# Write Shared Rules and Skills

Qualify one portable cross-project SmartKit Rule or Skill, author it through the public
[`write-rules-and-skills`](../../../skills/write-rules-and-skills/SKILL.md) workflow, and close its
portability obligations at handoff. This Skill owns qualification and closure; the public workflow
owns authoring and review mechanics.

## 1. Qualify the request

Continue only for exactly one portable cross-project SmartKit Rule or Skill whose shared owner
and independent provenance are supported. Resolve other requests before public invocation:

| Request | Route |
| --- | --- |
| Project-local artifact or Setup Authoring Contract | Route to its supported owner. |
| Request requiring both a Rule and a Skill | Return separate Rule and Skill requests for `split`. |
| `environment-owned` | Name the active owner and return no Candidate. |
| Other resolved nonshared request | Route to its supported owner. |
| Ambiguous, incompatible, or unresolved ownership | Follow the public `NEEDS_INPUT` route, naming the missing choice, relevant evidence, decision owner, and material consequence. |

Qualify every relied-on fact by owner, provenance, applicability, and limits. Admit portable meaning
only when its cross-project owner and independent provenance are supported. Candidate text,
source-project policy or success, repository layout, packaging or discovery, host injection, tool
availability, and peer transmission can locate or support evidence; none establishes portable
meaning by itself. Project and host instructions constrain work within their scope without adding
portable Candidate meaning or permission.

### Close the input

Prepare one consistent input covering every material portability obligation:

- **Meaning:** accepted outcome, non-goals, safety boundaries, exits, handoff, and the intended
  preservation, change, addition, move, or retirement of each inherited or new obligation.
- **Candidate:** shared owner, applicability, provenance, exact resources, presence expectations,
  and intended public loading, discovery, distribution, and Skill-interface routes.
- **Evidence:** each source, its discovery route, the facts it supports, its representative scope,
  and its source-local limits.
- **Dependencies:** every direct or transitive Rule, Skill, tool, schema, environment capability,
  or host behavior; its owner, required behavior, consumers, supported shared- or target-owned
  route, and observable available, unavailable, and failed-use outcomes.
- **Representative targets:** the smallest nonempty portfolio covering every materially distinct
  applicability, dependency, permission, execution, observation, recovery, and exit seam.
- **Acceptance:** validation and completion duties, accepted permissions and effects, evidence
  characteristics, and observable pass, blocked, and failure conditions.

Name obligations consistently enough to trace them without imposing an ID or record schema.

**Representative coverage.** A portfolio is minimal when removing any target would leave a material
seam uncovered; names and layouts alone do not create seams. For each seam, establish applicable
target facts, consumed obligations and dependencies, permissions, critical success and terminal
paths, recovery and mid-path stops, expected observations, and evidence characteristics. Specify
what evidence must establish, leaving commands, Reviewer identities, case selection, and result
rules to the public workflow.

Require the public Correctness perspective to cover:

- **Portable semantic authority:** shared ownership, applicability, qualified evidence, complete
  dependency routes, and absence of operative source-project assumptions.
- **Representative behavior:** every material seam, critical path, and exit.

Close applicable validation and representative runtime inputs, and require eventual closure
evidence to be bound to the final Candidate fingerprint.

**Permissions and effects.** Close them as accepted input for the public Author brief and the
public job's separate freeze. This private contract neither freezes authority nor defines generic
grant classes. Candidate mutation is limited to the exact Candidate resources; preserve both
endpoints of any requested move for the public write-scope freeze.

Require separate, exact authorization for each representative-target read or execution effect.
These effects remain disjoint from Candidate resources, and their authorization grants no Candidate
mutation; Candidate mutation authority likewise grants no representative-target access or effects.

The input is closed when every material fact, route, permission, pass condition, and completion
obligation has one supported answer and the intended work fits those permissions. Keep the closed
input in Agent context. A missing material answer returns the public `NEEDS_INPUT` result; stop
before public invocation.

## 2. Invoke the public workflow

Pass the closed input unchanged to the public workflow and await its result. Use its mechanisms
without adapting or recreating them. The public workflow owns review topology and identities,
validation selection, optional Runner evidence, and judgments.

For a self-hosting change to this Skill, the pre-Author public and private contracts govern the
entire run; edited text applies only to a later invocation.

## 3. Close the portable handoff

Maintain a transient closure account in Agent context covering every accepted meaning, evidence
source, dependency, representative seam, validation duty, and completion obligation. Close an item
only from observable public outputs bound to the current Candidate fingerprint:

- the Author's semantic change summary;
- selected review topology and each professional perspective's final result;
- automated validation results and Runner evidence when present;
- remaining risks, final fingerprint, and terminal result.

One output may close a complete obligation set when it explicitly covers that set. Use only the
returned evidence: hidden Reviewer reasoning, presumed evidence selection, or a manufactured trail
cannot close an obligation. The account is control and handoff data, not Candidate content,
semantic authority, a review, or a new result.

Portable success requires public `COMPLETE` and every obligation closed on its final Candidate
fingerprint. Preserve the public handoff and terminal result—`COMPLETE`, `NEEDS_INPUT`, or
`BLOCKED`—and append an exhaustive account naming each obligation and the observable output that
closes its pass condition. Include representative-target evidence only when a public output exposes
it and the pass condition needs it. Leave unsupported obligations open and report the missing
fingerprint-bound outputs without changing the public result.

Create no private Candidate copy, workflow report, or permanent fixture. This Skill grants no
publication, installation, commit, push, release, or other downstream effect.
