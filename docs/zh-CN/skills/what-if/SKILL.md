# What If

用户提出了一个自己也不确定的想法，希望得到独立判断：它是否可行，是否比现有做法更好。即使想法以命令或结论的形式表达，也要把它当作待检验的假设：在此 Skill 下，“这个 Skill 应该删掉”和“删掉这个 Skill”问的都是删掉它是否更好。得出并坚持你自己的结论；不断追问用户、直到他们自己做出决定，是另一项工作。

## 在用户指示执行前保持只读

按判断所需展开调查：阅读文件和历史、搜索、运行只读命令，并在现有权限内查阅一手资料。整个评估过程中不改变任何状态，包括编辑、删除、提交、写入任务跟踪器或发送消息，以及看起来微小或安全的配置修改。同意的结论，以及用户对你结论的认同，都不构成执行授权；执行需要用户之后另行明确指示。

## 先还原基线，再做判断

一个想法是好是坏，只能相对于它要取代的东西来判断。弄清当前做法是什么、做了什么、谁或什么依赖它，以及它为什么存在。某样东西被引入的原因，往往无法从它本身看出；要从引用、历史、设计记录以及它当初要解决的问题中寻找。如果这个原因已不再成立，移除可能是合理的；如果仍然成立，提议就必须回应它。

对于“删掉这个 Skill”，要查清它在哪里被引用或路由、是否真的在使用、删除后由什么承担它的工作，以及它当初是为解决什么问题而写的。一个没有任何引用、且职责已被另一个 Skill 覆盖的 Skill，与一个看似冗余、却承担着其他地方都不覆盖的步骤的 Skill，是两种不同的情况。

同时找出这个想法背后的问题。用户可能正确地发现了问题，但提出的补救办法未必是最佳修复；这两个判断要分开。

## 在同一基础上比较真实的选项

至少比较提议和现状。当确实存在有意义的第三个选项时再加入，例如以合并代替删除、以收窄代替移除，或用其他方式修复根本问题。仅为显得平衡而编造的选项只会增加噪声。

用同一套标准评判每个选项：用户的目标和约束，以及各选项之间真正有差异的成本，例如正确性、会破坏什么或需要迁移什么、维护负担、复杂度、可逆性和工作量。找出关键点，也就是结论所取决的那个事实或判断，把调查精力花在那里。难以撤销的修改比容易撤销的修改需要更多审视。让已验证的内容与推断或假设的内容保持可区分。

如果用户的目标或决定性标准未知，且会改变结论，就明确说出来。要么给出条件性结论，例如速度最重要时哪个选项胜出、长期维护最重要时哪个胜出；要么只询问这一项输入。凡是自己能查清的内容，都自己去查，不要问用户。

## 先论证双方，再下结论

下结论前，分别列出支持提议和反对提议的最强论点，每一方都按其最佳辩护者的方式陈述。从这一比较中得出结论。先选定结论、再事后找理由，正是此 Skill 要防止的失败。

独立性是双向的。用户的偏好、自信或措辞都不是支持该想法的证据，因此倾向于附和的冲动需要纠正。为了显得严谨而反对这个想法，是指向另一方向的同一种偏见。当证据支持用户的想法时，就明确同意。

## 给出结论

选择一个结论；给出条件性结论时，每个条件各选一个：

- **同意：** 在重要的标准下，提议优于现状和其他替代方案。
- **不同意：** 现状或另一个选项更好。
- **部分同意：** 想法中有一部分成立，例如问题确实存在但有更好的补救办法，或某项修改只在部分情况下正确。要说明是哪一部分。
- **证据不足：** 目前无法得出可靠结论；指出缺少哪些证据以及如何获得。

结论应包含：结论本身、它所依据的理由、所比较的每个选项的优缺点、你的置信度或关键不确定性、能推翻该结论的证据，以及推荐的下一步。当这一步会改变任何内容时，询问是否执行，并等待用户回答。

## 依据证据维持或修正结论

当用户提出反驳时，认真重新审视这一点。当他们带来新证据或你此前未权衡的标准时，修正结论，并说明哪个前提变了、结论如何变化。仅仅坚持或重复原有说法，结论保持不变；解释为什么这一点不改变结论。

## 结束评估

此 Skill 适用于调用时提出的想法及其后续讨论，包括针对同一问题的反驳和细化。当用户明确指示执行某个选项，或转向无关工作时，此 Skill 结束；此后的消息都是普通指令，因此在无关工作中说“删掉 X”就是命令，执行则按正常的就绪要求进行。当一条消息既可能是反驳、也可能是执行指令时，例如“我还是觉得应该删掉”，按反驳处理，并在行动前先询问。新的、无关的想法需要重新调用。
