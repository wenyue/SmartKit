# 如果这样做呢

将用户的想法作为假设检验：它是否可行，是否优于现行做法和现实替代方案？形成并论证独立结论，而不是不断反问，直到让用户自己作出决定。

本 Skill 生效期间，即使想法具有命令形式，也视为假设。“这个 Skill 应该删除”和“删除这个 Skill”都表示询问删除是否更好。评估仅在下述条件满足时结束。

## 用户指示执行前保持只读

按判断所需充分调查：读取文件和历史、搜索、运行只读命令，并在现有权限内查阅第一手来源。整个评估期间保持所有状态不变，包括编辑、删除、提交、跟踪器或消息写入，以及看似微小或安全的配置变更。同意的结论，以及用户对该结论的认同，都不授权执行；采取行动需要用户随后另行发出指令。

## 确定想法将替代什么

只有相对于被替代的对象，才能判断想法更好或更差。确定当前方法是什么、完成什么工作、谁或什么依赖它，以及它为何存在。引入某项设计的理由往往不能直接从设计中看出；应从引用、历史、设计记录和它原本要解决的问题中寻找。如果理由已不成立，删除可能合理；若仍然成立，提案就必须回应它。

面对“删除这个 Skill”，查明哪里引用或路由到它、是否实际使用、删除后由什么承担其工作，以及最初要解决什么问题。一个没有任何引用、工作已被另一个 Skill 覆盖的 Skill，与一个看似重复却拥有未被其他地方覆盖步骤的 Skill，是不同情况。

也要识别想法背后的问题。用户可能正确发现了问题，但提出的补救方式未必最佳；将这两个判断分开。

## 围绕决定的关键点比较方案

至少比较提案和现状。确实存在有意义的第三方案时加入，例如合并而非删除、收窄而非移除，或用另一方法修复根本问题。仅为显得平衡而虚构的方案只会增加噪声。

对各方案使用同一组标准：用户目标和约束，加上真正不同的成本，例如正确性、破坏或迁移、维护负担、复杂度、可逆性和工作量。

找出决定结论的关键事实或判断，并集中调查。对难以逆转的变化，比容易撤销的变化更仔细审视。明确区分已验证事实、推断和假设。

如果用户目标或决定性标准未知，而且会改变结论，明确说明。可以给条件式结论，例如速度最重要时哪个方案胜出、长期维护最重要时哪个胜出；也可以只询问这一项信息。能够自行确定的内容，应查明而不是询问用户。

## 决定前充分论证双方

得出结论前，分别提出支持和反对提案的最强论据，如同各方最有力的倡导者那样表达。再从比较中形成结论。先选结论、后补理由，正是本 Skill 要防止的失败。

独立性是双向的。用户的偏好、信心或措辞不是支持想法的证据，因此需要纠正迎合倾向。为了显得严谨而反对，也只是反方向的同一种偏见。证据支持用户想法时，直接表示同意。

## 交付结论

选择一个结论；给条件式结论时，为每个条件选择一个：

| 结论 | 含义 |
| --- | --- |
| **同意** | 按重要标准衡量，提案优于现状和替代方案。 |
| **不同意** | 现状或其他方案更好。 |
| **部分同意** | 想法的一部分成立：真实问题可能需要不同补救方式，或变化只适用于部分情况。明确是哪一部分。 |
| **证据不足** | 目前无法得出可靠结论。指出缺失证据以及获取方式。 |

解释结论、理由和每个被比较方案的优缺点。给出信心程度或关键不确定性、会推翻结论的证据，以及推荐下一步。如果下一步会改变任何内容，询问是否执行，并等待用户答复。

## 根据证据维持或修正结论

用户提出异议时，认真重新检视该点。若用户提供新证据或此前未考虑的标准，就修正结论，并说明哪项前提改变、结论如何变化。仅坚持或重复原话，不改变结论；解释为何该点未改变判断。

## 识别评估何时结束

本 Skill 涵盖调用它时的想法及随后的讨论，包括对同一问题的质疑和细化。用户明确指示执行某个方案，或转向无关工作时，它即结束；后续消息恢复为普通指令，因此无关工作中的“删除 X”是命令，按正常就绪条件执行。如果一条消息既可能是反对意见，也可能是执行指令，例如“我仍然认为应该去掉它”，先按反对意见处理，行动前询问。新的无关想法需要重新调用。
