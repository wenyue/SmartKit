# 代码设计

## Ponytail 加载

在任何编码任务中做决策前，阅读 [ponytail](../../../../skills/ponytail/SKILL.md)。

通过明确的所有者让行为容易理解。选择结构时，关注理解和修改行为所需的工作，而不是调用方是否更短或接口看起来是否更可复用。

## 选择收益足以抵偿成本的边界

为每个行为、状态、不变量和生命周期指定一个明确的所有者。将属于所有者的局部逻辑，以及理解和修改它所需的推理放在一起。

简短、直接、只使用一次的逻辑默认留在调用方。只有提取能显著减少理解和修改行为的总体工作量时，才进行提取。合理依据包括：

- 独立的职责、不变量或领域概念。
- 实际的生产复用。
- 显著的分支、状态或生命周期复杂度。
- 依赖隔离。

将收益与新增函数、类型、文件、API 和代码跳转的成本一起权衡。使用能实现收益的最小边界；同文件中的私有辅助函数可能已经足够。在调用方保留足够连贯的控制流，让操作容易理解。

缩短调用方、给小段代码命名、行数或假设中的复用，本身都不足以证明提取合理。通过私有逻辑所属的行为来测试它。测试接缝必须有生产设计所支持的职责或依赖边界，不能仅以直接测试私有逻辑的愿望为依据。

### 将失败处理和公共 API 留给其所有者

将失败处理放在它所属的操作中。仅仅重复捕获、记录日志或返回默认值，即使出现在多个调用方，也不足以引入回调包装。包装应有超越模板的连贯职责，例如清理、事务完成、必要的失败契约转换或实质性恢复；判断这种职责，而不是函数长度。

让公共接口对应稳定的产品或领域能力。通过所属契约满足测试和调用点的需求，不要仅为方便就扩大 API、移动所有者局部逻辑或增加间接层。

## 明确状态、副作用和生命周期

通过可见的所有者提供依赖，保持状态位置与所有权一致。每个单元只获得它需要的能力，并明确依赖方向和跨层边界。

让状态修改和生命周期转换从创建到清理都可预期。在异步工作和回调期间保留有效的依赖生命周期。

让副作用、失败模式、重试、回退和生命周期转换在契约或控制流中可见。

## 遵循项目已有设计

编辑代码前，检查目标文件以及附近处理类似工作的实现。遵循其既有命名、结构、控制流和 API 模式；只有更具体的规则或明确获批的设计要求有意识地偏离时，才采用不同做法。

## 先解决诊断，再考虑抑制

不要在配置层抑制编译器、分析器或 lint 工具的诊断。只有解决诊断会违反已批准的设计，或造成明显更差的结果时，才使用行内或文件级抑制。

每次抑制前，说明确切的诊断、范围和必要性，并取得覆盖该抑制的用户明确确认。已有确认覆盖相同诊断、范围和必要性时，可复用该确认。一般性批准或对另一项抑制的批准，不授权新增或扩大抑制。
