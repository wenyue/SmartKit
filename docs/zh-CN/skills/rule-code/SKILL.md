# 代码设计目标

强度：`Default`

适用范围：跨语言的代码编写、修改和审查，涵盖归属、边界、清晰度、局部一致性、状态完整性、依赖、抽象和诊断，以及受请求的上述事项评估。

在当前代码任务中应用此政策。受请求开展评估时，覆盖请求指定的代码，并在该请求范围内报告有依据的发现和重要证据缺口。

决定注释覆盖范围或是否需要注释前，阅读
[rule-code-comment](../rule-code-comment/SKILL.md)，包括可能适合省略注释的情况。
决定操作结果、失败传播或处理方式前，阅读
[rule-error-handling](../rule-error-handling/SKILL.md)，包括沿用既有传播方式的常规情况。
这些 Skills 分别负责自己的政策及配套资源的加载条件。

## 归属与 API

- 每项行为、状态、不变量和生命周期都要有一个明确的所有者。
- 所有者内部的逻辑应与所有者保持内聚；只有确实存在复用或边界时才移动逻辑。
- 公共接口应保持精简，并对应稳定的产品或领域能力。
- 测试和调用需求通过所属契约解决，不要仅为方便而扩大 API、移动所有者内部逻辑或增加间接层。

## 清晰度与抽象

- 修改代码前，先查看目标文件及附近实现中是否有类似逻辑。除非更具体的 Rule 或明确批准的设计要求
  有意采用不同做法，否则沿用既有的命名、结构、控制流、API 风格。
- 通过命名、类型和结构，让职责、有效状态和主要决策路径可以在局部理解。
- 在契约或控制流中清楚呈现副作用、失败方式、重试、后备行为和生命周期转换。
- 只有抽象能表达真实概念、保护不变量，或在降低维护成本的同时消除有意义的重复时，
  才引入它。
- 不要引入会模糊归属，或只服务于一个简单用法的辅助函数、适配器和通用层。

## 诊断与抑制

- 不要在配置层面屏蔽编译器、分析器或 linter 的诊断。只有在解决诊断会破坏已批准的设计，或导致
  明显更差的结果时，才能在行内或整个文件中屏蔽。每次屏蔽前，都要说明具体诊断、影响范围和必要性，
  并取得用户明确确认；笼统授权或以前的授权不能用于之后的屏蔽。

## 状态与依赖

- 从创建到清理，状态变更和生命周期转换都应当容易预测。
- 在异步工作和回调中维持正确的依赖生命周期。
- 每个代码单元只接收自身需要的能力，并明确依赖方向和跨层边界。
- 通过可见的所有者提供依赖，并按照该归属放置状态。
