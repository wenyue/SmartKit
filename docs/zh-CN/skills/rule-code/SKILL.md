# 代码设计目标

## Ponytail 加载

每项编码任务中，在作出决策前阅读 [ponytail](../ponytail/SKILL.md)。

## 让行为和 API 留在所属边界

每项行为、状态、不变量和生命周期都要有一个明确的所有者。让所有者内部的逻辑保持内聚，使理解和修改它所需的思考也集中在同一处。

简短、直接且只使用一次的逻辑默认留在调用方。当提取能显著降低理解和修改该行为的总体成本时，再进行提取。收益可以来自独立的职责、不变量或领域概念、实际生产复用、对显著的分支、状态或生命周期复杂性的封装，或依赖隔离。将这些收益与新增函数、类型、文件、API 和导航跳转的成本一并权衡。

使用能实现这些收益的最小边界；同一文件内的私有辅助函数可能已经足够。让调用方保留足够连贯的控制流，使整个操作易于理解。

仅凭缩短调用方、给小段逻辑命名、代码行数或假设中的复用，不足以支持提取。通过私有逻辑所属的行为来测试它。测试接缝需要有职责或依赖边界；该边界必须能由生产代码的设计独立证明其合理性，不能仅以直接测试私有逻辑为理由。

让失败处理与其所属操作保持在一起。即使有多个调用点，也不能仅为复用捕获、日志或默认值而增加回调包装。包装须承担模板之外的内聚职责，如清理、事务完成、必要的失败契约转换或实质性恢复；按职责判断，而非函数长度。

公共接口应对应稳定的产品或领域能力。测试和调用需求通过所属契约解决，不要仅为方便而扩大 API、移动所有者内部逻辑或增加间接层。

## 明确状态与依赖

通过可见的所有者提供依赖，并按照该归属放置状态。每个代码单元只接收自身需要的能力，并明确依赖方向和跨层边界。

从创建到清理，状态变更和生命周期转换都应当容易预测。在异步工作和回调中维持正确的依赖生命周期。

在契约或控制流中清楚呈现副作用、失败方式、重试、后备行为和生命周期转换。

## 依据局部证据组织代码

修改代码前，先查看目标文件及附近实现中是否有类似逻辑。除非更具体的 Rule 或明确批准的设计要求有意采用不同做法，否则沿用既有的命名、结构、控制流和 API 风格。

## 保留诊断

不要在配置层面屏蔽编译器、分析器或 linter 的诊断。只有在解决诊断会破坏已批准的设计，或导致明显更差的结果时，才能在行内或整个文件中屏蔽。

每次屏蔽前，都要说明具体诊断、影响范围和必要性，并取得覆盖该项屏蔽的用户明确确认。已有确认覆盖相同诊断、范围和必要性时，应复用该确认。笼统批准或对另一项屏蔽的批准，不能授权新增或扩大范围的屏蔽。
