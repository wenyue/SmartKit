# 编写代码注释

判断代码注释或文档注释是否必要，然后审查或编辑获准表面。有用的注释会保存所属代码、名称、类型、结构或文档无法足够清楚表达的重要含义。

## 原则

- **含义胜过复述。**保存不明显的理由、不变量、取舍、行为和约束。省略只是复述代码、重复名称或记录编辑历史的文字。
- **语义各归其主。**将每项事实放在其所属位置：调用方可见契约放在必要的 API 文档表面，更广泛概念放在其所属文档中，局部理由或约束放在实现旁边。
- **有依据的判断。**根据当前实现、契约、项目约定，以及所有者支持的语言或工具链机制来判断注释。只有当附近注释的所有权和适用性可信时，才能将其作为证据。
- **精确权限。**区分只读审查、注释编辑，以及独立获准的代码、名称、类型或结构变更。需要注释并不授予结构变更权限。
- **持久真实。**使注释与所属行为保持一致，并保留必要指令、生成标记、协议令牌、机器可读形式和外部规定的措辞。

## 确立决策

检查请求表面所需的实现、契约、项目约定、所有者文档和原生注释机制。只有当剩余不确定性可能改变注释的必要性、所有者、形式、分流、验证或真实性时，才扩大证据范围。若项目没有适用的注释约定，使用可靠确定的原生机制；仅仅缺少约定并不构成阻塞。说明会限制结论的证据边界。

行动前确认获准模式和目标所有者。对于生成或以其他方式托管的表面，只有当相关效果已获授权时，才遵循其规范编辑和生成路径。若所选操作所需的所有权、强制约定或写入权限无法确定，停止并报告确切缺失的事实或访问权限。

## 判断并行动

当适用约定要求注释，或未来维护者或调用方否则会遗漏重要理由、不变量、取舍、调用方可见行为，或生命周期、失败、顺序、并发、安全、兼容性或协议约束时，这条注释才值得存在。

如果一项独立获准的名称、类型、签名或结构修正能使事实变得可执行或不言自明，应优先采用它。没有该权限时，保持结构不变，交接确切修正及其所有者，而不是用注释绕过缺陷。

陈旧、误导、冗余或纯叙述文字不值得保留；仍然有效的不明显事实和受保护形式则应保留。

### 只读审查

保持文件和结构不变。覆盖请求位置，以及判断它们所必需的实现或契约路径。在精确位置报告每项可操作的缺失、误导、陈旧或冗余注释，并说明重要含义或冲突及其依据。

若现有证据无法支持穷尽式覆盖，说明已覆盖边界和未测试余项；不要作出更宽泛的“未发现问题”声明。若该边界内没有可操作问题，明确说明。

### 获准编辑

只更改选定的注释表面或独立获准的代码、名称、类型或结构，以及范围内必要的所有者托管输出。删除或更新不值得保留的文字，同时保留其中仍然有效的含义和受保护形式。使用目标既有术语和形式，在最窄的真实范围内表达缺失含义。代码变更后，使相关范围内注释保持一致。

若实现或所属契约似乎有误但不在范围内，应保持原样并交接确切冲突及其所有者，而不是让注释将预期行为写成事实。

## 验证与交接

运行获准目标及其必要所有者托管输出所需的每项所有者要求检查。补充负担最小、由所有者支持，并能实质提升对变更行为或可能回归的信心的检查。报告每项检查、覆盖目标和结果。若选定目标没有相关检查，将其标记为未测试；若必要检查无法运行或失败，报告阻塞或失败，不得宣称完成。

只有在所属要求得到保留且必要验证成功后，才完成请求的审查或编辑。交接内容包括变更或审查的位置、重要的不添加注释决策、保留的不明显含义、依据、验证状态，以及每项剩余不确定性、所有权冲突、受阻操作或范围外修正。
