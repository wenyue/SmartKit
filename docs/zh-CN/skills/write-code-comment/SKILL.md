# 编写代码注释

判断是否需要代码注释或文档注释，然后在请求授予的权限内审查或编辑注释。有用的注释所保留的
重要信息，是其归属的代码、名称、类型、结构或文档本身无法充分清楚表达的。

## 确立注释的权威依据

一并检查相关实现和契约，以及目标项目的现行规则、语言约定、归属方文档、配置和适用的受维护
注释。只有在附近注释的归属和适用性可信时，才将其作为证据。根据这些现行来源确定所需的语言、
术语、形式、位置、文档标签、指令、标记和验证；不得用记忆中的语法或工具清单替代。

确认请求仅授权审查、授权编辑注释，还是另外授权修正代码、名称、类型或结构；同时确认目标是否为
归属方所拥有的源文件。仅仅需要注释，并不授予修改结构的权限。如果结构修正没有获得独立的请求
授权，应报告确切的修正内容及其归属方。对于生成表面或其他受管理表面，只有在相应影响已获授权时，
才遵循规范归属方规定的编辑和生成路径。如果无法确定归属权、必要约定或写入权限，应停止并报告
确切缺失的事实或访问权限，不得修改该表面。

让每项事实归属于其语义所有者。调用方可见的行为和公共契约应放在项目要求的 API 文档表面；范围
更广的概念应放在其归属文档中。实现注释用于说明局部理由或约束。必须逐字保留必需的指令、生成
标记和协议令牌，除非其归属方授权修改。

## 判断文字是否值得保留

适用约定要求注释时，或者未来的维护者或调用方若没有注释便会遗漏重要理由、不变量、权衡、调用方
可见行为，或生命周期、失败、顺序、并发、安全、兼容性或协议约束时，注释才有必要。在已确立的
权限范围内，如果修正名称、类型、签名或结构能够使该事实可强制执行或不言自明，应优先采用这种
修正；否则应报告问题，而不是用注释掩饰缺陷。

省略对代码流程的复述、重复名称、编辑历史，以及已能从紧邻代码或归属文档中清楚得知的事实。将
每条保留的注释与当前行为和契约进行核对：更新或删除过时、误导或冗余的文字，同时保留仍然有效且
不直观的含义。

## 审查或编辑

对于只读审查，不得更改任何文件或结构。按可操作的位置报告每条缺失、误导、过时或冗余的注释，
说明其中的重要信息或冲突，并指出治理依据。如果没有可操作的问题，应明确说明。

对于已授权的编辑，只修改选定目标——注释表面，或已获得独立授权的代码、名称、类型或结构——以及
范围内必需的归属方管理输出。以最窄且真实的范围表达注释中缺失的含义，并采用目标既定的术语和
形式。保留因果理由和约束，不要复述实现；必需的机器可读形式和外部规定文字应保持原样。

如果范围内的相关代码发生变化，应使其注释与最终行为保持一致。如果代码或其归属契约看似错误，
但不在范围内，应保留原样并移交确切的冲突及其归属方，不得让注释把预期行为表述成事实。

## 验证并移交

在已授权影响的范围内，对每个选定且已授权的目标——注释、代码、名称、类型或结构变更——以及必需
的归属方管理输出，使用现行归属方声明的检查。报告每个目标的检查及结果。如果某个选定目标没有
相关检查，将该目标标记为未经测试。如果必需检查不可用或失败，应报告阻碍或失败，不得声称完成。

只有在完成所请求的审查或已授权编辑、保留归属要求并且必需验证成功后，任务才算完成。移交内容
应包括变更或审查的位置、针对所请求或所审查位置作出的重要“不添加注释”决定、所保留的不直观
含义、治理依据、验证状态，以及仍存在的每项不确定性、归属冲突、受阻操作或范围外修正。
