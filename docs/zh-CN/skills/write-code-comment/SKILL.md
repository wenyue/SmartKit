# 编写代码注释

在请求范围内完成专项注释评估、审查、补全、整理或迁移。当任务本身是注释工作，或用户显式调用时，使用此流程；功能开发中顺手编写注释仍由该开发任务的流程处理。

## 原则

- **基于证据判断。**依据实现、契约、目标中适用的要求和可比的局部证据作出决策。区分明确要求与观察到的习惯；习惯为判断提供参考，不构成约束。
- **信息各归其位。**将调用契约放在 API 文档中，局部原因放在实现处，更广泛的概念放在其所属文档中。确定信息应放在哪里，并不授予修改该位置的权限。
- **适度修改。**为实现获准结果，作出完整且相互协调的必要修改。注释工作本身不授予修改代码、名称、类型或结构的权限；这些修正超出范围时，提出建议。

## 确立决策

确定请求授权的是只读审查还是编辑，并明确目标位置及其所有者。检查判断注释的必要性、形式、内容和归属位置所需的实现、契约、适用文档要求、附近可比的代码与注释，以及原生注释机制。当剩余不确定性可能改变操作或验证时，扩大证据范围。没有适用约定时，采用有可靠依据的原生机制；仅仅缺少约定并不构成阻塞。

对于生成或以其他方式受管理的内容，在编辑前确定规范编辑路径及其必要操作的授权。若无法确定关键归属、必要约定、访问权限或授权，停止依赖这些条件的操作，并准确报告缺少什么。继续独立且已获授权的工作，将结论限定在现有证据支持的范围内。

## 审查或编辑

### 只读审查

保持文件和结构不变。覆盖请求位置，以及判断它们所必需的实现或契约路径。在准确位置报告可采取行动的注释缺失、误导、过时或冗余问题，并说明其重要含义或冲突以及判断依据。相关时，列出建议的信息迁移或结构修正及其所有者。

若没有可采取行动的问题，在已审查范围内明确说明。指出覆盖不完整的部分和未经测试的路径，不将“未发现问题”的结论扩大到证据范围之外。

### 获准编辑

依据目标的文档要求和已确定的证据，在范围内添加、修改、删除或移动注释。使用目标中的术语和形式，如实表达含义。整理或迁移时保留仍然有效的含义；即使删除含义已在代码或其他所属位置清楚表达的文字，也应保持这些含义。迁移信息时，只有在已获授权的目标位置妥善表达后，才删除原内容。对于范围外的信息迁移，提出建议，并保留尚无法安全迁移的信息。

保留必要的机器指令、生成标记、协议令牌、机器可读形式和外部规定的措辞。对受管理内容，遵循已获授权的规范路径，仅在该授权范围内包含必要输出。代码变更另有授权时，同步维护范围内的相关注释。

实现与所属契约冲突时，仅在授权范围内解决。否则，报告冲突及其所有者，不将预期行为写成已经实现的行为。

## 验证与交接

运行相关、可用且由所有者支持的检查，包括获准目标及必要受管理输出的每项必需检查。只有补充检查能实质提升对变更或潜在回归的把握时，才按需要适度增加。记录检查内容和结果；没有相关检查时，指出哪些目标未经测试。若必需检查无法运行或失败，报告阻塞或失败，并将工作保持为未完成状态。

保留所属要求且必需验证成功后，完成获准的审查或编辑。简要交接已审查或修改的位置、重要决策及其依据、验证状态，以及任何覆盖不完整之处、不确定性、受阻操作、归属冲突或建议的范围外修正。
