# 编写代码注释

日常开发确定需要编写或实质修改注释后，或处理专项注释任务时，使用此 Skill。根据请求范围选择分支，显式调用时也一样：

- **日常开发：**在获准的代码任务中应用写作指导和保障措施，沿用该任务的验证与交接。这不会启动单独的注释审计、报告或子代理流程。
- **专项注释工作：**应用写作指导和保障措施，然后执行下方的专项流程。

## 写作指导

像维护者向有经验的同事解释实现那样写作。除非目标另有规定，假定读者熟悉语言和框架，但不了解这份实现。以代码和所属契约为依据；当不确定性可能改变措辞或验证时，扩大证据范围。如实表达实际行为和调用方义务。

**信息与组织。**先说明具体职责或行为，再说明正确使用时的重要约束。选取相关的不变量、生命周期义务、外部要求或边界情况，无需罗列所有可能的关注点。

API 文档解释调用方契约；内部注释解释实现。无论出现在哪里，都按用途区分。局部原因、约束和取舍与实现放在一起，更广泛的概念放在所属文档中。先选择有用的信息归宿，再判断任务是否授权修改该位置。少量章节标签可以改善阅读和视觉组织，即使它们没有揭示隐藏知识。

**表达与形式。**使用具体、日常的词语，直接表达实质内容，而不是以“稳健而灵活的辅助工具”之类的笼统评价开头。让句式和篇幅适合解释需要；读者需要理解关系或推理时，可以写得更长。省去逐行复述、冗余名称和编辑历史。

遵循目标的文档语言、语法和明确的格式要求。观察到的习惯可为表达提供参考，但不构成要求；没有适用惯例时，使用成熟的原生注释机制。修改或删除文字时，保留仍然有效的含义，包括代码或其他所属载体已清楚表达的含义。保持必需的机器指令、生成标记、协议 token、机器可读形式和外部规定措辞完整。

写作或执行所请求的评估时，可按需参考相关[对照示例](references/examples.md)。它们用于校准信息选择和口吻，不规定覆盖策略、固定格式，也不提供目标的事实。

**最后通读。**以预期同事的视角，对照代码阅读注释。检查所选信息是否有用、措辞是否直接，以及说明在相关路径上是否仍然准确。保留仍有用的解释，删除过时或冗余的文字。

## 范围与编辑保障

在获准的位置和操作效果范围内工作。注释工作本身不授予修改代码、名称、类型或结构的权限；对范围外的必要修正提出建议。只读审查请求应保持文件和结构不变。

对于生成或以其他方式受管理的内容，在编辑前确定规范编辑路径及其必要操作的授权；仅在该授权范围内包含必要输出。若无法确定关键归属、适用的目标要求、必要资源、访问权限或授权，停止依赖这些条件的操作，并准确报告缺少什么。继续独立且已获授权的工作，将结论限定在现有证据支持的范围内。

迁移信息时，只有在已获授权的目标位置妥善表达其含义后，才删除原内容。对于范围外的信息迁移，提出建议，并保留尚无法安全迁移的信息。实现与所属契约冲突时，仅在授权范围内解决；否则报告冲突及其所有者，不将预期行为写成已经实现的行为。

## 专项注释流程

确定请求授权的是只读审查还是编辑，并明确目标位置及其所有者。根据独立适用的文档要求以及当前实现和契约证据，判断所请求的覆盖情况。

### 只读审查

覆盖请求位置。在准确位置报告可采取行动的注释缺失、误导、过时或冗余问题，并说明其重要含义或冲突以及判断依据。相关时，列出建议的信息迁移或结构修正及其所有者。

若没有可采取行动的问题，在已审查范围内明确说明。指出覆盖不完整的部分和未经测试的路径，不将“未发现问题”的结论扩大到证据范围之外。

### 获准编辑

应用写作指导和范围保障，添加、修改、删除或移动注释，完成范围内的结果。代码变更另有授权时，同步维护范围内的相关注释，然后执行最后通读。

### 验证与交接

运行相关、可用且由所有者支持的检查，包括获准目标及必要受管理输出的每项必需检查。只有补充检查能实质提升对变更或潜在回归的把握时，才按需要适度增加。记录检查内容和结果；没有相关检查时，指出哪些目标未经测试。若必需检查无法运行或失败，报告阻塞或失败，并将工作保持为未完成状态。

保留所属要求且必需验证成功后，完成获准的审查或编辑。简要交接已审查或修改的位置、重要决策及其依据、验证状态，以及任何覆盖不完整之处、不确定性、受阻操作、归属冲突或建议的范围外修正。
