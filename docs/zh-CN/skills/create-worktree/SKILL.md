# 创建工作树

选择或创建一个关联 Git 工作树，准备其环境，并返回调用者可使用的证据及 `ready` 或 `non-ready`。新建时默认携带源工作区的当前工作；隔离不会抹去这些工作的原始所有权。

调用者拥有已接受的范围和隔离要求。遵守其目标、基线、路径、所有权和效果约束，包括本次会话中已经作出的选择。本 Skill 拥有工作区选择和即时就绪判断。实施、提交、项目验证、收尾、清理和远程操作仍由原有所有者负责。

## 选择一个归属明确的工作区

确定已接受的范围及 `scope_owner`、源检出和主项目检出，以及物理 Git 公共目录。用与风险相称的仓库和文件系统证据确定这些身份；当具体风险可能影响保护或权限判断时，进一步调查别名或其他边界。

继续使用某个确切且归属明确的关联工作树时，将其物理根目录、注册信息、分支/引用、`HEAD`、基线关系及本地状态与保留的任务上下文比较。一致时复用它。保留其中已有的继承状态和任务状态，不要把源工作区的新修改覆盖上去。无需穷尽搜索无关候选，也无需迁移所选路径。身份或所有权不明确时返回 `non-ready`。

复用时，在环境准备前重新检查该目标的身份和受保护本地状态，然后直接进入环境准备，不创建或传输。新建工作树时，在修改状态前确定以下选择和源状态证据。

## 规划新建

### 选择基线及携带状态

冻结不可变基线和创建模式：

- **携带** 默认使用源的已冻结当前 `HEAD`，加上已暂存、未暂存以及未被忽略的未跟踪状态。
- **干净** 创建所选基线，不带入源修改。

明确指定不同基线时，必须明确选择干净模式，或约定兼容的携带语义；它不会隐含授权将另一个基线上的脏状态应用过来。要求所有状态都属于自身任务的调用者可以拒绝继承无关工作，但这不改变默认携带行为，也不授权丢失这些工作。

### 确定物理位置

提供了明确目标路径时使用该路径。否则优先使用 `<primary-project-root>/.worktrees/<task>`，即使当前从另一个关联检出调用。通过仓库拓扑确定主根目录，不要假定发起调用的检出就是主检出。直接使用已存在且有效的 `.worktrees` 容器。无效的现有条目、不安全的物理别名或已跟踪内容冲突，应作为冲突报告，而不是当成容器不存在。

当该容器不存在，且此前选择尚未确定位置时，请用户在恰好两个位置中选择，并展示两个具体拟议目标路径：

1. 创建 `<primary-project-root>/.worktrees/<task>`，并设置本地 Git 排除。
2. 使用插件的持久位置 `data/worktrees/<project-id>/<task>`。

从权威宿主或配置输入确定实际插件数据根目录。对于 Codex，SmartKit 建议使用 `<resolved-codex-configuration-root>/plugins/data/smartkit/worktrees/<project-id>/<task>`；这是 SmartKit 的存储约定，不是官方宿主能力。用 `<project-name>-<short-hash-of-canonical-git-common-dir>` 作为项目 ID：同名克隆保持区分，关联工作树则共享一个项目位置。不要将工作树放在带版本的插件缓存或已安装 Skill 目录内。在其他宿主上，如果缺少持久根目录信息，必须先取得明确位置，再提供具体的第二条路径；不要编造宿主路径。

根据当前文件系统和 Git 证据，选择安全、唯一的任务路径和具名分支。新建要求目标路径、分支和注册均不存在，并采用拒绝冲突的语义。不要覆盖或改作他用既有分支。解析物理路径，防止别名以及在发起调用的关联检出下递归嵌套容器。

选择项目内位置时，在创建前验证排除已实际生效。如有需要，通过 Git 解析实际本地 `info/exclude` 路径，仅添加 `/.worktrees/`，保留其他每个字节，并保持共享 `.gitignore` 不变。选择项目内位置会授权这项本地排除，但仍受调用者效果约束。将容器和排除项修改推迟到位置决定及下文适用的携带决定都已完成之后。

## 冻结源状态并解决携带确认

无论哪种创建模式，都记录足以证明保护成立的稳定源快照：物理源身份、`HEAD` 和分支/引用、索引条目及已暂存内容、工作区内容和文件类型/模式，以及未被忽略的未跟踪路径。存在冲突索引或含义不明确的进行中操作时，在修改状态前停止，除非所选机制明确支持保留该状态。

这份保护证据与传输数据不同。对于 **干净** 模式，预期目标是所选基线，索引和工作区均干净；跳过携带数据捕获、计数和批准。

对于 **携带** 模式，分别捕获已暂存和未暂存层，包括同一路径同时具有两层修改的情况。保留新增、删除、重命名、二进制内容、可执行模式，以及受支持的符号链接。根据所选基线和约定的携带语义，确定预期目标索引及工作区状态。同基线携带复现源状态；明确约定的兼容跨基线携带将源修改保留在所选基线之上。如果未解决的转换或冲突使预期结果无法确定，在修改状态前停止。

默认不携带被忽略文件、依赖缓存和嵌套工作树内容。将已知必需但被省略的输入交给环境准备，或返回缺少前置条件的结果。如果不受支持的文件或索引语义阻碍忠实传输，在修改状态前停止。

对携带模式，累计快照中已暂存和未暂存差异的新增行数与删除行数，包括新增未跟踪文本的行数。跨这些层及未跟踪文件，对每个不同的变更路径只计一次。二进制修改计入路径数，不要为其编造行数。

在任何创建或状态复制之前，如果 **行数 >= 300 或路径数 >= 10** ，展示源、目标、两项计数和将携带的内容，并取得用户明确的携带决定。无法测量的项目不能按零计：披露不确定性，并取得覆盖该情况的决定。两项都低于阈值时，按默认携带执行并报告计数。

批准覆盖的是已审阅的快照和目标。发生实质变化时，需要新的摘要和决定。没有回复不等于批准。如果用户拒绝携带，取得明确的干净 `HEAD`/基线选择，或取消；不要默默省略源修改。

## 建立并验证新目标

指定对本次尝试及恢复负责的 `creation_owner`。确定预期的本地文件系统、分支/引用和 Git 管理效果，以及每项效果的权限。使用适用的宿主负责的创建接口，或具有拒绝冲突语义的 Git 途径。当配置驱动的 hook、过滤器或子进程效果具有实质影响时，检查它们。凭据、网络、服务或其他持久效果的权限尚未解决时，停止该效果。

紧接修改状态之前，确认冻结的源快照、不可变基线、模式和必要决定仍有效，目标路径、分支和注册仍不存在。从该基线创建。对于 **干净** 模式，不传输源状态。对于 **携带** 模式，从已捕获修改复现约定的索引及工作区状态，包括范围内未跟踪输入。

保持源字节、索引、`HEAD` 和分支/引用不变。stash、提交、重置和移动源文件都不是传输方法。

验证目标已注册的物理根目录、具名分支及位于所选基线的 `HEAD`。将索引和工作区与预期干净或携带状态比较，包括内容、文件类型/模式以及已暂存与未暂存语义。比较索引内容和语义，不要求索引扩展元数据的二进制完全一致。两种模式都要证明源在捕获及建立期间保持不变，并说明已授权的容器、排除和创建效果。源发生漂移或比较不完整时返回 `non-ready`。

### 失败后保留归属明确的状态

尝试失败或中断后，观察实际效果，将部分路径、引用、注册、已复制状态和证据保留给恢复责任方。只有能证明某个工件完全属于本次尝试、不含用户或无关工作，且确切恢复权限允许删除时，才删除它。

只有从机制所有者支持的已观察状态出发，且选择和携带确认条件再次满足时，才重试。部分复制是恢复依据，不是覆盖后续工作或假定必须重做整个尝试的许可。

## 准备所选环境

通过所选目标的项目 Skill 发现机制解析 `worktree-environment-setup`。它存在时，针对该确切目标，在已接受的准备效果权限内调用它，并将继承修改标记为受保护。消费其 `environment-ready` 或 `environment-non-ready` 结果，复用有效且可归属的依赖证据，不重复其内部检查。依赖存在但不可用、失败、中断或结果含糊时，应得到 `non-ready`；这不等于 Skill 不存在。

目标 Skill 不存在时，记录 `not-provided` 并跳过它。已知不可缺少的准备或输入缺失，仍会阻止就绪。

本 Skill 不运行项目基线、构建、测试或项目健康检查。仓库要求的验证属于实施和收尾所有者。环境就绪不表示项目测试通过。

## 返回就绪状态和所有权

最后进行一次小范围的当前目标身份/状态检查，对照创建或复用证据及可归属的环境结果。确定预期状态时，计入已授权的准备效果。调查具体漂移或意外效果。

只有所选工作区及继承状态正确、保护成立、预期效果已授权、存在的环境准备成功，且没有已知不可缺少的前置条件缺失时，才返回 `ready`。否则返回 `non-ready`，为其所有者保留所选工作区和任何部分状态。未解决的重要选择和不受支持的效果不能变成就绪。

向调用者提供简洁交接，包含：

- 状态和原因；范围、`scope_owner`、复用/新建选择，以及适用时的 `creation_owner`。
- 源和目标根目录、物理仓库/Git 公共目录身份、注册、分支、不可变基线、当前 `HEAD`/树，以及这些事实的观察边界。
- 源快照和继承状态归属；已暂存、未暂存及未跟踪证据；携带计数与决定，或明确的干净基线选择。
- 环境状态和可归属证据；预期本地状态；预期及实际效果；保护结论；保留的部分或不确定状态。
- 对于 `non-ready`，给出阻碍事项、下一责任方和确切下一步行动。

继承工作保留原始所有权和保护。携带它不授权提交它；调用者按自身范围及提交策略处理继承工作。消费新鲜结果时，只需进行必要的当前目标身份/状态检查，并在修改状态前调查具体漂移。后续流程和 `finish-worktree` 会建立各自的当前契约。
