# 创建工作树

选择或创建一个 Git 关联工作树，新建时默认携带源工作区的当前改动，
准备其环境，然后返回 `ready` 或 `non-ready`。调用方负责已接受的范围和隔离要求；
此 Skill 负责工作区选择和即时就绪。实现、提交、项目验证、收尾、清理和远程操作
仍由各自原有的责任方负责。

## 原则

- **明确选择优先。**遵循用户或调用方对目标、基准、路径、归属和影响的限制，
  包括本会话中已经作出的选择。
- **保留起始工作。**携带状态只复制它，不改变源工作区的文件、
  索引、`HEAD` 或分支/引用。继承的改动保留原有归属和保护。
- **证据与风险相称。**判断仓库、工作区、状态和影响时，使用与风险相称的证据。
  只有具体风险可能影响状态保护或授权时，才进一步调查别名、钩子、过滤器、子进程或其他边界。
- **让不确定性可见。**遇到未解决的实质选择或不受支持的影响时，先停止。
  失败后保留可归属的部分工作和证据；不确定性不能被当作就绪。

## 1. 选择工作区

确定已接受的范围及其 `scope_owner`、源检出区、项目主检出区和实际 Git 公共目录。

继续一个明确且可归属的关联工作树时，根据保留的任务上下文，
核对其实际根目录、注册、分支/引用、`HEAD`、基准关系和本地状态。
一致时复用该目标；无需穷举无关候选工作树，也无需迁移路径。
保留其已有的继承状态和任务状态，不用源工作区的新改动覆盖它。
归属或身份含糊时返回 `non-ready`。

新建工作树时，冻结不可变基准和创建模式。默认采用**携带**模式：
以源检出区当前冻结的 `HEAD` 加上已暂存、未暂存以及未被忽略的未跟踪状态为起点。
**干净**模式从选定基准创建，不包含源改动。明确指定其他基准时，必须明确选择干净创建，
或确定兼容的携带语义；指定基准本身不隐含授权将另一个基准上的未提交状态应用过来。
要求所有状态均属于自身任务的调用方可以拒绝无关的继承改动，
但不能因此改变这个默认行为或授权丢弃这些改动。

提供了明确目标路径时，使用该路径。否则优先使用
`<primary-project-root>/.worktrees/<task>`，即使调用来自另一个关联检出区也是如此。
已有有效的 `.worktrees` 容器时直接使用。已有条目无效、实际路径别名不安全
或与已跟踪内容冲突时，应报告冲突，不能按容器不存在来选择备用位置。

容器不存在且此前没有选择能够确定位置时，请用户在以下两个位置中选择一个，
并展示建议目标的具体路径：

1. 创建 `<primary-project-root>/.worktrees/<task>`，并确保本地 Git 排除规则生效。
2. 使用插件的持久化 `data/worktrees/<project-id>/<task>` 位置。

根据权威宿主或配置输入确定实际插件数据根目录。对于 Codex，SmartKit 建议在解析出的
Codex 配置根目录下使用 `~/.codex/plugins/data/smartkit/worktrees/<project-id>/<task>`。
这是 SmartKit 的存储约定，不是官方宿主能力。
以 `<project-name>-<short-hash-of-canonical-git-common-dir>` 作为项目标识，
区分同名克隆，同时让关联工作树共享一个项目位置。不得将工作树放入带版本的插件缓存
或已安装 Skill 的目录。在其他宿主中，如果缺少持久化根目录信息，必须先取得明确位置，
才能提供第二个具体路径；不得虚构宿主路径。

通过当前文件系统和 Git 检查选择安全、唯一的任务路径和命名分支。
新建要求目标路径、分支和注册均不存在，并采用拒绝冲突的机制；不得覆盖或改作他用。
解析实际路径，防止别名问题，也防止在发起调用的关联检出区下递归嵌套容器。

放在项目内时，在创建工作树前验证有效的排除规则。需要时，通过 Git 解析实际本地
Git `info/exclude` 路径，仅添加 `/.worktrees/`，保留其他所有字节，
不改变共享的 `.gitignore`。选择项目内位置即授权这项本地排除操作，
但仍受调用方的影响限制约束。只有位置选择和下述适用的携带确认均完成后，
才创建容器和修改排除规则。

## 2. 捕获源状态并确认携带

两种创建模式都要记录足以验证源状态得到保留的稳定快照：
源工作区的实际身份、`HEAD` 和分支/引用、索引条目和已暂存内容、
工作区内容及文件类型/模式，以及未被忽略的未跟踪路径。
索引存在冲突或正在进行的操作含糊时，在修改前停止，
除非选定机制明确支持保留该状态。

采用**干净**模式时，预期目标是选定基准及其干净索引和工作区；跳过携带内容捕获、统计和确认。
采用**携带**模式时，分别捕获已暂存和未暂存两层状态，包括同一路径同时具有两层改动的情况。
在受支持的范围内保留新增、删除、重命名、二进制内容、可执行模式和符号链接。
根据选定基准和约定的携带语义，确定预期目标索引和工作区状态：
同基准携带应重现源状态；明确约定兼容的跨基准携带应在选定基准上保留源改动。
如果仍有未解决的转换或冲突，无法确定预期结果，则停止。

默认不携带被忽略文件、依赖缓存和嵌套工作树内容。
已知必需但未携带的输入交给环境准备处理，或报告为缺失前置条件。
不受支持的文件或索引语义若使忠实转移无法实现，也必须在修改前停止。

携带模式下，统计快照中已暂存和未暂存差异的新增行数与删除行数之和，
包括新建未跟踪文本文件的行数。对这两层状态和未跟踪文件中的变更路径去重计数；
二进制改动计入路径数，不虚构行数。
在任何工作树创建或状态复制之前，如果**行数 >= 300 或路径数 >= 10**，
展示源位置、目标位置、两项计数和将携带的内容，并取得用户明确的携带决定。
不得把无法计量的条目记为零：应说明不确定性，取得涵盖该不确定性的决定后再继续。
两项均低于门槛时，按默认行为携带并报告计数。

确认绑定到用户查看过的源快照和目标。实质变化要求重新展示摘要并取得决定。
没有回复不等于同意；拒绝携带后，必须明确选择干净的 `HEAD`/基准或取消，
不得静默省略改动。

## 3. 建立并验证目标

复用时，在准备环境前重新核对选定目标的身份和受保护的本地状态；
不执行创建或转移步骤。

新建时，指定对本次尝试及恢复负责的 `creation_owner`。
确定预期的本地文件系统、分支/引用和 Git 管理状态影响，以及这些影响的授权。
遵循适用的宿主自有创建接口，或使用拒绝冲突的 Git 机制。
配置驱动的钩子、过滤器或子进程影响具有实质意义时，应予以检查；
凭据、网络、服务或其他持久影响的授权未解决时，停止该影响。

紧接修改前，确认冻结的源快照、选定基准和创建模式、目标与分支不存在的状态，
以及必需决定仍然有效。从选定的不可变基准创建。
采用**干净**模式时，不转移任何源状态。
采用**携带**模式时，根据捕获的改动重现约定的目标索引和工作区状态，
包括选定边界内的未跟踪输入。使用保持源字节、索引和 `HEAD`/引用不变的方法；
stash、提交、reset 和移动源文件都不是转移方法。

验证目标的注册实际路径、命名分支，以及 `HEAD` 是否位于选定基准。
将目标的索引和工作区与预期的干净或携带状态比较，包括内容、文件类型/模式，
以及暂存和未暂存语义。索引验证比较内容和语义，不要求索引扩展元数据的二进制完全一致。
两种模式都要验证源工作区在捕获和建立过程中保持不变，
并核对获授权的容器、排除规则和创建影响。
源状态漂移或比较不完整时返回 `non-ready`。

尝试失败或中断后，检查实际影响，将部分路径、引用、注册、已复制状态和证据
交给其恢复责任方保留。只有证明某项产物完全来自本次尝试、
不包含用户或无关工作，并有准确的恢复授权允许删除时，才能移除。
只有在已观察到的状态下，机制责任方支持重试，且选择和携带门槛再次满足时，
才能重试。

## 4. 准备环境

检查选定目标是否有自己的 `worktree-environment-setup` Skill。
存在时，必须针对该准确目标调用它，传入已接受的设置影响授权，并将继承修改标记为受保护。
使用它返回的 `environment-ready` 或 `environment-non-ready` 结果，
复用有效且可归属的依赖证据，不重复执行该 Skill 的内部检查。
依赖存在但不可用、失败、中断或结果含糊时，属于 `non-ready`，不能当作不存在。

目标 Skill 不存在时，记录 `not-provided` 并跳过。
已知缺失的必需准备或输入仍会阻止就绪。此 Skill 不运行项目基线、构建、测试或项目健康检查。
仓库要求的验证仍由实现和收尾责任方负责；环境就绪不意味着测试通过。

## 5. 返回就绪结果

结束前，根据创建/复用和环境结果，小范围核对当前目标身份及预期状态。
调查具体漂移或意外影响。只有选定工作区和继承状态正确、状态保护成立、
预期影响获得授权、存在的环境准备成功，且没有已知必需前置条件缺失时，才返回 `ready`。
其他所有结果均为 `non-ready`，将选定工作区和部分状态保留给其责任方。

返回简洁的交接信息，包括：

- 状态和原因；范围、`scope_owner`、复用/新建选择，以及适用时的 `creation_owner`；
- 源与目标根目录、实际仓库/Git 公共目录身份、注册、分支、不可变基准、
  当前 `HEAD`/树，以及观察边界；
- 源快照和继承状态归属、暂存/未暂存/未跟踪证据、携带计数和决定，
  或明确选择的干净基准；
- 环境状态及可归属证据、预期本地状态、预期/实际影响、
  状态保护结论，以及保留的部分或不确定状态；以及
- 对于 `non-ready`，说明阻塞项、下一责任方和准确的下一步。

继承的源改动不会因这个结果而成为新任务的所有内容或获得提交授权。
调用方须按自身范围和提交策略独立核对其归属。使用新鲜结果时，
只需进行必要的当前目标身份/状态检查；出现具体漂移时，在修改前调查。
后续工作流和 `finish-worktree` 各自建立当前契约。
