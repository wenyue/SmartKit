# 创建工作树

当会改变仓库状态的工作需要一个隔离的关联 Git 工作树时，使用这项以流程为主导的技能。它会选择或创建工作树，验证其身份和保全边界，准备其环境，确定基线就绪状态，并返回机械式交接。

调用方或所属工作流提供已接受的范围和决策权限。控制器（即运行这项技能的智能体）执行此流程。宿主具有原生能力时，由宿主创建工作树；Git 是后备创建方式。`scope_owner` 负责实施范围，`creation_owner` 标明具体的创建方和生命周期责任方，`integration_owner` 负责后续集成，`cleanup_owner` 负责后续清理。这项技能不接管业务实施、提交、已完成改动的验证、集成、跟踪器状态或清理。

## 阶段 1：确定输入和保全边界

1. 获取已接受的实施范围，并记录：
   - 调用方提供的 `scope_owner`；
   - 若要复用，记录控制器当前关联工作树的确切路径和身份；若要创建，则记录全小写且以连字符连接的 slug；
   - 具名工作树分支；
   - 确切的基准提交；
   - `integration_owner` 和 `cleanup_owner`；
   - 宿主是否已经创建预定工作树；以及
   - 若要复用，记录具体的 `creation_owner`，并由调用方提供的证据或现有交接加以证明，无论该工作树是由宿主还是 Git 创建。
2. 根据所提供的基准提交，确定恰好一个具名基准分支及其检出目录。检查当前分支和 `HEAD`、Git 公共目录以及 `git worktree list --porcelain`。如果预定基准处于分离状态或存在歧义，或者确定的提交与所提供的提交不同，就停止。绝不能用当前分支的顶端提交替代所提供的提交。
3. 在任何改动之前，为基准检出目录的分支、`HEAD`、提交树、索引树、已暂存、未暂存和未跟踪状态创建快照。同时为每个已登记的工作树和本地分支创建快照。
4. 若要复用，还要为控制器当前的关联工作树创建快照，包括确切路径、具名分支、`HEAD`、提交树、索引树以及已暂存、未暂存和未跟踪状态。记录每项本地状态的责任方和允许的本地状态范围。任何项目的所有权存在歧义或超出已接受的实施范围时，都要停止。

只有具备一个确切的基准检出目录、具名基准分支、所提供的基准提交以及完整的改动前快照时，才能继续。若要复用，还必须具备完整的当前工作树快照、所有权映射和允许的本地状态范围。这些快照就是保全边界，也是就绪判定所接受的基准。

## 阶段 2：选择复用或创建

选择一条路径：

- **复用：**只能复用控制器当前的关联工作树，而且所属工作流必须已为这一确切范围选定该工作树。如果没有提供其确切路径和身份，或者控制器当前不在该工作树中，就停止。要求有一个经过证明且不存在歧义的 `creation_owner`，并要求其路径、具名分支、`HEAD`、提交树、索引树、已暂存、未暂存和未跟踪状态以及逐项所有权均与阶段 1 的快照和允许的本地状态范围相符。缺少 `creation_owner`、`creation_owner` 存在歧义，或者身份、状态、范围或所有权有任何不一致时，都要停止。
- **创建：**要求提供全小写且以连字符连接的 slug，然后选择 `<base-root>/.worktrees/<slug>`；slug 缺失或无效时停止。使用已经验证的仓库分支约定；如果没有已验证的约定，则使用 `worktree/<slug>`。验证分支名称，然后证明文件系统和已登记的工作树中均不存在该路径，并且已登记的工作树和本地分支中均不存在该分支。发生任何冲突时停止。

退出本阶段时，记录选定的路径和分支、将要复用还是创建工作树，以及本次实施允许的本地状态范围。

## 阶段 3：建立 `.worktrees/` 防护

对于 `<base-root>/.worktrees/` 下的每个选定路径：

1. 要求根目录的 `.gitignore` 包含有效的仓库相对路径条目 `.worktrees/`。
2. 如果该条目缺失或无效，只有在 `.gitignore` 归项目所有，并且编辑能够保留并区分所有现有内容和本地状态时，才能追加 `.worktrees/` 作为最小的有效修复。将新增内容记录为一项有意的项目自有改动。如果该文件是生成产物、处于只读状态、所有权存在歧义，或者与无法区分的本地工作重叠，就停止。
3. 对选定的仓库相对路径运行 `git check-ignore -v`。只有当输出证明根目录的 `.gitignore` 条目有效时，才能继续；全局排除规则或 `.git/info/exclude` 不满足这项关卡。
4. 若要创建，获取确切选定目录和工作树所需的任何权限。该权限只涵盖这个目录和工作树，不授权任何无关的 Git 或文件系统改动。

## 阶段 4：创建并验证工作树

若要复用，直接进入下方的验证关卡。若要创建：

1. 立即依据已记录的输入和快照，再次检查基准分支、`HEAD`、提交树、选定路径和选定分支。还要再次检查完整的基准索引树、已暂存、未暂存和未跟踪状态，只允许存在已记录且可区分的 `.gitignore` 修复。如果有任何其他值发生移动或出现，就在创建前停止，并报告完整的已记录状态和当前状态。
2. 宿主的原生工作树能力可用时，优先使用该能力，并将其具体的生命周期责任方记录为 `creation_owner`。只有不存在原生能力时，才严格运行：

   ```text
   git -C <base-root> worktree add -b <branch> <worktree-path> <base-commit>
   ```

   将执行后备方案的具体智能体记录为 `creation_owner`。
3. 如果创建失败，检查选定路径和 Git 的工作树元数据。只有证据证明未完成产物由本次尝试创建且不包含用户工作时，才能将其移除。如果无法取得这种证明，就保留产物和证据，明确指出确切的恢复责任方和操作，然后停止。安全移除后，重复步骤 1 中的完整创建前检查，包括完整的基准快照，然后重试一次。第二次失败时，保留所有剩余证据并停止。

验证关卡：

1. 使用 `git worktree list --porcelain` 证明选定路径、具名分支和 `HEAD` 与已记录的值相同。
2. 证明基准检出目录的 `HEAD`、提交树、索引树以及原有的已暂存、未暂存和未跟踪状态仍与快照相符。唯一允许的差异是 `.gitignore` 中已记录的 `.worktrees/` 新增条目。

只有选定工作树的身份得到证明且基准保全边界完好无损时，才能继续。

## 阶段 5：准备并判定就绪

1. 在选定的工作树内操作。如果目标仓库提供自己的 `worktree-environment-setup`，就在验证基线前运行它，并记录其命令和结果。只有该设置返回成功的就绪结果时，才能继续验证基线。如果该设置不可用、停止、失败或返回未就绪结果，就立即终止就绪判定，保留工作树，并在交接中记录失败的步骤、结果、确切的下一责任方和确切的下一操作。
2. 完成环境设置后，运行仓库声明的基线。记录确切的命令和结果。基线失败会终止就绪判定，除非用户明确接受该失败。没有声明基线也会终止就绪判定，除非所属工作流或用户明确接受这种缺失。记录已接受的失败或缺失；不得臆造命令，也不得以已完成改动的验证代替基线验证。
3. 只有以下条件全部满足时，才将结果标记为就绪：
   - 工作树有一个具名分支；
   - 它的 `HEAD` 和提交树与已接受的基准相同；
   - 目标方自有的 `worktree-environment-setup` 不存在，或者已经成功完成并返回就绪结果；
   - 基线已通过、其失败已得到用户明确接受，或者其已声明的缺失已得到所属工作流或用户明确接受；以及
   - 每个本地路径都只属于已接受的实施范围。

保留每个失败的工作树作为诊断证据。除非其所属工作流另行提供处置权限，否则还要保留任何其他未就绪的工作树；这项技能不授予删除它的权限。本阶段结束时，必须给出可观察的就绪结果和原因，并准确标明任何停止或失败。

## 阶段 6：返回机械式交接

每个终止出口都返回一份交接。只有完整的阶段 5 就绪谓词通过时，才将 `status` 设为 `ready`；之前的每次停止或失败都将其设为 `non-ready`。`failed_phase`、可观察的原因和确切的下一操作用于区分各种未就绪结果。

根据已经完成的边界填充每个交接字段。保留每个观察值及其确切的失败原因；凡是尚未确定、验证或运行的内容，都使用字面标记，不得推断：

- 阶段 2 选择工作树之前，将选定工作树、分支、`head` 和 `tree` 设为 `not-selected`。
- 创建分支选择路径和分支之后、创建工作树之前，报告确切的选定路径和分支，并将 `head` 和 `tree` 设为 `not-created`。
- 尝试创建之后，或者选择复用之后但验证关卡通过之前，报告选定的路径和分支，并在可取得时报告观察到的 `head` 和 `tree`，同时将身份标记为 `unverified`。无法取得的观察值报告为 `unavailable`；绝不能推断。
- 验证关卡通过后，包括设置或基线执行期间，报告经过验证的确切选定路径、具名分支、`head` 和 `tree`。
- 对于已接受的范围、基准检出目录、基准分支、基准提交和树、每个责任方、复用路径或创建 slug，以及允许的本地状态范围，在这些内容确定之前使用 `unavailable`。保留观察值，并在其适用关卡通过前将它标为 `unverified`；通过后报告经过验证的确切值。
- 对于 `.gitignore` 关卡，在阶段 3 之前报告 `not-run`。保留任何观察到的规则或修复结果，并在 `git check-ignore -v` 证明所需的根目录规则之前将其标为 `unverified`；证明后报告经过验证的确切结果。
- 对于环境设置和基线，在适用步骤运行之前，将其命令、结果和接受字段报告为 `not-run`。运行后，保留确切的命令和结果，并将任何仍未验证的结果标为 `unverified`。如果目标方证据证明某个步骤不存在，就报告该步骤确切的缺失情况及其所需的接受，而不是 `not-run`。
- 对于就绪状态，在阶段 5 的每个谓词通过之前，报告 `non-ready` 以及确切的失败阶段和原因。`ready` 交接不包含边界标记：每个必填字段都确切且已经验证，每个适用的设置和基线步骤都有确切结果。

交接包含：

- `status` 和已接受的实施范围；
- 按照上述已完成边界规则填充的工作树身份；
- 基准检出目录、具名基准分支、确切的提交和树，以及保全的本地状态；
- `scope_owner`、`creation_owner`、`integration_owner` 和 `cleanup_owner`；
- 确切的复用路径或创建 slug、`.gitignore` 结果，以及允许的本地状态范围；
- 环境设置和基线命令、结果，以及明确接受的失败或缺失；以及
- 就绪结果和原因。

对于任何未就绪结果，还要返回保留的状态、失败阶段、适用时失败的设置步骤和结果、下一责任方，以及确切的下一操作。调用方必须在实施或收尾前重新检查交接。交接中记录的值不授予任何更广泛的权限。
