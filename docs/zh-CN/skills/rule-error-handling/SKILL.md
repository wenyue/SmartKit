# 错误处理

## 保持承诺的结果

依据操作承诺区分成功、正常拒绝或缺失、契约内失败和程序契约违反，不以它们的表示形式、发生频率或可重试性为依据。

保持失败结果和部分副作用可见。捕获错误、提供默认值或恢复未来可用性，都不代表成功：当前操作必须履行其承诺，或达到已接受的降级或部分完成结果。

保持不会失败的操作直接明了。使用语言原生机制和项目实际契约，仅在调用方需要作出不同决策时引入稳定区分。在契约所属边界进行转换。穷尽处理封闭的业务结果集合；对于开放协议，保留明确的未知失败路径和有用原因，不把偶发失败转成正常拒绝。

将程序契约违反与普通否定结果区分开。生产所需的验证、控制流、副作用和不变量，必须在可选检查被禁用时仍然生效。

在理解数据语法和含义的边界进行验证，区分内容无效与 I/O 失败。当代码、类型和引用契约未清楚表达重要调用方义务时，补充说明。

## 审慎设计公开失败契约

优先采用语义准确的既有失败契约。新增公开区分可以让处理或诊断更清楚，但也会增加调用方需要了解的知识、处理选择和兼容承诺。即使这种区分只提供可选细节，也必须有足以抵偿这些成本的具体收益。

新增可供外部使用的失败区分前，须询问用户并取得对具体新增项的明确同意，除非它符合下述忠实细化条件。这项要求适用于各种原生错误机制：异常类型、错误标识或错误码、结果分支，以及新开放检查能力的底层失败，都可能增加公开失败契约。已有明确同意若覆盖该新增项，仍然有效；一般性的功能实现授权并不足够。

忠实细化必须保留语言或标准库中语义准确的具体失败类别，以及该类别承诺的识别方式、信息和处理行为。调用方无需适配，已有的类别层面处理就必须仍然有效；调用方可以按需使用具体细节。通过语言原生的匹配或分类机制确认这一点，不要求采用继承。仅继承通用异常基类或实现通用错误接口，不满足此条件。此豁免只免除额外取得用户同意的要求，不免除成本判断和保留受支持契约的责任。

## 明确责任直到操作完成

仅为当前边界负责的恢复、清理、补偿、必要契约转换或最终处理而处理失败；否则，通过已接受的契约如实传播。库可以通过向调用方移交失败结果履行责任。

为每个独立发起的操作确定最终负责人。必需的异步工作属于该操作的完成承诺；脱离当前操作的工作需要独立的完成、失败和生命周期归属。在成功、失败、取消和中断路径上保证应负责的清理。

停止传播失败或委托报告，不会消除对残留状态、清理、重试和反馈的责任。将未解决结果和重要副作用传递给最终负责人。

## 在既定范围内处理失败

有依据认为正常条件通常成立、失败属于异常情况时，优先直接执行，并在局部处理当前边界负责的失败，避免重复预检查。无法确认条件通常有效时，优先采用可靠、低成本的显式检查。

遵守语言的安全前提；捕获失败不能使未定义行为或其他不安全的执行变得安全。对可变状态的预检查只能确认检查当时的条件。即使检查通过，仍须处理或传播实际操作的失败。

使用原生匹配或分类机制，只处理当前边界已有既定处置的失败。将处理限制在相关操作，保留程序缺陷和无关失败所需的传播或报告。遵守语言和库赋予失败机制的语义：普通返回错误与 panic 或等效中断，可能有不同的处理约束。`Error` 这样的名称或技术上能够拦截某种失败，本身不能决定其处置；实际契约和安全处理方式才是依据。

同一种恢复、回退或转换，只有适用于其覆盖的每种失败时才安全。在编写的代码中，每个宽泛拦截点附近都要留下有意义的维护者注释，说明为何必须宽泛拦截，以及为何处置对每种被拦截失败都安全。这包括宽泛的异常捕获和类似 panic 的拦截。常规检查操作返回的错误后如实传播，不属于宽泛拦截，也不要求这类注释。

## 保留证据与反馈

区分原始失败与恢复、清理或补偿失败。在转换和最终处理过程中保留可用的原始错误、原因链、堆栈和有用上下文。过滤敏感数据，包括凭据和不必要的隐私信息。面向人的解释用于补充这些证据，而非替代它们。

分别决定诊断证据的保留与公开错误的识别能力。让底层错误可通过原生匹配或解包机制接受检查，可能使它成为调用方的依赖。保留已有承诺的识别能力，并在新增此类承诺前应用上述公开失败契约政策。保留有用证据本身，不足以证明新增公开包装或检查契约合理，也不要求每种原生错误表示都携带堆栈。

每个需要报告的事件都应有一个最终报告负责人。补充诊断与面向受众的反馈可以并存；传播不应产生重复事件报告。

依据影响、运行预期和所需响应，采用项目定义的严重级别和告警规则，不仅凭错误通道或是否恢复来决定。恢复成功也可能仍需调查。

最终反馈必须通过所属边界传达有用的上下文、影响和处置，包括重要损失或功能不可用，即使受众无法修复。

在最终处理边界，只有实际执行者具备相应能力、权限和可用工具，且能以合理工作量完成补救时，才能依赖人工补救。暴露失败并不能证明接收它的人能够解决问题。

## 加载相关分支

普通传播、明确的转换或捕获、常规审查、I/O 失败移交及异步归属，适用上述政策。在选择、修改或审查以下行为前，阅读对应资源：

- [恢复与副作用](references/recovery-and-effects.md)：恢复、重试、补偿或已接受的部分完成策略，需要副作用、重放或结果状态方面的约束时。
- [持久化数据](references/persisted-data.md)：修复、重建、丢弃或降级使用持久化或序列化数据，需要决定权限、损失、后续读取或数据解释时。仅传播普通 I/O 失败不触发此分支。
- [补救](references/remediation.md)：最终处置依赖人工行动，或需要明确跨角色的解决与反馈责任时。若诊断或反馈变更保持既定处置及其责任不变，则该变更本身不触发此分支。

## 在任务内明确并验证

依据受影响的结果控制调查范围，沿实现、调用方和契约证据，从起点经过转换追踪到最终归属及生产中的强制执行。区分已观察行为与拟议修正，为每项不一致确定最小且完整的修正及其效果。在所属边界进行获准变更，保留无关结果和受支持契约。仅评估的工作保持只读；本政策不增加远程或破坏性操作权限。

在询问缺失的处置、损失、归属或受众负担决定前，先调查能够查明的事实。根因未知时仍可采用已有依据的安全处置；需要根因调查时，使用适用的诊断流程。必要资源、重要契约或决定、证据、工具、访问条件或权限不可用时，报告缺口，暂停依赖它的工作。所属流程允许时，可以继续独立且获准的工作。

通过负责的公共操作或边界，使用已发现的所属检查和可用工具验证变更后的结果。覆盖范围内有意义的成功、缺失或拒绝、传播、最终反馈和残留状态；次生失败、取消和中断影响这些结果时，也应覆盖。检查失败意味着需要修正或结果尚不能确定；必要验证失败或不可用，工作就仍未完成。

使用当前任务的验证和交接，不另起常规审计或报告。对于经过调查的工作，为每条已识别路径给出处置或证据缺口，报告范围、有依据的发现或已修正问题、实际验证、未解决决定及未验证部分。缺口既不是已验证路径，也不是已完成修正。
