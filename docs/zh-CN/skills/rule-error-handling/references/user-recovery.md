# 用户恢复

用户或其他人员接收失败反馈、重试、修复状态，或接手未解决工作时，使用本参考。

## 留下实际可行的后续行动

按操作契约保留输入、草稿、已完成工作和仍有效的可见状态。刷新失败不一定需要清空此前的有用内容；保存被拒绝不一定需要关闭编辑器。过期或未保存状态有影响时，清楚标明。重试或其他受支持的行动仍可用时，在失败或拒绝后恢复交互，复用既有 UI 状态和生命周期，而不另建恢复状态机。

提供能起作用的最简单受支持行动，例如等待、重试安全的未完成步骤、登录、选择有效位置，或联系负责的运维人员。用受众能理解的方式，说明相关原因、影响、结果状态和行动。路径等技术细节有助于理解或行动时，应提供它们。

## 将人工修复交给能执行的人

只有实际执行者有相应的访问条件、权限、工具和能力，能以合理的工作量采取行动时，才依赖人工补救。根据实际部署和受众确定执行者。有人值守的服务通常由运维人员修复基础设施。客户端应用通常在自身权限内处理失败，或为普通用户或具备相应能力的人员提供受支持的行动方式。

无法直接修复时，如果有可行且受支持的升级处理渠道，就提供该渠道。如果处置依赖人工行动，却找不到有能力且有权限的执行者，应先明确归属和处置，再实现相关行为。运行时提示可以在既定产品契约下收集有限的选择；恢复方式或数据损失的决定尚未明确时，应先与负责方确定，再实现依赖该决定的行为。

向接手者传递影响及适合其受众的证据，并明确由谁负责完成和最终反馈。仅报告失败或显示联系说明，并不代表移交完成。

## 让补救行动的完成情况可见

需要采取行动的人应能知道补救行动成功、失败或发生了有实质影响的中断。行动失败时，重新启用控件或保留可操作的失败状态；通过各自的诊断负责人保留原始事件和任何新失败。反馈交付本身也可能失败：采用可行的既定回退方式，避免递归通知或替换原始操作结果。

依据需要采取的行动选择反馈的保留方式。未解决条件需要后续关注，否则会变得不可见时，短暂通知并不足够。在负责的用户边界验证输入保留、交互可用、受支持的重试或升级处理，以及补救失败。
