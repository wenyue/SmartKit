# 用户恢复

## 留下实际可行的后续行动

保留所需输入、草稿、已完成工作和仍有效的可见状态。刷新失败不一定需要清空此前内容；保存被拒绝不一定需要关闭编辑器。清楚标明有影响的过期或未保存状态；仍有受支持的行动时，通过既有 UI 状态和生命周期恢复可用交互。

提供能起作用的最简单受支持行动：等待、重试安全的未完成步骤、登录、选择有效位置，或联系负责的运维人员。路径等技术细节对相应受众有用时，应提供它们。

## 将人工修复交给能执行的人

只有实际部署中的执行者有相应的访问条件、权限、工具和能力，能以合理的工作量完成时，才依赖人工修复。

无法直接修复时，如果有可行且受支持的升级处理渠道，就使用它。如果没有有能力且有权限的执行者能够完成必要补救，应先明确归属和处置，再实现相关行为。产品可以在既定契约下询问用户有限的选择；未解决的恢复或数据损失政策，需要先由其负责人作出决定。

人工移交必须传递影响及适合受众的证据，并分配完成和反馈责任。仅显示联系说明不代表移交完成。

## 让补救行动的完成情况可见

需要采取行动的人应能知道补救成功、失败或发生了有实质影响的中断。失败时，重新启用控件或保留可操作状态，并通过各自负责人保留原始事件和新失败。反馈交付失败时，使用既定且可行的回退方式，避免递归通知或替换操作结果。

按所需行动的需要，保持反馈可用。短暂通知会让需要后续关注的未解决条件变得不可见时，它就不足够。
