# 补救

设计、修改或审查依赖人工行动的最终处置，或需要明确跨角色的解决与反馈责任时，使用本资源。

## 将可行行动交给有权执行的角色

依据实际部署、访问条件、可用工具、调用方和预期用途，确定谁能执行行动。专业排障和复杂修复由具备资格的角色负责。以下默认判断可作为调查起点：

- 对于由开发人员或运维人员运营的服务，启动或基础设施故障默认由运营者负责补救。将可诊断的失败送入其受支持的修复或告警流程，可以是适当的处置。服务的业务用户并不因此承担运营责任。
- 客户端应用默认面向检查或修改内部状态能力有限的普通用户。应用必须在其权限内解决问题，或提供受支持的机制，让用户或具备资格的角色能够解决问题。没有可行的后续行动时，仅显示异常并不足够。

以实际证据为准：专业客户端可能有修复工具，服务却可能没有具备必要访问权限的运营者。产品类型不能证明修复能力或赋予权限；具体产品事实和恢复机制留在项目契约与政策中。

无法直接修复时，若存在受支持且可行的升级处理途径，就提供该途径。尚未确定可由具备能力且获授权的角色执行的可行行动时，保持补救未解决状态，暂停依赖它的设计，直到归属和处置明确。

运行时提示可以在既定契约下收集范围明确的产品选择，但不能解决开发阶段缺失的数据或恢复契约。在实现依赖行为前，调查可用证据，并向负责方取得缺失决定。

例如，持久化数据不变时，确定性的重建失败会在后续读取中再次出现。如果普通客户端用户无法检查或修复该数据，仅将异常移交给用户就会留下反复出现的失败。依据数据契约选择修复、明确降级或隔离，或受支持的升级处理，并保留未经授权不得丢失的数据。已接受的降级结果必须保持失败及其重要影响可见；捕获异常或保留原始字节，都不足以证明处置完整。满足相应条件时，遵循技能入口中的持久化数据和恢复分支。这是面向人的最终处置决策；内部层级仍可通过其已接受的契约传播失败。

## 使反馈对应实际结果状态

区分受众需要理解或执行的内容，与维护者调查所需的证据。将结果状态的反馈与已为该受众确定的可行行动或受支持升级途径联系起来。

对于移交处理责任的库或组件，沿返回或失败契约，将影响、诊断和补救信息追踪到调用方或既定反馈负责人。委托必须保留行动状态和完成责任的归属。

例如，假设只有维护者同时具有修复存储的访问条件和权限，而用户有受支持的登录或求助途径。维护者可能需要路径和诊断证据来修复存储；用户则需要了解受影响的能力，以及自己可以采取的下一步行动。这种区别来自各自的责任和访问条件，并不规定通用的通道或受众角色。

反馈必须准确反映结果状态。确认收到或委托他人，不能证明恢复已经完成。

## 负责到行动完成

从失败状态开始，追踪每项行动直到成功完成、失败或任何中途停止。根据证据确定执行负责人、最终报告人和反馈负责人。明确残留状态、结果接收者，以及行动成功或失败时反馈如何变化。

使用适合受众和环境的通道。仅发起行动或显示提示，不能证明已有可观察的结果。

通过负责的公共边界验证有意义的路径，适用时包括次生失败、取消或中断。归属移交后，完成、失败和保留状态仍应可观察。
