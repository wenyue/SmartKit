# 补救

设计、修改或审查人工补救行动，或跨角色的解决与反馈责任，需要作出能力、权限或工作负担决定时，使用本资源。

## 将可行行动交给有权执行的角色

依据实际访问条件、调用方和预期用途，确定谁能执行行动，而不是根据模块或界面名称判断。执行者必须同时具有能力和权限，行动的复杂度与工作负担也必须适合该受众。专业排障和复杂修复由具备资格的角色负责。无法直接修复时，若存在受支持且可行的升级处理途径，就提供该途径。尚未确定具备能力且获授权的角色时，保持补救未解决状态，暂停依赖它的设计，直到归属明确。

运行时提示可以在既定契约下收集范围明确的产品选择，但不能解决开发阶段缺失的数据或恢复契约。在实现依赖行为前，调查可用证据，并向负责方取得缺失决定。

## 使反馈对应实际结果状态

区分受众需要理解或执行的内容，与维护者调查所需的证据。将结果状态的反馈与已为该受众确定的可行行动或受支持升级途径联系起来。

对于移交处理责任的库或组件，沿返回或失败契约，将影响、诊断和补救信息追踪到调用方或既定反馈负责人。委托必须保留行动状态和完成责任的归属。维护者可能需要用于存储修复的路径和诊断证据，普通用户则需要了解受影响能力，以及受支持的登录或求助途径。这些只是责任差异的说明，不是强制通道或受众角色。

反馈必须准确反映结果状态，不得暗示确认收到或委托他人就意味着恢复完成。

## 负责到行动完成

从失败状态开始，追踪每项行动直到成功完成、失败或任何中途停止。根据证据确定执行负责人、最终报告人和反馈负责人。明确残留状态、结果接收者，以及行动成功或失败时反馈如何变化。使用适合受众和环境的通道；仅发起行动或显示提示，不能证明已有可观察的结果。

通过负责的公共边界验证有意义的路径，适用时包括次生失败、取消或中断。归属移交后，完成、失败和保留状态仍应可观察。
