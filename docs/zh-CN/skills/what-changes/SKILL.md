# 有哪些修改

在实施前，将当前对话中累积的修改意图整理成用户可以审阅的范围。厘清哪些意图仍然有效、哪些已经搁置、哪些尚不明确，并说明拟议的文件修改如何服务于这个范围。

当用户显式调用，或要求执行多项累积修改、当前对话中相隔较远讨论过的修改时，运行此流程。根据修改意图判断是否自主调用，不要仅依据对话长度。小而清楚的请求按通常方式执行。

此审阅是只读的。调用授权的是为报告进行必要检查，而不是实施或其他修改。

## 重建当前意图

使用对话及理解其修改意图所需的显式引用源工件。当只读检查仓库路径有助于识别受影响的文件或模块时，进行该检查。将后续决定与早期建议、被否决的想法、已被取代的计划和已完成的工作相协调，让报告描述仍需完成的内容。

区分项目的状态与其提出时间或来源。仍然有效的 Agent 建议即使尚未获得用户明确认可，也应列入目标；将其标为建议，而不是用户已同意的要求。较早提出、未完成也未取消的目标，如果当前是否有效仍不清楚，应放入待确认。只有现有证据无法确定状态或重要细节时，才放入该栏目。

说明可访问历史或证据中的缺口，不要虚构决定或路径。如果缺失的对话历史使范围审阅无法可靠完成，将这一覆盖缺口列入待确认。

## 呈现可审阅的范围

按以下顺序使用四个语义栏目，采用这些带 emoji 前缀的粗体标签。省略空栏目：

1. ❓ **待确认** — 尚未确定的状态、重要细节或覆盖缺口。未决项目可能涉及的文件范围也放在这里，不要将其呈现为已确定的修改。
2. 🎯 **目标** — 正在审阅的有效目标，包括仍然有效的 Agent 建议。
3. 🚫 **排除的想法** — 相关的已否决或已被取代的建议，以及取代它们的决定。
4. 📝 **计划修改的文件** — 仅列出服务于上述目标的修改。

将相关验证计划和证据限制放在它们所限定的项目旁。

对每个计划修改的文件或模块，在同一段说明中结合“改什么”和“为什么改”，明确它与适用目标的关系。当预计受影响范围不大且证据支持时，列出精确路径。达到约 30 个或更多文件时，可在有助于阅读的情况下按模块分组，同时仍点名重要的单个文件。分组应帮助用户判断修改，而不是隐藏其涉及范围。

## 确定范围后再询问是否实施

在报告结尾请用户解决待确认项目。每次得到回答后，更新并重新检查报告。只有没有待确认项目时，才询问是否开始实施；如果初始报告就没有待确认项目，直接以实施问题结尾。

只有获得对该问题的肯定回答后才实施。更早的执行请求不算该问题的回答。仅解决一个待确认项目也不等于确认实施。

## 报告示例

这些占位内容代表由对话支持的目标、决定和路径。示例展示了全部四个栏目及一个未决目标；实际报告中应省略空栏目。

- 较早提出的目标 C 是否仍然有效尚不明确。`<possible-file>` 只是可能涉及的范围。

🎯 **目标**

- **G1** ：交付结果 A。
- **G2** （仍然有效的 Agent 建议）：保持结果 B 与结果 A 一致。

🚫 **排除的想法**

- 方案 X 已被针对 G1 的后续决定取代。

| `<module-b>/`（约 30 个文件，包括重要的 `<file-b>`） | G1, G2 | 更新共享行为，使结果 A 与结果 B 保持一致。 |
