# 变更范围

在实现前，将累积的预期改动整理成用户可以审阅的范围。核对仍有效的目标、已被替代的想法和未决问题，再将拟议文件改动与这些结果对应起来。

用户明确调用时，或要求执行许多累积改动、执行当前对话中相隔较远讨论的改动时，运行此流程。根据预期改动判断是否自主调用，不要仅凭对话长度。小而清晰的请求按正常方式执行。

审查是只读的。调用授权为报告进行必要检查，不授权实现或其他改动。

## 从当前对话重建意图

使用对话，以及为理解预期改动而需要的、被明确引用的源材料。只读检查仓库路径，帮助确定受影响的文件或模块。将后续决定与先前建议、被否决的想法、被替代的计划和已完成工作核对，使报告描述仍需完成的内容。

根据每个事项的当前状态分类，而不是根据其时间或来源：

- 将仍有效的 Agent 建议纳入目标，即使用户尚未明确认可；将其标为建议，而不是已达成一致的用户要求。
- 较早提出、尚未完成且未取消的目标，其当前有效性仍不清楚时，放入待确认项。
- 只有现有证据无法确定事项状态或重要细节时，才使用待确认分类。

说明可访问历史或证据的缺口，不要编造决定或路径。如果缺少对话历史导致无法可靠审查范围，将该覆盖缺口列入待确认项。

## 将目标与文件改动一起呈现

使用以下四个语义部分，顺序和 emoji 加粗标签如下。省略空部分：

1. ❓ **待确认** — 未确定的状态、重要细节或覆盖缺口。未决事项的可能文件范围也留在这里，不要呈现为已经决定的改动。
2. 🎯 **目标** — 正在审查的有效结果，包括仍有效的 Agent 建议。
3. 🚫 **排除的想法** — 相关的已否决或已被替代建议，以及取代它们的决定。
4. 📝 **计划修改的文件** — 仅列出服务于上述目标的改动。

将相关验证计划和证据限制放在它们所限定的事项旁边。

对每个计划修改的文件或模块，将改动与理由一起解释，并对应到适用目标。受影响集合较小时，在证据支持的情况下列出精确路径。约 30 个或更多文件时，可按模块分组以改善可读性，同时仍点名重要的单个文件。分组应展示工作覆盖范围，而不是将其隐藏。

## 先解决未决事项，再确认实现

报告结尾请用户解决待确认项。每次得到答复后，更新并重新检查报告。只有不再有待确认项时，才询问是否开始实现；如果初次报告没有待确认项，就以该实现问题结尾。

只有用户对该问题明确肯定答复后，才进行实现。较早的执行请求不算对它的答复。仅解决待确认项，也不等于确认实现。
