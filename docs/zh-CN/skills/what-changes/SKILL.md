# 将改什么

在开始执行前，回顾当前对话中累积的待修改事项。用户明确调用本 Skill 时，或用户要求执行修改且此前已累积较多待修改项或修改跨度较大时，执行此流程。是否自动调用取决于待修改事项的数量和跨度，不能只看对话长度；范围小且清楚的请求正常执行。以只读方式输出范围清单。调用本 Skill 只授权为形成清单而进行的检查，不授权实施或其他修改。

1. 根据当前对话和理解其内容所需的明确引用资料，重建当前范围。需要确定受影响的文件或模块时，以只读方式检查仓库路径。根据后来的决定，核对早先的建议、被否定的想法、已被替代的计划和已完成的工作。对于无法获取的对话历史或证据，说明缺口，不臆造决定或路径。
2. 按当前状态归类讨论事项。将当前仍有效的目标放在目标栏目，其中包括用户尚未明确采纳、但仍有效的 Agent 建议。将相关的已否定或已被替代的建议放在已排除栏目。只有现有证据无法确定归类或重要细节时，才使用待确认栏目。对于未完成、未取消的早先目标，如果无法确定它目前是否仍有效，就将其放在待确认栏目。如果无法获取的对话历史使可靠的范围核对无法完成，在待确认栏目中说明覆盖缺口。
3. 按此顺序报告四类内容：❓ **待确认**、🎯 **目标**、🚫 **已排除**、📝 **待修改文件**。使用这些带 emoji 前缀的加粗栏目标签，栏目名翻译成回答所用语言；省略没有内容的栏目。与判断有关的验证计划和证据限制，写在其所限定的事项中。
4. 在待修改文件栏目中，只列出服务于目标的修改。对每个文件或模块，将打算修改的内容及其原因合并说明，并明确它与哪个或哪些目标相关。当预计涉及的文件较少且有证据支持时，写出具体路径。预计涉及约 30 个或更多文件时，可以按模块归纳，以便阅读；如有影响范围判断的关键文件，仍需单独列出。未确定事项可能涉及的文件范围，只在对应的待确认事项中说明，不将其写成已决定的修改。
5. 报告最后一句应是一个问题：有待确认事项时询问所需决定；没有时询问是否开始实施。每次收到待确认事项的答复后，更新并核对报告，直到能询问是否实施。仅在用户明确同意实施后开始；先前的执行请求不构成这一同意。

- 早先的目标 C 是否仍有效尚不明确。`<possible-file>` 只是可能涉及的范围。

- **G1**：实现结果 A。
- **G2**：让结果 B 与结果 A 保持一致。

- 方案 X 已被后来针对 G1 的决定取代。
