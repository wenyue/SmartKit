# 实施工单

按依赖顺序完成一个已冻结的工单集合，每票保留一个已验收提交，最后对整个批次审查并收尾一次。经证明为空的选择返回 `nothing-to-do`，不创建工作树，也不产生其他操作效果。

当前 Agent 是**Controller**，负责选择、串行实施、独立验收和最终证据交接。项目配置的跟踪器负责资格、依赖、认领和跟踪器中的完成状态。公共 `create-worktree` 负责工作区就绪及其环境依赖；公共 `code-review` 负责 Standards 和 Spec 审查；公共 `finish-worktree` 负责历史准备、所选结果、其操作效果的恢复和清理。使用前读取这些依赖的当前公共契约。通过目标项目的 `docs/agents/issue-tracker.md` 及其配置的分诊负责人解析跟踪器；通过适用项目规则和已有文档中的验证接口解析必需验证。必需能力缺失、不可用、失败或含义不明时，在其负责人处停止，并保留可归属的状态。依赖存在但执行失败，不能按依赖缺失处理。

仅使用已接受请求、适用策略和上述负责人契约提供的权限。使用并重新核对工作树就绪结果后，范围内的本地候选提交和受限 amend 使用工作流的提交权限，并运行仓库正常 hooks。它们不授予跟踪器、远程、安装、最终收尾或清理操作权限。保留规范检出和无关工作。默认保留已验收提交；合并历史需要单独明确选择。

## 1. 确立批次

识别有界输入范围和目标。重新选择工单前，观察相关仓库及已注册工作树的状态、分支历史、保留的选择与依赖交接，以及活动 Worker 或最终收尾执行者的身份。首次观察跟踪器前，读取[跟踪器边界](references/tracker.md)。如果这些观察表明存在既有或可能的批次尝试，使用[暂停与恢复](references/resume.md)恢复其原始阶段和冻结范围。先前的最终收尾或闭合交接优先于当前工单资格。

只有证据支持建立新批次时，才能重新选择。确立已接受的已提交基线 `batch_base`、请求的最终收尾结果、历史策略和确切操作权限。使用 `tracker.md` 解析同范围依赖，冻结成员、顺序、完整验收要求及其来源版本、排除项和负责人支持的认领计划。报告选定工单和排除项；选择结果不承诺完成用户更广输入中的全部工作。经证明为空的新选择在此无操作地结束。

## 2. 建立一个环境

如果选定工单依赖源检出中未提交的工作，在批次实施前暂停，由那部分工作的负责人通过单独授权解决已提交基线。保留源检出；不要自动提交、丢弃、重新实施或将其中的工作纳入工单变更。协调好已接受的基线后再继续。

在其他批次写入前，完成所有必需的初始认领。通过公共 `create-worktree`，在冻结的 `batch_base` 上明确请求**clean**创建，并提供已接受的范围、归属、放置位置和环境设置操作权限。明确选择 clean，可以保留脏源工作区而不导入其中的变更。放置决策、源状态保留和环境准备仍由该负责人处理，包括其目标 `worktree-environment-setup` 依赖。

只使用可归属且当前有效的 `ready` 结果。在首次 Worker 或延后认领操作前，重新核对物理路径、Git 共同身份、链接工作树注册、分支、基线、HEAD/tree、索引和预期本地状态。将这个确切工作树绑定到批次。所有 Worker 和 Reviewer 复用其环境；发生实质漂移或控制中断时，按 `resume.md` 刷新就绪证明。项目必需检查的输入变化后，仍要重新运行相应检查。

## 3. 逐票实施与验收

对每张依赖已就绪的工单，执行[处理一张工单](references/process-one-ticket.md)。该流程负责派发、非空候选与审查循环或独立无改动分支，以及 Controller 验收。向其提供冻结工单和前一个已验收 HEAD；只有收到 `completed-in-batch`，且其中恰好有一个独立验收通过的第一父级提交，才能继续下一票。此前已验收提交保持固定。工单保持打开，认领继续保留。

## 4. 验证并审查批次

全部选定工单验收通过且 Worker 已停止活动后，冻结最终 HEAD/tree，运行必需的整批验证。在调用审查前，根据最终状态与不可变 `batch_base` 的 diff 选择审查路径：

- diff 非空时，调用公共 `code-review`，提供每项已接受工单和规格来源及其出处。两个维度都检查完整组合结果，重点关注交互、共享约束、回归和整体要求是否满足。单票报告提供上下文，不能代替对最终状态的检查，也不能将覆盖范围缩小为只看交互。
- diff 为空时，包括有改动工单的效果相互抵消的情况，使用[独立空差异验收](references/review.md#independently-accept-an-empty-difference)，检查最终实现和全部已接受要求。

整批检查或审查发现需要修复的问题时，进入[批次修复](references/review.md#repair-the-whole-batch)。两条路径都保留工单边界。只有必需检查和两个独立判断都在确切最终状态上通过，且完整覆盖已接受范围，才能验收批次。

## 5. 收尾并报告

读取[完成已验收批次的收尾](references/complete-run.md)。重新验证冻结的来源事实和当前工作树、目标证据，再向公共 `finish-worktree` 提供已接受范围、确切 base/HEAD/tree、工单边界、完整验证和审查证据、所选结果与历史策略，以及确切操作权限。它使用这些证据，不重复进行正式审查，并执行对自身操作敏感的验证。

同时保留原始状态，使用其最强的已证明分类。只有它返回的 `authoritative delivery` 分类允许关闭跟踪器工单。PR、保留工作树、返回审查的转移以及空 diff 都不构成交付。报告已验收工单、排除项、最终收尾结果、跟踪器和生命周期处置、保留位置，以及每个未完成边界的下一位负责人和操作。

遇到实质阻塞时，使用 `resume.md` 暂停整个批次并保留部分工作。受支持的普通修复在仍有进展时继续；能力不可用或失败后无法取得进展时，停止并指明确切负责人。不得通过跳过工单、改变队列、回退工作或重复可能已完成的外部操作来绕过阻塞。
