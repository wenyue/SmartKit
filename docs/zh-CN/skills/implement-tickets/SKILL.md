# 实施票据

在一个准备就绪的工作树中完成一个已冻结、按依赖排序的批次。为每张票据验收一个固定提交，再验收组合结果并交给选定的收尾流程。跟踪器完成状态以已证明的权威交付为依据，不能仅凭实现完成或交接成功。经证明为空的新选择返回 `nothing-to-do`，不做任何修改。

当前 Agent 是 **Controller** ，负责选择、推进和验收。新的限定范围 **Worker** 实现票据及修复。保持冻结的需求、成员、顺序和已验收提交边界不变。一张票据受阻就暂停批次；跳过它不能解决阻碍。每张票据和组合批次各接受一轮独立 Standards/Spec 审查，随后进行限定范围修正和 Controller 验证，直到验收。Worker 返回是验证进展的时点，不是停止修复或制造改动的理由。

## 使用各所有者的契约

使用公开 `create-worktree`、`code-review` 和 `finish-worktree` 之前先加载它们。它们分别负责工作区/环境就绪、通用独立审查和收尾。通过目标项目的 `docs/agents/issue-tracker.md` 及其所有者指针确定跟踪器和分诊策略。适用的项目规则及文档化验证接口提供必需检查；独立提供的 SmartKit 核心治理负责权限、优先级和无进展判断。

此工作流保护规范检出及无关工作。当前工作树就绪状态允许通过正常钩子创建本地范围内的候选提交和有限 amend，但不授予跟踪器、远端、安装、收尾或清理效果的权限。向其所有者确定这些权限。配置缺失，或必需能力不可用、失败、含糊时，保留可归属状态并停止依赖工作；已存在但失败的依赖不能当作不存在。

在新选择之前，从仓库/工作树状态、分支历史、跟踪器观测、保留交接及存活 Worker/收尾者身份中查找已有或可能存在的尝试。遇到该分支、控制中断、证据缺失或重要阻碍时，先阅读[暂停与恢复](references/resume.md)再继续。优先恢复原尝试。其收尾和跟踪器关闭优先于当前队列会选出的工作。

## 冻结合格且按依赖排序的批次

对于已证明的新尝试，确定调用方的有限范围、权威目标、已提交且不可变的 `batch_base`、选定收尾结果、历史策略和确切效果权限。观察完整候选集及确定依赖闭包所需的边。保留规范身份、完整需求和来源修订、状态、所有者/领取记录、排序证据，以及肯定的合格证明或排除理由。身份、成员、合格性或依赖不确定时不能选择。

仅在有肯定合格证明时，递归纳入同范围内仍开放的阻塞票据。已完成、已拒绝、人类持有、信息受阻、外部已领取及其他权威否定结果均属排除项。外部阻塞项需要权威完成证明，否则排除其依赖票据。传播未满足依赖，拒绝环，并按依赖给闭合选择排序。跟踪器稳定公开顺序仅用于同等就绪票据之间的排序。

写入前确定每张所选票据的领取路线：

| 路线 | 必需时机 |
| --- | --- |
| 初始领取 | 跟踪器允许现在领取；在创建或其他批次写入前完成所有必需初始领取。 |
| 即时领取 | 所有者明确支持在后续流程中该票据依赖就绪时再领取。 |
| 无需领取 | 跟踪器不要求领取；到达该票据时确认当前合格性。 |

考虑会话和时机约束。存在领取操作不意味着可以在依赖就绪前领取。路线不兼容或不确定时，在写入前停止。冻结成员、图/顺序、需求与来源修订、外部完成证明、排除项和领取计划。报告选择及排除项。如果据此证明新选择为空，返回 `nothing-to-do`；不创建批次、不改变状态。

### 保留跟踪器事实和效果来源

在领取、票据验收和收尾边界，重新观察相关票据及阻塞项，与冻结选择比较。票据验收时检查完整已接受来源；收尾前检查全部所选来源和完整图。使用权威修订、摘要或变更信号，信号缺失或变化时重读内容。已验收的 `completed-in-batch` 提交及其证明可以满足后续票据的该项所选依赖。

只有本批次已消费操作所证明的确切领取/所有者变化，可以免于漂移处理。其他重要需求、状态、所有者、领取或边变化都会暂停推进，交由所有者协调。保留冻结成员和需求。刷新受影响检查，并判断原审查覆盖加定向收束是否足以支持协调后的状态。覆盖不足或重要决定/权限缺口仍是阻碍。

对每次领取、完成或释放，确定文档化操作、成功含义和确切权限。观察操作前状态，请求效果一次，保留原始结果，并在依赖工作前证明权威操作后状态。既有状态只有具备足以支持本批次的含义和来源时才能消费，否则属于漂移。成功响应本身不是证明，返回失败仍是失败尝试。对含糊或缺失响应恢复原操作，不为取得回执而重复执行。

持有已取得的领取权直至权威交付。仅当跟踪器将单独释放规定为关闭的一部分时才执行；其他处置需要跟踪器的单独确切权限。

## 准备一个干净基线环境

如果所选工作依赖源检出中未提交的改动，保留它们并暂停，等待其所有者提供单独获授权的已提交基线。协调已接受基线后再继续。此工作流不能吸收、重建、提交或丢弃该源工作。

在初始或即时领取之前，如果释放、重新分配或过期语义可能使后续派发失败导致领取权被困，先只读确认派发条件。确定运行时可用性、受支持的观察/控制、范围权限，以及不存在可能仍存活的竞争尝试。明确现有工作树的独占归属；创建前仍将就绪状态保留为实际派发的前提。复用当前共同事实，并评估票据特有约束。这一确认既不派发 Worker，也不预留容量或创建状态。未解决的重要派发风险会停止领取，并给出事实及下一所有者。

按稳定依赖顺序执行全部必需初始领取，在下一项前证明每项操作后状态。创建或任何其他批次写入之前完成它们。即时领取留到相应票据的执行时点。

调用公开 `create-worktree`，明确要求在 `batch_base` 进行 **干净** 创建，提供已接受范围、所有权、位置和设置效果权限。该所有者保护源并准备环境，包括其 `worktree-environment-setup` 依赖。消费可归属的 `ready` 结果，将其确切工作树绑定到批次。

首个 Worker 或延后领取之前，将物理路径、Git common 身份、注册、分支、基线、HEAD/tree、index 和预期本地状态与该结果比较。使用时重新核对当前绑定，调查重要漂移。全部 Worker 和 Reviewer 使用这个已准备环境；项目检查在输入变化时仍需重跑。控制缺口或就绪失效遵循[暂停与恢复](references/resume.md)。

## 产出一个票据候选

按冻结顺序取下一张依赖就绪的票据。重新验证其完整已接受来源、阻塞项、状态和领取权。消费已证明的初始领取，执行受支持的即时领取，或确定无需领取时的合格性。在前一已验收 HEAD 冻结 `ticket_base` 及其树；第一张票据使用 `batch_base`。

### 派发并观察有边界的 Worker

每张票据使用一个新 Worker，其实现与修复由同一 Worker 完成。后续批次修复也按此协议使用新 Worker。派发前，除派发能力外，还必须具备受支持的身份、观察、中断和静止确认接口。

证明确切工作树、工作单元基线、HEAD/tree、完整本地状态归属及范围权限，并确认先前写入者已静止。至多一个 Worker 写入。写入者暂停时，独立只读角色可以并行运行。向 Worker 提供：

- 规范票据身份或批次修复范围、完整需求及来源修订、项目规则、已接受依赖结果和相关研究指针。
- 确切工作树、批次/单元基线、先前已验收提交、必需定向检查，以及范围内写入/正常钩子提交权限。
- 对于修复，提供原审查证据、合并后的发现、检查失败和定向验证证据。

Worker 只拥有当前候选。已验收提交、跟踪器效果、收尾及授权自己的完成标记都不在该范围内。要求可归属的返回：Agent 身份与原始状态、候选及最终 HEAD/tree、完整自有本地状态、检查及其输入、返回/中断阶段、未完成工作和下一行动。修复返回还需给出发现处置及确切增量。

即使文件看似完成，仍保留失败尝试的失败性质。审查前证明写入暂停，验收前证明静止。经过时间或缺少响应都不能证明这些条件；Worker 状态不确定时走原尝试恢复路线。

### 确定完整预期结果

Worker 实现票据，并提供验收和安全后续工作所需的检查。披露确实非关键且延后到组合关卡的覆盖。冻结审查前，继续实现、测试和调试。

对于非空改动，通过正常钩子创建一个候选，其唯一父提交为 `ticket_base`。消息携带所配置跟踪器可发现的票据引用，不带 `SmartKit-Ticket` 尾注。如果既有行为已经满足票据，保留基线状态以进行肯定的逐需求审查。省略预期改动不能构成无改动结果。

暂停写入，独立验证完整预期结果、通过的票据检查，以及符合项目判定的干净 index/工作树。重要未跟踪或忽略状态必须归属明确。冻结审查前，将遗漏或检查失败交回同一 Worker。

## 审查一次，再针对结果状态收束发现

这一契约同时约束每张票据和组合关卡。冻结比较基线（`ticket_base` 或 `batch_base`）、HEAD/tree、完整预期 diff，以及带来源身份/修订的全部已接受需求。确认写入者暂停，且没有遗漏任何预期任务改动。

对于非空 diff，以这些确切输入调用公开 `code-review`，提供 **全部** 已接受来源，即使从提交只发现一个来源。Standards 和 Spec 必须相互独立，且独立于 Worker，两轴都必需。提供适用标准、公开的建议性 smell baseline 处理方式、检查证据，以及覆盖以下内容的深入审查说明：

- 每项已接受需求的实现和验证，包括缺失、部分、错误或没有依据的实现，以及意外范围扩张。
- 变更行之外的相关调用方、被调用方和受影响契约；边缘、错误和恢复路径、兼容性及回归。组合审查还覆盖整个批次的共同约束、冲突需求及交互。
- 全部有用且基于证据的发现，给出来源位置、需求或标准、行为及支持证据，区分严重性、建议性代码异味、覆盖缺口和不确定性。

保持两轴及其发现独立。公开摘要容纳不下时，保留完整支持报告。

### 对空结果进行肯定审查

公开 `code-review` 拒绝空 diff。对于空票据或批次，在同一唯一轮次中使用两个独立只读 Standards 和 Spec 角色，提供冻结的实现/基线、完整来源、标准、检查和上述深入审查说明。要求每项需求的满足证据，以及 Standards 对相关实现的覆盖。

空票据必须在 `ticket_base` 已得到满足。净空批次即使票据改动互相抵消，也必须满足每项所选需求；保留其票据提交。空本身或 Worker 的断言都不能证明满足。缺少必需角色或输入会停止该路线。

### 修复前收齐原始报告

取得两份完整报告，每份都标明角色、不可变输入、覆盖、发现及不确定性。保留原件或恢复位置，以及每一轴可归属的 `never-started`、`in-flight`、`complete` 或未解决状态。修复前恢复不完整或缺失报告；缺少覆盖不等于无问题结论。

### 收束发现直到 Controller 能够验收 <a id="close-findings-until-the-controller-can-accept"></a>

依据已接受需求和标准判断每项发现。对每项给出有理由的处置，包括建议性及不采纳的发现，并将汇总修复集和检查失败交给 Worker。保持原始报告和已审查身份不变。

每次返回后暂停写入，在结果状态上重复必需检查。记录相对审查的确切增量，验证每项已接受发现的解决情况，并检查修复对直接受影响行为/契约的影响，包括回归、钩子和提交敏感检查。说明原覆盖加本次定向验证如何支持确切最终 HEAD/tree 和范围。这是 Controller 对修复的验收，不是对未审查代码新增 Reviewer 通过结论。

将未完成修复、相关检查失败、修复回归和定向验证发现的遗漏交回 Worker。继续修正和验证直到验收。不需要修复时，使用未变报告继续。仅通过正常钩子 amend 当前未发布、未验收候选。票据修复若从基线引入改动，则创建其唯一候选；若修复清空候选，则保留它作为该票据的空提交。

验收需要完整原始覆盖、每项发现有依据的处置、没有未解决阻碍或必需检查失败、存在修复时其增量可归属且获授权，以及 Controller 对确切最终状态的验证。仅元数据变化的等价状态需要明确绑定并刷新依赖检查。diff 形状、Worker、提交、来源事实、路线、恢复或收尾返回发生变化，都不授予新正式轮次或更大范围。

遇到重要决定/权限缺口、前提不可用、不安全或含糊状态、原覆盖不足以至需要新正式审查，或适用规则下的无进展时，停止。通过恢复保留原工作和下一所有者。后续范围内内容变更使用相同定向收束；已验收提交保持固定。

## 固定已验收票据边界

收束后，Controller 授权对确切候选进行一次有边界的正常钩子标记操作，保留规范可发现票据引用，并添加一个完成尾注：

```text
SmartKit-Ticket: <canonical-id>
```

amend 既有候选消息。对于没有候选的无改动票据，创建一个以 `ticket_base` 为唯一父提交的空提交。如果修复清空了既有候选，amend 为同一票据的空提交，不要再追加第二个票据提交。

检查所得提交、树和 diff。将仅元数据等价绑定到原报告，并刷新提交身份和钩子敏感检查。无改动票据必须等于基线树，且保留肯定满足证据。钩子产生的新内容使票据未完成：将候选交回 Worker 移除过早标记，在原审查下收束该增量，再重新授权标记。尾注或钩子成功都不能证明验收。

写入暂停时，证明从 `ticket_base` 起的 first-parent 范围恰好一个提交、其唯一父提交，以及恰好一个规范 ID 尾注。还需证明完整票据范围、先前已验收提交未变、最终树/diff 绑定到原审查和修复收束、必需检查通过、本地状态干净及 Worker 静止。重新核对工作树/目标绑定、冻结来源、阻塞项、状态和领取权。

将此固定提交返回为 `completed-in-batch`。它满足批次内依赖；跟踪器票据仍开放且领取权保持持有。自动继续下一张依赖就绪票据，或在所有所选票据都验收后进入组合验收。对已验收票据的修正属于组合结果。

## 验收组合批次

所有票据已验收且 Worker 静止后，冻结 HEAD/tree 并运行必需整批检查。对不可变 `batch_base`、完整组合 diff 和全部已接受需求应用上述审查与收束契约。即使只有一张票据或批次净空，也需要两份独立报告。票据证据提供上下文，不能替代组合关卡。

选择修复前收集发现和检查失败。普通检查失败不必阻止对有意义且可审查冻结状态的审查；前提缺失或证据不完整会暂停关卡。需要修复时，在已验收 HEAD 冻结 `repair_base`，保留失败状态、原报告和全部已验收票据提交，按有边界协议派发新批次修复 Worker，提供合并发现、检查和范围权限。

内容变更至多创建一个独立的正常钩子修复候选，以 `repair_base` 为唯一父提交，不带票据尾注。仅 amend 该未发布、未验收候选以继续定向收束。不需要改内容时，保留 HEAD 及解决失败的证据。

只有收束和必需整批检查支持 `batch_base` 范围内确切最终 HEAD/tree 时，才能验收。证明范围、已验收票据历史未变、本地状态干净、Worker 静止、来源新鲜及完整验收证据。修复候选必须是从 `repair_base` 起的唯一提交，以其为唯一父提交，不带票据尾注；没有修复候选时证明 HEAD 未变。对未解决工作继续限定范围修复，停止时保留它。

验收会固定修复提交。后续范围内修正若此前没有修复候选，可以建立这个唯一批次修复候选。改动已验收修复提交或再添加一个，需要其历史所有者及单独权限。

## 将已接受结果交给收尾

重新验证每张冻结票据、来源和依赖边。将工作树当前身份、基线、HEAD/tree 和完整本地状态与最终验收比较。重新核对权威目标，说明重要未跟踪/忽略残留。重要内容、来源或目标漂移需要先由所有者协调并完成受影响定向收束，之后才能继续。

读取公开 `finish-worktree` 的选定路线，以及必需历史、效果恢复和结果契约。提供一份包含以下内容的交接：

- 已接受范围和完整票据/规格来源；确切源/目标身份、不可变基线、已接受 HEAD/tree/diff，以及票据/批次修复提交边界。
- 原审查输入及完整报告、每项发现处置、获授权修复增量、检查来源，以及绑定到已接受状态的 Controller 收束。
- 选定结果和历史策略、确切效果及清理权限、发布/本地残留、保护及生命周期所有者。

默认保留票据历史。单独获授权的合并整理仍保留原源边界，用于恢复和跟踪器关闭。使用收尾者的实现所有者验收证据路线：原报告加 Controller 收束，不再进行正式审查。其操作敏感检查仍然适用。返回的内容或源/目标变化需要所有者协调和相同定向收束，并保留已验收历史及原效果来源。其他历史操作需要其所有者契约和权限。

对于 **已经交付** ，包括净空批次，通过与覆盖状态的已证明等价，将既有逐需求验收证据绑定到确切权威目标，并刷新目标依赖检查。收尾者独立证明该目标上的全部已接受效果。源为空本身不够。等价或满足情况未被证明时，暂停以等待外部解决的证据，或遵循已选定且受支持的结果；这不授权新正式轮次、制造改动、制造交付或空 PR。

针对已接受结果调用收尾者一次。保留可归属调用、原始响应及效果，在替代效果之前恢复任何先前或中断的尝试。

### 消费结果 <a id="consume-the-result"></a>

原样消费公开结果：原始状态、因果边界、各阶段结果、效果和最强已证明分类。只有可归属的 `authoritative delivery`，包括收尾者自己的 Already Delivered 证明，才允许关闭跟踪器。该证明不因 stopped/failed 状态或清理未完成而失效。

权威交付后，按依赖顺序重新观察票据，执行每项文档化完成操作及单独要求的领取释放，并按跟踪器效果契约证明每项操作后状态。消费已证明完成的前缀，只继续未解决后缀。第一个失败或含糊效果会停止关闭，后续票据保持未动。保留交付及已接受源/恢复边界。将关闭证明交给收尾者指定的生命周期所有者，用于获授权的保留、释放或清理，不重复交付。

其他所有分类在继续其指定后续行动时，均保持票据开放和领取权持有，除非单独的跟踪器权限解决其处置。保留可归属 PR、保留工作树、传输、获授权丢弃及部分结果证据。取消时若需处置领取权，由跟踪器所有者在单独确切权限下负责。分类不可用或含糊时交回收尾所有者；它既不证明交付，也不证明重试权限。

在保留交接中记录结果消费，只恢复指定的未完成行动。保留已证明效果、源历史和恢复项，直到其所有者确定处置。报告已验收票据、排除项、原始收尾结果、跟踪器及生命周期状态、保留位置，以及任何未完成事项的下一所有者/行动。
