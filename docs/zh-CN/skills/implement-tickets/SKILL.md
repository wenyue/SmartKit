# 实施工单

在一个已准备好的工作树中，按依赖顺序完成一个冻结批次。逐票独立验收一个提交，再验收组合结果，最后按所选结果完成收尾。只有已证明的权威交付才允许将跟踪器中的工单标记完成。经证明为空的新选择返回 `nothing-to-do`，不产生变更。

当前 Agent 是**Controller**，负责选择、推进和验收。范围受限的**Worker**负责实施工单和修复。在以下边界内选择适合当前工作的方法：

- 保留冻结的成员、要求、顺序和已验收提交边界。一张工单受阻时，暂停整个批次；解决阻塞后再推进。
- 每张工单和整个批次各进行一轮独立的 Standards/Spec 审查，随后在范围内更正并由 Controller 验证，直到验收通过。Worker 返回是验证时点；结果无问题时无需制造编辑。
- 保留规范检出和无关工作。当前工作树已就绪时，允许通过正常 hooks 创建仅限任务范围的本地候选提交和受限 amend。这项权限不授予跟踪器、远程、安装、收尾或清理操作。

使用公共 `create-worktree`、`code-review` 和 `finish-worktree` 的契约前，先加载它们。它们分别负责工作区与环境就绪、通用独立审查和最终收尾。通过目标项目的 `docs/agents/issue-tracker.md` 及其负责人指针解析跟踪器和分诊契约；通过适用项目规则及已有文档中的验证接口解析必需检查。普通权限、优先级和无进展判断遵循已安装的 SmartKit 核心治理。配置缺失，或必需能力不可用、失败、含糊时，在其负责人处停止并保留可归属状态；依赖存在但失败，不能当作依赖不存在。

遇到可能的先前尝试、控制中断、证据缺失或实质阻塞时，先读取[暂停与恢复](references/resume.md)，再继续。该分支保留原有工作及操作效果；正常路径如下。

## 1. 确立批次

选择工作前，观察仓库和已注册工作树状态、分支历史、跟踪器状态、保留交接，以及活动 Worker 和最终收尾执行者身份。先恢复任何既有或可能存在的尝试。原始收尾和闭合优先于当前工单资格。

确认属于新尝试后，确立调用方的有界范围、权威目标、已提交且不可变的 `batch_base`、所选收尾结果、历史策略和确切操作权限。观察完整候选集合和依赖闭合所需的每条边。保留身份、完整要求及来源版本、状态、负责人和认领、排序证据，以及明确的资格证明或排除理由。成员、资格、身份或依赖边不确定时，不能完成选择。

只在有明确资格证明时，递归纳入同范围内尚未完成的阻塞工单。将已完成、被拒绝、由人工负责、缺少信息而受阻、被外部认领及其他权威否定结果记录为排除项。外部阻塞项需要权威完成证明，否则排除依赖它的工单。传播未满足的依赖，拒绝依赖环，按依赖为闭合后的选择排序；仅在工单同样就绪时，使用跟踪器的稳定公共顺序打破平局。

解析每张工单由负责人支持的认领路径，以及会话和时机约束：在其他批次写入前初始认领、明确兼容后续实施边界的即时认领，或无需认领时不认领。认领操作存在，并不意味着可以在依赖尚未就绪时认领工单。时机不兼容或不确定时，在写入前停止。

冻结成员、依赖图与顺序、要求和来源版本、外部完成证明、排除项及认领路径。报告选择与排除项。经证明合格选择为空时，携带证据返回 `nothing-to-do`，不产生变更，也不建立批次。

### 保持跟踪器事实与操作效果可归属

在每次认领、工单验收和最终收尾边界，重新观察相关工单和阻塞项，并与冻结选择比较。单票验收检查完整已接受来源，最终收尾前检查所有选定来源和完整依赖图。使用权威版本、摘要或变更信号；信号不可用或已变化时，重读内容。已验收的 `completed-in-batch` 提交及其证明，可满足后续工单对该选定工单的依赖。

仅豁免此批次已使用操作所证明的确切认领与负责人变化。其他要求、状态、负责人、认领或依赖边的实质变化，使批次暂停，由对应负责人协调。保留冻结要求和成员；刷新受影响检查，判断原始审查覆盖加上针对性闭合能否支持协调后的结果。覆盖不足或实质决策、权限缺口仍构成阻塞。

每次认领、完成或释放，都需要负责人文档定义的操作、成功含义和确切操作权限。观察操作前状态，请求一次效果，保留原始结果，并在依赖它的工作开始前证明权威结果状态。已经存在的状态，只有其含义和出处足以适用于此批次时才能使用，否则按漂移处理。仅有成功响应并不足够，返回的失败仍保留为失败尝试。响应含糊或缺失时，恢复原始操作，不为获取记录而重复执行。保留已取得的认领直到权威交付；仅当跟踪器将单独释放定义为闭合的一部分时，才另行释放。

## 2. 准备一个环境

选定工作依赖源检出中未提交的变更时，保留它们并暂停，由其负责人提供单独授权的已提交基线。协调已接受基线后再继续；此工作流不吸收、重建、提交或丢弃这些源工作。

初始或即时认领前，如果释放、重新分配或到期语义意味着后续派发失败可能使认领滞留，则以只读方式确认派发可行。确立运行时可用、观察与控制受支持、范围内权限明确，以及不存在可能仍活动的竞争尝试。有工作树时确认其独占归属；创建前则保留派发前必须就绪的关卡。复用当前共用事实，评估单票特有约束。此检查不派发 Worker、不预留容量，也不创建状态。实质派发风险未解决时，停止认领并指出事实和下一位负责人。

按稳定依赖顺序执行必需初始认领，每次证明操作后状态再处理下一项，并在创建或任何其他批次写入前完成全部初始认领。即时认领延后到对应工单的实施边界。

向公共 `create-worktree` 明确请求在 `batch_base` 上进行**clean**创建，提供已接受范围、归属、位置和环境设置操作权限。该负责人保留源状态并准备环境，包括其 `worktree-environment-setup` 依赖。使用可归属的 `ready` 结果，将该确切工作树绑定到此批次。

首次 Worker 或延后认领前，将当前物理路径、Git 共同身份、注册、分支、基线、HEAD/tree、索引和预期本地状态与就绪结果比较。使用时重新核对当前绑定，并调查实质漂移。所有 Worker 和 Reviewer 复用已准备环境；项目检查的输入变化时，仍需重跑相应检查。控制中断或就绪失效后的恢复遵循 `resume.md`。

## 3. 完成每张工单

按冻结顺序处理下一张依赖已就绪的工单。重新验证其完整已接受来源、阻塞项、状态和认领。使用已证明的初始认领、执行受支持的即时认领，或确立当前无需认领的资格。将 `ticket_base` 及其树冻结在前一个已验收 HEAD；首张工单使用 `batch_base`。

### 给 Worker 一个有界单元

每张工单使用新的 Worker，由同一 Worker 连续负责该票的实施和修复。后续批次修复按同一协议使用新的 Worker。派发前，要求运行时提供受支持的派发、身份、观察、中断和停止活动确认接口。

证明确切工作树、单元基线、HEAD/tree、完整本地状态归属和范围内权限，并确认先前写入者已停止活动。最多一个 Worker 可以写入；写入者暂停时，独立只读角色可以并行运行。向 Worker 提供：

- 规范工单身份或批次修复范围、完整要求和来源版本、项目规则、已验收依赖结果及相关研究指针；
- 确切工作树、批次与单元基线、此前已验收提交、必需针对性检查，以及范围受限的写入和正常 hook 提交权限；以及
- 对于修复，提供原始审查证据、汇总发现、检查失败和针对性验证证据。

Worker 只负责当前候选。已验收提交、跟踪器操作、最终收尾，以及授权自身完成标记，均不在其权限内。要求返回可归属结果，包含 Agent 身份和原始状态、候选与最终 HEAD/tree、完整自有本地状态、检查及输入、阶段已返回还是中断、未解决工作和下一步操作。修复结果还应指出发现处置和确切差异。即使文件看起来完整，也应保留失败尝试的事实。审查前证明写入已暂停，验收前证明 Worker 已停止活动；经过的时间或缺失响应都不能证明这两点。

### 确立完整候选

要求 Worker 产出预期工单结果，以及验收和后续安全工作所需的检查。明确说明确实不关键、延后到整批关卡的覆盖。审查冻结前持续进行实施、测试和调试。

变更非空时，通过正常 hooks 创建一个候选，以 `ticket_base` 为唯一父提交，消息中使用配置跟踪器可发现的工单引用，且不含 `SmartKit-Ticket` trailer。如果既有行为已满足工单，保留基线状态，用于明确证明要求已满足的审查。遗漏预期变更不能构成无改动结果。

暂停写入。独立验证候选包含完整预期结果、工单检查已通过、索引与工作树按项目判据为干净状态，且重要未跟踪或忽略状态归属明确。冻结审查前，将遗漏和失败检查交回同一 Worker。

### 获得一轮独立审查

单票与整批关卡共用此审查和闭合契约。冻结比较基线（单票使用 `ticket_base`，整批使用 `batch_base`）、HEAD/tree、完整预期 diff，以及带来源身份和版本的已接受要求。确认写入者已暂停，且没有遗漏任何预期任务变更。

diff 非空时，使用这些确切输入和**全部**已接受来源调用公共 `code-review`，即使从提交中只发现一个来源。Standards 和 Spec 须独立于 Worker，且彼此独立。两个维度都不可缺少。提供适用标准、公共建议性代码异味基线的处理方式、检查证据，以及以下深入审查说明：

- 将每项已接受要求追踪到实现和验证。识别缺失、部分完成、错误或缺乏依据的满足情况，以及意外扩大范围的行为。
- 检查变更行之外的相关调用方、被调用方和受影响契约；主动检查边界、错误和恢复路径、兼容性及回归。整批审查覆盖全部要求、共享约束、冲突要求和交互。
- 报告全部有用且有证据支持的发现，给出具体来源位置、要求或标准、行为及证据。区分严重程度、建议性异味、覆盖缺口和不确定性。保留分开的维度与发现；公共摘要容纳不下时，保留完整支持报告。

公共 `code-review` 拒绝空 diff。单票或整批 diff 为空时，在同一且唯一的轮次中，使用两个独立只读的 Standards 和 Spec 角色，提供冻结实现与基线、完整来源、标准、检查及上文说明。要求每项需求都有明确的满足证据，Standards 覆盖相关实现。单票必须在 `ticket_base` 已满足要求；净差异为空的批次必须满足所有选定要求，即使工单变更相互抵消。保留工单提交。仅凭空差异或 Worker 声明不能证明任何满足情况。缺少角色或输入时，停止这条路径。

修复前收集两个完整报告。每份报告标明角色、不可变输入、覆盖、发现和不确定性。保留原始报告或恢复位置，以及每个维度可归属的 `never-started`、`in-flight`、`complete` 或未解决状态。修复前恢复不完整或缺失报告；覆盖缺失不能成为无问题结论。

### 闭合发现，直到 Controller 可以验收 <a id="close-findings-until-the-controller-can-accept"></a>

根据已接受要求和标准判断每项发现，逐项给出有理由的处置，包括建议性和不采纳的发现。向 Worker 提供汇总修复集和检查失败。原始报告和受审身份保持不变。

每次返回后，暂停写入，在结果状态上重跑必需检查，并记录相对受审状态的确切差异。验证每项已接受发现的解决情况，以及修复对直接受影响行为和契约的影响，包括回归、hooks 和依赖提交的检查。说明原始覆盖与此次针对性闭合如何支持确切最终 HEAD/tree 和范围。这是 Controller 对修复的验收，不是给未受审代码新增审查者通过结论。

将未完成修复、相关检查失败、修复引入的回归，以及针对性验证发现的遗漏交回 Worker。持续更正和验证直到验收通过；一次返回不会耗尽修复权限。无需修复时，使用未变的报告继续。只通过正常 hooks amend 当前未发布、未验收候选。单票修复使基线产生变更时，创建其唯一候选；修复使该候选变为空差异时，保留它作为同一票的空提交。

验收要求原始覆盖完整、每项发现都有合理处置、没有未解决阻塞或必需检查失败、存在修复时其差异可归属且已获授权，以及 Controller 在确切最终状态上完成验证。仅元数据变化的等价结果，需要明确绑定并刷新相关检查。diff 形态、Worker、提交、来源事实、路径、恢复或最终收尾返回发生变化，都不启动另一轮正式审查，也不扩大范围。

遇到实质决策或权限缺口、必需前置条件不可用、状态不安全或含糊、原始覆盖不足且需要新一轮正式审查，或按适用规则判断已无进展时停止。通过恢复流程保留原始工作并指出下一位负责人。后续范围内的内容变更需要相同的针对性闭合；已验收提交保持固定。

### 标记并验收工单提交

问题闭合后，Controller 授权在确切候选上执行一次受限的正常 hook 操作，携带规范且可发现的工单引用，以及一个完成 trailer：

```text
SmartKit-Ticket: <canonical-id>
```

amend 已有候选的消息。无改动工单尚无候选时，创建一个以 `ticket_base` 为唯一父提交的空提交。修复使候选变为空差异时，通过 amend 将它变为同一个空提交，不追加另一个工单提交。

检查结果提交、树和 diff。将仅元数据变化的等价结果绑定到原始报告，并刷新依赖提交身份和 hooks 的检查。无改动工单必须与基线树相同，且保留明确的满足要求证据。hook 产生内容变更时，工单仍未完成：将候选交回 Worker，移除过早标记，在原始审查下闭合差异，再重新授权标记。仅有 trailer 或 hook 成功不能证明验收通过。

写入暂停后，Controller 证明从 `ticket_base` 起的第一父级范围恰好包含一个提交，以该基线为唯一父提交，且恰有一个包含规范 ID 的 trailer。证明完整工单范围、此前已验收提交未变、最终 tree/diff 已绑定到原始审查及任何修复闭合证据、必需检查通过、本地状态干净且 Worker 已停止活动。重新核对工作树与目标绑定，以及冻结来源、阻塞项、状态和认领。

将这个固定提交作为 `completed-in-batch` 返回。它满足批内依赖，同时跟踪器工单保持打开，认领继续保留。自动继续下一张就绪工单；全部选定工单已验收后，进入组合结果关卡。后续对已验收工单的更正归于组合结果。

## 4. 验收组合结果

全部工单已验收且 Worker 已停止活动后，冻结 HEAD/tree，运行必需整批检查。按上文审查契约，基于不可变 `batch_base`、整个组合 diff 和全部已接受要求，获得两个完整独立报告。单票证据提供上下文，不能替代整批审查。单票批次和净差异为空的批次同样适用此关卡。

选择修复前，收集检查失败和发现。普通检查失败不必妨碍审查仍有意义的冻结状态；前置条件缺失或证据不完整时，暂停关卡。需要修复时，将 `repair_base` 冻结在已验收 HEAD，保留失败状态、原始报告及每个已验收工单提交。按有界单元协议派发新的批次修复 Worker，提供汇总发现、检查和范围内权限。

内容变化时，最多通过正常 hooks 创建一个独立修复候选，以 `repair_base` 为唯一父提交，且没有工单 trailer。在持续进行针对性闭合时，只 amend 这个未发布、未验收候选。内容无需变化时，保留 HEAD 和失败已解决的证据。

只有闭合与必需整批检查支持 `batch_base` 范围内的确切最终 HEAD/tree，才能验收。证明范围、已验收工单历史未变、本地状态干净、Worker 已停止活动、来源仍有效，以及验收证据完整。修复候选必须是从 `repair_base` 起的唯一提交，以该基线为唯一父提交，且没有工单 trailer；否则证明 HEAD 未变。存在未解决工作时继续范围内修复，停止时保留工作。验收后修复提交固定。后续范围内更正若尚无批次修复候选，可以建立唯一候选；修改已验收修复提交或添加另一个提交，需要其历史负责人和单独授权。

## 5. 按交付结果完成收尾与闭合

重新验证每张冻结工单、来源和依赖边。对照最终验收结果，检查所绑定工作树的当前身份、基线、HEAD/tree 和完整本地状态；重新核对权威目标，并说明重要未跟踪或忽略残留。内容、来源或目标发生实质漂移时，须先由负责人协调并完成受影响部分的针对性闭合，再继续推进。

读取公共 `finish-worktree` 的所选路径，以及必需历史、操作效果恢复和结果契约。提供一份已验收交接，包含：

- 范围和完整工单、规格来源；确切来源与目标身份、不可变基线和已接受 HEAD/tree/diff；工单及任何批次修复提交边界；
- 原始审查输入和完整报告、每项处置、已授权修复差异、检查出处，以及绑定到已接受状态的 Controller 闭合证据；以及
- 所选结果和历史策略、确切操作与清理权限、发布和本地残留、保留及生命周期负责人。

默认保留每票历史。另行授权的历史合并也应保留原始源边界，以供恢复和跟踪器闭合。使用最终收尾的实施负责人验收证据路径：它使用原始报告和 Controller 闭合证据，不再进行正式审查，并保留对自身操作敏感的检查。返回的内容或来源、目标变化需要负责人协调及相同的针对性闭合，同时保留已验收历史和原始操作效果出处。不同的历史操作需要其负责人的契约和权限。

对于**Already Delivered**，包括净差异为空的批次，通过证明目标与已覆盖状态等价，将既有的基于要求的验收证据绑定到确切权威目标，并刷新依赖目标的检查。最终收尾负责人独立证明该目标包含每项已接受效果。仅凭源差异为空并不足够。等价性或要求满足情况未获证明时，暂停以待外部解决证据，或交由已选定的受支持结果路径处理；这既不允许另一轮正式审查，也不允许制造变更、交付或空 PR。

针对这个已验收结果调用最终收尾一次，保留可归属的调用、原始响应和操作效果。任何替代操作前，先恢复先前或中断的尝试。

### 使用结果 <a id="consume-the-result"></a>

原样使用公共结果：原始状态、因果边界、阶段结果、操作效果和最强已证明分类。只有可归属的 `authoritative delivery`，包括最终收尾自身的 Already Delivered 证明，才允许跟踪器闭合。即使同时出现 stopped 或 failed 状态，或清理尚未完成，交付仍保持已证明状态。

对于权威交付，按依赖顺序重新观察工单，执行每项已有文档定义的完成操作及任何单独要求的认领释放，并通过上文跟踪器操作效果契约证明每项结果状态。使用已经证明完成的前缀，只继续未解决后缀。第一项失败或含糊操作即停止闭合，后续工单保持未动。保留交付事实及已接受来源、恢复边界。将完整闭合证明交给最终收尾指定的生命周期负责人，用于已授权的保留、释放或清理，不重复交付。

其他分类均在沿指定接续操作推进时保持工单打开、认领保留，除非单独的跟踪器权限解决了处置。保留可归属的 PR、保留工作树、转移、已授权丢弃和部分结果证据。取消时如需处置认领，仍由跟踪器负责人在单独的确切权限下处理。分类不可用或含糊时，交回最终收尾负责人；它既不证明交付，也不授予重试权限。

在保留交接中记录结果已被使用，只恢复指定的未完成操作。保留已证明效果、源历史和恢复项，直到其负责人确立处置。报告已验收工单、排除项、原始收尾结果、跟踪器与生命周期状态、保留位置，以及任何未完成事项的下一位负责人和操作。
