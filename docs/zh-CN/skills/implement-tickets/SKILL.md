# 实施工单

按依赖顺序完成一个冻结的选择集合，逐票独立验收一个提交，再验收组合结果并收尾。经证明为空的新选择返回 `nothing-to-do`，不产生操作效果。

当前 Agent 是**Controller**，负责推进批次和验收；Worker 实施有界单元。选择适合当前工作的调查、实施和验证方法。以下边界约束结果：

- **冻结范围。**保留选定成员、要求、依赖顺序和已验收提交边界。阻塞使批次暂停；跳过工单或改变队列不能解决阻塞。
- **独立验收。**每张工单和整个批次都执行[审查与修复](references/review.md)定义的深入审查和有界问题闭合。
- **范围内权限。**保留规范检出和无关工作。确立当前工作树就绪后，本地候选提交和受限 amend 使用正常 hooks，以及工作流仅限任务范围的提交权限。它们不授予跟踪器、远程、安装、收尾或清理操作权限。

使用公共 `create-worktree`、`code-review` 和 `finish-worktree` 的契约前，先读取它们。它们分别负责工作区与环境就绪、通用独立审查和最终收尾。通过[跟踪器边界](references/tracker.md)解析跟踪器策略，通过适用项目规则及已有文档中的验证接口解析必需检查。必需能力缺失、不可用、失败或含糊时，在其负责人处停止并保留可归属状态。依赖存在但失败，绝不能按缺失处理。

## 1. 确立批次

重新选择前，观察仓库和已注册工作树状态、分支历史、保留交接，以及活动 Worker 或最终收尾执行者身份。观察跟踪器前读取 `tracker.md`。任何既有或可能存在的尝试都进入[暂停与恢复](references/resume.md)；先前收尾或闭合优先于当前资格。

只有证据支持新批次时，才能选择。确立有界输入范围、目标、已提交且不可变的 `batch_base`、所选收尾结果、历史策略和确切操作权限。使用 `tracker.md` 确认依赖完整，冻结成员、顺序、带来源版本的完整已接受要求、排除项及认领路径。报告选择与排除项，使用户明确其输入中的哪些部分会被处理。经证明为空的选择在此结束。

## 2. 建立一个环境

选定工单依赖源检出中未提交的工作时，暂停，由该工作负责人提供单独授权的已提交基线。保留这部分工作；自动提交、丢弃、重新实施或将其纳入工单变更，均超出此工作流范围。协调好已接受基线后再继续。

在其他批次写入前完成全部必需初始认领。通过 `create-worktree`，明确请求在冻结 `batch_base` 上进行**clean**创建，提供范围、归属、位置和环境设置操作权限。该负责人保留源状态并准备环境，包括其 `worktree-environment-setup` 依赖。

使用可归属的 `ready` 结果，将其确切工作树绑定到此批次。首次 Worker 或延后认领操作前，对照该结果检查当前物理路径、Git 共同身份、注册、分支、基线、HEAD/tree、索引和预期本地状态。Worker 和 Reviewer 复用该环境；漂移或控制中断后的刷新由 `resume.md` 规定。项目必需检查的输入变化后，仍应重新运行相应检查。

## 3. 逐票验收

对每张依赖已就绪的工单，按[处理一张工单](references/process-one-ticket.md)执行，提供冻结要求和前一个已验收 HEAD。只有 Controller 返回 `completed-in-batch` 才能继续：结果必须恰好包含一个独立验收通过的第一父级工单提交。此前已验收提交保持固定；工单保持打开，认领继续保留。

## 4. 验收组合结果

全部选定工单已验收且 Worker 已停止活动后，进入[审查与修复](references/review.md#accept-the-whole-batch)中的整批流程。只有该契约验收通过确切最终 HEAD/tree，且所有工单边界得到保留，才能继续。只有一张工单的批次和净差异为空的结果也适用这一关卡。

## 5. 为已验收批次收尾

通过 `tracker.md` 重新验证所有冻结工单、来源和依赖边。对照最终验收结果，检查所绑定工作树的当前身份、基线、HEAD/tree 和完整本地状态，并重新核对权威目标。说明重要未跟踪和忽略残留。内容、来源或目标发生实质漂移时，暂停并交由其负责人协调；在 `review.md` 既有剩余次数范围内刷新受影响证据。

读取 `finish-worktree` 的所选路径及必需历史、恢复和公共结果契约。提供一份已验收交接：范围和完整工单、规格来源；确切来源与目标身份、不可变基线和已接受 HEAD/tree/diff；工单及任何批次修复提交边界；以及 `review.md` 定义的验收证据。还应包含所选结果和历史策略、确切操作及清理权限、发布与本地残留，以及保留和生命周期负责人。除非另行明确选择合并历史，否则保留每票历史；即使选择合并，也应保留原始源边界，以便恢复和跟踪器闭合。

使用最终收尾负责人的实施负责人验收证据路径。它使用原始报告和 Controller 修复闭合证据，不再进行正式审查，同时保留对自身操作敏感的检查。返回的内容或来源、目标变化在此重新进入获授权的协调。只有尚未使用的批次修复机会且原始覆盖充分时，才能改变已接受结果；不同的历史操作需要其负责人的契约与权限。

对于**Already Delivered**，包括净差异为空的批次，提供既有的基于要求的验收证据，并通过证明目标与已覆盖状态等价，将其绑定到确切权威目标。刷新依赖目标的检查。最终收尾负责人独立证明该目标包含每项已接受效果；仅凭源差异为空并不足够。等价性或要求满足情况未获证明时，暂停以待外部解决证据，或交由已选定的受支持结果路径处理。这不会增加目标审查次数，也不能成为伪造内容、交付或空 PR 的理由。

针对这个已验收结果调用最终收尾流程一次，保留其原始响应和操作效果。存在先前或中断尝试时，先按 `resume.md` 处理，再考虑任何替代操作。

### 使用结果 <a id="consume-the-result"></a>

原样使用最终收尾的公共结果，保留原始状态、因果边界、阶段结果、操作效果和最强已证明分类。只有可归属的 `authoritative delivery`，包括其自身的 Already Delivered 证明，才能进入[跟踪器闭合](references/tracker.md#close-after-authoritative-delivery)。同时出现 stopped 或 failed 状态、或清理未完成，不会使交付失效。将闭合证明交给指定生命周期负责人，处理剩余保留或清理，不重复交付。

其他分类均沿指定接续操作处理，工单保持打开、认领保留，除非单独的跟踪器权限解决了其处置。保留公共契约提供的 PR、工作树、转移、已授权丢弃或部分结果证据。分类不可用或含糊时，交回最终收尾负责人；它既不证明交付，也不授予重试权限。

在保留交接中记录结果已被使用，只恢复指定的未完成操作。保留已证明效果和已接受来源、恢复边界，直到跟踪器和生命周期负责人解决其处置。报告已验收工单、排除项、原始收尾结果、跟踪器与生命周期状态、保留位置，以及任何未完成事项的下一位负责人和操作。

任何实质阻塞都使用 `resume.md` 保留部分工作并暂停整个批次。能力不可用、次数已用尽或失败未解决时，仍由其确切负责人处理；绝不通过重复可能已完成的外部操作来绕过阻塞。
