# 处理一个工单

进入时已有一个冻结且依赖就绪的工单，并独占控制当前批次工作树。唯一成功结果是 `completed-in-batch`：一个经过独立证明、用于本单元的第一父级工单提交。Worker 尝试实现该单元；本 reference 负责验收。

## 确立并运行单元

通过 [`tracker.md`](tracker.md) 重新观察工单、完整来源、状态、声明和阻塞项。若冻结的声明计划中存在已证明的初始声明，则使用它。否则，在跟踪器授权的即时声明前，只有当后续派发失败可能依照跟踪器所属生命周期遗留该声明时，才要求 [`worker-transaction.md`](worker-transaction.md) 的非变更性资格判断，然后使用有文档说明的声明操作。声明路径缺失、陈旧或不兼容时，在变更前停止。对于无需声明的路径，只能依据其当前跟踪器所有证明继续。

将当前 `HEAD` 和树冻结为 `ticket_base`；恢复时则重建它，并将之后的每个第一父级提交和本地状态项核对为本工单的恢复状态。所有权混杂或模糊时停止。

向 [`worker-transaction.md`](worker-transaction.md) 提供一个工单单元，其中包含规范工单和来源、阻塞项证明、批次工作树和不可变批次基点、`ticket_base`、更早的工单提交、当前所属状态、范围内写入与提交权限，以及仓库验证。其成功谓词要求：

- 完整工单来源得到满足，且每个变更项均属于本工单；
- 足以发现会导致该工单不宜提交或污染后续批次工作的失败的针对性检查通过，并记录任何延后到整个批次屏障的非关键覆盖；
- 最终工作树干净；
- `ticket_base` 之后的第一父级范围以恰好一个工单提交结束，该提交恰好包含规范 trailer，之前的每个检查点都不含工单 trailer。只有当独立比较证明工单所有净变更为零，并且完整的已接受行为在 `ticket_base` 时已经得到满足——包括通过更早选择的边界得到满足——工单提交才可以为空。不得为了制造这种情况而创建检查点。

**完成条件：**当前工单、基点、所属状态、声明处置、Worker 权限和成功谓词均精确无误。

## 证明工单提交

使用 Worker 事务返回或恢复的结果，不改写其状态。独立验证 Worker 已静止、`ticket_base` 之后的所有提交和本地状态均属于本单元、针对性检查覆盖最终 `HEAD` 和树、工作树干净、目标和基点仍有效，而且唯一工单提交和 trailer 精确无误。接受前重新观察工单和阻塞项。若 Worker 的工单来源证据可归因于该不可变状态，则接受它；只调查矛盾、对验收工单提交具有实质影响的缺口，或因最终状态而失效的证据。

零净变更结果还要求树相对 `ticket_base` 未改变、存在充分来源证据证明已接受行为已经满足、与该声明实质相关的检查完成，并且存在经过常规钩子验证的空工单提交和确切 trailer 边界。它不能隐藏实质变更，也不能放宽其他成功谓词。

若存在不匹配、返回失败、活动或有歧义的 Worker、来源发生变化，或要求未得到证明，则携带原始 Worker 结果和当前 Git 证据进入 [`stop.md`](stop.md)。否则将工单提交以 `completed-in-batch` 返回。它可以解锁之后选定的工单，但既不代表跟踪器完成，也不代表批次交付。

**完成条件：**恰好一个经过独立证明的工单提交闭合本工单单元。
