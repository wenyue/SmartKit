# 处理一个工单

进入时，应持有一个已冻结且依赖就绪的工单，并对当前批次工作树拥有互斥控制权。唯一成功结果是`completed-in-batch`。

## 完成该单元

通过[`tracker.md`](tracker.md)重新观察工单、完整来源、状态、认领和阻断项。如果冻结认领计划中存在已证明的初始认领，则消费它。否则，在跟踪器授权的即时认领之前，先取得[`worker-transaction.md`](worker-transaction.md)当前的非变更资格结果，然后使用已有文档说明的认领操作。如果认领路径缺失、陈旧或不兼容，应在变更前停止。无需认领的路径只有在当前由跟踪器所有者提供的证明仍然有效时才能继续。

把当前`HEAD`和树冻结为`ticket_base`；若为恢复，则重建该基准，并将之后每个第一父提交和本地状态项归为本工单的恢复状态。所有权混杂或含糊时停止。

向[`worker-transaction.md`](worker-transaction.md)提供一个工单单元，其中包含规范工单及其来源、阻断项证明、批次工作树与不可变批次基准、`ticket_base`、更早的工单提交、当前自有状态、限定范围的写入和提交授权，以及仓库验证。其成功谓词要求：

- 完整满足工单来源，并且每个变更项都归属于本工单；
- 定向验证及仓库要求的完整验证均通过，并且该单元已对照所有工单来源完成自审；
- 最终工作树干净；并且
- `ticket_base`之后的第一父范围以恰好一个工单提交结束，该提交恰好带有规范 trailer，而之前每个检查点都不带工单 trailer。只有独立比较证明工单自有净变更为零，并且在`ticket_base`处已经完全满足已接受的行为——包括通过更早的选定边界满足——工单提交才可以为空。不得创建检查点来制造这种情况。

**完成条件：**当前工单、基准、自有状态、认领处置、执行者授权和成功谓词均准确无误。

## 证明边界

消费执行者事务返回或恢复的结果，不得改写其状态。独立验证执行者已经静止，`ticket_base`之后的所有提交和本地状态都属于该单元，验证和自审覆盖最终`HEAD`和树，工作树干净，目标/基准仍然有效，并且唯一工单提交及其 trailer 准确无误。接受前重新观察工单和阻断项。

零净变更结果还要求从`ticket_base`起树保持不变、来源和验证证明完整，并且空工单提交通过正常 hook 验证且具有准确 trailer 边界。它不得掩盖实质性变更，也不得放宽任何其他成功谓词。

不匹配、返回失败、执行者仍在运行或状态含糊、来源发生变化，或者要求未得到证明时，应携带原始执行者结果和当前 Git 证据进入[`stop.md`](stop.md)。否则，将工单提交作为`completed-in-batch`返回。它可能解锁之后的选定工单，但既不表示跟踪器完成，也不表示批次交付。

**完成条件：**恰好一个经独立证明的工单提交关闭当前工单单元。
