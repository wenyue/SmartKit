# 跟踪器边界

使用目标项目配置的跟踪器和分诊契约，确定权威身份、Agent 可执行资格、阻塞项、排序、认领、完成和释放。通过 `docs/agents/issue-tracker.md` 及其负责人指针解析这些契约。配置缺失或操作不受支持时，在对应负责人处停止；不得自行发明认领、比较并交换、释放、游标或恢复接口。

## 选择并冻结

观察调用方有界范围内的完整候选集合，以及依赖闭合所需的每一条边。保留每个候选的身份、来源、状态、负责人或认领、排序证据，以及明确的资格证明或排除理由。资格含义缺失、成员不确定、身份冲突或依赖边含糊时，不能完成选择。

只在有明确资格证明时，递归纳入同范围内尚未完成的阻塞工单。将已完成、被拒绝、由人工负责、缺少信息而受阻、被外部认领或其他权威否定结果记录为排除项。只有跟踪器证明外部阻塞项已完成，才算满足该依赖；否则排除依赖它的工单。传播未满足的依赖，使每张选定工单都有闭合的就绪证明。拒绝依赖环。按依赖排序，仅在多张工单同样就绪时，使用负责人提供的稳定公共顺序打破平局。

解析每种涉及策略的认领要求、会话边界和合法时机。每张工单都需要一条负责人支持的路径：在其他批次写入前初始认领、明确兼容先前批次操作后的即时认领，或负责人不要求认领时无需认领。单票认领语法本身不授予认领尚未就绪工单的权限。认领时机不兼容或不确定时，在写入前停止。

冻结选择结果，包括成员、依赖图与顺序、完整的已接受要求和来源版本、外部完成证明、排除项与理由，以及每张工单的认领路径。合格选择为空时，携带观察和排除项返回 `nothing-to-do`，不建立批次，也不产生变更。非空选择应在行动前报告，避免将被排除的输入误认为批次将完成的工作。

## 认领与重新验证

在初始或即时认领前，只有当派发失败可能按跟踪器生命周期规则使认领无法妥善处置时，才使用 [Worker 边界](worker-transaction.md)的只读资格检查。在 `create-worktree` 或其他批次写入前，按稳定依赖顺序完成全部必需的初始认领。每次认领后，先证明其结果状态，再处理下一项。即时认领推迟到相应工单就绪时；已证明的初始认领直接使用，不重复执行，并重新证明当前无需认领时的执行资格。

在每次认领、工单验收和最终收尾边界，重新观察相关工单和阻塞项，通过权威版本、摘要或变更信号验证已接受要求。不存在稳定信号或来源发生变化时，重读内容。工单验收检查其全部已接受来源；最终收尾检查所有选定工单和完整依赖图。带有保留验收证明的 `completed-in-batch` 提交，可满足后续批内工单对该选定工单的依赖。

与冻结选择进行比较。仅豁免本批次已使用跟踪器操作中已经证明的确切认领或负责人变化。任何其他实质性的要求、状态、负责人、认领或依赖边变化，都要暂停整个批次进行协调。保留成员和要求，当前观察不能悄然改写它们。验收协调后的结果前，刷新输入已改变的检查和审查。

## 执行一次已有文档定义的操作

认领、完成或释放都需要负责人文档定义的操作、可观察的成功含义，以及确切操作权限。观察操作前状态，请求一次，保留原始响应，再观察权威结果状态。如果预期状态已经存在，只有其出处和含义足以适用于本批次时才能使用，否则按漂移处理。只有成功响应而没有所需结果状态，不能通过。保留返回的失败。

响应缺失或结果含糊时，保留原始尝试、工单、预期变化、操作前状态、原始证据、当前观察，以及下一位负责人和操作。通过该负责人的观察或恢复路径继续；不得为获取响应而重复可能已完成的操作。遇到第一项未解决操作时，停止依赖它的工作。保持已取得的认领，直到权威交付；仅当跟踪器将单独释放定义为闭合的一部分时，才需要执行该释放。

## 权威交付后闭合

只有持有公共 `finish-worktree` 可归属的 `authoritative delivery` 分类，以及可恢复的已验收工单边界，才能进入。按依赖顺序重新观察每张工单，执行其必需且已有文档定义的完成操作，以及任何单独要求的认领释放，并证明每项结果状态。使用已证明完成的前缀，只继续未解决的后缀。第一项失败或含糊操作即停止闭合；保留交付事实，不处理后面的工单。

PR、保留工作树、返回审查的转移、历史准备和明确丢弃，都不允许将跟踪器工单标记完成。取消时如需处置认领，应留给跟踪器负责人，并具有单独的确切权限。闭合已证明后，将证明交给最终收尾结果指定的生命周期负责人。保留源历史和恢复项，直到其负责人证明已获授权的保留、释放或移除处置。
