# 完成运行

本参考有三个互斥入口：

- **正常：**所有工单提交边界均已证明，批次认领仍被保留，批次工作树干净，不可变目标/基准仍然有效，并且不存在收尾器效果尝试。从下方验证开始。
- **修复恢复：**同一批次绑定已冻结的完整审查发现、`repair_base`、每个工单提交边界、保留的认领、已完整说明的修复自有提交和本地状态，以及持久的执行者交接；不存在收尾器效果尝试。只能进入**修复并重放**。
- **已返回响应：**准确的持久`finish-worktree`响应及其尝试，绑定到彼此一致且处于`result-awaiting-consumption`状态的收尾后标记和批次交接。只能进入**消费返回的结果**；不要重新运行验证、审查、修复或收尾。

每次进行不可变审查时，都应组装一个临时的**原始 Spec 输入**：完整已接受批次范围、每个选定工单及其完整验收来源，以及这些来源引用的每个治理 Spec 的并集/包。保留每个组成部分的身份、来源和完整内容。该包既不把组成部分折叠成新的规范性 Spec，也不持久化审查适配器。

## 验证并审查一个不可变状态

冻结一个候选`HEAD`和树。运行仓库要求的完整验证，然后从不可变批次基准调用一次公开的`code-review`，将完整的临时原始 Spec 输入作为其唯一原始 issue/spec 输入。分别保留 Standards 和 Spec 报告。证明两个维度和每个打包来源都针对同一基准、`HEAD`和树得到覆盖。

Spec 要求不匹配以及有文档依据的标准违规都具有阻断性。基线异味不阻断，除非某项已接受的项目标准或来源独立规定其具有阻断性。缺少维度、来源消费不完整、发现无法分类、验证失败或审查证据失败，都不能通过屏障。

如果存在阻断发现，将完整发现集、已审查状态、`repair_base`、允许路径、工单提交边界、保留的认领和任何修复自有状态冻结成一个**修复单元**，然后进入下方修复路径。

**完成条件：**完整验证和两个审查维度在同一不可变基准/`HEAD`/树上通过且没有阻断发现，并保留每个工单提交边界。

## 修复并重放

首次需要执行者时，读取[`worker-transaction.md`](worker-transaction.md)。向其提供已冻结的修复单元和持久的执行者交接，并且只消费其完整、不完整或含糊结果以及替代资格。获准的替代仍留在该事务内，并使用一次全新尝试；否则，不完整或含糊的交接应读取[`stop.md`](stop.md)并返回，不要适配执行者状态。

作为修复单元所有者，独立证明交接完整：执行者静止；从`repair_base`开始的完整第一父范围；所有权和允许路径；每项已冻结发现均已解决；不存在工单 trailer；工单提交边界未变化；要求的验证和自审；干净的最终`HEAD`和树；认领仍被保留；以及目标/基准未变化。缺少任何证明都进入`stop.md`。

通过该证明后，冻结修复后的`HEAD`和树，返回**验证并审查一个不可变状态**。针对同一不可变基准和一个重新组装的完整临时原始 Spec 输入，重新运行要求的完整验证和两个公开审查维度。修复后不保留任何旧证明；批次以外的发现或已耗尽授权修复容量均进入`stop.md`。

**完成条件：**修复后的状态已经独立证明，并在其上通过完整验证和双维度审查屏障。

## 恰好调用一次收尾器

根据已证明的当前证据构造`finish-worktree`输入：准确工作树与目标、不可变基准、已审查的`HEAD`和树、完整批次自有范围、保留的边界历史、验证和两份审查报告、选定结果与历史政策、生命周期所有者、保留边界，以及每项必要的效果/发布/清理授权。不要提供跟踪器操作或替代交付规则。

调用前，通过持久化契约转换一条收尾器尝试记录。绑定其唯一身份、预期前状态、授权、准确冻结的依赖契约与输入，以及已审查的基准/`HEAD`/树。恰好调用一次`finish-worktree`。如果依赖响应缺失、中断或无法建立因果归属，则该收尾器效果尝试保持进行中；读取[`recover-finalizer.md`](recover-finalizer.md)，不要调用另一项收尾器效果尝试。

对于可建立因果归属的原始响应，根据该尝试，通过持久化契约转换完整响应、`result-awaiting-consumption`标记和当前批次交接。如果持久化能力、权限或证明路径不可用，或者该转换的调用或后状态含糊，则进入[`stop.md`](stop.md)的**持久化不可用或尚未解决**入口，并保持相同的持久化边界。不要把该条件路由到收尾器恢复，也不要发起另一次响应转换。只有在冻结的持久化恢复所有者协调了同一次转换，并重新证明其准确的待消费后状态后，才能进入下方结果路径。

## 消费返回的结果

完全按返回内容消费响应的`status`、`classification`、`causal_boundary`、`history_result`、`outcome_result`、`cleanup_result`、效果、残留项和交接。这是唯一的公开结果路径。它绝不根据目标状态推导分类，也不提升、降级或替换依赖项的状态。选定分支执行效果、返回或交接前，通过持久化契约一并转换其标记和当前批次交接，并证明下述彼此一致的准确后状态。转换不可用或含糊时，`result-awaiting-consumption`保持进行中并阻断该分支：

- `authoritative delivery`，其中只有`finish-worktree`提供的**Already Delivered**才包含在内；转换为带准确原始结果和交付阶段的`delivery-consumed(first-tracker-cursor)`，然后进入[`tracker.md`](tracker.md)的交付闭环部分。权威分类之外，仍保留原始`stopped`或`failed`状态。
- `non-integrating handoff`转换为带准确依赖交接、所有者/操作和生命周期/留存处置的`non-delivery-consumed`，然后将其返回。工单和认领保持开放；保留该交接要求的工作树、来源边界历史、发布和恢复证据。
- `history finalized`或`no positive result`以`non-delivery-consumed`作为其拥有的批次交接转换所需标记状态，进入[`stop.md`](stop.md)，然后返回原始的已停止/已失败/其他未完成交接。不授权跟踪器闭环。
- 不可用或含糊的依赖分类转换为`non-delivery-consumed`，其中带有准确的原始响应和收尾器所有者尚未解决的交接；然后返回该所有者和操作，不做推断或重试。

权威交付和跟踪器闭环完成后，把其证明交给同一次尝试的现有`finish-worktree`/生命周期清理所有者。保留已审查的来源历史，直到跟踪器闭环，并且该所有者证明每个工作树、ref、边界和恢复项的处置。这个清理延续不会重新运行历史或结果效果。

**完成条件：**本次唯一尝试具有权威原始结果，并且其标记与批次交接证明其唯一结果路径在返回前已被消费；或者保留了其进行中的恢复所有者及下一操作。
