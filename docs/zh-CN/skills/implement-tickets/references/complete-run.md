# 完成已验收批次的收尾

进入时，每张选定工单均已验收，确切最终批次状态已通过验证与独立审查，没有未解决的 Worker，也没有未解决的先前最终收尾尝试。保留的最终收尾响应直接进入**使用结果**；响应缺失或可能仍在运行时，先使用[暂停与恢复](resume.md)。

## 向最终收尾流程提供一个已验收结果

读取公共 `finish-worktree`、所选结果的引用，以及它要求的历史、恢复和结果契约。保留调用方选择的结果和确切权限。其受支持结果为 `keep-for-later`、`create-pull-request`、`merge-locally`、`return-for-review` 和明确丢弃；任何一项都不隐含选择另一项。默认保留每票历史。单独明确选择合并历史时，使用最终收尾的历史契约，并保留源边界用于恢复和跟踪器闭合。

交接前立即重新核对物理工作树、Git 共同身份、注册、分支、不可变批次基线、HEAD/tree、索引与本地状态，以及权威目标。要求最终状态已经验收，且全部变更归属已明确，包括重要的未跟踪或已忽略残留项。使用[跟踪器边界](tracker.md)重新验证所有冻结工单、来源和依赖。内容、来源或目标发生实质漂移时暂停，由其负责人协调；保留证据，只刷新实际输入已变化的证明。

向最终收尾流程提供完整已接受范围及工单和规格来源；确切源和目标身份；不可变批次基线及已验收 HEAD/tree/diff；完整工单与修复提交边界；完整的必需验证和独立审查报告、出处及任何等价状态绑定；所选结果与历史策略；已观察到的发布情况与本地残留项；保留边界和生命周期负责人；以及确切的结果、历史和清理权限。

最终收尾流程验证并使用这些证据，不启动另一轮正式审查。它对自身操作敏感的检查仍然必需。内容变化、失效的来源事实或目标移动，应在受影响操作继续前交回本实施工作流，完成受支持的同步、验证和审查。已验收源提交保持固定；必要的新修复按[批次修复](review.md#repair-the-whole-batch)进行。同步需要不同历史操作时，必须由相应契约及权限支持，不能临时自行改写历史。

对于净差异为空的批次，提供完整的基于要求的验收报告。只有独立证明确切权威目标满足每项已接受效果后，`finish-worktree` 才能分类为**已交付**。必要时，提供绑定到目标的验证和独立验收；仅源状态为空不足以证明交付。如果无法证明目标已满足要求，则交回以补齐该证据，或执行已经选定且受支持的结果。不得伪造交付、制造内容变更或空 PR 来绕过此边界。

针对这个已验收结果调用最终收尾流程一次，保留可归属的原始响应和已观察到的操作效果。它自己的外部操作回执与本 Skill 不建立批次 journal 的模型兼容。中断尝试由原负责人恢复，不启动替代调用。

## 使用结果

保留原始 `status`、`classification`、`causal_boundary`、阶段结果、操作效果、证据、残留项，以及下一位负责人和操作。按最强的独立已证明分类路由：

- `authoritative delivery`，包括仅由最终收尾流程自身判断的**已交付**结果：继续[跟踪器闭合](tracker.md#close-after-authoritative-delivery)。同时出现的 stopped 或 failed 状态不会抹去交付事实。将闭合证明交给指定生命周期负责人，处理剩余清理或保留，不重复交付。
- `non-integrating handoff`：返回 PR、保留工作树或转移证据，以及被点名的继续操作。工单保持打开，认领继续保留，并保留必需的源状态与恢复状态。
- `explicit discard`：保留其确切、已授权的损失证据和残留处置；它不代表跟踪器完成。任何待处理的跟踪器处置仍属于该负责人。
- `history finalized` 或 `no positive result`：保留确切结果及未完成事项的负责人和操作；两者都不允许完成跟踪器工单，也不能据此推断可以启动替代的最终收尾。
- 分类不可用或含糊：保留一个未解决交接，包含完整原始结果，并将分类交回最终收尾负责人。不推断交付或新操作权限。

在保留的交接中记录该响应已被使用。只恢复其指定的未完成操作：已证明的跟踪器前缀、历史、发布、所选结果和清理效果仍保持已证明状态。保留已验收源边界，直到跟踪器和生命周期负责人确立其所需处置，包括明确授权合并交付历史之后。
