# 空差异与批次修复

工单无需代码变更、最终批次 diff 为空，或最终验证与审查需要修复时，使用这些分支。其余非空候选按主流程使用公共 `code-review`。它拒绝空 diff，不意味着审查通过。

## 独立验收空差异

冻结确切实现状态、比较基线和完整的已接受要求，并保留来源出处。证明索引或工作树中没有遗漏的任务变更。向两个独立、只读的审查角色**Standards**和**Spec**提供相关现有实现、全部已接受要求、适用标准（包括公共审查负责人对代码异味基线的处理方式）和验证证据。它们必须独立于实施 Worker，也彼此独立，可以在同一环境中并行运行。

要求每项需求都有明确的满足证据，Standards 覆盖相关实现，且两个角色都给出绑定到确切状态的明确结果。没有编辑、跳过某一维度、缺乏依据的假设或先前 Worker 的声明，都不能构成验收。输入缺失或独立角色不可用时停止。普通发现交回实施负责人修复；如果结果 diff 非空，必须使用公共 `code-review`。

对于**单张工单**，证明已接受行为在 `ticket_base` 时就已满足。两个角色通过后，Controller 授权 Worker 通过正常 hooks 创建一个空提交，携带规范工单引用和唯一的 `SmartKit-Ticket: <canonical-id>` trailer。如果修复已经为该工单产生未验收候选，就将这个未发布候选 amend 为空工单提交，不追加第二个提交。验证其唯一父提交为 `ticket_base`、树与该基线相等、相关证据和检查仍适用，并满足其余全部[工单验收条件](process-one-ticket.md#accept-the-ticket-commit)。重新运行依赖提交或 hooks 的检查。hooks 产生内容变更时退出此分支：工单保持未完成，在受支持的修复中移除过早加入的完成标记，再执行正常的候选、检查、公共审查和标记顺序。空提交本身不能关闭工单。

对于**最终批次**，在整批验证后，对最终实现和全部选定要求进行同样的独立、基于要求的验收。这既覆盖全部工单都无需改动的情况，也覆盖有改动工单的组合 diff 为空的情况。保留单票提交，检查要求冲突、交互和回归；变更相互抵消并不是满足要求的证据。得到的完整报告作为 `complete-run.md` 的最终审查证据，仍须经过最终收尾负责人对权威目标的独立交付证明。

## 修复整个批次

保留失败时的不可变状态、所有阻塞性的必需检查或审查发现，以及已验收工单提交。将 `repair_base` 冻结在当前已验收 HEAD，并通过 [Worker 边界](worker-transaction.md)派发一个新的批次修复 Worker，提供完整批次范围、来源、发现、先前证据和确切修复权限。该 Worker 只负责当前修复。

针对性检查后，通过正常 hooks 创建一个独立修复候选，其唯一父提交为 `repair_base`，且没有工单完成 trailer。暂停写入，验证其全部预期结果已提交且工作树干净，然后从不可变 `batch_base` 重新运行必需的整批验证和两个独立审查维度。批次 diff 非空时使用公共 `code-review`，否则使用上方空差异分支。先前报告提供上下文，不能代替对修复后整个批次的完整覆盖。

普通发现交回同一个 Worker。它通过正常 hooks 只 amend 当前未发布、未验收的修复候选，然后暂停，重新进行验证和两个维度的审查。只有完整验收关卡通过，才能认定发现已解决。在验收修复后的批次前，Controller 独立验证修复提交的父提交与唯一提交范围、范围归属、已验收工单边界未变、不含工单 trailer、工作树干净、Worker 已停止活动、来源仍有效，以及确切证据绑定。

保留此前所有已验收工单和修复提交。批次验收后的后续修复，要由新的 Worker 追加新修复候选，并完成自身验收循环。遇到实质阻塞或修复无法取得进展时，通过[暂停与恢复](resume.md)暂停，保留当前候选和部分文件；不得回退已验收历史，也不得运行后续阶段绕过失败的验收关卡。
