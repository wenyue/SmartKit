# 审查与修复

本引用负责每张工单和整个批次的审查深度、次数及 Controller 问题闭合。公共 `code-review` 负责通用的独立 Standards/Spec 机制和建议性代码异味基线。[处理一张工单](process-one-ticket.md)负责单票顺序和共用 Worker 协议；本引用负责最终整批关卡。

## 一轮审查、最多一次修复

每张工单和整个批次都在一个不可变状态上进行且仅进行一轮正式审查。两个独立维度在修复前收集全部发现，共同构成一轮。只有一张工单的批次仍分别进行单票轮次和整批轮次。

完整审查证据齐备后，将值得修复的发现和必需检查失败汇总为每个单元最多一次的集中修复。两者都不存在时无需修复。一次修复是一个可归属的派发至返回阶段，包括实施、调试、正常 hook 操作和检查。阶段中断后可以接续未完成工作；已返回阶段仍需更正时，暂停批次。工单审查冻结前的普通实施和测试不消耗修复机会，冻结后的更正则消耗。批次验收不会重新开放普通实施阶段。

更换 Worker、提交、diff 形态、来源事实或路径，恢复控制，或从最终收尾返回，都保留原轮次和剩余次数。不得通过正式复审或新建单元重置它们。

保留不可变审查输入、角色身份、各维度的 `never-started`、`in-flight`、`complete` 或未解决状态，以及完整原始报告或恢复位置。保留检查失败、发现处置、修复的 `unused`、`in-flight` 或 `returned` 状态和 Worker 身份、确切差异、针对性闭合及剩余次数。将这些放入[暂停与恢复](resume.md)描述的既有交接；未知尝试状态保持未解决，不能当作尚未使用。

## 提供深入审查说明

冻结比较基线、HEAD/tree、完整预期 diff，以及带来源身份和版本的已接受要求。证明写入者已暂停，且受审状态没有遗漏预期任务变更。diff 非空时，使用这些确切输入和全部已接受来源调用公共 `code-review`，即使提交发现只找到一个来源。diff 为空时，使用下方独立路径。Spec 维度缺失或被跳过，都不能满足验收。

针对适用工单或完整批次，向两个维度提供以下说明：

- 将每项已接受要求追踪到实现和验证证据，识别缺失、部分完成、错误或缺乏依据的满足情况，以及意外扩大范围的行为。
- 检查变更行之外的相关调用方、被调用方和受影响契约。主动检查边界、错误和恢复路径、兼容性及回归。整批覆盖还包括共享约束、冲突要求和交互，不能缩小为只看交互。
- 收集全部有用且有证据支持的发现。引用具体来源位置、要求或标准、行为和支持证据。区分严重程度、建议性异味、覆盖缺口和不确定性；优先关注实际影响，避免臆测的表面问题。
- 保持独立维度和各自发现分开。简短公共摘要容纳不下全部发现和覆盖时，保留完整支持报告并从摘要链接过去。明确说明限制；摘要简短不能成为遗漏发现的理由。

每个角色的完整报告应标明不可变输入、覆盖、发现和不确定性。派发修复前，通过 `resume.md` 恢复不完整或缺失报告；覆盖不完整不能成为无问题结论。

### 空差异

公共 `code-review` 拒绝空 diff。在该单元同一且唯一的轮次中，使用两个独立、只读的**Standards**和**Spec**角色，它们须独立于 Worker，也彼此独立。提供冻结实现与基线、已接受要求、适用标准、公共代码异味基线的处理方式、检查和上文深入审查说明。它们可以在已建立环境中并行运行。缺少角色或必需输入时停止。

要求每项需求都有明确证据，Standards 覆盖相关实现。对于工单，证明要求在 `ticket_base` 已经满足；对于最终批次，证明全部选定要求，包括有改动工单相互抵消的情况。保留各工单提交。没有编辑、变更抵消或 Worker 声明本身，都不足以构成证据。

修复使空 diff 变为非空或反向变化时，使用原始覆盖及下文针对性闭合来证明要求满足。不得切换到第二条正式审查路径。证据不足时暂停；工单标记仍由单票流程负责，交付证明仍由最终收尾负责人负责。

## 闭合发现

Controller 根据已接受要求和标准判断每项发现，为每项记录有理由的处置，包括建议性或不采纳的发现。向实施负责人提供汇总修复集和检查失败。保留原始报告和受审身份不变。

任何修复返回后，暂停写入，在结果状态上重新运行必需检查，包括正常 hooks 和提交身份的影响，并记录相对受审状态的确切差异。执行针对性验证：证明每项已接受发现都已解决，检查修复对直接受影响行为和契约的影响是否造成回归，并说明完整原始覆盖加上闭合证据如何支持最终状态。这是问题解决和修复影响验证，不是新一轮开放式 Standards/Spec 审查。

验收要求原始覆盖完整、每项发现都有合理处置、没有未解决阻塞或必需检查失败、存在修复时其差异可归属且已获授权，以及 Controller 验证绑定到确切最终 HEAD/tree 和已接受范围。状态未变时使用原始报告；仅元数据变化时，需要明确等价证明并刷新相关检查。对于修复后的代码，报告 Controller 根据修复闭合证据验收，绝不能声称审查角色未看过的状态获得了其通过结论。

仍需进一步修复、覆盖不足或存在实质不确定性时，保留工作并暂停整个批次，指出确切下一位负责人和操作。后续内容变更只能使用适用单元尚未使用的修复机会，且原始证据必须充分。已验收工单提交保持固定；批次审查后的更正属于批次次数限制。

## 验收整个批次 <a id="accept-the-whole-batch"></a>

全部工单已验收且 Worker 已停止活动后，冻结最终 HEAD/tree。运行必需整批检查，并按上文契约，基于不可变 `batch_base` 和全部已接受要求获得两个完整独立报告。单票报告为审查完整组合结果提供上下文，包括交互和回归。

选择修复前，收集检查失败和发现。普通检查失败不必妨碍审查仍有意义的冻结状态；前置条件缺失或证据不完整时，暂停关卡。需要修复时，将 `repair_base` 冻结在已验收 HEAD，保留该失败状态、完整报告和每个已验收工单提交。按 [Worker 协议](process-one-ticket.md#worker-protocol)派发新的批次修复 Worker，提供上述输入及汇总发现、范围和剩余权限。

在该阶段内运行针对性检查；内容变化时，最多通过正常 hooks 创建一个独立修复候选，以 `repair_base` 为唯一父提交，且没有工单 trailer。只在阶段返回前 amend 这个未发布、未验收候选。内容无需变化时，保留 HEAD 和失败已解决的证据。

在 `batch_base` 范围内，对确切最终状态执行 Controller 问题闭合和必需整批检查。证明范围、已验收工单历史未变、本地状态干净、Worker 已停止活动、来源仍有效，以及验收证据完整。存在修复候选时，还要证明其唯一父提交、仅含一个提交的范围及没有工单 trailer；否则证明 HEAD 未变。闭合失败时，保留候选并暂停。验收后修复提交固定；次数已用尽后，最终收尾或漂移不能再产生另一个修复提交或验收循环。
