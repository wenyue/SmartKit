# 共同判断依据

制品指一个 Rule 或 Skill；Candidate 指当前正在编写和审查的制品及其范围内的配套资源。Controller、Author 和 Quality 在各自职责内，将这些判断应用于两种制品类型，分别用于对齐、分配及 Author brief；编写；质量审查。行动和结论的权限仍由各自的角色合同规定。

## 实际生效的含义

具有权威性的已接受要求确立制品的预期含义；现有 Candidate 文本是回归证据。制品的治理指令表达最终要求，并保留其含义、条件、例外和非目标。只有中间推理或未选的编写方案对读者理解或执行已接受的要求有实质帮助时，才将其提炼为有用的理由、边界或例外予以保留。对话历史仍是编写和审查的证据；出现在证据中，本身并不构成将其纳入制品的理由。这一要求适用于制品自身的指令，也包括要求产出方案比较内容的指令。

围绕有意义的决策组织内容，在适当的加载边界内，将每项要求与应用它所需的证据、行动和验证放在一起。结果依赖顺序时，明确规定顺序；否则将方法留给 Agent 判断。通过准确的引用条件按需展开真实分支，而不是依照任意长度阈值拆分。判断连贯性和完整性时，不强制规定标题、清单、字数预算，也不另加一套重复政策的工作流。

只有正向措辞无法可靠避免实质性混淆、错误适用或安全风险时，负向边界才可作为必要的硬性护栏。

## 职责与加载

已安装的 SmartKit 核心治理负责 Rule、规则导向 Skill 和任务型 Skill 的适用性、强度、优先级及组合。依照该所有者处理，不重复或重新定义其比较规则。当有意采用的任务替代要求或项目委托会影响受支持的决策时，应明确表达相关条件、预期偏离或委托结果，以及仍须遵守的约束。

Rule 负责在相关工作中持续生效、且边界清晰的政策领域。任务型 Skill 负责有明确结果和边界的触发式任务，以及该任务所需的约束；规则导向 Skill 则负责应用于现有工作的政策。规则导向 Skill 是通过原生 Skill 发现机制提供的 Rule，不是争取独立交付物的任务工作流。根据含义，将共享的持续性政策分配给最合适的现有政策所有者，无论它是 Rule 文件还是规则导向 Skill，必要时完善该所有者。无条件加载可以作为可用性的证据，但不能成为将项目或 Skill 专属义务提升为全局政策的理由。如果某项事实已由代码、配置、schema 或其他现有所有者负责，则相应变更归该所有者负责。

每条政策在相关 Rule 和 Skill 中只保留一个完整定义。引用应符合受支持的途径：Rule 文件可以引用 Rule 和 Skill；Skill 可以调用或引用其他 Skill，包括规则导向 Skill，但不得直接引用独立加载的 Rule 文件。在这些边界内，使用指向所有者的简短引用，以及作出决策所需的本地背景，将政策定义保留在其所有者处。合并职责归属时，保留该所有者内部有价值的条件加载边界；一个公开 Skill 不必只有一个包揽所有内容的入口。Skill 的加载途径可以加载规则导向政策，但不会改变该政策的条件或例外。

评估合适的现有所有者时，检查相关 Rule 和 Skill、适用且无条件加载的项目 Rule 和 SmartKit 全局 Rule，以及在受支持的使用场景中可能共同加载的条件 Rule。通过环境支持的发现与加载途径，确认它们的含义、触发条件和规范源。仅凭当前编写会话，无法确认未来使用者能否获得它们。

比较含义，包括条件、例外和配置，而不是匹配措辞。对于独立加载的 Rule 文件，Skill 不能使其适用或激活它。只有在 Skill 支持相应行为的所有场景中都有受支持的独立加载保证时，才可依赖其中的具体约束，并仅保留作出自身决策所需的本地背景。无论采用哪种加载途径，都要保留政策的条件和例外。移除 Skill 中的义务，须先解决职责分配和加载问题；仅有引用并不能证明适用性或可用性。

可编辑的安装缓存或 Skill 中的重复政策都不能替代规范所有者。缺少源文件、访问条件或权限时，仍存在需要由负责角色解决的所有者依赖。

## 制品形态

选择适合所分配工作的形态。对每种形态都应用上文的共同判断；选择、编写或评估其形态时，应用下文相应的标准。

### Rule

编写 Rule 时，以治理政策开篇。

Rule 的所有者、强度、可观察条件与结果、例外和优先级都必须可以还原。

### Skill

编写 Skill 时，将 `SKILL-MECHANICS.md` 应用于调用和包装。描述只保留结合名称、任务和加载前通常可见的上下文选择该 Skill 所必需的信息；正文无法弥补遗漏的加载入口。面向模型的描述应在保证选择可靠的前提下降低固定上下文成本；用户显式调用的描述则服务于人的选择。用典型适用场景、相近但不适用的场景，以及容易漏掉的必要场景检查。静态推演足以支持这一判断，但不能作为加载准确率的实测结果。

从三种并列写法中选择适合工作的形态：

- **原则导向的 Skill**说明结果、治理原则、会产生实质后果的约束和完成条件，同时将具体方法留给 Agent 判断。
- **流程导向的 Skill**在顺序或协议会影响结果、正确性、安全、所有权、协作、恢复或外部影响时，明确规定步骤及顺序。
- **规则导向的 Skill**通过要求和例外约束相关工作。

原则导向和流程导向的任务型 Skill 因具体任务而被触发。优先保证任务匹配准确、所需上下文完整和执行连贯。如果将普遍必需的方法或步骤放在一起更有利于任务，就保持这种组织方式；仅为缩短入口而拆分必需方法，会增加间接访问，却无法避免加载所需上下文。简洁、相关性和可靠的渐进加载等通用要求仍然适用。

**混合型 Skill**在这些写法能发挥实质作用的地方加以组合。分别对相应部分应用政策加载和任务执行方面的考虑，而不是为整个制品设置一个统一的大小目标。围绕决策整合其含义，而不是拼接一段规则说明和一套工作流。

### 规则导向 Skill

将 `rule-<domain>` 名称保留给这种写法，命名不随强度变化。这类 Skill 是面向广泛相关工作的按条件加载 Rule。面向模型的描述应依据任务与治理领域的相关性，在治理决策前触发加载，而不是将发现条件限制为一组编码操作或政策主题。在入口中声明默认强度，将影响行为的条件放在相应要求旁边。让显式调用和受支持的专项评估都能被发现。

正常激活时，约束当前工作，而不是另外启动审计或报告。用户要求的评估有自身明确的覆盖范围和结果，仍须遵守政策条件和请求授权。两种途径都不授予额外权限。

对于这类宽触发的政策型 Skill，在保证义务完整、决策正确和可靠加载的前提下，首次激活 token 成本低是编写和验收要求。区分与其设计有关的成本：

- **发现：**描述及其他始终存在的引用。在保留广泛领域覆盖的同时精简措辞。
- **首次激活：**入口以及无条件触达的全部必需读取内容，包括传递依赖。只适用于部分分支的指令放在入口中时，仍会产生预先加载成本；无条件资源引用链只是将这项成本移到了别处。
- **后续分支：**仅在满足条件时，才于依赖它的决策或行动之前读取的额外内容。

在入口中保留基础政策、Strength，以及足以支持决策的证据、条件和例外。入口应能支撑普通但有实质内容的工作，包括简单明确的修改和常规审查，直至据此采取行动并判断是否完成。只能支持不采取行动、维持既有传播或选择其他资源的入口，尚未满足这一要求。将共同政策及应用它所需的上下文放在一起；所有或几乎所有受支持的工作都需要的内容，应留在入口，或重新考虑使其成为必读内容的加载边界。

当某个分支需要额外知识或约束才能正确决策时，将相关内容放入自身负责的资源中按需加载。编写、审查、诊断或评估这些动作本身，并不足以证明这种需要。明确区分该分支的事实，让读者在读取资源前就能识别，而不是依赖对复杂程度的主观判断，或笼统要求“需要时阅读”。每处引用都应准确说明读什么、何时读，使依赖相关义务的决策或行动，包括审查判断，都能预先获得完整要求。通过受支持的途径确认资源可用。加载不授予额外权限。

编写和验收时，沿具有代表性的普通实质工作和深入处理路径，追踪实际会触达的文件及传递资源链。检查每项决策需要什么、入口能否让普通修改和常规审查无需多余读取就完成，同时确保深入分支及时获得完整义务。名义上按条件加载、实际上普通工作几乎总要经过的资源链，无法达到降低首次激活成本的目标。修订或合并职责归属时，保留必需含义，并将原有加载边界作为回归证据，避免合并悄然使条件加载的方法变成无条件加载。判断清晰性、完整性和整体读取路径，不采用任意 token 或行数预算、配额、机械评分，也不强制拆分。静态源文件追踪即可，无需关于任务频率的实证断言、单独报告或运行实验。

对自身负责的规范性资源采用核心治理的继承规则，并将其与示例材料和独立所有者的政策区分开；独立政策保留自身契约。原生 Skill 发现和公开暴露仍由既有所有者负责；写出规则导向入口并不等于注册它，也不等于将其他政策迁入其中。
