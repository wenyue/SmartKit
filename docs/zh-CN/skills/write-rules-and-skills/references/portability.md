# 跨项目可移植性

对于跨项目 Candidate，应确定共享 Owner、适用性、公开发现方式、自有资源、硬依赖，以及受
支持的代表性上下文。冻结覆盖所有已有证据接缝的最小组合；这些接缝必须可能实质改变适用性、
依赖可用性、权限、执行或出口。仅名称和布局差异不能区分上下文。

可移植含义只能来自已接受决策、specification、管辖合同、可观察的共享实现，以及权威已获
独立确认的代表性证据。源项目策略、本地名称、偶然布局、context document 和仅在源项目成功
都不能提供可移植含义。

声明每个必需 Rule、Skill、工具、schema、环境能力和宿主行为，以及它的共享或目标自有路径。
只在真实边界处对平台机制附加条件。缺失事实、依赖路径或可移植权威时，对齐尚未完成。

扩展 Spec Fidelity and Semantic Integrity，使其覆盖共享归属、适用性、依赖闭包和源上下文
排除。扩展 Critical Behavioral Integrity，使其覆盖代表性路径与出口。若静态和 Machine
证据不能高置信地确认运行时可行性，应把相应上下文路由到 Acceptance。只有依赖闭包完整、
两份扩展后的 Correctness 裁决均通过，且每个必需代表性 Acceptance 用例都通过，可移植性才
通过。
