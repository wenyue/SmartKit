# OpenAI 元数据

编写 `agents/openai.yaml`，让理解自己任务但不熟悉该 Skill 的用户能够识别其用途、有把握地选择它，并发起有用的请求。展示名称建立身份对应关系，简短简介提供选择依据，默认提示展示一种受支持的用法。

通过本工作流创建或修订的每个 Skill，都要包含非空的 `interface.display_name`、`interface.short_description`、`interface.default_prompt`、`interface.icon_small`、`interface.icon_large` 和 `interface.brand_color`。这些是本工作流的创作约定：平台允许其中部分字段为可选。元数据不保证客户端何时展示或插入提示，默认提示也不改变调用策略。[OpenAI 字段文档](https://learn.chatgpt.com/docs/build-skills#optional-metadata)和[元数据验证参考](https://developers.openai.com/plugins/deploy/submission-errors#skill-agent-metadata-errors)说明了平台字段。

## 编写有助于选择和使用的文案

将 `display_name` 写成简短、自然的英文标题，主要遵循 Skill 本身的名称，让两者有明显的对应关系。专有名称保留原文，用户明确指定的展示标题按原文使用。可以调整空格和大小写以改善可读性；通过简介解释抽象名称，而不是另造一个身份。

将 `short_description` 写成简体中文，严格用一句简洁的话说完。在这一边界内，优先说明有助于读者选择的任务或结果；能自然容纳时，再补充有用的使用时机或区别。文案以实际支持的行为为依据，而不是机械翻译标题，或罗列内部角色和步骤。相似 Skill 容易混淆时，优先说明会改变用户选择的区别。

例如，两个代码审查 Skill 需要不同的选择依据：“审查代码改动的逻辑、安全性和复杂度，找出影响实际使用的问题。”描述技术质量，而“检查代码改动是否符合项目规范和原始需求。”描述规范与需求的一致性。这一区别有助于选择，也不会强迫每条简介都列出所有审查维度。

为每个 Skill 编写 `default_prompt`，包括 Rule Skill 和后台辅助技能。使用简洁的简体中文请求，包含字面字符 `$`，后面紧跟 Skill 的实际名称，通常用一句话表达。描述一个典型的受支持任务，把未知事实留给用户：“使用 $write-rules-and-skills，将我提供的要求整理成一份可执行的 Agent 规则或技能。”展示了一个创作请求，没有编造其主题或要求。对于 Rule Skill 或辅助技能，表达其受支持的应用或评估，而不是编造另一套用户工作流。提示是起始请求，不能替代 Skill 的说明或必需输入。

## 为每个 Skill 提供可用的图标

根据 Skill 的实际角色选择图标。提供领域政策的 Rule Skill 可以共用盾牌；其他通常不由用户主动调用的辅助技能可以共用齿轮。其余每个 Skill 都需要与自身用途相关的专用图形，通过形状区分，而不是给共用符号换个颜色。根据受支持的任务和目标用户判断这些角色；仅凭 `allow_implicit_invocation` 不能识别后台辅助技能。

采用统一的简洁线形风格、透明背景，以及不依赖外部图片或字体的独立 SVG。大小图标保持同一图形主题，两个尺寸下的线条和形状都应清楚可辨。可缩放的 SVG 可以同时用于两个字段；也可以为小尺寸简化细节，同时保留图形主题。项目有明确视觉要求、规定不同风格或调色板时，遵循项目要求。

已有合适素材且符合这些要求时复用，否则创建一个。本 Skill 在相对自身根目录的 `assets/rule.svg` 和 `assets/background.svg` 中提供可复用的盾牌和齿轮。将选中的共用素材复制到目标 Skill 自己的 `assets/` 目录中。专用图标也放在那里，两个图标字段都通过相对目标 Skill 根目录的路径指向真实的本地文件，例如 `./assets/icon.svg`，而不是指向本创作 Skill、已安装的缓存或远程 URL。本地副本保证独立分发的 Skill 资源完整。

必需的素材、来源或创建能力不可用时，按照现有工作流向 Controller 报告准确的缺失前提。必备图标不能被默默省略，不能用不存在的路径替代，也不能在依赖尚未解决时视为完成。

## 一致使用三种颜色

项目有明确视觉要求时遵循其要求；否则，`brand_color` 和图标线条颜色使用这套全局默认调色板。先识别 Rule Skill 和后台辅助技能，再根据其他 Skill 的主要用途选色。多用途 Skill 使用核心任务对应的颜色，而不是为每项次要活动另选一种颜色。

| 主要角色或用途 | 颜色 | 十六进制色值 |
| --- | --- | --- |
| Rule Skill 和后台辅助技能 | 灰蓝 | `#64748B` |
| 理解、研究、规划、诊断、审查 | 蓝 | `#2563EB` |
| 编写、创建、实现、设置、维护、发布 | 绿 | `#15803D` |

颜色提供粗略识别，不表示调用权限或风险等级；专用图形区分各个 Skill。除非主要用途或适用的项目要求发生变化，否则修订时保持分类一致。

## 保留行为并检查完整资源包

修订展示元数据和素材时，保留现有的 `policy`、`dependencies`，以及其他无关或未知字段。除非其变更获得独立授权，否则保留受支持的调用设置和依赖声明。展示文案必须描述实际存在的 Skill，不能暗示正文未提供的能力或权限。

以下示例展示本创作 Skill 的必填字段；其他 Skill 需要自己的文案、分类和配套素材：

```yaml
interface:
  display_name: "Write Rules and Skills"
  short_description: "设计、编写并验证一份可供 Agent 使用的规则或技能。"
  icon_small: "./assets/write-rules-and-skills.svg"
  icon_large: "./assets/write-rules-and-skills.svg"
  brand_color: "#15803D"
  default_prompt: "使用 $write-rules-and-skills，将我提供的要求整理成一份可执行的 Agent 规则或技能。"
```

交付前，检查完整资源包：

- **元数据：** YAML 可以解析，六个必填字段都是非空字符串，默认提示使用实际 Skill 名称，且 `brand_color` 是六位十六进制颜色。
- **素材：** 以目标 Skill 根目录为基准解析每个图标路径，并确认配套文件能够打开。在小、大尺寸下检查图形的透明背景、可辨识性和主题是否合适。
- **文案：** 对照 Skill 的实际行为阅读，检查简介是否只有一句话，以及起始请求是否有用。

运行所属工作流要求的检查。格式检查本身不能证明文案质量或视觉效果。
