# 工件关系

这份受支持的公共 reference 定义 Agent 工件之间的依赖。从选定的 writer 来源直接阅读它；查阅不会调用 writer 的工作流。结合工件所有者已接受的依赖范围和受支持接口应用这些关系。

## 什么构成依赖

当一个工件的指令要求使用另一个工件的指导、能力、结果或资源时，就构成依赖：调用 Skill、向它委派工作、读取指定章节或使用其脚本，都属于依赖。依赖从需要某项内容或能力的工件指向提供它的工件。正文中的操作性引用即使只要求阅读而非执行，也属于依赖。

依赖单位是一个 Rule 或 Skill 及其所属资源。读取自身 reference 或组织自身工作流，不构成工件之间的依赖。归属说明、作为当前工作对象的工件，以及所需材料已在本地提供的自足示例，也不构成依赖。按引用要求的行为分类，不以措辞或链接格式判断。

在这份依赖契约中， **Rule** 包括 rule-led Skill，不受其命名影响； **Skill** 指普通 Skill，不包括 rule-led Skill。这种分类只约束依赖。指令的适用性、权威和冲突优先级仍由原有所有者按原有顺序处理。

## 区分职责与执行

Rule 或 Skill 正文需要澄清职责时，在简介之后、其他正文章节之前，使用不编号的 `## Responsibility boundaries` 章节。使用表头为 `Artifact | Responsibility` 的两列表格，先列当前工件，再列各相关负责方。工件列的每个单元格（包括当前工件）都使用可解析的 Markdown 链接，指向实际 Rule 文件或 Skill 的 `SKILL.md` 入口。不需要澄清分界时，省略该章节。简体中文镜像使用 `## 职责分界` 和 `工件 | 职责`，结构保持一致。

表格描述职责归属和必要条件，不放入读取、调用或委派指令。可以指明同级工件或上层调用者负责当前工件范围外的工作。只要分界说明既不执行或委派该工作，也不需要所指工件的内容或可用性，就不构成依赖。转交结果和交接步骤留在操作流程正文中；它们可以携带判断分界时已查明的事实。

例如，分界表可以将纯重命名工作归给重命名 Skill，而工作流使用设计词汇 Skill 解决接口选择。只有后者构成依赖。把调用或必需的阅读移到分界章节，不会使它变成职责说明。

## 保持政策独立，克制使用能力依赖

Rule 不依赖其他 Rule：每个 Rule 都有清晰的政策边界。Rule 可以依赖普通 Skill。有限的例外是项目 Rule 显式补充或覆盖其共享提供方的适用 Rule。克制使用这一例外，说明条件和预期差异，并按现有优先级契约解决冲突。

Skill 可以隐式提及独立适用的政策，例如遵循项目代码风格。必需政策必须有受支持的加载路径；当前对话中可见并不构成保证。依靠该路径，而不直接依赖 Rule 文件。一般性的政策提示不能代替实际的能力依赖，例如调用项目 Skill 准备环境。

克制使用 Skill 依赖，仅用于上层 Skill 需要一项职责明确的下层能力时。按依赖方工件允许的范围检查每条直接依赖，并保证完整依赖图在直接和传递关系上都无环。通过输入提供调用者上下文，使被依赖 Skill 对其受支持调用者保持正确；对某个潜在调用者的引用也按同样的依赖规则判断，不因提到调用者名称就被禁止。这些关系即可确立方向，无需全局分层登记表。

## 尊重项目与提供方边界

项目 Skill 位于其已接受共享提供方的普通 Skill 之上，可以依赖这些 Skill 或本项目提供的其他普通 Skill。其他提供方的 Skill 不在该声明范围内。根据已接受的所有权和来源确立提供方及支持范围，不以当前工作目录或已安装插件判断；无关工件仍遵循各自所有者的依赖范围。

共享提供方可以明确将选定的项目 Skill 公开为反向依赖扩展接口。这些已声明目标对提供方可见，可以作为普通 Skill 依赖，且目标自身可以依赖其他项目 Skill。这一例外不会公开任意项目 Skill，也不放宽全局无环约束：要沿着扩展及其依赖，追踪返回提供方的关系。所属政策负责确定受支持的目标及其查找方式。

## 区分访问、可用性与权限

通过另一个工件的受支持入口或明确支持的公共资源接口使用它。查阅公共资源会形成对其所有者的依赖，但不会调用其工作流；查阅既不授予调用受限 Skill 的许可，也不授予执行其操作的权限。访问私有资源需要所属政策明确许可。保留资源的所有者、加载和失败要求，以及使用方任务特有的输入、输出、权限和生命周期约束。

在允许的范围内，如果受支持环境随依赖方工件、通过已接受的提供方或通过同一项目提供某个 Skill，就视其为可用。按通常的结果处理方式处理其失败结果。对于项目可能提供也可能不提供的获准扩展，需要说明存在和缺失两种结果：若最终结果仍有意义，可以跳过并报告省略的工作；若它不可或缺，则停止并指出缺失的前置条件。安装不会扩大依赖许可，也不能证明执行成功。

其他依赖，例如命令行工具、MCP 服务、网络访问、凭据和其他环境能力，在受支持的使用情形中可能缺失或失败。检查工件直接或通过其资源使用的此类依赖，并说明不可用或失败时的结果；被依赖 Skill 自己负责其内部依赖的结果。某项能力在当前会话中可见，并不能证明未来使用时也会存在。打包和发现机制均不产生新的政策或许可。

## 按依赖顺序编写协同集合

编写一组待生成的 Skill 前，协调该集合的调用者应确立并提供依赖项先于使用方的顺序。每个生成的 Skill 只能依赖该集合中排在前面的 Skill。升级时也遵循同样的顺序，即使排在后面的 Skill 已有旧版本。编写依赖这些关系的内容前，先通过调整职责分配解决冲突的依赖。调用者负责规划和执行这一顺序，无论是独立编写，还是通过 setup 工作流编写。
