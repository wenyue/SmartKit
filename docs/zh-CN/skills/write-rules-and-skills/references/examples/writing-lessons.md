# 写作讲解

这些案例解释成品指导中的写作取舍。选择能解决当前写作难题的案例，连同其中指明的完整范例一起阅读。引用段落和示例都是说明性材料，不是你正在编写的工件需要额外遵守的政策。它们的主题、标题、长度和语气都不是模板。应根据读者的实际任务运用其背后的取舍。

来源身份、改编说明和保留的许可文本见 [SOURCES.md](SOURCES.md)。引用片段和本地示例已提供全部教学材料，不要求阅读上游内容。

## 将方向与明确边界结合

Ponytail 开篇先给出一种工作姿态：

> 你是一位懒惰的资深开发者。懒惰意味着高效，而不是草率。

接着，它给出一个决策阶梯：质疑需求是否必要，寻找已有方案，考虑标准库和原生平台，最后才编写足以奏效的最少代码。这种姿态与阶梯相互强化。“懒惰”让一个普通关注点更容易被记住；阶梯则指出去哪里寻找更省事的做法。两者都不必枚举未来每一种编程问题。

Ponytail 在明确的边界内应用这些简化建议：

> 保留已确认的要求和可观察行为。在缩减已确认的功能、改变可见行为或引入重要成本取舍前，先讨论并等待用户决定。

值得学习的是这种结合。读者在开放选择上获得方向，也能在这种方向可能被过度运用的地方看到明确边界。把工作姿态改造成几十项强制检查，会失去它的适用广度；只留下姿态，则可能导致缩水的结果。角色设定能集中一种有用习惯时，才值得存在。这并不意味着每份 Rule 都需要角色设定。

阅读[生成文件](elegant-rule.md)，了解一个内容自足的政策案例。它的明确要求是让所属源文件与生成输出一致。具体的生成器和验证方法留给仓库决定，因为这些事实因环境而异。这份 Rule 对结果有明确要求，同时不假装了解每一种环境。

[文档链接](elegant-rule-led-skill/example.md)展示了如何在由模型调用的 Rule-led Skill 入口中承载同样的政策角色，并针对实际的目标变更披露更深入的知识。这里将该入口作为普通 Markdown 教学材料呈现，使它仍属于本节讲解，而不会成为可独立发现的 Skill。

## 把细节用在需要判断的部分

在 Matt Pocock 的 diagnosing-bugs Skill 中，展开最充分的部分是如何获得一个能够暴露所报告缺陷的反馈回路。它提供了构造回路、收紧回路的方法，以及识别有效信号的方式。其他阶段可以使用这个信号；缺少它，再工整的阶段顺序也帮不上多少忙。强调在这里投入更多精力，既有具体对象，也有因果依据。

阅读[复现症状](elegant-procedure-led-skill.md)，它是对这一部分的精简改编。注意哪些地方要求精确：运行复现、区分所报告故障与环境设置错误，以及简化后重新运行。这些行动把结果与证据联系起来。也注意它在哪些地方留出空间：根据症状选择测试、请求、命令或专用运行程序。选择是开放的，但示例解释了什么会使一种选择优于另一种。

“让回路更快”和“让回路更可靠”可能冲突。关于间歇性故障的段落和竞态示例，在指导优化时保留了建立回路的目的。通用的运行时间阈值看起来更精确，却可能更偏离任务。这份改编没有复述上游诊断流程，也没有引入其全部门槛。

## 用一对案例教会区分

在 Matt Pocock 的 TDD 示例中，结账是公开操作。一项测试检查其内部支付服务是否被调用；另一项检查有效购物车是否产生已确认的结账结果。后者检查的是调用者收到的结果。重构可能替换支付辅助组件，却保持该结果不变，从而让第一项测试在行为并未退化的情况下失败。这个对比解释了“测试行为”的含义，不依赖附带的 API 名称。

将这一技巧用于[决策备忘录](elegant-principle-led-skill.md)。下面两条关于不确定成本比较的指令都看似合理，它们展示了一项有用的取舍：

> 按价格、可靠性和迁移难度给各项服务评分，然后推荐总分最高的一项。

> 比较可能改变决策的差异。如果价格更低依赖预测用量，就说明这一优势在什么情况下消失；如果迁移难以撤销，就在解释中给予这种不确定性更多权重。

当双方认可的尺度和权重已经表达了决策者的优先事项时，第一条很有用。缺少这些前提时，它的精确表象可能掩盖任意判断。第二条指出了证据和取舍，同时允许使用表格、计算或段落。它能指导尚不能化为分数的工作。哪种选择更好，取决于任务，而不是对文字优于数字的普遍偏好。

完整范例还围绕同一个价格例子，将证据、推断和假设放在一起。这样就能看清它们的关系：输入有来源，并不意味着由它得出的每个结论都确定。好的示例提供能迁移到其他情形的区分；讲解则应说明哪些细节承载了这种区分。

## 让读者的问题决定文档形态

Matt Pocock 的 prototype Skill 区分了两个问题：状态模型是否按预期工作，以及界面应该是什么样子。对于前者，交互式演示让用户尝试状态转换，并观察每次操作之后的状态。对于后者，可切换的界面方案让用户比较外观。两类问题需要不同的工件和知识，因此入口会先帮助读者选择分支，再加载相应细节。拆分的价值来自具体工作，而不是“一个 Skill 应该有多少个文件”。

比较上面的两个完整范例。决策备忘录围绕选择和解释组织；作者可能在撰写任何一节时发现缺失的假设。复现则存在必要顺序：只有先观察到故障，简化才有信息价值；交接依赖实际运行过什么。编号适合后一种关系。给备忘录增加阶段，并不会产生同样的依赖。

即使不需要新增分支或文件，也可以用段落区分不同问题。在“让它适合反复运行”这一标题下，复现范例先解释可以移除什么，再解释如何验证一次移除，最后说明怎样处理间歇性故障。它们属于同一个标题，但每段都给读者一个不同的关注点。合并成一整块会掩盖这些关注点的转换，却没有减少读者需要掌握的知识。

两个示例都给常规能力留出了空间。它们给出足够内容，让困难选择可见、预期结果可识别，然后让读者补足常规方法。其价值不在于把细节或简短程度推到极致。
