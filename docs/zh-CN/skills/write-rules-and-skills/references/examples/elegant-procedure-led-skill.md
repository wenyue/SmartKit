# 复现症状

把缺陷报告转化为能够暴露所报告故障的反馈回路。有用的结果是调查时可以再次运行的信号，而不是听起来合理的缺陷解释。

## 1. 找到能反映这个症状的信号

从报告和现有证据中，识别触发输入或操作、预期行为，以及观察到的偏差。在任务允许的访问和权限内，找到能够触发该行为的受支持方法。准备可丢弃的复现，不修改被测实现。

把精力用在信号上。测试、命令、请求或小型专用运行程序都可能适用；选择能触发所报告行为的最简单方法。如果报告关注的是缺少数据行，请求成功返回并不足以说明问题。当故障依赖某种交互，而直接调用 API 会跳过它时，浏览器检查就有价值。观察能够区分故障与预期行为的属性。

运行复现，检查实际结果。环境设置错误反映的是复现运行环境的问题，并不能证明所报告的故障发生了。在范围内修正运行环境，或指出缺少的前提。只有观察结果与所报告症状相符后，才开始简化。

## 2. 让它适合反复运行

围绕故障收紧回路。去掉无关设置，控制需要保持稳定的输入，减少会妨碍反复运行的延迟。保留影响故障的上下文：如果操作串行化后竞态消失了，复现并没有因此变得更好。

每次简化一个疑似无关的部分，然后重新运行。只有信号仍然暴露所报告故障时，才保留这项简化。这让更小的案例与观察结果保持关联，而不是假定更短的脚本仍代表同一个缺陷。

对于间歇性故障，记录尝试次数、观察到的故障率，以及产生这些结果的条件。一次正常运行不能证明故障不存在。尽可能提高可重复性；报告剩余波动，不要把它包装成确定性检查。重复执行应受任务的时间、资源和访问限制约束。

## 3. 交接已观察的案例

将调用方式、必要输入和设置、预期结果及捕获的故障放在一起。共享的调用说明和输出中不得包含秘密信息。说明已知波动，以及简化过程中发生的变化，让下一位调查者理解信号的局限。

完成的复现必须已经运行、触发所报告的行为，并捕获相对于预期结果的实际偏差。如果在现有边界内无法观察到症状，就返回尝试记录，以及具体缺少的证据或访问条件，标明复现尚未完成。关于原因的理论不能代替观察。诊断和生产修复仍是独立任务。
