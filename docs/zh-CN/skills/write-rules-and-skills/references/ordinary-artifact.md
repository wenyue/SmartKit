# 直接使用型工件

直接使用型工件是直接作为政策或触发作业使用的 Rule 或 Skill。此引用负责判断其生命周期类型、运行时
边界以及代表性应用方式。

## 遵守所提供的归属边界

| 调用方范围 | 契约 |
| --- | --- |
| Project-local | 根据显式提供的仓库事实编写项目行为，并将其放在最窄的项目归属中。 |
| Shared | 只保留显式提供的共享依赖和可移植性证据所支持的行为。 |

只有项目私有的共享工作流可以声明 Shared。仅仅删除项目细节或调用公共工作流，并不能提供源上下文
或可移植性证明。

## 证明行为塑造需求

如果一条拟议指令唯一的作用是改变智能体的默认行为，而且没有已经观察到的失败证明需要这样做，编写
前先运行一次软隔离的行为对照。重写时使用先前确认的工件，新建时不提供候选项，并让新的智能体
执行与候选项验收计划相同的任务。原始返回结果保留在控制器上下文中，供后续审查。

政策权限、项目事实、参考材料或已经观察到的失败不需要对照。如果对照在没有新指令时已经产生所需
行为，就省略这条没有实际作用的指令，除非另有已经确认的证据要求明确写出政策。

## 编写运行时工件

- 陈述最终政策或作业，而不是编写历史、语义台账、审查过程或资格证据。
- 项目事实只写在 Project-local 工件中。Shared 工件只说明稳定协议，并告诉智能体如何查找
  本地事实，或者在发现无法解决时停止。
- 每项要求只保留在一个归属中。遵循更具体的 Rule 和受支持的本地覆盖，不要将其复制到更宽泛的正文。
- 只包含 schema 要求或能改变行为且不能从可靠加载归属推导出的指令。

## 验收代表性使用

所选的 `rule-semantics.md` 或 `skill-semantics.md` 提供对应类型的案例。应用父 Skill 选定的通用
验收执行者协议。

- 对于 Project-local 工件，明确提供仓库声明、归属边界、真实入口或执行点，以及相关的本地案例。
- 对于 Shared 工件，使用其归属工作流提供的案例、依赖和可移植性证据。

只有工件在声明范围内始终表达同一个含义、每个选定案例都产生有依据的结果，而且无需虚构项目事实、
操作或退出方式，验收才通过。
