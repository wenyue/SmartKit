# 编写决策

## 区分完整 setup、恢复与同步

这些路径可能生成看起来相似的文件，但确立的结果不同。完整 setup 会重新评估项目指引和 Agents，并准备 CodeGraph；恢复保留已接受备份的原始字节；本地同步根据已确立的输入进行渲染。复制来的 setup 标记或已收敛的配置不能代替完整 setup 成功。因此，先选择操作，再进入各条路径的前置流程。

## 分别判断本地可用性与备份身份

新 checkout 可能已有可用配置，但复制来的仓库绑定仍缺少本地成功同步记录。将复制来的绑定视为权威，就会选用未经确认的来源；将这种情况视为配置不可用，又会强制进行不必要的恢复或初始化。通过两个问题选择操作，能够保留这两项区别。

## 由 writer 负责单个工件，由 Setup 负责整个集合

每个蓝图请求都有独立的公共 writer Candidate 和完整审查。Setup 提供职责分配和依赖顺序，再在登记前协调组合结果及映射后的链接。单个工件通过审查不能证明整个集合覆盖完整，而 Controller 直接修复会破坏已接受的指纹和 Author 所有权。

传递 Skill 蓝图的完整资源目录，让 writer 解释已接受的固定内容输入。Setup 将已登记输出的字节封存到应用完成，而不重复实现元数据检查。这样既让蓝图编写可以独立使用，也避免 Setup 成为内容要求的第二个来源；临时封存不限制项目后续自行编辑。

## 冻结 setup 输入，同时允许仅刷新运行时

与 setup 相关的来源或目标发生漂移时，必须取消并启动新会话，即使该编辑已由另一任务授权。CodeGraph 运行时状态不在冻结范围内，因此守护进程因空闲退出后，可在首次尝试 finish 前刷新。这条边界既避免悄悄改变已接受的输入，也避免仅因暂时的运行时状态而无谓重启。

## 终结清理完成后才记录成功

最终 setup 版本更新在私有会话成功清理后进行，并使用带保护检查的写入。分别保留来源保存、目标应用、清理、版本更新和发布的结果：这些步骤可能在不同文件系统上独立失败；恢复既不能抹去已保存的源工作，也不能声称完成了实际并未发生的原子回滚。
