# 恢复本地配置

Setup 入口选定恢复操作后，阅读本指南。复用入口已解析的 `<skill-root>`、`<maintain>` 和 `<target-root>`、其“所有权”指导，以及已接受的操作范围。此路径用于恢复丢失或已改变的本地配置，或应用配置仓库中的变更，适用于新 checkout 和已配置的项目。阅读 [项目配置维护](../../maintain-project-config/references/maintenance.md)，了解绑定、备份范围、恢复、Git 排除和失败恢复。直接使用其受支持命令，不调用仅限用户调用的维护 Skill。此路径不需要完整会话预检、Matt 上下文、迁移、自定义 Agent 重新评估或生成内容编写。

1. **确定要使用的备份。** 复用 Setup 入口在选择操作时取得的、仍有效的本地检查结果。结果不可用或已过期时，检查选定的 checkout。

   ```text
   python "<maintain>" inspect --target "<target-root>"
   python "<maintain>" bind --help
   ```

   已有绑定且存在匹配的本地成功同步记录时，沿用仓库地址、分支和条目，除非用户要求改变。仍需选择或确认时，包括用户要求变更却未提供新值的情况，按 [选择配置仓库](choose-configuration-repository.md) 询问并等待回复。

   对尚未验证的来源，在绑定前使用经认证的只读仓库证据，确认所选仓库和分支包含预期备份的 `projects/<entry>/manifest.json`。条目不存在或无法核实其存在时，在 `bind` 前停止。只有必要时才按维护参考的仓库 `bind` 路径处理，并保留现有来源和目标中的工作。复制来的绑定本身不授予恢复或自动同步权限。

2. **展示应用该备份会改变什么。** 更新已绑定来源，再检查实际效果：

   ```text
   python "<maintain>" update --target "<target-root>"
   python "<maintain>" inspect --target "<target-root>"
   ```

   认证、拉取或更新失败时停止应用。保留已有状态并报告原因。成功更新后，展示选定完整文件和目录的差异，包括新增、覆盖和删除。

   如果存在差异，按 [确认配置改动](confirm-configuration-changes.md) 询问用户如何处理整次恢复，并等待回复。保留本地会跳过快照应用，并保留当时的目标内容和仍存在的同步记录。已经单独接受的绑定切换及其对 Git 或同步记录的影响继续有效。依赖源与目标一致的工作仍待完成。应用备份时，通过 `--accept-existing` 传入准确的检查指纹。源与目标已一致时，无需差异接受令牌。

   说明保留本地并不会将这些文件保存回仓库。要把有意进行的目标编辑保留到仓库中，必须另行接受维护所有者的采纳路径。检查后任一侧发生变化时，展示新的差异，并在应用前取得新的选择；先前的选择针对的是不同内容。

3. **单独设置启动偏好并应用。** 适用的已记录偏好或用户对当前 checkout 的明确答复均无法确定选择，或用户要求改动但新值还不明确时，按 [选择启动自动同步](choose-startup-sync.md) 处理。沿用已有偏好，除非用户要求改变。

   按已记录或新接受的偏好应用；只要接受了差异，就添加 `--accept-existing "<inspect-fingerprint>"`：

   ```text
   python "<maintain>" apply --help
   python "<maintain>" apply --target "<target-root>" --auto-sync off
   python "<maintain>" inspect --target "<target-root>"
   ```

   `--auto-sync` 使用已记录或新接受的值。通过共享参考中的只读 Git 检查，核验来源与目标一致、目标本地同步记录和适用的 Git 排除。结果应是所恢复快照的原始字节。复制来的 `setupVersion` 或所有权记录，既不能证明本 checkout 已成功完成完整 setup，也不能证明运行时已就绪。

4. **检查本机能否使用恢复后的配置。** 使用各自所有者支持的只读检查，核验本地工具、凭据和服务。报告缺失或无法核验的前置条件，不在恢复过程中安装工具、启动服务或重写快照。

   报告来源、恢复和保留的路径、同步偏好、排除规则、实际前置条件结果，以及任何失败或恢复证据。区分已恢复的内容和本地就绪状态，并明确说明未执行完整 setup。恢复不生成配置、不记录新的成功 setup 版本，也不提交或发布来源变更。用户请求的初始化或升级走独立的完整 setup 流程。
