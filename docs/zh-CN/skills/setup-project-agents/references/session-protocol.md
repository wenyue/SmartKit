# 完整会话协议

## 前置检查 <a id="preflight"></a>

只解决会影响随附默认值、项目所有的输入或已授权操作的实质性选择。优先使用合格的仓库证据，仅询问确实尚未解决的选择。

`start` 检查归项目所有的 Matt 上下文。如果它报告设置不完整，结束本次调用，请用户在目标仓库中调用 `setup-matt-pocock-skills`；该工作流完成后，再开始新的调用。设置流程既不创建，也不拥有该上下文。

在每项操作之前，确认已接受的会话意图授权了该操作：私有系统临时存储、一次对规范 SmartKit `master` 的只读获取、已配置的外部 Skill 获取、生成内容编写，以及目标变更。这些是不同的授权；已接受的设置意图可能已经涵盖它们。只询问缺失的授权，不重复确认已经解决的事项。生成内容编写所涉及的下游操作仍需各自的权限。

获取操作只能访问各自声明的仓库，可以创建私有临时工作区，并在使用后移除。操作以非交互方式运行，不使用环境中的 Git 配置、credential helpers、代理、SSH 或 askpass 状态。这些获取权限不授权依赖安装、发布、Git 历史变更或任何其他目标写入。未授权的操作必须在执行前停止。若无法获取规范来源，`start` 可以使用经过验证的已安装插件根目录，并报告 `source_commit: null`；已配置的外部来源仍需各自的网络权限。

修改目标前，脚本验证已配置的外部来源、许可证、Skill 文件树、名称、目标冲突，以及记录中的 tag 稳定性。若 `start` 拒绝某项声明或来源，应修正报告的原因，然后开始新的调用。

## 启动冻结会话

通过公共入口 `scripts/workflow.py` 启动一个私有会话：

```text
python "<skill-root>/scripts/workflow.py" start --target "<target-root>"
```

会话操作包括 `start`、`register`、`finish` 和 `cancel`。参数见各命令的 `--help`；`sync-project` 和 `sync-project-rules` 是独立的本地操作。

结果非零时停止。将 `session` 记为 `SESSION`，将 `generated` 记为 `GENERATED`，并保存返回的 `request`、`source_root`、`source_commit` 和 `source_fingerprint`。请求会冻结设置输入、外部快照、生成请求，以及来源和设置相关目标的指纹。目标指纹仅覆盖设置流程使用的证据：项目设置配置、所有权及托管资产、生成目标、项目 Rule 元数据、项目 Agent 源文件，以及涉及的宿主原生配置。Git 历史和索引状态、缓存、日志及其他项目所有的工作都在此范围之外。若固定来源未请求 catalog 中的全部当前契约，公共启动器会拒绝它。编写前，确认返回的请求符合已接受的意图。规范来源运行由提交和指纹固定；已安装来源的后备模式则由根目录、空提交和指纹标识。

保持这一私有会话，直到执行一次 `finish` 或 `cancel`。将请求和来源视为不可变内容。如果另一操作持有会话占用标记，应保留会话并停止。`start` 之后，只要冻结的设置相关目标范围内发生任何变化，包括在该范围内单独授权的编写操作，本会话就应结束：取消会话，并从变化后已接受的目标状态重新开始。范围外的变化不触发重新生成；应将它们作为无关状态保留。这样可以使编写操作保持各自的授权边界，而不是暗中纳入设置流程。

## 完成一次

每个请求都已注册最终输出后，运行一次 `finish`：

```text
python "<skill-root>/scripts/workflow.py" finish --session "<SESSION>"
```

Finish 验证完整输出、冻结证据、所有权和计划，然后在同一回滚边界内应用计划并检查干净后置条件。在完成或失败处理结束前，给予它对所有计划目标路径的独占访问：文件系统检查无法防止不配合的写入者在检查与修改之间被覆盖。成功必须同时满足退出码为零，以及 JSON 中包含 `phase: finish` 和 `check: clean`；只有这样，会话才会作为已完成事务移除。

## 停止与恢复 <a id="stop-and-recover"></a>

如果 `start` 后、尝试任何 `finish` 之前必须停止工作，应取消会话：

```text
python "<skill-root>/scripts/workflow.py" cancel --session "<SESSION>"
```

Finish 之前，声明未解决、所有权或摘要冲突，以及设置相关目标漂移，都要求取消会话，并在修正后启动新会话。取消失败属于终止情况，原样报告。

固定来源的 finish 或事务失败后，保留准确错误。事务会尝试恢复 finish 前的设置状态；如果检查发现第三方并发变更，它会拒绝执行相应的回滚修改。报告中的回滚失败会指出残留的目标状态，供人工检查。回滚的检查与修改之间也存在同样的文件系统限制，因此在整个失败处理期间都应保持独占访问。随后，Finish 会尝试移除私有会话，清理失败时必须报告准确的会话路径。

清理失败既可能发生在目标已经达到干净预期状态之后，也可能发生在事务失败之后，因此不能据此推断已成功零退出或已完成回滚。不得复用、finish 或 cancel 该残留会话。将剩余的占用标记或部分会话内容视为失败证据。报告目标和准确的残留会话路径，以便恢复。在适当的恢复权限下解决原始原因，并处理经过确认的工作流所属残留，再启动新会话。清理仅限于经过确认的工作流所属残留。
