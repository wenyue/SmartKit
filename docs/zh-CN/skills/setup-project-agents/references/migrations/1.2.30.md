# 合并项目规则并保留项目政策

**发布版本：1.2.30。** 默认蓝图集现在生成 `.agents/rules/constraints.md`、`.agents/skills/prepare-worktree-environment/` 和 `.agents/skills/change-set-verification/`。独立的 Tools、Contracts 和 Structure Rule 蓝图已退役。合并必须保留其中的项目专有义务；两个执行型 Skills 保留各自职责及受支持的项目补充。

在完整 setup 期间，使用[生成编写](../generated-authoring.md)和[约束蓝图](../../../../setup-assets/blueprints/rules/constraints.md)：

- 根据 `.agents/smartkit.lock.json` 中的 `blueprint-project-tools`、`blueprint-project-contracts` 和 `blueprint-project-structure` 记录识别旧 Rule 输出。按实际路径阅读每个已记录输出，包括历史上带编号的名称，并一并阅读现有项目政策和当前证据。输出缺失需要有依据的处置，例如证据支持的有意删除；含义丢失的问题未解决前，不得退役。
- 在共同计划中记录旧输出、相关证据及其中义务的处置方式。将完整旧内容作为迁移证据，与常规蓝图输入一并提供给每个受影响的 writer；仅有当前蓝图请求并不包含已移除的蓝图。将有效的项目专有约束、例外和必需加载触发条件保留在新 Rule 或已有的可达所有者中。删除重复的共享指引，将执行流程留给其所属 Skills。保留政策的适用条件；文件变短不能证明义务已得到保留。
- 保留独立所有的 Rules、专项 `rule-*` Skills、脚本、支持文件和 ADR。文件名类似待退役输出，不构成删除授权。如果 `.agents/rules/constraints.md` 已存在，应在替换前通过现有冲突处理和编写路径协调其所有权与完整内容。必需修改超出冻结生成请求时，须在登记前由其所有者完成已接受的修正。
- 对照最终集合协调受影响的链接和加载路径。在本迁移的最终映射链接检查中，将最终集合未保留的每个已记录旧输出作为 `GENERATED` 下不存在的 `--context-path` 加入；如果路径已包含在冻结 Candidate 路径的并集中，则无需重复加入。这样可防止链接因解析到实际目标中仍存在、但即将删除的文件而误通过；这不授予 writer 修改该文件的权限。由完整 setup 仅退役其已记录输出，并更新生成的索引和适配文件。在编写和验证期间保留旧文件可供读取；不要手动删除它们，只为使新目录看起来已收敛。

保留项目的维护模式、来源绑定和启动偏好。在仓库模式下，通过现有维护和 setup 路径使用选定配置来源及业务项目证据。合并不引入独立同步机制。

OpenWiki 可以提供可选导航和解释，但须向所属来源核实。生成 Wiki 是独立任务；本迁移既不要求已有 Wiki，也不把操作性政策或已接受决策移入生成的 Wiki 正文。

在同一次完整 setup 中应用较早选定的迁移，将仍适用的要求保留在当前所有者处。历史上对三份退役 Rules 的引用不要求重新创建这些文件。重复 setup 时，如果含义和证据仍然可靠，则保留完整当前内容。

完成迁移要求新 Rule 和两个执行型 Skills 满足其 writer 验收要求，每个退役输出的处置及受影响引用都已解决，并且独立项目内容得到保留。成功的完整 `finish` 在配置收敛、CodeGraph 就绪和会话清理完成后记录 `setupVersion`；仅完成编写或 Rule 索引同步不代表完成本迁移。
