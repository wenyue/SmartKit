# 设置项目 Agents

先确定用户请求的结果：完整 setup、从配置仓库恢复，还是有限范围的本地同步。每条路径负责的效果和完成条件各不相同。

迁移检查要求配置工作时，完整 Setup 会重新评估每份已声明蓝图和每个项目自定义 Agent，包括指纹未变化的情况，并为目标准备 CodeGraph。完整 Setup 也会复用仓库已有的 OpenWiki，或生成第一版。恢复会将已接受备份的原始字节复制到当前项目，并检查本机前置条件。

## 1. 选择请求的操作

将本目录解析为 `<skill-root>`，将相邻的维护入口 `<skill-root>/../maintain-project-config/scripts/maintain.py` 解析为 `<maintain>`，将业务项目解析为 `<target-root>`。执行选定操作前，阅读 [所有权](references/ownership.md)，确定权威输入和替换边界。目录清单和 schema 定义支持的输入；脚本验证并应用这些输入。Setup 选择操作、明确项目决策、协调编写者，并检查最终配置能否作为一个整体正常工作。

用户已指明操作时，直接遵循：

| 请求的工作 | 执行路径 | 选择这条路径的原因 |
| --- | --- | --- |
| 初始化、升级或迁移项目配置 | 第 2 步的迁移检查，随后进入第 9 步的 OpenWiki 流程 | 初始化、缺少成功基线或存在适用迁移时，需要运行配置会话。OpenWiki 步骤也可单独续跑。 |
| 从配置仓库更新或恢复本地配置 | 下文的恢复分支 | 请求需要将已有备份应用到此项目。 |
| 仅同步本地 Rule/Skill 发现及已声明的 Agent/MCP 映射 | 本地同步 | 请求只需根据已确立的本地输入进行渲染。 |
| 仅更新 `AGENTS.md` Rule 索引 | “本地同步”中范围更窄的 Rule 索引分支 | 只需更新生成的 Rule 列表。 |

保留对话中已经选定的操作和声明的范围限制。只有请求尚未确定操作时，才请用户选择。

### 用户尚未选择操作时

先确定本地状态，再推荐操作。阅读 [项目配置维护](../maintain-project-config/references/maintenance.md)，了解绑定、快照和本地同步记录证据，然后在获取来源或改变项目输入前运行以下只读检查：

```text
python "<skill-root>/scripts/workflow.py" inspect --help
python "<skill-root>/scripts/workflow.py" inspect --target "<target-root>"
python "<maintain>" inspect --target "<target-root>"
```

结合检查结果、已有受管理内容，以及必要时查看的 `.agents/config.json`、`.agents/smartkit.lock.json` 和 `.agents/project-config-sync.json`，回答两个相互独立的问题：

1. **本地受管理配置是否可用？** 新 checkout 也可能已有可用配置。checkout 的新旧、复制来的 setup 记录和运行时就绪状态，都不能回答这个问题。无法确定是否可用时，只查明分类所需的事实。
2. **备份来源是否已确立？** 检查绑定是否具有匹配的本地同步记录，证明曾按维护契约成功应用配置。缺少该记录的复制绑定只是一项需由用户确认的来源提议；它不会让原本可用的本地配置变得不可用。

仅有 lock 文件或复制来的 `setupVersion`，不能证明本 checkout 已成功完成 setup。同样，仅凭 `automatic: false` 不能确定是否存在成功同步记录。来源证据不可用意味着来源仍然未知；报告缺口，仅将依赖来源的决策保留为待处理。向用户获取缺失的来源信息，不从业务远端猜测，也不扫描已知仓库或其他 checkout。

根据这些答案，使用用户的语言展示适用的选择：

| 情况 | 提供的选择 | 建议及理由 |
| --- | --- | --- |
| 本地受管理配置可用，包括新 checkout 中的可用配置 | A. 检查必要的项目迁移，并在需要时完成首版 OpenWiki。配置仓库绑定已确立，或用户确认其来源时，还提供 B. 从配置仓库更新或恢复。 | 推荐 A。由迁移检查决定是否需要配置工作。保留已有维护选择。复制来的绑定须先确认，才能将恢复视为已可执行。 |
| 本地受管理配置不存在或已确认不可用，且已确认的来源具有现存备份条目 | A. 从配置仓库更新或恢复。B. 初始化配置。 | 推荐 A：用户已有配置可供复用。初始化仍可选择，并按“所有权”保留现有内容。 |
| 本地受管理配置不存在或已确认不可用，且没有已知备份，也没有尚未解决的来源证据问题 | A. 初始化配置。B. 我已有配置备份。 | 推荐 A。选择 B 会开始确认来源，并不表示恢复已可直接执行。 |

请用户选择前，先说明操作效果。完整 Setup 涵盖配置、本地 CodeGraph 和首版 OpenWiki 生成。恢复的方向是 **配置仓库 → 当前项目** ，可能在已接受快照的范围内新增、覆盖或删除本地文件。将本地修改保存回该仓库属于独立的采纳／发布操作。对于已知来源，展示已取得的变更路径，并说明是否来自本地快照。只有更新来源后，才能核实远端的最新内容。

等待用户选择操作，再继续对应流程，不重复询问同一个问题。这项选择确定要做什么；需要时，来源确认、接受实际差异、维护模式和启动同步仍需分别决定。推荐某项操作并不替用户作出这些决定。

检查失败仅阻止依赖缺失证据的决策。报告这些缺口；恢复不要求进入完整 setup、Matt 初始化或 CodeGraph 准备。会话 hook 不发现缺失配置，也不询问是否恢复；配置相关启动处理仅服务于已明确启用同步、且有效的既有 checkout 绑定。其他就绪检查保留各自的所有者。

## 从配置仓库更新或恢复本地配置

此分支既用于恢复丢失或已改变的本地配置，也用于应用配置仓库中的变更，适用于新 checkout 和已配置的项目。阅读 [项目配置维护](../maintain-project-config/references/maintenance.md)，了解绑定、备份范围、恢复、Git 排除和失败恢复。直接使用其受支持命令，不调用仅限用户调用的维护 Skill。此路径不需要完整会话预检、Matt 上下文、迁移、自定义 Agent 重新评估或生成内容编写。

1. **确定要使用的备份。** 复用第 1 步中仍然有效的本地检查结果，并检查选定 checkout：

   ```text
   python "<maintain>" inspect --target "<target-root>"
   python "<maintain>" bind --help
   ```

   绑定已确立且具有匹配的本地成功同步记录时，复用其仓库地址、分支和条目。只有复制来的绑定时，请用户确认这项来源提议。没有绑定时，向用户获取缺失的值。仅询问缺失信息、来源确认或用户请求的来源变更；绝不从业务远端推断来源，也不扫描已知仓库。

   绑定前，核验条目存在且确实是预期备份。缺少条目时，恢复保持未完成；创建新备份属于另一项操作。仅在需要时，使用维护参考中的仓库 `bind` 路径，并保留已有的来源和目标工作。复制来的绑定本身既不授予恢复权限，也不授予自动同步权限。

2. **展示应用该备份会改变什么。** 更新已绑定来源，再检查实际效果：

   ```text
   python "<maintain>" update --target "<target-root>"
   python "<maintain>" inspect --target "<target-root>"
   ```

   认证、拉取或更新失败时停止应用。保留已有状态并报告原因。成功更新后，展示选定完整文件和目录的差异，包括新增、覆盖和删除。

   存在差异时，暂停整次同步，提供 **A. 保留本地** 或 **B. 使用配置仓库** 。每次应用存在差异时都需作出这项选择，包括仅配置仓库发生变化的情况。选择 A 会跳过并结束本次恢复，保留目标内容和原有同步记录，并将依赖配置收敛的工作保留为待处理。B 应用完整且已审阅的恢复内容，通过 `--accept-existing` 传入精确检查指纹。等待选择期间，不得应用任何部分内容。来源和目标已经一致时，无需接受差异的令牌。

   说明保留本地并不会将这些文件保存回仓库。要把有意进行的目标编辑保留到仓库中，必须另行接受维护所有者的采纳路径。检查后任一侧发生变化时，展示新的差异，并在应用前取得新的选择；先前的选择针对的是不同内容。

3. **单独设置启动偏好并应用。** 未记录偏好时，提供 A. 开启启动自动同步或 B. 关闭，默认关闭。除非用户要求改变，否则保留已记录的偏好。说明维护参考规定的启动行为：更新并检查，自动恢复已确认仅配置仓库发生的更新，询问是否上传仅本地发生的改动，并在双方都变或方向不明时取得用户选择。接受上传即包含其范围内的提交和正常推送；开启自动同步本身不授予上传权限。

   按已记录或新接受的偏好应用；只要接受了差异，就添加 `--accept-existing "<inspect-fingerprint>"`：

   ```text
   python "<maintain>" apply --help
   python "<maintain>" apply --target "<target-root>" --auto-sync off
   python "<maintain>" inspect --target "<target-root>"
   ```

   `--auto-sync` 使用已记录或新接受的值。通过共享参考中的只读 Git 检查，核验来源与目标一致、目标本地同步记录和适用的 Git 排除。结果应是所恢复快照的原始字节。复制来的 `setupVersion` 或所有权记录，既不能证明本 checkout 已成功完成完整 setup，也不能证明运行时已就绪。

4. **检查本机能否使用恢复后的配置。** 使用各自所有者支持的只读检查，核验本地工具、凭据和服务。报告缺失或无法核验的前置条件，不在恢复过程中安装工具、启动服务或重写快照。

   报告来源、恢复和保留的路径、同步偏好、排除规则、实际前置条件结果，以及任何失败或恢复证据。区分已恢复的内容和本地就绪状态，并明确说明未执行完整 setup。恢复不生成配置、不记录新的成功 setup 版本，也不提交或发布来源变更。用户请求的初始化或升级走独立的完整 setup 流程。

## 2. 确定项目状态及其维护模式

选定的初始化、升级或迁移路径，从这里的只读迁移检查开始。阅读 [完整会话协议](references/session-protocol.md)，了解效果权限、Matt 上下文、SmartKit 来源选择和恢复；阅读 [项目迁移](references/migrations.md)，了解基线和发布义务；阅读 [项目配置维护](../maintain-project-config/references/maintenance.md)，了解配置来源绑定、私有仓库访问、应用、发布和 Wiki 维护。Setup 使用维护参考、受支持命令和配置引擎，不调用这个仅限用户调用的 Skill。

先运行 setup 检查。复用操作选择阶段仍然有效的结果，并在输入改变后刷新受影响的检查结果。命令帮助说明报告的检查和退出码：

```text
python "<skill-root>/scripts/workflow.py" inspect --help
python "<skill-root>/scripts/workflow.py" inspect --target "<target-root>"
```

检查报告 `skipped: true` 时，说明当前无需配置迁移，然后进入 [第 9 步](#9-complete-openwiki-and-hand-off)。如果证据表明配置发布仍待完成，先按第 8 步恢复发布。保留已记录的 `setupVersion`，沿用现有配置。

迁移检查要求完整 setup 时，再取得维护检查结果：

```text
python "<maintain>" inspect --target "<target-root>"
```

结合检查结果，以及通过项目文档约定取得的完整项目配置、所有权、既有生成内容和决策记录进行判断。在依赖某项前置条件的步骤开始前，解决该前置条件的错误。对于完整运行，setup 检查退出码为 0 时，`pending_assessment` 仍须由 Setup 处理，不代表评估已完成。先确定维护来源，再按下文流程在本次调用内补齐缺失的 Matt 上下文。

如果备份选择了 `openwiki/`，而进行中的 OpenWiki 队列阻止检查或应用备份，保留队列，并暂缓涉及该备份的配置工作，直到 Wiki 所有者处理完毕。报告受阻的操作，备份可以协调后，再从本步骤恢复配置工作。

### 选择在哪里维护配置 <a id="choose-where-configuration-will-be-maintained"></a>

首次 setup 和升级都需要这项决策。检查报告 `selection_required` 时，使用用户的语言询问一次，同时呈现全部三种选择。否则保留已记录的模式、仓库、分支和条目。已有 `local` 表示项目共享；仅缺少维护声明不能说明这是新项目。

| 选择 | 操作效果 | 选择理由 |
| --- | --- | --- |
| A. 项目共享（`local`） | 将权威配置保留在业务项目中，随其仓库进行版本管理。 | 配置应与共享项目放在一起。 |
| B. 仅本机（`local-only`） | 将权威配置保留在业务项目中，并通过本地规则排除在业务 Git 之外。不需要 GitHub 来源。 | 配置应只保留在本机。 |
| C. 独立配置仓库（`repository`） | 在个人私有 GitHub 仓库中维护配置，并通过本地规则将目标配置排除在业务 Git 之外。 | 配置需要独立仓库，与业务项目历史分开。 |

通过维护命令的 `bind` 路径记录新接受的选择。只有用户要求时，才能切换已记录的模式或条目，并须先比较、保留旧来源和目标中的工作。Git 排除和已跟踪文件遵循维护参考：选择模式本身不会取消对现有文件的跟踪。

对于 C，说明本地配置成功完成后，会按确切范围提交配置来源并正常推送。用户要求仅保留本地结果时，保留在本地。共享发布契约约束此结果及第 9 步中适用的 Wiki 发布。

### 确定来源并妥善处理现有工作

首次 setup 时，先识别现有项目指令、个人配置和独立所有者，再决定 setup 将管理哪些内容。升级时，确定上次成功的 setup 版本，收集每项适用迁移，不猜测缺失历史。已初始化但没有成功版本的项目，保留其所有权记录和内容，由本次完整 setup 建立基线。

两种本地模式都使用项目的权威输入。仓库模式下，确定个人仓库身份、分支和项目条目。连接现有私有仓库；仅在用户指定所有者和名称后，才能创建仓库。不同项目可以使用同一仓库中的不同条目。只导入已识别且已接受的现有个人文件；保留业务项目中已跟踪的内容和独立所有者的配置。在另一台机器上连接现有条目时，首次应用前必须与当前目标比较。

编辑持久保留的仓库来源前，先更新它。如果绑定或先前维护已刷新来源，并产生了已接受的待处理改动，就核验并保留证据，基于这些改动继续。再次运行要求干净检出的更新，会打断这些已接受的工作。结合业务项目和选定源条目评估迁移。

刷新备份后，用 `reconcile --adopt-local` 为已核实的本地更新生成保存计划。Setup 的授权范围包含这些差异文件的完整内容时，审查内容，保留已接受的 `planned` JSON，再通过 `--accept-plan` 执行。将返回的 `source_changes` 纳入第 8 步。

```text
python "<maintain>" reconcile --target "<target-root>" --adopt-local
python "<maintain>" reconcile --target "<target-root>" --adopt-local --accept-plan "<plan-fingerprint>"
```

返回 `needs-choice` 时，通过维护参考取得用户对整次同步的选择。`source-updated` 表示已确认仅配置仓库发生更新，但自动恢复权限仅适用于已启用的启动同步；完整 setup 仍需要用户接受有差异的应用。选择保留本地且备份仍有差异时，依赖同步结果的完整 setup 保持待处理。仓库模式下，在所选来源条目中修正配置，编辑后重新检查。在冻结会话前应用已接受的结果。有差异的恢复使用当前检查指纹。

### 单独选择启动自动同步

只有仓库模式有这项偏好。未记录偏好时，提供 **A. 开启** 或 **B. 关闭** ，默认关闭。说明维护参考规定的启动行为：已确认仅配置仓库发生的更新会自动恢复，仅本地改动会询问上传还是暂不同步，双方都变或方向不明时需要用户选择。接受上传即包含其范围内的提交和正常推送；启动偏好本身不允许上传。

刷新来源、检查并解决差异后，通过维护命令的 `apply --auto-sync on|off` 路径，记录新偏好或有意改变的偏好。常规 setup 和升级保留已有偏好；仅在建立或有意改变偏好时使用显式标志。启动同步除需明确开启外，还要求有效的既有 checkout 绑定及匹配的本地成功同步记录。

### 补齐缺失的 Matt 上下文

维护选择、来源和初始冲突确定，且已接受的源改动已应用后，重新运行 setup 检查，读取当前的 `matt` 结果：

| 检查结果 | 行动 | 原因 |
| --- | --- | --- |
| 上下文已存在 | 保留并继续。 | 已满足这项前置条件。 |
| 上下文不完整 | 完整阅读并遵循 `<skill-root>/../setup-matt-pocock-skills/references/project-context.md` 中的共享参考，在本次调用内初始化或补齐。 | 完整 setup 需要先具备该项目上下文，才能冻结请求。 |
| 参考文档或必需资源不可用、重大选择未解决，或必需写入被拒绝或失败 | 报告缺口，将依赖它的完整 setup 保留为未完成；有帮助时继续独立检查。 | 尚未满足前置条件。 |

直接使用参考文档，不调用仅限用户调用的 Matt Skill。复用已接受的项目决策，保留现有内容，并按该参考的要求，为新增或修改的写入取得草稿确认。提供业务目标用于探索，并提供权威输出路径用于写入：本地模式使用项目的权威输入，仓库模式使用选定的源副本。同时告知参考文档必须配置 triage：完整 setup 依赖 SmartKit 捆绑的 `triage` Skill，因此 `triage` Skill 不可用即表示插件分发不完整；按此报告，并让完整 setup 保持未完成。按维护契约解决任何仓库备份范围扩展，再通过其受保护的路径应用已接受的改动。补齐 Matt 上下文不会扩大备份或替换权限。

应用后重新检查；`matt.present` 为真后，在同一次调用中继续。其他检查结果保留各自的就绪要求。恢复、本地同步和仅更新 Rule 索引的操作不进入这项前置流程。

### 为完整运行准备最终输入

按照“所有权”指明的 schema 协调配置，保留无关工作。编辑选定的权威输入，并在 `start` 前应用已接受的仓库源改动。将已接受的初始导入、准备阶段的源改动及其来源证据带入最终发布。尚无首次提交的分支应包含已接受的完整导入，而不只是后续生成的差异。

上述项目配置来源与 SmartKit 实现来源是两回事。预检迁移来自已加载插件；第 4 步确认会话选定的 SmartKit 来源。项目状态、来源选择、输入决策、迁移要求和前置条件缺口均已明确后，继续执行。

## 3. 发现并协调每个项目自定义 Agent

使用预检清单；项目输入改变后刷新：

```text
python "<skill-root>/scripts/adopt_project_agents.py" inspect --target "<target-root>"
```

自动发现覆盖四个受支持的原生 Agent 目录，以及项目 `.codex/config.toml` 中角色的 `config_file` 引用，后者相对于声明它的配置文件解析。清单对匹配的发现去重，报告身份冲突、不安全路径和不可用文件；绝不读取目标之外的内容。

未使用独立配置文件的 Codex 角色列在 `role_declarations` 中：评估其声明和继承设置，无需将其转换为使用独立配置文件的形式。显式无效引用仍算问题。原生角色语义见 [Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。

手动检查其他已启用的宿主发现机制。用户配置和不受支持的布局不在自动覆盖范围内；不受支持的布局需要由宿主所有者修正，或进行保留源内容的位置调整。

读取每个自定义 Agent 的完整提示词和配置，包括未声明的 Agents；按照“所有权”区分已记录的插件默认 Agents。根据职责和引用匹配身份，保留工具、权限、沙箱边界、宿主元数据和特意继承的设置。

每次完整运行，都依据当前官方提供方、宿主资料及可取得的模型证据，评估每个 Agent 的模型和思考设置。仅有新版本发布不要求迁移。按以下条件决定保留设置、选择后继模型，还是询问用户：

| 情况 | 行动或选择 | 原因 |
| --- | --- | --- |
| 后继模型合适，已核验可用，且适合同一职责及成本／延迟档位 | 若不改变项目的明确选择，则选择它并采用兼容的思考设置。 | Agent 应保留其职责，以及成本与延迟方面的取舍。 |
| 拟议变更跨越模型档位、显著增加成本，或改变项目的明确选择 | 说明各方案及影响，改变前先询问用户。 | 这会改变一项需要项目所有者决定的事项。 |
| 无法核验可用性 | 保留现有值，报告评估未完成，并继续独立工作。 | 缺少证据不能成为替换设置的理由。 |
| 证据表明模型不可用 | 暂停该 Agent，直到确定受支持的选择。 | 已知不可用的模型不能算作正常工作的 Agent。 |

需要保留完整原生文档时，使用“所有权”中的 `native_source` 路径。清单中标有 `requires_relocation` 的条目需要先进行明确的、保留源内容的位置调整，再纳管：处理实际生效的宿主引用，并确保提示词和配置的相对引用在安装位置仍然有效。仅复制文件不会让宿主改用新位置。

首次纳管时，根据清单捕获的摘要准备完整最终原生内容和清单文件。说明模型变更及其他行为如何保留，然后在任何维护模式下使用受保护的导入：

```text
python "<skill-root>/scripts/adopt_project_agents.py" apply --help
python "<skill-root>/scripts/adopt_project_agents.py" apply --target "<target-root>" --manifest "<adoption-plan.json>"
```

在仓库模式下，受保护的导入先将已接受的来源和配置变更保存到选定源条目，再应用既有的受保护目标事务，并记录已应用来源。清单、摘要和所有权保护仍然必需。如果该事务失败，保留已保存的源工作，单独报告目标恢复情况。

对于已管理的适配文件，编辑其选定的权威源；完整 setup 在现有摘要保护下渲染。转换结构化声明前，解决源文件和设置的所有权。该工具不选择模型，也不证明语义保留。

发生冲突时，列出路径、字段和值、各个选项的影响及需要作出的决定。保留冲突输入，继续独立检查。只有每个自定义 Agent 都有映射并得到交代、报告的问题均已解决，且模型变更、保留和未完成验证已清楚区分，才能进入冻结。遗漏 Agent 或存在未解决冲突都不算完成。

## 4. 准备 CodeGraph 并启动一个冻结会话

目标、当前宿主和输入决策确定后，按照协议确定 CodeGraph 效果权限，并在冻结前准备运行时：

```text
python "<skill-root>/scripts/workflow.py" setup-codegraph --target "<target-root>" --harness "<active-harness>" --approved
python "<skill-root>/scripts/workflow.py" start --target "<target-root>"
```

只有准备操作返回退出码 0、`phase: setup-codegraph` 和 `ready: true` 后，才运行 `start`。保留 `start` 返回的会话、请求及来源、版本和迁移信息。从该来源读取选定的迁移指南；对照已接受的项目与 Agent 决策，验证完整蓝图请求。新发现的输入修正需求遵循协议的取消并重启规则。

只有运行时就绪经过验证、完整请求有效，且该来源要求的前置条件均已解决，才能继续。

## 5. 规划完整生成集合

阅读 [生成编写](references/generated-authoring.md)。从冻结来源读取每份请求的蓝图及其更新重点，同时读取完整既有内容和合格项目证据。在生成及保留的 Rules、相关 Skills 和适用全局策略之间，规划职责、覆盖和加载。

对每个请求，指出哪些仍有效、哪些必须改变，以及原因。保留项目义务和影响结果的例外；修正过时事实和实际重复。指纹变化和追求新措辞都不能作为重写理由。每个请求都有依据明确的方向、证据及在整个集合计划中的位置后，继续执行。

## 6. 取得并协调完整编写结果

将已确定的共同计划保存到私有会话中、`GENERATED` 之外，包含合格证据引用和所有者依赖状态。使用当前有效会话准备输入：

```text
python "<skill-root>/scripts/workflow.py" writer-inputs --help
python "<skill-root>/scripts/workflow.py" writer-inputs --session "<SESSION>" --plan "<SESSION>/common-plan.md"
```

按照“生成编写”，为每个请求的一个 Candidate 调用固定来源的公共 writer，并协调组合结果。输入包提供证据，不是语义交接结果。只有每个请求，包括未变化工件及其支持输出，都取得各自最终的 `COMPLETE`，且整个集合符合计划，才能继续。修正、编写受阻和依赖遵循该引用文档中的登记与取消边界。

## 7. 登记并完成

每份协调后的交接结果只登记一次，列出完整输出。命令帮助提供路径语法：

```text
python "<skill-root>/scripts/workflow.py" register --help
python "<skill-root>/scripts/workflow.py" register --session "<SESSION>" --request-id "<ID>" --output "<PATH>"
python "<skill-root>/scripts/workflow.py" finish --session "<SESSION>"
```

首次尝试 `finish` 前，确认 CodeGraph 就绪；若守护进程因空闲退出，遵循协议的运行时刷新分支。在仓库模式下，finish 先将已接受的生成项目源保存到条目，再应用常规目标计划；任一部分失败时，都要保留来源和目标两侧的证据。只有取得协议规定的成功本地 finish 结果，包括清理和最终 setup 版本记录，才能继续发布。finish 失败会阻止本次操作的发布，并须遵循原始尝试的恢复路径。

## 8. 发布配置结果

本地结束流程成功后，仓库模式按经过验证的确切范围发布。已接受范围、必需检查、发布例外、常规推送验证和保留提交的恢复均遵循维护参考。两种本地维护模式都没有配置仓库推送。直接使用受支持命令：

```text
python "<maintain>" publish --help
python "<maintain>" publish --target "<target-root>" --path "projects/<entry>/manifest.json" --path "projects/<entry>/files/.agents/rules/example.md" --message "Set up project configuration"
```

将示例路径替换为本次 Setup 已接受并保留的确切来源文件范围，每个文件使用一个 `--path`。对于已验证的保留提交，改用命令的 `--commit` 路径和共享恢复契约。核实配置发布成功或确认适用的发布例外后，进入第 9 步。发布失败时，报告本地配置已成功完成、远端同步仍待完成，并保留版本、来源范围和保留的提交以便恢复。

## 9. 完成 OpenWiki 并交付 <a id="9-complete-openwiki-and-hand-off"></a>

将 Git 顶层绝对路径作为 `<wiki-root>`。使用 `git -C "<wiki-root>" rev-parse --absolute-git-dir` 找到当前工作树的 Git 目录，将 Setup 恢复记录 `smartkit-setup-openwiki` 保存在那里。如果 Git 元数据受保护，改用系统临时目录下私有目录 `smartkit-setup-openwiki-<digest>` 中的 `recovery`。`<digest>` 是规范化 Git 目录绝对路径的 SHA-256 值，路径使用 UTF-8 编码且末尾无换行。检查两个位置，确认备用目录仅供当前用户访问。同一次尝试继续使用已核实的位置，保留有冲突的记录以便处理。

| 本地证据 | 操作 |
| --- | --- |
| 匹配的 Setup 恢复记录 | 先完成待处理的普通配置工作。续跑记录中的首次运行，或在已核实英文基线完成时继续备份交接。 |
| 已完成且可用的 Wiki 基线 | 复用 Wiki，并保留任何独立更新。 |
| 缺少 Wiki，或有归属明确且尚未完成的首次运行 | 在当前工作树完成首版 Wiki。 |
| 归属不清、独立运行的 Wiki 不可用，或恢复记录不匹配 | 保留现有产物并报告待处理工作。 |

结合实际页面和完成证据判断基线。OpenWiki 在 `openwiki/.last-update.json` 中记录 `status: complete`。活动的 `openwiki/.run.json` 保留 `previousLastUpdate`。独立更新中断时，只有仍能确认先前已经完成，才复用现有页面。

核对恢复记录对应的工作树、已接受的项目绑定或绑定变更，以及获准操作。复用 Wiki 或继续生成前，先根据保留的来源证据处理普通配置。如果尚未发起生成，重新检查是否已有可用基线，若有则复用。根据记录中的运行 ID 核对活动队列。如果发起生成时发生中断，则核对记录中的调用及调用前的队列状态。运行已经完成时，先用 `openwiki/.page-manifest.json` 验证页面版本和运行归属，再继续记录中的交接。

### 准备新运行

Wiki 沿用所选项目的维护绑定。确认 Git 根目录写入已获授权，再按维护参考中的 Wiki 命令操作，以 `<target-root>` 为项目目标。如果 Git 根目录已有独立绑定，则将受影响的 Wiki 写入留待该绑定的维护方处理。

在任何普通配置写入前，在恢复记录中写明已接受的绑定或绑定变更以及来源范围。如果迁移检查已跳过，且 Wiki 需要项目建立首次绑定，使用[第 2 步的项目维护选择](#choose-where-configuration-will-be-maintained)。绑定或导入前，记录选定输入的摘要及预期生成的文件。验证生成的清单和绑定，并保留实际摘要。完成适用的来源、采纳和启动偏好步骤，再带着现有 setup 基线回到此处。

对于已核实的本地更新，在恢复记录中保留已接受的 `reconcile --adopt-local` 计划，再用 `--accept-plan` 执行。生成 Wiki 或交付复用的 Wiki 之前，按维护契约应用并完成普通配置发布。保留的计划涵盖完整已接受范围时，使用 `publish --plan`。保留提交或已接受的仅本地结果证据，以便恢复。

刷新备份或复用该绑定仍有效的证据后，按继承的绑定执行 `wiki prepare`。项目根目录和 Wiki 根目录相同，且已批准的 Setup 范围包含已核实的本地更新时，用同一套可恢复采纳流程处理普通项目快照。其他有差异的恢复按维护参考处理。`wiki prepare` 返回 `ready` 后，如果准备过程改变了 Setup 输入，重新执行配置检查并确认受影响的条件已就绪。随后复用任何已恢复的可用 Wiki。

迁移已跳过且缺少本地配置完成证据时，按第 1 步确认项目配置可用，再运行 `python "<skill-root>/../../runtime/recommended-tools/codegraph_runtime.py" check --target "<target-root>"`。未就绪时，使用第 4 步的限定范围准备命令。

### 生成 Wiki 或完成交接

发起生成前，保存恢复记录。记录 Setup 目标、Wiki 根目录和工作树的 Git 目录、没有可用基线的证据、绑定和获准操作、调用前的队列状态、预定模式、语言和调用时间。调用随附的 [OpenWiki Skill](../../../../skills/openwiki/SKILL.md) 时，传入项目目标、Wiki 根目录、绑定、当前维护证据、仅本地结果的限制，以及恢复记录由 Setup 管理的信息。任何备份写入之前，OpenWiki 先把已验证的生成结果交还 Setup。OpenWiki 启动或续跑时，记录运行 ID。归属明确的活动队列应在其原工作树续跑，完成后再执行任何 Wiki 备份操作。如果已有操作者，等待其完成。验证完成状态已持久保存，且英文 Wiki 可用，必要时完成英文补充更新。

仓库模式下，在使用 `--accept-plan` 保存前，在恢复记录中保留 `wiki save` 的计划 JSON 和已接受的文件选择。重试时，用原计划确认哪些字节已保存，以及还有哪些同步记录或发布工作待完成。需要发布时，使用 `wiki publish --plan` 发布已验证的结果。保留需要续接的提交或已接受的仅本地结果例外。验证适用的交接完成，或完成记录中的普通配置工作并确认复用的 Wiki 可用后，再清除恢复记录。

前置条件缺失或操作失败时，报告待完成的工作，并保留已完成的配置、Wiki 状态和恢复记录。使用备用记录时，报告其路径。

评估全部直接项目 Rules 始终加载带来的上下文开销。只有大量策略依赖可识别的条件时，才建议采用原生 `rule-<domain>` Skills；不能仅凭大小就移动无条件策略。

按以下方面组织交接，方便检查：

| 方面 | 报告内容 |
| --- | --- |
| 来源与范围 | 维护模式和适用时的仓库条目、SmartKit 来源信息、之前和最终的 setup 版本、迁移、启用宿主、改动及保留路径，以及外部来源。 |
| 决策 | 自定义 Agent/模型决策，以及全部直接 Rules 的上下文评估。 |
| 验证与限制 | 实际配置检查、Git 排除与已跟踪路径、CodeGraph 安装/索引/运行时结果、未完成验证和恢复证据。 |
| OpenWiki | 复用的基线或完成的首版生成、适用的备份和远端结果，或待完成的步骤及恢复证据。 |

迁移检查要求的配置工作、适用的发布和 OpenWiki 步骤均完成后，报告完整 Setup 完成。结果为 `skipped: true` 时，报告已跳过配置迁移，并说明 Wiki 结果。列出已保存的确切来源范围及已执行工作的证据，包括已验证的远端结果或适用的发布例外。

## 本地同步

使用已加载插件中的 `<maintain>`，同步前阅读其 [项目配置维护](../maintain-project-config/references/maintenance.md) 参考。这些命令使用维护拥有的引擎；setup 工作流中的 `project-config`、`sync-project` 和 `sync-project-rules` 阶段仍是转发至同一所有者的入口。此路径不执行获取、生成、模型评估、蓝图/共享/外部更新或 CodeGraph 准备。“所有权”定义前置条件及保留边界；`clean` 只证明配置收敛。

1. 检查请求的范围：

   ```text
   python "<maintain>" sync-project --target "<target-root>" --check
   ```

   广泛同步需要已有的项目映射所有权，且外部 Skill 声明没有变化。报告完整 setup 依赖，不扩大请求。仅处理 Rule 索引时，使用 `sync-project-rules --check`；完整 setup 之前也可使用。

2. 省略 `--check`，应用获准范围。Rule 索引路径为：

   ```text
   python "<maintain>" sync-project-rules --target "<target-root>" --check
   python "<maintain>" sync-project-rules --target "<target-root>"
   ```

   应用和回滚期间保持独占访问。退出码 0 且 `check: clean` 表示收敛；退出码 1 且 `check: drift` 列出计划改动；退出码 2 表示拒绝或失败。重试前解决报告的原因。

3. 报告操作、结果、改动及保留路径，以及任何拒绝或恢复证据。两条本地路径都不推进 `setupVersion`。
