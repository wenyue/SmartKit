# 设置项目 Agents

更新项目的 Agent 配置，同时保留仍然有用的决定。完整 setup 检查全部声明的 Rules 和 Skills，以及每个项目自定义 Agent。每份蓝图决定哪些内容值得更新；有效内容可以逐字节保留。以下步骤将项目决策、冻结后的生成和机械应用分开处理。

## 1. 选择请求的操作

将本目录解析为 `<skill-root>`，将仓库解析为 `<target-root>`。在获取源文件或改变项目输入前，根据调用者意图选择操作：

| 意图 | 路径 |
| --- | --- |
| 首次 setup、未限定范围的 setup/更新，或必要的项目迁移 | 完整 setup：继续执行第 2 至第 8 步。 |
| 明确仅同步本地 Rule/Skill 发现及已声明的 Agent/MCP 映射 | 遵循下文“本地同步”。 |
| 明确仅处理 `AGENTS.md` 的 Rule 索引 | 遵循下文仅同步 Rule 索引的分支。 |

完整运行会检查每份当前蓝图，即使指纹一致；这不要求每个工件都换一套措辞。本地同步请求既不更新模型，也不授权完整 setup。按需查看受支持的命令接口：

```text
python "<skill-root>/scripts/workflow.py" --help
```

目标与操作符合已接受意图时，本步骤完成。对尚未解决的范围选择，先交给用户决定，再执行依赖这些选择的效果。

## 输入与所有权

执行任一路径前，阅读 [所有权](references/ownership.md)。项目输入和已记录所有权决定哪些文件与字段可以改变；位置相近或看起来过时不构成所有权。目录和 schema 负责支持的输入形式；脚本负责源选择、验证、事务和恢复； setup 负责项目证据、更新判断、编写协调及整体结果的一致性。源文件编写不授予提交、推送、发布、安装依赖或在目标仓库之外安装的权限。

## 2. 确定项目状态与迁移要求

阅读 [完整会话协议](references/session-protocol.md)，包括效果授权和 Matt 上下文前置条件。按照项目文档约定，读取项目配置、所有权记录、已有生成内容及项目决策记录。保留无关工作。识别上次成功的 `setupVersion`，或记录已初始化项目缺少基线这一事实。不能从已安装插件文件推断过去使用的版本。

阅读 [项目迁移](references/migrations.md)，了解建立基线和必要升级动作。强制迁移由发布声明决定，而非版本不一致。没有 setup 记录的项目不会被 hook 强制初始化；已初始化但没有成功版本记录的项目必须完成完整 setup。所有权证据格式错误时需要诊断，不能替换为空记录。跨过多个版本时，在一次运行中应用全部适用条目。

根据 `<skill-root>/../../setup-assets/catalog/project-config.schema.json` 准备项目自有输入。在 `start` 前解决重大选择和效果权限；通常的 setup 意图可能已经提供这些权限。选定源可能与已加载插件不同。第 4 步会在生成前确认该源的确切迁移要求和 schema。

已有状态、计划迁移和前置条件均已明确时，本步骤完成。缺少 Matt 上下文时结束本次调用：请求执行 `setup-matt-pocock-skills`，待其完成后重新调用 setup。

## 3. 发现并协调每个项目自定义 Agent

盘点已声明 Agents 和所有受支持宿主的原生 Agent 目录。同时检查宿主配置中的引用，包括非标准 Agent 位置。使用随附的只读盘点工具：

```text
python "<skill-root>/scripts/adopt_project_agents.py" inspect --target "<target-root>"
```

区分项目自定义 Agents 和已记录的插件默认 Agents。尚未登记的自定义 Agent 也必须纳入本次评估。读取完整提示词和配置，根据实际职责与引用匹配身份，不能只看文件名。保留工具、权限、沙箱边界、宿主特定元数据，以及为继承默认值而特意省略的设置。原生文档可以通过 schema 的 `native_source` 分支作为权威源，以保留结构化映射无法表达的设置。结构化映射仍使用共享提示词源。

每次完整运行都评估模型和思考设置，依据当前官方提供方与宿主资料，以及可取得的模型证据。选择当前可用、适合同一职责且成本与延迟定位相近的后继模型，并采用兼容的思考设置。跨模型档位、显著增加成本或改变项目明确选择前，先询问用户。无法验证可用性时保留现有值，报告评估未完成，并继续其他工作。证据表明当前模型不可用时，暂停受影响 Agent 的处理，直到确定受支持的选择。仅有新模型发布不构成强制项目迁移。

首次纳管时，根据盘点捕获的摘要准备完整最终原生内容和清单。说明改变的模型字段，并证明其余行为得到保留。冻结会话前，执行所属工具支持的导入：

```text
python "<skill-root>/scripts/adopt_project_agents.py" apply --help
python "<skill-root>/scripts/adopt_project_agents.py" apply --target "<target-root>" --manifest "<adoption-plan.json>"
```

该工具以原子方式导入权威原生源、记录声明，并对齐之前未管理的适配文件。它检查捕获的字节和独立所有权，不负责选择模型，也不证明语义等价。对于已管理的适配文件，只修改权威源；完整 setup 在现有摘要保护下进行渲染。确保原生相对引用在安装后的适配文件位置仍然有效。转换结构化声明时保留完整内容，并在导入前解决其源文件和设置的所有权。不能修改锁文件来绕过冲突。

职责、来源、权限或明确选择发生冲突时，列出双方文件路径、冲突字段和值、各项选择的影响，以及需要作出的决定。保留冲突输入。可以继续独立检查，但冲突未解决前不能宣告完整 setup 完成。不受支持的原生布局需要明确的、保留源内容的位置调整，或由宿主所有者修正；遗漏 Agent 不算成功盘点。

每个自定义 Agent 都有映射并得到交代，且模型变更、保留和未完成验证清楚区分时，本步骤完成。所有已接受的输入变更都在 `start` 前完成；之后的变更遵循协议的取消并重启规则。

## 4. 启动并确认一个冻结会话

```text
python "<skill-root>/scripts/workflow.py" start --target "<target-root>"
```

返回非零结果时停止。保留 `session`、`generated`、`request`、来源信息、之前和目标 setup 版本，以及选定的迁移条目。从该 `source_root` 读取每项选定指引。确认请求包含每份当前蓝图，且冻结输入符合已接受的项目与 Agent 决策。如果选定迁移还需要修改输入，先取消，进行获准修正，再重新启动。保持源和 setup 相关目标证据冻结；无关工作仍在会话边界之外。

只有完整请求有效且所有源特定迁移前置条件均已解决，本步骤才完成。源可用性、schema 拒绝和漂移按协议各自的停止与恢复路径处理。

## 5. 规划完整生成集合

阅读 [生成内容编写](references/generated-authoring.md)。从冻结源读取每份请求的不可变蓝图，以及既有目标内容和合格项目证据。遵循该蓝图的具体编写重点和更新偏好。工具清单与结构映射应跟随当前事实；稳定流程应保留仍然有效的决定。指纹变了或没变，都不能单独决定一句话是否需要重写。

在生成及保留的 Rules、相关 Skills 和适用全局策略之间，规划覆盖、职责和加载方式。对每个请求工件，指出哪些仍有效、哪些必须改变，以及支持该变化的证据。保留项目补充、义务和影响结果的例外。修正过时事实和实际重复；单纯追求新措辞不是重写理由。

每个请求都有有依据的更新方向、所需证据，以及在整个集合中的所有者和加载位置时，本步骤完成。冻结范围之外的依赖，按协议交给其所有者解决，不能悄悄扩大生成范围。

## 6. 取得并协调完整编写结果

按“生成内容编写”的规定，使用固定版本的公共编写流程及其同源依赖。每次调用只提供一个 Candidate、其蓝图、完整既有内容和共同计划。每个请求都需要独立的 `COMPLETE`，未变化的工件也不例外：编写者可以在 `GENERATED` 下返回经过验证的精确副本及其支持文件。

对照计划检查组合结果，查找遗漏义务、过时证据、所有者冲突、重复的操作性要求和失效加载路径。必要修正应取得新的编写交接结果。登记前完成协调；单项编写结果不能证明整个集合一致。

每个请求都有最终完整交接结果，且组合后的集合符合蓝图、没有丢失有效项目含义时，本步骤完成。缺少权限、编写受阻或修正超出范围时，按协议取消。

## 7. 登记并完成

每份最终交接结果只登记一次，包含所有支持文件输出路径，然后完成：

```text
python "<skill-root>/scripts/workflow.py" register --session "<SESSION>" --request-id "<ID>" --output "<PATH>"
python "<skill-root>/scripts/workflow.py" finish --session "<SESSION>"
```

每个支持文件重复一次 `--output`。保留完整请求集合；复制未变化工件也要提供完整输出。字节相同的内容可以收敛，而无需重写目标文件。 Finish 验证、应用并检查配置，移除私有会话，然后以原子方式将源发布版本记录为 `setupVersion`。应用、清理或版本提交失败都不算成功，也不建立新基线。遵循原始尝试的恢复分支；保留报告中剩余的目标或会话状态，不要重试残留会话。

只有退出码为 0，`phase: finish`、`check: clean`、报告的成功 setup 版本均正确，且会话清理完成，本步骤才算完成。本地同步绝不推进该版本。

## 8. 交付经过验证的结果

评估全部直接项目 Rules 始终加载带来的上下文开销。只有大量策略依赖可识别的条件时，才建议将其移至原生 `rule-<domain>` Skills；不能仅凭文件大小就移动无条件基线策略。

报告源模式、根目录、指纹和提交，源发布版本，之前和最终的 setup 版本，已应用迁移、启用宿主、改动与保留路径、自定义 Agent/模型决策和外部来源。包含实际 clean 检查状态、上下文评估、未完成的模型验证，以及恢复证据。将快照交给维护者审查和提交；配置收敛不能证明 MCP 运行时就绪。

用户无需重建会话过程，就能区分已应用改动、保留行为及剩余限制时，交付完成。

## 本地同步

先阅读“所有权”。本地操作使用包含已加载 Skill 的插件根目录，不获取源，也不执行生成、模型评估、蓝图更新或共享/外部升级。

1. **检查请求的变化。** 对于本地发现及已声明的 Agent/MCP 映射：

   ```text
   python "<skill-root>/scripts/workflow.py" sync-project --target "<target-root>" --check
   ```

   广泛同步需要已有的项目映射所有权记录。记录缺失或过旧、外部 Skill 声明改变时，需要完整 setup；报告这个依赖，不扩大请求。仅更新 Rule 索引时使用 `sync-project-rules --check`；完整 setup 之前也可以使用。

2. **应用获准范围。** 从选定命令中移除 `--check`。Rule 索引路径为：

   ```text
   python "<skill-root>/scripts/workflow.py" sync-project-rules --target "<target-root>" --check
   python "<skill-root>/scripts/workflow.py" sync-project-rules --target "<target-root>"
   ```

   Apply 保留受管 `AGENTS.md` 章节之外的字节，只移除已记录的映射。 Check 模式绝不写入。退出码 0 且 `check: clean` 表示收敛；退出码 1 且 `check: drift` 列出计划改动；退出码 2 表示拒绝或失败。应用和回滚期间保持独占访问，重试前解决报告中的所有权、输入格式或漂移原因。

3. **报告结果。** 给出操作、状态、改动路径、保留输入，以及确切拒绝或恢复证据。完成要求取得 clean 结果；任何本地路径都不更新成功的完整 setup 版本，也不证明运行时就绪。
