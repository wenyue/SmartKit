# 历史准备

发布、集成或明确选择压缩历史时，读取本契约。将工作绑定到一个已接受范围、不可变基线、源分支及 HEAD/树、完整的任务自有提交范围和目标边界。保留提交，除非用户明确要求压缩，或适用项目策略要求压缩。两种历史策略都不授权在收尾期间同步分叉或改变已接受内容。

## 确定已接受状态

必需检查必须已通过。通常，无阻碍的正式审查覆盖确切的已接受 HEAD/树。只有实施所有者的契约明确授权，且该所有者一并提供以下全部材料时，才可采用替代途径：原始审查报告及其不可变输入、每个发现的处置、有界且已授权的修复差异，以及对该差异的所有者验证和确切最终 HEAD/树上所有阻碍发现的闭合证明。

该替代途径是所有者验收，不是新的正式审查结论。保持原始报告和已审查身份完整，不要把它们重标为对修复后状态的审查。收尾消费任一受支持的证据途径，本身不开展正式审查。

证据缺失或无效、阻碍未解决，或已接受提交之外仍有任务工作时，按实施所有者的修复和审查限制交回该所有者。所选操作无法影响无关本地状态且可证明其保护时，该状态可以保留。

## 已交付

重写历史或再次交付前，先检查是否已经交付。权威目标必须已包含每项已接受效果。祖先关系足以证明确切已接受范围时，可以作为充分依据。否则，需要覆盖全部效果的无歧义等价变更证据，加上绑定确切目标 HEAD/树的已接受状态证据。从实施所有者消费该证明，或将当前目标交回该所有者验收。

空 diff、相似提交消息、追踪器状态、部分补丁、PR 或保留分支本身都不能确定该结果。已证明的 **Already Delivered** 避免重写历史、推送和集成；在历史和结果两个阶段记录权威目标身份及证明。

## 保留已接受提交

按冻结边界核对范围内每个提交。源 HEAD/树仍匹配已接受状态绑定时，该 HEAD 就是交付提交，历史无需修改即可得到证明。所选结果与已观察到的发布兼容时，已发布提交仍然适用。保留已接受结果和效果边界之外的本地状态。

## 仅压缩已授权范围

压缩要求范围完全属于任务、尚未发布且未被依赖，确切目标是其祖先，源在 `git status --porcelain=v1 -z` 下干净。确定提交权限和正常仓库 hook。在准备前探测 helper：

```text
python "<skill-root>/scripts/consolidate_worktree_history.py" --help
```

探测失败时，在历史效果发生前停止。在受影响工作树之外准备自有消息文件，并预留 `refs/smartkit/recovery/` 下唯一且预期不存在的引用，以及由其派生的 `<recovery-ref>-candidate` 引用。外部[操作回执](recovery.md#operation-receipt)记录确切的创建/保留/删除权限、预期值、消息字节和生命周期所有者。消息只创建一次，使用前验证。

```text
python "<skill-root>/scripts/consolidate_worktree_history.py" --repository "<source-worktree>" --target "<exact-target-oid>" --message-file "<external-message-file>" --recovery-ref "<new-recovery-ref>"
```

helper 将检查点保留在恢复引用下，并通过正常 hook 创建提交。其 Git 操作构成一次尝试。它检查新提交的唯一父提交是确切目标，且树等于已接受树；将其 JSON 与观察到的仓库状态重新核对。

成功后，独立证明源 HEAD 和分支、唯一父提交、相同树、干净检出和保留的恢复引用。通过相同树和未变的已接受 diff 延续验收证据，保留原始输入身份。重新运行结果依赖提交身份或 hook 的检查。hook 改变树时，验收绑定失效，将该状态交回实施所有者。

失败后，检查检出、分支、索引、工作文件和两个恢复引用。受保护的 helper 恢复可能已还原受控检出状态；恢复不安全时则保留部分状态。即使提交被 hook 拒绝，也可能已经创建恢复引用。为其所有者保留候选、消息和回执，并在继续前使用[效果恢复](recovery.md)。

## 将证明带入结果阶段

记录历史策略、基线和目标边界、已接受状态证据、交付 HEAD/树或 Already Delivered 证明，以及恢复项目。后续目标移动或结果失败不替换这份已证明记录。只有结果阶段的依赖仍匹配时才继续。否则，将观察交给实施或目标移动所有者，按上述证据契约同步并验收。新接受状态有自己的绑定；它不会改写先前证明。
