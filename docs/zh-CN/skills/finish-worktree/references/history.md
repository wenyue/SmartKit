# 历史准备

发布、整合，以及明确选择整理提交时，使用本引用。绑定已接受范围与不可变基点、来源分支和 HEAD/树、完整的任务归属
提交范围、目标边界、必需验证，以及没有阻塞问题的正式审查。实施工作流负责这些证据。缺少审查或已接受提交之外
仍有任务工作时，应在交付前交回该负责人；只有选定操作不会影响无关本地状态、且能够证明其受到保护时，才可将其保留。

默认保留提交。只有用户明确要求或适用项目规则要求时，才整理检查点提交。仅选择某个结果，并不意味着要求重写历史。
历史准备不能暗中同步分叉目标，也不能改变已审查内容。

## 已经交付

重写历史或交付前，检查权威目标是否已经包含每项已接受影响。祖先关系能够证明准确的已接受范围时，就足够了。
否则，应要求覆盖每项影响的明确等价改动证据，以及绑定到准确目标 HEAD/树的必需验证和无阻塞正式审查。使用实施
负责人提供的证明，或将当前目标交回该负责人。空 diff、相似提交消息、工作项状态或部分补丁都不能证明交付。

已经证实的**Already Delivered**结果可以避免不必要的重写、推送或整合。在历史和结果记录中保留其权威目标身份及
证据。仅有 PR 或保留分支不能提供这种证明。

## 保留提交

相对冻结边界枚举已接受范围，并解释每个提交。证明来源仍处于已经验证和审查的 HEAD 与树。该准确 HEAD 就是交付
提交；记录 `history_result: proven`，不修改历史。已发布提交在选定结果与已观察发布情况兼容时可以使用。
保留已接受结果及选定影响边界之外的本地状态。

## 整理检查点提交

要求来源按 `git status --porcelain=v1 -z` 判断为干净，整个范围归属任务、准确目标是其祖先，并有证据证明该范围
尚未发布且没有被依赖。确定提交权限和仓库正常 hook。准备前使用 `--help` 探测相应启动器。两个启动器都只按
`python3`、`python` 的顺序检查，选择 Python 3.10+；若都不满足，只报告一次要求并以退出码 2 结束，不产生历史影响。

在受影响工作树之外准备自有提交消息文件。在 `refs/smartkit/recovery/` 下预留一个预期不存在的唯一引用，及其派生的
`<recovery-ref>-candidate` 引用。在外部[操作记录](recovery.md)中记录准确创建、保留、删除权限、预期值、消息字节
及生命周期负责人。消息文件只创建一次，并在调用工具前验证。

在 POSIX 上调用：

```sh
sh "<skill-root>/scripts/consolidate_worktree_history.sh"   --repository <source-worktree> --target <exact-target-oid>   --message-file <external-message-file> --recovery-ref <new-recovery-ref>
```

在 PowerShell 上使用 `scripts/consolidate_worktree_history.ps1`，参数相同。工具通过正常提交运行 hook，将检查点
保留在恢复引用上，并检查新提交以目标为唯一父提交、已审查树保持不变。它内部的 Git 操作属于一次历史尝试。
其 JSON 是需要复核的证据，不是权威阶段结果。

成功后，独立证明新的来源 HEAD、分支、唯一父提交、相同树、干净检出目录及保留的恢复引用。将原审查绑定到相同的
结果树和未变的已接受 diff；重新运行有效性依赖提交身份或 hook 的检查。hook 改变树时，该绑定失效，应交回实施流程。

失败后，检查实际检出目录、分支、暂存区、工作文件及两个恢复引用。工具可以在保护条件成立时恢复受控检出状态；
否则保留部分状态。即使提交 hook 拒绝提交，已经创建的恢复引用也属于已发生影响。候选提交、消息和操作记录应保留到
负责人解决该尝试为止。遵循[恢复](recovery.md)，不要以原参数再次调用工具。

## 保留结果

以策略、基点和目标边界、已审查 HEAD/树、交付 HEAD/树或 Already Delivered 证明，以及恢复项，冻结
`history_result: proven`。后续目标移动或结果操作失败都不能替换它。仅当结果操作的依赖仍匹配时才继续；
否则将观察状态交回实施或目标移动负责人，同步并重新验证和审查。这会产生新的已接受状态，不会改写已经证实的历史记录。
