# 传回检出

公开的 `return-for-review` 路线在审查前或后，将已接受任务修改放入一个检出的工作文件。精确保留目标 HEAD 和完整索引，使原有已暂存内容仍保持已暂存。结果始终是非集成交接。

## 确定修改和接收状态

决定写入内容前，冻结三个不同输入：

| 输入 | 含义 |
| --- | --- |
| **B** | 衡量任务修改的不可变共同基线，以提交/树 OID 固定。 |
| **S** | 已接受任务结果，冻结为确切字节、不存在状态、类型和模式。 |
| **W** | 准备时目标的实际工作文件，包含已提交演进和本地修改。 |

S 可以包含可归属的已暂存、未暂存和未跟踪工作，无须创建提交或改变源索引。将这些层解析为已接受最终内容，并排除无关工作。所有权、B 或 S 不明确时，停止准备，将决定交回结果所有者，同时保留两侧状态。

只传输 **B → S** ，不要复制整个源检出。目标 HEAD 或索引版本不是 W，其当前 HEAD 也不能为了方便而替代共同 B。只有独立项目/调用者策略，或明确选择的历史操作要求正式审查时，才适用正式审查。

## 确定完整组合结果

从 B → S 推导每个受影响路径，包括受支持重命名的两端。捕获有界的路径和祖先证据，并在批次边界捕获完整目标 HEAD/索引证据。依赖仍匹配时，复用不可变 B 和已接受 S 的证据。因具体保护风险而检查无关路径；普通传输不要求反复读取全局状态或清点未跟踪/被忽略文件。

W 等于 B 时，输出就是 S。保留目标独有修改，相同编辑只纳入一次。对于重叠的普通文本，可用原生三方合并，以 B 为祖先、W 为本地、S 为传入；例如，对临时文件使用 `git merge-file -p`。文本合并无冲突，仍需要语义检查并验证组合行为。

目标写入前确定所有输出。冲突块、删除/修改情形、复杂重命名、二进制重叠、不受支持的类型或模式、不兼容行为以及含糊生成输出，都会停止此次准备。重新生成仍属于其确定性所有者，并需要已接受权限。

## 冻结机制能够保护的计划

对于已接纳的、现有目录内普通文件创建/更新/删除，读取[传输机制](transfer-mechanism.md)，并准备一个包含预期 W 和全部已接受输出的 helper 计划。W=B 时直接使用已接受 S 文件；存在重叠时，提供已准备的组合输出。helper 在应用前冻结完整计划及可读外部备份。主动准备这个批次，不要通过 Agent 调用逐文件驱动子进程。

Agent 负责任务归属、B/S/W 判断、语义和验证。helper 负责其较窄的可接受输入、能力检查及受保护写入。将不受支持情况交回实施所有者，或使用另一种已授权机制，证明同样的完整计划准备和保护，包括不存在状态、类型、模式、别名和符号链接祖先。能力拒绝不授权绕过其边界。准备失败会保持目标工作文件不变，但外部准备工件可能需要保留和说明。

## 带着保护证据应用 <a id="apply-with-preservation-evidence"></a>

协调写入者，使用入口、路径和退出保护及持久写入记录，只应用一次已准备批次。复用源、目标 HEAD/索引和输出证明，不要对每个子操作重复全仓库检查。依赖变化或漂移需要重新观察。部分写入、缺失响应和漂移，要求在继续前检查原回执并进行[部分传输恢复](transfer-mechanism.md#partial-file-transfer)。协作式并发和漂移检测不会让多文件写入变成原子操作，也不能排除任意并发写入者。

对组合目标运行相关的非修改验证。复用有效检查，刷新输入已变化的检查。格式化、修复或生成属于需要明确权限的独立效果。结合 helper 证明及具体外部依赖的有界证据来证明保护。如果完整应用后验证失败，保留可审阅的组合目标、源、备份及失败；不要通过回滚抹去该结果。

结果证明包括保护、必需验证、确切源/目标/备份位置，以及下一步审查或验收行动。保留源工作树、分支、快照、备份及必需恢复项目，直到用户接受传输。任何被委派的验收都必须可追溯到用户权限；拥有清理责任并不授予验收权限。接受之前，清理意味着保留。之后，删除仍遵循既有清理权限和生命周期条件。目标已存在相同修改，也不会让此次交接变成交付。
