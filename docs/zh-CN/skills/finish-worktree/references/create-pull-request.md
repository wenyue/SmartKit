# 创建拉取请求

通过仓库宿主接口发布一个确切的已接受提交，并建立其 PR。根据已接受范围和项目惯例确定常规标题、正文和草稿状态。此路线证明供审阅的交接；单有 PR 并不能证明权威交付。

## 绑定预期发布

确定远端仓库、基线分支及观察到的基线 OID、头引用和宿主状态。创建前按仓库、基线和头查找既有 PR。复用匹配的打开状态 PR，核对其实际头提交，并只做已授权的元数据更新。已关闭、已合并、不兼容或含糊的匹配需要继续处理决定。缺少创建响应不证明 PR 不存在。

消费[历史准备](history.md)及其已接受状态绑定。已接受提交之外的任务工作交回实施所有者，除非另有独立授权的后继范围。发布无法影响无关本地工作且已确定其保护时，可以保留其脏状态。

紧接发布前刷新绑定、远端基线和头。基线移动时遵循历史准备的结果保留边界。如果权威目标已包含该结果并有 **Already Delivered** 证明，报告该结果，不创建空 PR。如果确切 PR 已存在，复用它，不重复推送或创建。

## 发布并观察每项效果

以非强制推送将确切交付 OID 推到确切头引用。观察远端引用等于交付 OID 后，再创建 PR。推送和 PR 创建是[恢复回执](recovery.md)中的独立效果，因为前者可能成功而后者失败。

出现竞争、拒绝、超时或缺失响应后，检查服务端状态并解决原尝试，再决定是否重试。已证明推送成功而 PR 创建失败时，发布仍是已知效果；保留完成 PR 所需的源、引用、回执和恢复责任方。

要证明结果，将远端头和 PR 头绑定到交付 OID，并验证仓库、基线、头引用、打开状态、必需元数据及 URL。保留审阅和更新所需的项目及其所有者和释放条件。即使尚无法证明 PR 结果，失败报告也要保留已独立证明的发布。
