# 失败路径

调用方行为使失败通道或负责人不清楚，或部分副作用、补救行动使恢复方式不明显时，阅读本参考。

## 将调用方作为证据

对照被调用方的承诺与调用方实际作出的决策：

- 如果空的可选值表示记录缺失，读取失败后返回它，就会将失败变成缺失。
  确定恢复是否确实建立了承诺中的缺失状态，还是调用方仍需要接收失败结果。
- 如果调用方针对两种失败作出不同的有效决策，在共享边界定位稳定的区分。
  对于封闭的业务失败分类，检查是否覆盖每个契约内情况。对于开放协议，跟随陌生失败进入未知结果路径，
  检查其是否保留失败和有用原因，而非变成正常业务拒绝。所有调用方都以相同方式中止时，
  调查新增区分是否服务于任何契约。
- 对于返回错误的库，在提出本地报告前，跟随正常结果和失败返回值进入调用方。
  库的责任可能在忠实移交契约结果后结束；识别独立发起的操作接下来在何处承担最终结果责任。
- 对于同时报告和传播的处理者，跟随失败到最终报告者。确定前面的输出是在补充上下文，还是重复报告同一事件。
  相反，处理者消费失败时，检查它如何履行处理责任：全局观察者将不再接收该失败。
- 发起异步操作可能让发起者在必要工作完成前报告成功。确定承诺是否包含该工作完成，
  再检查完成链，或脱离调用链操作的生命周期与最终失败负责人。跟随取消和中断经过相同的状态及归属转换。
- 如果持有资源的工作失败，释放资源也失败，检查语言或生命周期机制的实际行为。
  确定最终负责人能否区分原始失败、清理失败及残留资源状态。清理失败替换原始原因，可能掩盖调用方仍须作出的决策。

这些是推理模式，不是根据语法作出的结论。依据当前契约确认每项含义，包括哪些生产检查执行契约，
以及哪些诊断能够经由目标原生失败机制保留下来。

## 根据部分副作用推理

识别会改变恢复决策的副作用：持久写入、远程修改、持有资源、已发送事件或可见状态。
判断重试安全前，检查完整重放路径，包括恢复和补偿。可复用的检查点需要证据证明其参数、状态、资源
和已完成副作用仍允许达成承诺结果。

例如，远端创建可能成功，而必要的本地刷新随后失败。重试整个操作可能重复创建远端对象。
已确立的幂等键可能使重放安全；否则，负责人可以仅重试刷新、补偿创建，或报告受支持的部分完成结果。
确定观察到的副作用和已接受契约支持哪种选择。没有受支持的选择时，将失败和残留远端状态交给最终负责人。

通过公共操作验证这个场景。创建加上必要刷新应完成承诺；创建失败后不应刷新；创建成功但刷新失败时，
应保留已创建的状态，而不宣称完全成功。对于仅刷新恢复，证明没有再次创建，并在选定边界停止。
对于补偿，检查删除成功和失败两种情况，保留刷新失败及残留远端对象。
创建后或补偿过程中可能取消或中断时，纳入相应的中止情况。这些检查来自操作承诺和副作用，不要求测试无关失败。

## 跟随反馈直到完成

定位负责反馈的边界，检查其受众能够理解和改变什么。对于移交处理责任的库或组件，
沿返回或失败契约追踪有用的诊断、影响和补救信息，直到调用方或既有反馈负责人。
根据实际访问权限、调用方和预期使用方式，而非模块或界面名称，确定能力和授权。
对于每项拟议行动，识别可行行动或受支持的升级处理途径，
以及受众需要理解的影响。尚未确立具备能力且获授权的角色时，将补救保持为未解决状态，并把缺失决定交回就绪判断步骤。

维护者可能需要路径和诊断证据来修复存储；普通用户可能只需要了解不可用的能力，以及受支持的登录或支持途径。
操作具有产品反馈时，对照结果状态检查该反馈，即使用户无法修复，也包括重要损失或不可用情况。
专业修复设计交给具备能力的负责人；让用户在运行时作出有限产品选择的提示，不能解决开发期缺失的数据契约。

从报告调用向前追溯失败状态，并向后跟随每项补救行动。对于重置行动，检查谁负责完成、成功时反馈如何改变，
以及失败或中途停止如何通过环境支持的渠道保持可观察。委托反馈后，行动状态和完成责任仍须明确。
单独检查诊断：有用的操作上下文、影响、处置情况及已有原因，应到达最终报告者，同时排除凭据和不必要的隐私数据。
互补的追踪信息与受众反馈可以和一次事件报告共存；根据项目严重程度策略，恢复成功仍可能值得调查。
