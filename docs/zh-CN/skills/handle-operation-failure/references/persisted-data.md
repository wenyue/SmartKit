# 持久化数据恢复

失败涉及持久化文件、序列化内容、模式或迁移状态时，阅读本参考。选择处置方式前，调查其含义和受支持的恢复方式。

## 明确数据契约

识别所有者、数据用途、恢复权限、可接受损失，以及已接受结果所要求的状态。
明确恢复承诺是否要求改变后续读取的行为，以及当前边界是否有权修改存储。根据相关问题收集证据：

- 对于派生数据或缓存，什么来源支持重建？重建期间或获准丢弃之后，缺失是否是有效状态？
- 对于访问凭据或本地状态，哪个角色或服务能够重新创建？在此之前，哪项能力仍不可用？
- 对于可采用默认值的状态，默认值是否有效？是否接受丢失被替换的选择或进度？
- 对于重要、用户创作、导入或仅有一份的数据，是否存在权威替代来源？
  什么依据授予具体损失的权限，并确立结果状态的有效性？这两个决定中任何一个未解决时，都保留原始字节。
- 对于模式或迁移元数据，其值如何控制其他记录的解释方式，以及必要迁移步骤的选择？

证据可以支持已接受的降级、重建、修复或获准丢弃。已接受契约允许不经精确重建就建立有效状态时，无需精确重建。
路径、格式或数据损坏的发现本身不构成损失授权。将未解决的重要决定交回流程的就绪判断步骤。

## 设计并检查恢复

定位失败阶段：读取字节、验证语法或含义，或执行修复。区分内容无效的证据与 I/O 失败的证据；
在理解内容的边界检查校验方式，不根据任意失败推断数据损坏。

例如，只读库的契约可能允许跳过损坏记录，并返回明确的降级结果。
检查结果是否向调用方保留了跳过记录的影响和有用诊断，以及在存储字节保持不变时，后续读取是否符合承诺。
履行这种契约无需修复持久化状态。

对于可写入的应用，假设所属解析器证明保存的登录状态结构无效，已接受的数据契约允许丢弃它，因为登录能够重建该状态，
并且恢复承诺之后的启动读取不再遇到该损坏。确认应用有权移除无效字节，并验证移除结果。
本次需要身份验证的操作仍报告该能力不可用。
检查结果中的未登录状态是否有效，以及下次读取是否不再遇到相同损坏。
代码、类型和引用契约未清楚表达损失权限或重建假设时，在恢复逻辑旁解释依据。

如果存储只读导致移除失败，说明内容恢复本来受支持，但尝试的修复没有建立预期状态。
将内容无效的原因、移除失败、受影响状态及有助于行动的路径，一直追踪到最终负责人，
而不将默认值当作恢复成功的证明。对于拟议重试，识别什么能够改变该条件、重复修复可能产生的副作用，以及停止边界。
与此对照，唯一副本记录的损失未获授权时，应保留记录和失败结果，等待所有者解决恢复权限。

迁移标记说明了为什么语法有效本身不能证明修复合理。将无效标记替换为当前版本，可能使旧记录看起来已经迁移。
检查加载器如何推导之前的版本并执行遗漏的迁移，明确拟议恢复如何保留对现有记录的正确解释。
存在相应路径时，将异步完成、部分写入后的中断、重复读取及恢复失败纳入验证。
副作用、角色选择、反馈或补救行动需要进一步调查时，阅读[失败路径](failure-paths.md)。
