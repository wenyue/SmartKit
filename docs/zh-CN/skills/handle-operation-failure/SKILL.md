# 处理操作失败

使具体操作从公共承诺到恢复或最终反馈的失败行为保持一致。采用目标的语言机制和实际项目契约；
结果可以通过返回失败、异常或其他受支持的完成协议表达。

## 工作流程

1. **理解承诺及其归属。**通过目标可用的代码和文件系统工具，检查操作、实现、调用方及相关契约。
   明确成功、正常缺失或拒绝、已接受的降级、失败，以及程序契约违反。识别调用方需要的区分，
   以及边界承诺的是封闭分类还是允许未知失败。定位独立发起操作的最终处理负责人；
   对于库，明确其向调用方移交失败的受支持方式。从项目的 Agent 指令、Skill 目录及所属测试配置中发现适用的验证流程。
2. **追踪相关路径。**跟随范围内的每种结果，从起点追踪到转换、异步完成、清理和最终处理。
   纳入脱离调用链的工作、取消或中断、有实质影响的部分副作用，以及补救行动。
   检查必要校验和不变量在生产中何处执行。记录证据和缺口。通道或归属不清楚，
   或部分副作用、补救方式需要调查时，阅读[失败路径](references/failure-paths.md)。
   涉及持久化或序列化状态时，阅读[持久化数据恢复](references/persisted-data.md)。
3. **确定各路径的处置。**在责任边界对照实际行为、操作承诺和调用方决策，明确受支持的传播、转换、清理、
   恢复、补偿或最终处理。对于恢复，确定有效的结果状态、可接受的损失及其授权、重试安全与停止边界，
   以及恢复也失败时的结果。区分完成本次操作与恢复未来可用性。追踪原始失败、后续失败、残留副作用
   和有用诊断如何到达负责人。识别事件的最终报告者及反馈或人工补救的实际受众；
   根据影响、运行预期和所需响应，应用项目拥有的严重程度策略。区分已证实的行为与拟议修正。
4. **解决就绪条件并陈述判断。**为每项不一致引用证据，说明最小且完整的修正及可观察后果。
   先调查可推导的事实，再就处置、可接受损失、软件或人工归属、用户负担方面缺失的决定询问协作用户；
   在解决之前暂停依赖该决定的实现。仅根因未知不妨碍继续，前提是既有契约已确立安全处置方式。
   通用根因调查采用任务适用的诊断流程。访问、工具、契约或权限不可用时，明确缺口并停止依赖它的动作。
   请求仅为评估时，以不修改状态的方式结束。
5. **在授权后修改并验证。**在所属边界实现修改，保留无关结果和受支持的契约。
   既有设计或修复授权继续有效；本 Skill 不授予额外的远程或破坏性操作权限。
   仅当代码、类型和引用契约未清楚表达重要含义时，补充调用方义务和恢复依据，尤其是数据损失权限或重试安全。
   通过负责的公共操作或边界，采用已发现的验证负责人和可用工具进行验证。
   覆盖范围内有意义的成功、缺失或拒绝、恢复、传播和最终反馈结果；适用时纳入不受支持的恢复、保留状态、
   后续失败、取消或中途停止，以及补救行动的完成或失败。检查失败是修正或无法得出结论的证据，不能证明预期行为成立。

结束时，为每条已识别的范围内路径给出处置结论或明确的证据缺口。对于修改，报告已修正的不一致
及实际执行的适度验证。说明检查范围、未解决决定和未测试部分；证据缺口不能算作已验证路径或已完成修正。
