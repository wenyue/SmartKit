# Go 包契约

有意识地设计包的公共行为：API、错误身份、初始化和共享状态都应有明确的所有者。

## 为生产用途设计 API 和初始化

让产品需求塑造公共 API。仅凭测试或推测中的复用，不足以引入导出名称、接口或新的接缝。

保持简单调用的简洁；位置参数掩盖意图时，用内聚的参数结构体并按字段名赋值。按职责命名（`Request`、`Options`、`Config`），明确默认值和有意义的零值，仅在需要时区分未提供的值。组合参数时优先使用普通结构体；只有组合或封装收益值得增加机制时，才使用 functional options。

通过构造函数、`main` 或包所属的设置函数显式初始化，而不是添加 `init()` 函数。包级全局变量应经过有意识的选择、保持稳定，并在一处初始化。

## 通过所属契约处理每个错误

将每个返回错误绑定到具名值，检查它，并通过所属契约处理或传播。通过空白标识符丢弃错误，就失去了这次决策。

### 选择错误的表达方式

如果现有错误的身份和上下文已满足调用方需要，直接返回它。底层原因属于调用方可检查的契约时，用带一个 `%w` 的 `fmt.Errorf` 添加操作上下文。单个 `%w` 提供一个 `Unwrap() error` 链接。

现有哨兵错误能表达调用方按身份匹配的稳定条件时，使用该错误。契约需要新的错误身份时，定义新的哨兵错误。普通错误和包装无法满足契约时，使用自定义错误类型，例如需要调用方可检查的字段、供 `errors.As` 匹配的独立类型或自定义匹配行为。该类型若暴露单一原因，应实现 `Unwrap() error`。

### 按身份或类型匹配错误

用 `errors.Is` 匹配哨兵错误，用 `errors.As` 匹配类型，两者都支持已包装的错误。错误消息留作诊断。包装使底层错误可由调用方检查。在拥有契约的边界转换仅属于实现的失败，并通过既定报告路径保留原始错误、原因链和最终处理所需的诊断上下文。

### 保留每个相关原因

现有表达能保留已承诺的匹配行为、原因链接和结构化细节时，沿用该表达。调用方依赖 `Unwrap() error` 或 `errors.Unwrap` 时，保留单一原因链接。

Go 1.20 及更高版本支持错误树。多个 `%w` 可在添加上下文时，同时让哨兵错误及其底层原因可供检查。当多项独立的相关失败都应包含在返回错误中，且每项都须可供检查时，可以用 `errors.Join` 保留它们。保留调用方需要区分的各项失败。

### 有意识地选择运行时检查和终止

类型断言可能失败时，使用 `value, ok := x.(T)` 并检查 `ok`。只有可见的不变量保证类型正确时，才使用 `x.(T)`。

将 `panic`、`logger.Fatal` 和 `os.Exit` 限于无法继续执行的顶层启动路径。

## 响应取消并同步共享状态

适用标准 Go 模式时，将 `context.Context` 放在首位。让循环和长时间运行的工作响应取消。

用所属包的同步原语保护共享可变状态。

## 通过所属包提供诊断

运行时输出遵循所属包的日志约定，不要引入 `fmt.Print*` 或标准 `log` 包。说明操作，并包含诊断失败所需的值。

## 让仓库工具管理机械规范

由仓库的格式化器和 lint 工具管理布局、命名、限制、导入、注释及抑制语法。在所属配置中修改已配置的阈值，不要在这里复制。
