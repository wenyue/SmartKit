# Go 指引

## 有意设计包 API 与初始化

公共 API 应由产品需求驱动。不要仅为测试或臆测的复用而导出名称、添加接口或引入接缝。

从构造函数、`main` 或包自有的初始化函数中显式初始化，不要添加 `init()` 函数。包级全局变量应有明确用途、保持稳定，并集中在一个位置初始化。

## 跨包边界时保留错误契约

将每个返回的错误绑定到具名变量，而不是空白标识符，并检查它。通过所属契约处理或传播错误。

包的公开错误契约决定哪些错误跨越其边界。为这些错误提供有用上下文，并用 `%w` 包装；通过 `errors.Is` 或 `errors.As` 检查。包装会让调用方能够检查底层错误的身份或类型，因此既要保留已经承诺的检查行为，也要避免无意中把实现细节变成新的 API。

在公开契约所属的边界转换仅属于实现细节的错误，保留最终处理所需的原因和诊断证据。创建动态错误前，优先使用能够表达契约结果的已有哨兵错误。

类型断言可能失败时，使用 `value, ok := x.(T)` 并检查 `ok`。只有可见的不变量保证类型正确时，才使用 `x.(T)`。

`panic`、`logger.Fatal` 和 `os.Exit` 仅用于无法继续运行的顶层启动路径。

## 响应取消并保护共享状态

符合 Go 常规模式时，将 `context.Context` 放在首个参数。在循环和长时间运行的工作中响应其取消。

使用所属包的同步原语保护共享可变状态。

## 使用所属包的诊断方式

运行时输出沿用所属包的日志约定，不引入 `fmt.Print*` 或标准库 `log`。日志消息应写明操作，并包含排查失败所需的值。

## 将机械规范交给仓库工具

由仓库的格式化工具和 linter 负责布局、命名、限制、导入、注释和屏蔽语法。配置阈值应在负责它的配置中修改，不要在本规则中重复。
