# 面向人类的审查

帮助读者判断改动是否解决了该解决的问题、实现的收益是否值得其成本，以及下一步该怎么做。固定证据，解释一组完整的文件，再按用户的选择行动。审查请求授权采集证据和准备链接。修复、交付和推进的权限来自用户选定的动作。

## 固定比较范围和阅读顺序

审查 PR 或需对齐远端的分支时，在选择工作区或收集版本证据前阅读[准备](references/preparation.md)。准备指南负责工作区选择、源对齐和已认证查看者的文件过滤。明确审查本地分支或未暂存改动时，使用下表中相应的比较方式。必需指南不可用时，报告缺口，依赖它的工作仍未完成。

| 请求 | 比较及初始证据 |
| --- | --- |
| PR | 按准备指南核实源与工作区，固定 base 和 head，取得已认证查看者完整的文件级 Viewed 过滤信息。 |
| 分支 | 固定分支顶端，以及与已可靠确定的比较基准之间的共同祖先。基准未知时询问用户。`main` 只有在基准已确定时才可使用。 |
| 本地改动或未说明范围 | 比较暂存区与工作区，只看未暂存改动。 |
| 选定文件 | 把适用的比较限制在所选路径。 |

遵守用户明确选择的比较方式和历史版本。默认情况下，PR 和分支比较排除本地未提交改动。本地审查排除只在暂存区有改动的文件，对部分暂存的文件只看未暂存部分，并把工作区对已暂存改动的反向修改视为未暂存改动。只有明确要求时才纳入未跟踪的新增文件。这些默认值优先于其他审查指南的不同默认值。

依据仓库的测试分类，在主审查、补充审查和修复复审中跳过测试代码的语义审查，包括单元、集成和端到端测试。需要证据时查阅相关测试。先应用测试排除、选定文件、Viewed 和本地范围过滤，再统计文件、修改和进度。交付指南另行核算完整提交范围及待推送范围。提交及其必要检查仍按完整范围处理。

只读审查使用源码、测试定义和现有有效结果。完成文件组、完成审查或单独记录 Viewed，都无需因此运行单元测试或执行完整变更集验证。审查期间实施的变更按下文的修复结果要求检查。用户明确要求验证时，按其指定的范围执行。缺少执行证据时，指出它影响哪些判断，并继续有独立证据支持的评估。

采用 GitHub 目录树的文件顺序。递归地先列出子目录中的变更文件，再列出当前目录的直接变更文件。有已知的同级顺序时沿用它，其余情况分别按名称排序同级目录和直接文件。这样 `src/z/api.dart` 会排在 `src/a.dart` 前面。保留排序后的符合条件的文件、固定提交、完整的前后内容，以及 PR 查看者和过滤证据。本地审查还要保留原始暂存区基线，即使选择了不同的起始版本。

第一组前说明比较方式和排除项。范围为空时，直接结束并省略进度分数。证据不全的已知文件仍计入总数。指出缺失内容，暂停相应评估。

### 提供所评估版本的链接

从已加载的 SmartKit 资源中定位 `local_web`，阅读它支持的接口。

```text
python "<local_web>" --help
python "<local_web>" diff --input "<batch.json>"
```

为每个文件提供使用正斜杠的完整仓库相对 `path`，省略 `title`。按 ID 对应返回的 Markdown，原样用作文件名链接，保留完整标签、转义和 URL 绑定。在采集快照时生成基于暂存区的本地链接。固定版本的比较提供经核实的起始提交、已有 blob 或确认不存在的证据，以及重命名路径。

准备指南提供 PR 元数据和经核实的显示模式。本地改动和明确按本地版本审查的分支无需远端对齐。纯分支链接按分支上下文绑定到经核实的确切显示工作区。每个实时链接都绑定到其经核实的工作区。实时内容有未提交改动或与评估版本不同时，披露差异，继续按原评估和 Viewed 标准判断。链接生成成功只说明链接可用，编辑器的实际显示需要另有证据。生成失败时，保留比较和已选模式，排查后再完成依赖该链接的报告。

## 判断改动的需要和调用者受到的影响

阅读完整的范围内改动，以及判断它所需的上下文，包括调用者、同类实现、契约、责任方和生命周期。对每项符合条件的改动都判断合理性和优雅性，包括文档、翻译及无需单独解释的小改动。应用项目规则和用户已接受的决定。保留对任务要求或标准的实质发现，区分亲自核实的证据和作者报告的结果。测试通过只证明它在实际覆盖的条件和假设下观察到了相应行为。

先确定目的，再评价设计。调用者需要什么，原版提供了什么，改动增加或去掉了什么？在相同要求下比较更简单的实现。认可额外复杂度时，说明简化会失去什么，以及为什么这一点值得相应的成本。改变受支持行为的提议需要范围决定。

对优雅性的评估投入比合理性更多的精力。查清每个新增文件，以及每个新增或改变的函数、类型、成员或状态承担什么职责，包括私有成员。边界或契约有变动时，弄清原责任方、现在谁依赖它及依赖多久，并判断直接调用或现有责任方能否服务这些调用者。解释实质性的取舍。

检查派生状态时，先确定每个输入的责任方。用源码引用找到每个会更新、移除或重置输入或源实体的相关生产入口，包括差异之外的路径。逐个入口在内部记录有源码支持的证据，说明各责任方写入、清除或保留什么，以及改动前后消费者实际收到什么。覆盖一个输入清除或更新而另一个保留原值的情况。对派生状态或异步反馈，追踪从结果可用到交付期间允许出现的顺序，包括中途写入、清除、处理、中断或关闭。检查写入、清除状态或将其标记为已处理的相关生产入口，包括由其他责任方更新的输入。把实质性的证据缺口作为不确定性。一次测试能证明它实际覆盖的顺序。

共用辅助函数或移动副作用时，追踪每个受影响的生产入口和输入路径。新操作会不会在原本能成功的调用路径上失败？确认哪些内容实际保存、调用者收到什么，以及该结果是否受契约支持。报告缺陷时，用源码、受支持的调用序列、适用契约或有代表性的复现，把可达的触发条件与受影响的义务或用户体验连起来。

### 独立判断两条轴

从两条轴判断每项修改。无论肯定还是否定，确定判词都需要基于相关证据的高置信度。没有发现缺陷，或缺少原始对话，这些情况本身都不足以决定任一轴的结论。

| 判词 | 依据 |
| --- | --- |
| ⚖️ **合理** | 必要结果、已接受范围、受支持的行为与契约，以及有依据的运行成本和风险。 |
| ⚖️ **不合理** | 任务、行为或契约上的实质缺陷，包括违反结构义务、超出必要范围，或没有依据的运行成本与风险。指出严重度、受影响的条件、后果和修正。 |
| 🎨 **优雅** | 职责、边界和接口带来的收益值得理解与维护成本。表达易读，抽象、状态、分支、重复和防御都有具体收益。同类模式和接口保持一致，偏离时有依据。 |
| 🎨 **需要改进** | 结构缺陷违反受支持的义务。解释义务、具体后果和必要修正。同一项也记为不合理发现。 |
| 🎨 **可选改进** | 结构符合受支持的义务，但有更简单或更一致的保行为方案，其收益值得改动成本。解释当前负担、做法和收益，保留是否优化的选择。 |
| 任一轴为 **不确定** | 说明已确定的事实、实质不确定性和解决所需的证据。保留另一条轴上已有支持的结论。 |

每个证据充分的缺陷和值得考虑的可选改进都要有可行动的 M 项。把它关联到负责的修改，并说明触发条件、后果和修正做法或收益。纳入由本次改动引入、触发或加重的未修改代码缺陷。一处修改做得好，也要单独交代其他修改的缺陷或负担。省略收益很小的润色和个人偏好。

行为缺陷本身不足以证明有结构缺陷。违反结构义务的修改同时判为不合理和 **需要改进**。为同一问题保留一个 ID、一份解释和一个修正做法。推进或交付前须修复或由用户明确保留，仅记录 Viewed 的交付也适用。严重度只用于不合理发现。P0 为紧急且需立即处理，P1 为严重且应尽快修正，P2 为正常优先级，P3 为影响较小但值得修正。可选优化应保留受支持的行为。

功能正确和用户同意，本身不足以证明实现优雅。分别判断已观察到的负担、其依据，以及用户是否接受。缺少理由或要求，导致无法判断复杂度是否必要或能否安全简化时，将受影响的轴标为 **不确定**。在原 M ID 下保留不确定性，以警告归纳，并说明查到哪些证据可以解决。它本身不产生 O 项、修复范围、优化范围或优化选项。保留该修改上有独立证据支持的结论和补救做法。

## 解释一组完整文件

首次出报告或动作菜单前，完整阅读[报告格式](references/report-format.md)。普通、补充、修复及选定 O 项的报告都要应用它。上下文中已有完整且当前有效的内容时，可以复用。内容缺失时恢复全文，包括上下文压缩后丢失的情况。指南变化后重新加载。报告格式负责开头的改动总览、文件块、每项解释深度、收尾披露和菜单呈现。

跨文件和分组给修改分配连续的 M ID。解决同一问题的实现步骤合在一起，需要不同解释的独立改动分开。一份本地化文件算一项修改。没有发现的小幅伴随编辑可以放在总览或省略单独解释，评估仍要覆盖。每个报告中每项只出现一次，补审和修复时沿用原 ID。需要单独解释的支持性修改使用下一个未用的 M ID，并保留与原发现的关系。

在内部确定主审查分组大小。只需简短解释的修改计 1 个单元，需要更多细节的计 2 个。累计至少 20 个单元时，以达到该总数的完整文件为组尾。下一组重新计数，范围最后一组可以较短。用户要求展开解释，分组大小继续按原计数。

报告累计已展示的主审查文件数与符合条件的文件总数，每份文件只计一次，同时报告实际累计展示的主修改数。补充项、修复项和附带观察都不计入主审查单元或进度。跨回复保留固定证据、分组、判词、发现、决定、下一个位置和下一个 M ID。仅在范围变化时修改总数。工作区变干净后仍须保留符合条件但尚未展示的改动。交付和 Viewed 状态应分别核实。

### 报告独立的附带观察

必要的阅读可能发现此前就存在的问题。用证据确认本次改动没有引入、触发或加重它。给它单独的连续 O ID、标题、源码链接或位置、证据、影响、独立性说明和建议或收益。可归属到文件时，按报告格式放在来源文件处。检查限于任务所需的上下文。

O 项不计入主文件数、修改数或进度，也不自动获得 Viewed 资格。批量修复、优化、忽略或接受只在明确选择或扩展范围时包含 O 项。未选的 O 项建议不阻塞主审查或交付。选定 O 项修复后，用单独的证据、检查及双轴复审来评估改动和受影响的上下文。保留 O 身份和主进度。其改动进入交付覆盖范围，新发现或失败的检查可能阻塞交付。

## 提供本组证据支持的选择

完整展示本组后，把先前分组仍未处理的问题纳入下一项决定。收尾时给出结论、实际检查与限制、未处理不合理发现的 ID、严重度及影响、已接受的取舍，以及可选做法和收益。已完成检查和复审的修复，回到同一套选择。交付或其他组合动作已待执行时，按原选择继续。

通过和继续或结束都需要当前版本和正确性证据、成功完成适用的修复或用户明确要求的验证检查、完成受影响内容的复审，以及处理或明确保留待办的不合理发现，其中也包括早先分组的发现。仅有优雅性不确定时，可以作为警告随结果交接。可选改进和未选 O 项建议仍由用户选择。先查明可推导的事实。确实缺少只能由用户提供的事实或范围决定时，直接询问。已确认的阻碍没有可用的补救方式时，解释该阻碍。

有交付效果需要执行且可以推进时，阅读[交付](references/delivery.md)，主动把通过与继续或结束一起提供。说明选定的工作区、适用的整个工作区提交、待推送内容、Viewed 效果及后续推进。未覆盖的暂存或本地改动、待推送提交及交付检查，都可以由选择通过启动。用户先选交付或已完成准备并非提供通过的必要条件。提供符合已知条件和已确定范围的效果。

| 当前情况 | 推荐动作 | 选项顺序 |
| --- | --- | --- |
| 有待处理的不合理发现，未提供可选改进 | **修复** | **修复**、**忽略** |
| 有待处理的不合理发现，也提供了可选改进 | **修复** | **修复**、**优化**、**忽略** |
| 只提供可选改进 | **优化** | **优化**、**通过**、**继续** |
| 没有提出未处理的发现或改进 | **通过** | **通过**、**继续** |

这些常见情况按表取适用动作、推荐和顺序。其他情况运用同样原则。范围结束时使用结束，继续的说明应写明目的和下一位置。改进对应的行可以按 O 项自己的范围规则纳入可选 O 项。工作区选择表由准备指南负责。

每种适用动作只呈现一个选项，用连续字母标记，推荐项放在 A。每个选项说明默认选中的 ID、后果和效果。把适用的 M 和 O 项补救办法合在修复或优化下，并明确哪些 O 项需要显式选择。只有存在已披露且尚未处理的具体可选改进，才提供优化。推荐项和唯一选项仍需用户选择。

### 理解用户选了什么

按最新的适用菜单解释字母，忽略大小写。清楚的自然语言可以选定子集和组合效果。无歧义选项以其披露的范围为准，包括其中明确选定的 O 项。仅提及其他 O 项时，批量 M 动作范围仍按原选项。多个选项都匹配时，询问具体 ID。单独提供 ID 只指明事项。

- **修复** 处理选定的不合理发现。菜单未明确范围时，单说修复指所有已展示且尚未处理的不合理 M 发现，包括早先分组。
- **优化** 实现选定的可选改进，保留受支持的行为和契约。菜单未明确范围时，单说优化指所有已展示且尚未处理的可选 M 改进，包括早先分组。用户可在自然语言中用 **修复并优化** 明确同时选择两类补救。
- **忽略** 记录明确选择的事项、后果以及用户接受或拒绝的决定。清楚的自然语言保留决定即可。事项或意图有歧义时，先澄清。已保留的事项在评估过的内容和影响保持一致时，视为已处理。原判词仍有效，已接受的同一负担无需重复请求优化。忽略本身不推进，也不免除检查。
- **通过** 按交付的完成与并发规则准备、完成适用交付，再推进或结束。选择通过时，明确保留的可选项仅限该选项中列明且已评估的事项。请求 **交付** 或 **仅交付** 选择同样的交付，并保留当前审查位置，除非用户也选择继续。仅交付无需作为固定菜单项。两者的权限均限于交付范围，PR 审批和合并需要相应授权。
- **继续** 推进已完整展示的分组，不交付。**结束** 结束已完整展示的审查，不交付。可选项可以延后决定。

记录用户关于代码行为的决定时，应用 `rule-code-comment` 判断是否需要补源码注释。

已选动作可以执行时直接行动。问题、推荐或不同意见本身不增加权限。遵守用户明确变更的请求、暂停或停止。停止时报告已完成和剩余的工作。用户可以直接停止或取消。

## 检查选定的修复并接续工作

修复时带上选定的发现、支持性路径、经核实的修正理由、已接受的取舍和已披露的效果。在工作及中断期间保留固定比较、工作区、ID、分组、保存的位置及待完成的组合请求。

改动限于选定的补救及必要的支持性变更。在此范围内，按适用指导判断经核实的保留行为理由是否值得写注释。保留决定本身没有授予注释编辑权限。在只读审查、明确要求不编辑或未选中的无关事项中，以建议的方式提出注释改动。如果保全请求可能指保留行为，也可能指禁止所有编辑，在编辑前澄清边界。

使用项目支持的验证方法对修复后的内容运行必要检查，并更新前后证据和链接。复用完整且适用的指导，保留支持性记录和已有的完整日志。证据只在仍适用于确切内容、依赖和效果时复用。修复后的内容仍须通过必要检查。固定的 PR 证据描述原比较，未发布的修复应分别验证。

任何修复触及尚未完整审查的 PR 文件时，判断整文件 Viewed 资格前阅读[交付](references/delivery.md)。

独立复审每份改变的非测试文件，包括必要的支持性文件和意外改动，并检查先前审过且受影响的部分。测试仍承担证据作用和必要检查。按报告格式单独回复修复结果，覆盖每份改动的非测试文件。这个回复与尚未展示的主审查文件分开，主进度沿用原计数。修复或优化只有经过必要检查和受影响部分复审后才算完成。必需检查失败或不可用时，依赖工作仍未完成。

单独的修复、优化或忽略完成后，停在更新后的选择。用户还明确选定了其他效果时，完成必要检查和复审、单独报告修复结果后，继续其余已授权工作。待完成的交付按下文处理。

## 完成选定的交付

使用[交付](references/delivery.md)执行清点、检查、覆盖判断、实际写入、并发和恢复。明确要求准备时，可以启动准备工作，实际写入仍需要对应授权。选择通过或仅交付后，在补充审查和中断期间保留原选择。执行前披露具体方案。范围、目的地和效果都在所选边界内时，沿用已有授权。

交付的必需覆盖发现任何未解决的不合理事项时，暂停写入，也包括复用已有评估的早先发现。该范围内新披露的、值得做的可选改进也需要决定。已选择的 O 项同样按此处理。早先的通过授权限于当时披露的内容，后续发现和未选修复仍须另行决定。已经明确保留的事项，在所评估的内容和影响仍然适用时保持已解决。未选 O 项建议无需由当前交付处理。交付待执行时，按下表选择。

| 当前情况 | 推荐动作 | 选项顺序 |
| --- | --- | --- |
| 补充审查只有待处理的不合理发现 | **修复** | **修复**、**忽略** |
| 补充审查有待处理的不合理发现及可选改进 | **修复** | **修复**、**优化**、**忽略** |
| 补充审查只有可选改进 | **优化** | **优化**、**忽略** |
| 必需覆盖没有待处理的发现或改进 | 完成已选交付 | 直接完成必要步骤并接续交付 |

只提供适用的补救与保留选择。修复或优化可能只解决其中一部分。完成检查、专门报告和复审后，依据此表处理剩余决定。解决相关发现并满足前提后，继续原来的通过或仅交付请求。原选择已经确定接续方式。

保留已经确认的效果，超出现有权限的变化要取得具体决定。适用的提交和发布完成后，如果只剩记录 Viewed，通过可以按交付指南的版本和流程规则，并行开始保存的下一组只读审查。仅交付停在保存的位置，除非用户也选择继续。报告已确认、未知及剩余的效果，并保留未完成的交付及其意图，以便按支持的方式恢复。
