# 面向人类的审查

帮助用户理解每项改动做了什么、是否合理，以及实现是否优雅。先只读审查所选比较，再执行用户选择的操作。采集证据和准备 diff 链接属于审查；修改被审查文件或 Git 状态，需要相应操作的授权。

每次提问都列出具体选项，依次用 **A**、**B**、**C** 等大写字母编号，包括范围问题、工作区创建或同步、补救措施和收尾菜单。使用对话语言说明效果，并请用户选择字母。按最新菜单解释字母，不区分大小写；接受含义明确的自然语言选择，包括对已明确说明的操作表示同意。M 和 O 编号用于选择条目，而非操作。澄清有歧义的回答；提问和异议不构成操作授权。

## 确定比较范围

| 请求范围 | 审查证据 |
| --- | --- |
| PR | 确认 PR 及其源仓库和分支。完成工作区检查后，固定 PR 的 base 和 head，并应用下述 Viewed 筛选。 |
| 分支 | 固定分支顶端提交，以及它与可靠确定的比较基准之间的 merge-base。基准不明确时询问用户，不要假定为 `main`。 |
| 本地改动，或未明确指定范围 | 比较暂存区与工作树：仅审查未暂存改动。 |
| 指定文件 | 将适用的比较范围筛选到这些文件。 |

明确指定 PR 或分支比较时，除非用户要求，否则不包含本地未提交改动。遵守明确选择的历史版本。应用默认范围不同的其他审查指导时，保留已选范围。

本地默认审查跳过仅已暂存的编辑，对部分暂存的文件只审查其未暂存部分。将已暂存编辑在工作树中撤销，也属于相对于暂存区的未暂存改动。只有用户明确要求时，才将未跟踪文件作为新增文件纳入。明确选择其他本地比较方式时，覆盖这些默认值。比较结果为空就保持为空。

### 检查审查工作区

每次 PR 审查前都运行共享的只读工作区检查，即使当前检出已经使用 PR 分支也一样。从已加载的 SmartKit 资源中解析 `local_web`，按其帮助准备输入并读取结果：

```text
python "<local_web>" --help
python "<local_web>" diff --inspect --input "<context.json>"
```

提供当前权威 PR 元数据，区分 PR 所属仓库与源 fork。使用返回的工作区匹配结果和版本新旧关系作出下述决定；过期的本地跟踪数据无法证明 PR 当前的 head。

检查命令要求 PR 上下文。仅审查分支时，通过只读 Git 检查当前检出和已注册的关联工作树。在权威远端已指定或可可靠确定时，与其比较；缺少目标时询问用户，不要臆造上游。有意选择本地分支或本地未暂存改动进行审查时，无需远端同步。明确选择的历史版本仍是审查目标。

对选定工作区，使用只读 Git 清点已暂存、未暂存和未跟踪改动；PR 检查仅通过 dirty 标志反映这些状态。报告其路径、分支、提交、本地改动以及与目标的关系。未知证据不能视为干净或最新状态。在筛选或展示文件前解决适用的选择；下表中的固定快照选项仅适用于 PR，且要求已有固定比较所需的证据。

| 工作区状态 | 选择 |
| --- | --- |
| 没有已验证的匹配项 | 在已验证目标上创建干净工作树；不创建工作树而审查固定 PR 比较；或取消。 |
| 提交相同 | 直接继续，无需询问同步。若实时链接会显示本地改动，应说明这些改动。 |
| 落后 | 按具体、安全的方案同步；不同步而审查固定 PR 比较；或取消。 |
| 领先或分叉 | 说明本地提交；分叉时也说明远端独有的提交。提供以下选择：保留这些提交，为固定审查使用实时链接；使用固定 PR 快照链接；或准备同步方案供另行决定。 |
| 未知 | 说明缺失的证据。提供可行的证据获取方式、已验证的固定 PR 比较，或取消。 |

仅审查分支且没有可用的展示工作区时，提供授权创建、改选范围或取消的选项。

获得创建授权后，使用 [create-worktree](../create-worktree/SKILL.md)，传入用户选择的干净模式和已验证的不可变基准。同步前说明工作区、目标、方法、受影响提交，以及如何保留已暂存、未暂存和未跟踪工作。取得对这些具体效果的授权；“同步”不授权未说明的历史变更或发布。

审查前验证创建或同步结果及本地工作的保留情况，再刷新 PR base/head 和 Viewed 证据，重新评估已变化的目标。中断后先检查实际结果再重试；在完成验证、用户明确改选受支持的固定审查或取消之前，审查保持待处理。保留已验证的工作区和选定的链接模式。

### 筛选文件并保留快照

对 PR，获取当前已认证 GitHub 查看者完整的文件级 Viewed 状态。排除 `VIEWED`，纳入 `UNVIEWED` 和 `DISMISSED`。完成分页，并验证获取过程中 base 和 head 保持不变。审批、评论和先前对话中的展示都不能证明 Viewed 状态，当前状态也不能建立历史快照的筛选结果。明确要求纳入已查看文件时，覆盖该筛选。所需状态不可用时暂停，并提供获取状态或不筛选而审查所有其他符合条件文件的选择。

测试文件不进入文件报告、修改项计数或进度。先应用指定文件、Viewed 和本地范围筛选，再计数。这些报告筛选不排除后续整分支提交或其检查中的改动。按 GitHub Files changed 的目录树排列文件：递归列出子目录中的改动文件，再列出当前目录的直接文件；能观察到同级顺序时沿用，否则分别按名称排序同级目录和直接文件。因此，`src/z/api.dart` 排在 `src/a.dart` 前。

保留固定的修改前后证据、固定的比较提交、有序文件清单，以及 PR 查看者和筛选证据。本地比较还要保留原始暂存区基准，即使用户选择了其他修改前版本，以便完成操作时清点已有暂存工作。展示第一组前说明范围和排除项。如果没有剩余文件，直接说明并结束，不虚构报告或进度比例。

所需范围或源证据不可用时，指出缺口并暂停依赖它的审查。已知文件即使证据不完整，也保留在总数中，对受影响的判断报告证据不足。所选改动引入、触发或加剧的缺陷应在对应修改项中评估，即使证据位于未改动代码。无关的既有问题按下述 O 类观察处理。

## 准备文件名链接

每个被审查文件的文件名链接都使用共享工具，输入遵循其帮助：

```text
python "<local_web>" diff --input "<batch.json>"
```

根据保留的比较证据准备链接：本地暂存区比较的链接与审查快照一并采集；分支和 PR 比较使用固定的修改前提交、已有 blob 或真实的不存在状态。按帮助要求提供固定的被审查 PR head、其他 PR 元数据以及重命名路径。

对 PR，明确选择历史目标、选择固定比较或源身份不可用时，设置 `view="snapshot"`，并提供所需固定证据。明确选择或新准备的工作区使用 `view="worktree"` 及其已验证路径，包括本地分支别名；其他情况使用默认选择。仅审查分支时，提供已验证的展示工作区，不提供 PR 上下文。

使用返回的 ID 将返回的 Markdown 与文件对应。即使实时链接或 GitHub 展示更新的内容，审查证据和 Viewed 资格仍绑定已评估的固定版本。

链接准备失败时，报告诊断信息并暂停依赖它的报告；解决问题时保留所选比较和模式。仅生成链接不能证明编辑器已展示内容。

## 解释每个文件

使用[报告示例](references/report-examples.md)校准解释、观察和菜单的表达。每个完整文件块以 `📄 **[path](diff-destination)**` 开始，简述文件职责和总体改动。用普通语言解释对用户或调用者的影响，保留影响判断的技术细节。

按改动解决的问题或场景划分修改项。相关实现步骤放在一起；只有改动彼此独立或无法用一个简单说明解释时才拆分。一个本地化文件算一个修改项。附带的小改动可放在概述中，也可省略。

用 `🔧 **M1** - **<title>**` 标记修改项，跨文件和分组连续编号。在发现、建议、选择和复审中保留 M 编号。emoji 和周边标点放在粗体之外；保留代码和路径自身的标点。

### 给出两个独立判断

每个修改项都要给出两个判断，各占一个段落，包含明确结论和理由。代码、文字和翻译都适用。用 ⚖️ 表示合理性，🎨 表示优雅性，emoji 后不再重复维度名称。

| 判断 | 依据 |
| --- | --- |
| ⚖️ **合理**。 | 改动服务于任务，正确且安全，符合范围，成本有合理依据。 |
| ⚖️ **不合理** (P1): | 证据表明存在实质缺陷、不必要的范围或不合理成本。解释影响，并给出具体修正建议及其收益。使用实际的 P0–P3 严重级别。 |
| 🎨 **优雅**。 | 改动在恰当的职责位置解决问题，结构清晰，很少有不必要的状态、分支或重复。 |
| 🎨 **可以改进**。 | 指出可避免的复杂度或重复，以及有依据的更简单做法，解释其清晰度或维护收益。仅有风格偏好并不足够。 |
| ⚖️ **证据不足**。或 🎨 **证据不足**。 | 指出该维度缺少什么证据以及如何补足。另一个维度仍可得出有依据的判断。 |

合理的改动也可能不够优雅。优雅性问题属于可选改进；只有另有证据支持的合理性缺陷才要求先修复或明确忽略。只对不合理发现分配严重级别：P0 为关键问题，需立即处理；P1 为严重问题，需尽快修正；P2 为普通优先级；P3 为影响较低但值得修正的问题。依据后果和受影响条件判断。

保留底层审查中的实质发现及限定条件，包括任务和规范方面的问题。区分实际执行的检查与作者报告的结果。

### 选择解释深度

行为直接、范围清楚且没有实质风险或权衡时，使用 **简洁** 解释：一个简短的前后变化段落，再分别给出 ⚖️ 和 🎨 段落。不使用例子、代码片段、emoji 前缀或修改前后标签。

复杂机制、重要契约、实质发现或权衡，以及关键证据缺口，使用 **展开** 解释：先 ⏪ **修改前**，再 ⏩ **修改后**，然后给出两个判断。对代码，从保留的证据中展示最小而有用的前后片段，并解释它们如何产生所比较的行为。保留相关错误、状态或生命周期条件。清楚标明示意性简化并保持其行为；代码不能帮助理解时省略。一行 diff 也可能需要展开。

## 分组展示并维护进度

用 `---` 分隔完整文件块。在某个文件使本组修改项数达到至少 10 时结束该组；不要拆分文件。范围结束时展示最后不足一组的内容。组末使用 `---` 和 `📊 **Progress**: **displayed files / files requiring review**`，明确说明该数值表示已展示的文件数。

跨回复保留分组成员、已审查改动、下一位置和 M 编号、判断、发现的处理决定、待处理建议，以及各组已验证的完成结果。主审查中的每个文件只计一次。整分支提交可能在文件尚未全部展示前就使工作树变干净；继续根据保留证据展示未见分组，不要从新暂存区重建范围。只有范围实际变化时才更新总数。

### 单独处理顺带观察

在必要阅读中，只有证据既能证明一个无关既有问题确实存在，又能证明所选改动没有引入、触发或加剧它时，才报告该问题。这不授权扩大审计范围。

为观察分配连续的 **O1**、**O2** 等编号。最初只在分组收尾的 `📌 **Incidental observations (outside this review's scope)**` 下展示，包含标题、源位置或链接、证据与影响、它与所选改动的独立关系，以及建议和收益。

O 条目不增加主审查文件数、修改项、进度或 Viewed 资格。仅作为建议时，它既不阻止推进，也不授权修复。未限定范围的修复、优化和忽略全部操作不包含 O 条目。选定的 O 修复需要单独确定结果、授权、检查和专门复审；除非用户明确扩大主范围，否则保持独立。

## 提供操作

| 操作 | 效果 |
| --- | --- |
| **修复** | 修复选定的待处理不合理发现；未限定范围时，选择所有已展示且未解决的发现，包括之前分组。 |
| **忽略** | 只将选定发现标记为已忽略，保留严重级别和影响。若存在多个可能条目，除非用户明确选择全部，否则澄清选择。 |
| **优化** | 实现选定且有依据的 🎨 建议；未限定范围时，选择所有已展示且未完成的建议。待处理不合理发现仍保持待处理。 |
| **通过并继续** | 完成必要的整分支提交和已说明的 PR 发布，将符合条件的 PR 文件记录为 Viewed，验证完成后再推进。 |
| **继续** | 不暂存、不提交、不推送，也不标记 Viewed，直接推进。保留改动和建议。 |

按对话语言本地化操作名称和说明。M 编号将操作限定到条目，不代表选择整组完成。推进到保存的下一组；全部文件展示后，使用 **通过并结束** 和 **结束**。

区分以下范围：

- **审查和进度：** 选定、符合条件且实际展示的文件和差异。
- **提交和发布：** 分支全部待提交改动；推送时还包括完整的待发布提交祖先链，须满足下述准备和确认要求。
- **Viewed：** 当前组符合条件且已审查的文件，以及中途完成操作中明确纳入的先前文件。最终的 **通过并结束** 覆盖所有已展示并审查的分组，包括通过 **继续** 推进的分组。

纳入提交或推送不等于已经审查。本地或分支审查无需 PR，也不授予推送权限。PR 完成操作要求已验证的 PR；发布还需要对已说明的发布差异取得明确授权。两种推进操作都不批准或合并 PR；已忽略的发现仍是已忽略。

### 判断哪些操作已就绪

两种推进操作都要求：所有已展示的不合理发现均已修复或明确忽略，正确性与版本证据可用，必要审查检查通过，受影响部分的复审已完成，且任何先前选定的完成操作都已充分验证。仅有可选改进或缺少优雅性证据，不阻止推进。

提供完成选项前，为其实际效果执行可推导的只读准备。按以下优先顺序处理：

| 状态 | 菜单 |
| --- | --- |
| 有待处理的不合理发现 | 提供修复、忽略，以及有依据的优化。解释两种推进操作为何都不可用。 |
| 缺少正确性或版本证据、审查检查失败或未完成，或审查已过时 | 说明缺口及补救方式；先完成已授权工作，再提供推进选项。 |
| 选定的提交、推送或 Viewed 操作尚未完成 | 保留该选择。就绪后，将剩余步骤作为同一个完成操作提供；普通继续不能绕过它。 |
| 推进已就绪，但完成操作的目标、接口、检查或安全范围不可用 | 说明具体前提。继续仍可用。额外分支内容的检查只有影响审查时才阻止继续。 |
| 额外内容需要确认纳入 | 说明该内容；其他前提都就绪时，提供确认并完成的组合选项，同时提供继续。 |
| 完成操作已就绪 | 提供实际剩余的提交、推送和 Viewed 效果，同时提供继续。复用已验证完成的工作，不创建空提交或进行不必要的推送。 |

本地或分支审查就绪后，完成操作会提交待提交改动并验证。PR 就绪后，完成操作会在需要且获授权时发布审查改动，再将符合条件的文件记录为 Viewed；不需要提交或发布时，提供仅记录 Viewed 的通过选项。说明将复用的任何已验证结果。只要仍有有依据的建议，就加入优化选项。

每次收尾都说明完成操作是否就绪，包括修复后或专门复审的收尾。不可用操作的解释放在可执行菜单外。进度之后按以下顺序展示各节，省略空节：

1. **待处理发现**，包括之前分组：`**M1** (P1): <impact summary>`。
2. **可选改进**，包括之前分组：编号、改进建议及收益。
3. 📌 **顺带观察（本次审查范围外）**。
4. **可用操作**，使用上述字母选项和具体效果。适用时说明完整提交范围、额外内容确认、发布差异以及 Viewed 集合。

以一句简短的字母选择提示结尾；没有剩余选择时省略提示。[收尾示例](references/report-examples.md#example-closings-for-different-results)展示了这些状态的表达方式。

用户在受阻时要求推进，应说明待处理编号或前提，并重新生成可用菜单；继续从不等于忽略。问题和争议发现需要回答或重新评估，不自动推进。用户始终可以明确停止或暂停：报告已展示进度，以及未解决的发现、证据、改动、发布或操作，不宣称工作已经完成。

## 修复并复审

将已授权的修复或优化限定在选定条目及必要支持改动内；优化保留受支持的行为和契约。被审查内容变化后，或任何 O 条目修复后：

1. 成功完成必要检查，刷新修改前后证据和链接。对尚未发布的 PR 改动，同时保留固定的远端版本和经检查、准备发布的本地内容；O 证据单独保留。
2. 独立复审已变化或受影响的已审查部分，包括意外改动。在专门回复中展示完整更新后的文件块及两个判断，与尚未展示的文件分开。对 O 修复，在专门的 O 复审中评估行为及受影响依赖，给出源位置、前后解释和两个有理由的判断。
3. 保留原始 M/O 编号和分组成员，不重复计数文件。O 复审不产生主进度或 Viewed 资格。只有检查和复审确认结果后，才将修复或建议标记为完成。

单次修复、忽略或优化以更新菜单结束，不推进。明确的复合请求授权其有序效果，包括先完成专门复审，再执行完成操作和推进；继续执行这些已授权步骤，无需例行再次确认。新发现、检查失败、效果变化或新发现的额外内容会暂停依赖它的步骤。单独授权的优化可在仍有发现时进行，但不能满足推进条件。

## 准备完成操作

对于没有本次审查所产生的未发布改动、且没有尚未完成的已选提交或发布操作的 PR，通过可以在不提交或推送的情况下核验固定的远端 PR 版本并记录 Viewed。通过只读检查确认，包括子模块检出差异在内的无关本地差异，不会影响固定审查差异及其依赖，也不会使逐文件的完整审查覆盖失效；保留这些差异。它们的存在本身不要求发布或确认纳入。本次审查产生的未发布改动，包括修复和优化，必须先进入已验证的 PR 版本，才能记录 Viewed；尚未完成的已选提交或发布操作仍须保留完整范围并完成剩余步骤。

### 清点整个分支

完成操作包含提交或推送时，确认准确的仓库、分支和工作树。清点所有已暂存、未暂存和未跟踪改动，以及拟议推送会发布的每个已有提交。保留分支顶端、暂存区、工作树和适用的未跟踪内容，作为恢复证据。

完成操作中的提交包含整个分支的待提交状态，包括测试、支持或生成文件、仅已暂存改动，以及未展示或被排除的文件。遵守仓库对敏感、被忽略或临时文件的限制；与用户解决不安全的纳入问题，不要悄悄缩小提交范围。对于部分暂存，确定一致的最终工作树内容，说明它取代了哪些暂存内容，并保留原始暂存区。未解决的内容冲突阻止完成。

根据本次对话记录的操作和基准确定来源，包括同一文件中来源混合的代码块。对于在其他地方产生或来源未知的改动，说明具体路径或提交、行为和实质效果，并在提交或发布前取得明确纳入确认。已有确认适用于相同内容和效果；对已审查分组的一般认可不覆盖未说明的额外内容。没有确认或用户拒绝时，保留改动，让整分支完成操作保持待处理；提供继续或调整范围，不自动改成更小的提交。

说明提交和推送范围与已展示审查及 Viewed 范围的差异。同一对话产生的额外内容需要清点和检查，但不需要额外的来源同意。对完整拟提交或发布范围运行必要检查，评估对已展示审查的影响，并在需要时完成专门复审，包括每一项选定的 O 修复。纳入同意不能替代审查或检查。

### 准备 PR 发布和 Viewed 记录

提供 PR 完成选项前，验证 PR 所属仓库、源分支与远端、查看者、当前 base/head，以及实际写入操作和回读所需的可用接口。涉及发布时，还要验证待发布提交祖先链，并将完整推送差异与 Viewed 集合分开说明，包括已有未推送提交。若无法正常推送到已验证的源分支，说明缺少的前提；该操作不隐含授权变基、强推或排除提交。

Viewed 覆盖 PR 某个版本上的整个文件。提供标记某路径的选项前，将其完整的拟发布 PR 差异与保留的已展示评估比较。对每个尚未覆盖的改动块进行专门复审并给出两个判断，即使它是已获准纳入的独立额外内容。保留编号、原始分组和进度。O 复审不会让原本不符合条件的路径获得资格。

如果覆盖范围缺少证据或需要范围决定，让路径保持未标记，完成操作保持不可用或待处理。保留选定的 Viewed 集合，不要靠丢弃路径来完成。检查通过、纳入同意以及先前改动块未变化，都不能补足缺失的覆盖。

## 执行完成操作并验证

只执行所选操作已说明且获授权的效果。复用已验证的提交、推送和 Viewed 结果，不重复写入。

1. **重新验证。** 将审查证据、适用的远端 base/head，以及与所选效果相关的本地状态，与准备好的状态比较；提交或发布时，还要纳入分支顶端、暂存区、工作树和待发布提交祖先链。发生相关偏移时刷新清单，运行适用检查并复审受影响部分；将要提交或发布的额外内容发生变化或新增时，需要重新确认纳入。
2. **需要时提交。** 暂存已说明的完整最终内容，并将暂存区与预期文件树核对。通过正常钩子提交，然后验证提交、父提交、完整文件树、暂存区及剩余工作树状态。钩子产生的改动需要适用检查和受影响部分复审；超出已确认内容的改动还需要更新同意。所有预期改动都必须已提交，且没有无法解释的残留。本地或分支完成操作此时可以推进。
3. **获得授权且需要时发布。** 钩子执行后重新验证完整待发布差异，正常推送到已验证的 PR 源分支，再回读 base/head 和完整已发布差异。确认提交符合预期、内容经过检查，且已展示评估仍有效。
4. **记录 Viewed。** 在实际 PR 版本上验证查看者和两个提交 ID，确认选定集合中每条路径都已完整覆盖。只将符合条件且仍待记录的选定路径标为 Viewed。回读每条选定路径，包括复用的结果，以及 PR 版本。全部路径都必须是 `VIEWED`，且记录期间 base/head 保持不变。
5. **推进或结束。** 确认已验证的结果，从保存的位置继续。最终完成涵盖所有已展示分组，包括此前未记录而直接推进的分组。

预期的新 head 需要验证，不必重复已经覆盖的审查。内容、base 或受影响依赖发生意外变化时，复审受影响部分；仅凭文本相等无法证明效果未变。结果不再代表获授权的已审查版本时，刷新证据并取得新选择。标记较新版本不能证明它已被审查。

### 恢复未完成操作

写入、接口或验证失败时暂停，不推进、不自动回滚，也不改用继续或结束。报告已确认、失败和未知的效果，包括提交、推送状态、剩余改动、部分暂存和 Viewed 路径。

保留清单、来源确认、固定证据、选定的发布和 Viewed 范围、查看者与版本、分组状态及恢复位置。响应丢失后先检查实际本地和远端状态，再重试。就绪后，只恢复同一个完成操作的缺失步骤；不要悄悄加入内容、扩大中途选定的 Viewed 集合或重复成功写入。

完成要求所有必要回读都成功。明确停止可以留下残余工作，但必须报告。成功恢复后保留进度，不要重新应用筛选来删除已展示的文件。
