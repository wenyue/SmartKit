# 帮助人类审核

帮助人类 reviewer 理解 PR 或分支改动：改了什么、是否合理、实现是否优雅且有品味，以及哪些地方需要留意。仅在用户要求时使用此 Skill。在选定的范围内进行只读审核；只有用户通过下文所述的操作授权修复或优雅性优化时，才修改被审核的内容。

加载必要的 Skill 和 Rule 进行审核。

## 确定审核范围

### 选择比较范围

明确任务预期达到的结果，并按下表选择比较范围。通过可用的只读 Git 或 GitHub 接口，例如 CLI、连接器或已认证的 GitHub 界面，获取修改前后的证据。

| 用户指定的范围 | 比较方式 |
| --- | --- |
| PR | 获取该 PR 的改动文件及比较证据，记录其 base 和 head 的提交 ID。审核这个固定的 PR 版本，并应用下文的文件级查看状态筛选。 |
| 分支，可能指定了比较基准 | 确定被审核分支的最新提交和可靠的比较基准，比较两者的共同祖先与该分支最新提交之间的改动，并固定两个提交 ID。无法可靠确定基准时，询问用户，不擅自假定为 `main`。 |
| 本地改动，或未明确指定范围 | 比较暂存区与当前工作区，使用 `git diff` 或等效证据。 |
| 选定文件 | 在适用的比较范围内筛选这些文件，统计和报告筛选后的范围，而不是整个 PR 或分支。 |

明确指定的 PR 或分支比较不包含本地未提交改动，除非用户要求纳入。

### 审核本地修改

本地默认只审核 unstaged 改动，以暂存区内容作为修改前的版本。跳过只有 staged 改动的文件；文件部分暂存时，只审核其中未暂存的部分。如果暂存的修改随后在工作区被撤回，相对暂存区的这次撤回属于需要审核的 unstaged 改动。用户明确要求纳入 staged 改动或采用其他本地比较方式时，覆盖这一默认行为。不纳入此前的提交，选定的比较为空时也不回退到 staged 改动或最后一次提交。除非用户明确要求纳入，否则排除 untracked 文件；明确纳入时，将其作为新增文件审核。

### 筛选 PR 文件

审核 PR 时，默认跳过当前已认证 GitHub 查看者标记为已查看的文件。通过可用的、已认证且只读的 GitHub 接口获取完整的文件级状态；GitHub GraphQL 通过 [`PullRequestChangedFile.viewerViewedState`](https://docs.github.com/en/graphql/reference/pulls#pullrequestchangedfile) 提供这些状态。排除 `VIEWED`；纳入 `UNVIEWED` 和 `DISMISSED`，后者表示文件在上次查看后发生了变化。完成所有分页，并检查获取文件列表和状态期间 PR 的 base 与 head 没有变化，确保筛选对应固定的版本。当前查看状态不能作为旧 PR 快照的筛选依据。PR 批准、评论或此前聊天中展示过的文件，都不能证明文件的查看状态。

用户可以明确要求纳入已审核文件，覆盖这一排除项。如果无法获取所需的查看状态证据，说明缺少的前提条件，暂停依赖这些证据的审核，并询问能否获取该证据，或是否不应用这项筛选、纳入其余符合条件的全部文件。将缺失状态视为未知，不视为 `UNVIEWED`。

### 固定快照与待审文件列表

加载默认范围不同的其他审核指导时，保留本 Skill 已选定的比较范围。如果没有可用的 `HEAD`、无法获取所需引用或 PR 证据，或无法使用必要接口，说明缺少的前提条件，并暂停依赖它们的审核。

固定审核版本，并保留用于展示报告的有序文件列表。记录 PR 和分支比较的提交 ID、本地比较的修改前后内容（未暂存审核须包括暂存区基准），以及 PR 筛选所用的查看者身份和文件级状态。所有审核范围的展示顺序都与 GitHub 的 Files changed 目录树一致：在每个目录内，先递归列出各子目录中的改动文件，再列出该目录直属的文件。能获取拉取请求的实际目录树时，采用其中的同级顺序；否则，将同级子目录和直属文件分别按名称排序。例如，`src/z/api.dart` 排在 `src/a.dart` 前面；直接对 `git diff` 中的完整路径排序，无法得到这种顺序。

完全跳过测试文件：不审核，也不计入进度或修改项。先应用范围筛选，再统计数量；被跳过的已查看 PR 文件和只有 staged 改动的本地文件，不生成文件报告，也不计入进度或修改项。在展示第一组之前，统计其余文件的数量。简要说明范围和排除项，让读者理解总数的含义。如果没有需要审核的文件，说明情况并结束，不拼凑报告或进度比例。

无法获得范围、必要指导或源证据时，说明缺少什么及其影响。暂停依赖这些信息的审核，不编造事实、总数或已经完成的评估。已知文件即使证据不完整，仍计入总数；在该文件的报告中解释缺口，并在必要时给出“证据不足”的评价。

## 围绕文件解决的问题进行说明

每个文件以 **📄 文件：路径** 开头，简要说明文件的职责和整体修改。可获得源链接和相关行号时，一并提供。用通俗语言解释修改对用户或调用者意味着什么，同时保留影响判断的技术细节。

按照业务问题或人类容易理解的场景划分修改项，优先将相关修改放在一起。只有逻辑上相互独立，或无法用一个简单例子共同解释时，才拆分。方法、diff 块和单个实现步骤本身不足以成为拆分理由。例如，记录尚未完成的工作、拒绝新工作，以及关闭资源前等待，可以合成一个“关闭时安全完成已有工作”的修改项。

顺带的小修改，例如注释拼写错误，可以在文件总说明中提及，也可以省略。每个 l10n 翻译文件作为一个整体修改项说明，不把其中的字符串拆成多个修改项。

修改项使用 **🔧 1.** 、 **🔧 2.** 等标签，附上标题，并在同一报告中跨所有文件和继续展示的分组连续编号。

### 每个修改项都从两个独立维度判断

所有修改项采用同样的思考方式：确认修改前后发生了什么变化、产生什么影响、有哪些证据支持，再分别判断合理性和优雅性。两个维度适用于所有修改，包括修复、新功能、重构、文档和翻译。文字的优雅性侧重表达和组织是否清楚；代码的优雅性侧重机制和结构。调整的是表达篇幅，不是评估的覆盖范围。

每个修改项都使用固定的 **⚖️** 标记合理性、 **🎨** 标记优雅性，即使只有一句话也如此。判断标签直接使用 emoji 加结论，不再重复维度名称。每个维度都要给出明确结论和理由；emoji 区分的是维度，不表示评价是正面还是负面。

- **⚖️ 合理。** 修改服务于预期任务；行为正确且安全，范围符合任务，现有证据足以支持其成本。
- **⚖️ 不合理。** 存在实质性缺陷、不必要的范围扩大或缺乏充分依据的成本，使修改在任务要求下成为较差的选择。为每个发现标注 P0 至 P3 的问题级别，解释有证据支持的影响，并给出具体建议，说明其在相同要求下的优势。仅有更优雅的方案、微小优化或风格偏好，不足以达到这一标准。
- **🎨 优雅。** 修改在恰当的职责或位置解决根本问题，结构清楚，尽量减少不必要的状态、分支和重复。解释哪些选择使其易于理解和维护。
- **🎨 可改进。** 行为可以是合理的，但机制或表达带来可以避免的复杂度或重复。指出可以改进的具体结构，在有依据时提出更简单的方案，并解释对维护或理解的好处。区分这些好处与个人风格偏好。
- **⚖️ 证据不足。** 或 **🎨 证据不足。** 说明什么阻碍了对该维度的可靠判断，以及哪些证据可以解决问题。区分已确认的事实与假设。一个维度可以有充分依据的结论，而另一个维度仍缺少证据。

修改可以合理但不够优雅。单独的优雅性问题属于可选的改进建议，不触发必须选择修复或忽略的暂停。如果同一结构还造成有证据支持的实质性缺陷、风险或缺乏充分依据的成本，也要在合理性下独立报告该影响；这类不合理问题遵循正常的暂停与修复流程。

仅为不合理问题标注 P0–P3，纯粹的优雅性建议或风格偏好不标问题级别。P0 表示需要立即干预的严重问题；P1 表示需要尽快修正的重大问题；P2 表示正常优先级的问题；P3 表示影响较小但值得修正的问题。根据有证据支持的后果及其适用条件确定级别，而不是根据代码修改量。例如： **⚖️ 不合理（P1）。** ，随后说明影响和建议的修复方案。

将底层审核发现的重要问题及限定条件带入相应修改项；当规范问题与任务范围问题的区别影响判断时，保留各自依据。通俗解释仍须保留可能改变人类 reviewer 决定的限制。报告实际执行的检查，并与修改作者提供的检查结果区分。

### 选择展示详略

行为变化直接、影响范围清楚、没有需要展开的实质性风险或取舍时，采用压缩说明。用一两句自然表达解释修改，并包含两个带 emoji 的判断及其理由。省略固定的“修改前”“修改后”“合理性”“优雅性”栏目，以及无助于理解的代码。根据读者需要理解的内容判断是否简单，而不是根据 diff 行数：一行修改也可能影响异常处理或持久化。

涉及复杂机制、重要契约、实质性风险或审核发现、重要取舍、关键证据缺口的修改项，需要展开。纵向依次展示 **⏪ 修改前** 、 **⏩ 修改后** 、带 **⚖️** 的合理性判断、带 **🎨** 的优雅性判断；两个判断标签都使用 emoji 加结论。解释前后的行为，无需单列“不改的后果”。优先使用项目语言中的简短实际代码，只保留说明场景所需的部分。用通俗语言解释代码，准确保留所比较的行为。简化例子必须能让人看出是示意，不要让读者误以为是逐字引用的源代码。代码无助于理解时，例如说明文字组织，可以省略。

## 每次展示一组并处理操作

### 分组展示

文件之间用 `---` 分隔，按既定顺序展示完整文件。加入某个文件后，本组修改项达到或超过 10 项，就结束本组。文件不能拆分，单个文件超过 10 项也如此。例如，含 3 项和 8 项的两个文件合为一组，共 11 项；下个文件留到下一次回复。范围结束时，展示最后不足 10 项的一组。

每组末尾展示 `---` 和 **📊 审核进度：已展示文件数 / 需要审核文件总数** ，明确说明文件已展示。进度统计已展示文件，不统计修改项，也不表示判断已确定。跨回复保留审核版本、有序文件列表、下一个未审核位置、下一个修改项编号、判断、问题状态和待处理的优雅性建议。

### 选择操作

面向人类的标签、摘要、操作名称和问题使用对话所用的语言。在中文对话中，操作名称使用 **修复** 、 **忽略** 、 **优化** 和 **继续** ，其含义分别与英文操作名 **fix** 、 **ignore** 、 **optimize** 和 **continue** 相同。按含义理解自然语言选择，不要求用户使用命令语法。

修改项编号用于选择该项中的相关问题或建议。“全部”仅指当前报告中已展示、仍待处理的对应维度事项，包括前面的分组。选择含糊、矛盾或无效时，先澄清再修改。

| 操作 | 不带修改项编号 | 带修改项编号 |
| --- | --- | --- |
| **修复** | 修复所有待处理且未被忽略的不合理问题。 | 仅修复选定的待处理且未被忽略的不合理问题。 |
| **忽略** | 追问要忽略哪些修改项；只有明确回复 **忽略全部** 才忽略全部待处理的不合理问题。 | 忽略选定的问题，并自动修复其余所有待处理且未被忽略的不合理问题。 |
| **优化** | 优化所有待处理且有充分依据的 **🎨 可改进** 建议。 | 仅优化选定的待处理且有充分依据的优雅性建议。 |

**忽略** 没有默认值，即使只有一个问题也如此。如果用户没有明确要忽略哪些问题，询问其要选择哪些修改项，或是否明确忽略全部，说明其余待处理且未被忽略的问题都会修复，然后等待，不作修改。保留被忽略问题的级别，记录为已忽略，不表示已修复或认可。忽略只作用于合理性，不妨碍另行授权的优雅性优化。

### 清晰呈现结尾的操作选择

进度之后，用 Markdown 分开展示 **待修复问题** 、 **可选优化** 和 **可用操作** ，省略为空的部分。按项号、问题级别和简短的影响说明列出待处理的不合理问题。按项号、改进方案和收益列出有充分依据的优雅性建议。这些摘要涵盖前面各组及当前组中仍待处理的事项。

只提供下文继续规则允许的操作。用简短列表解释各操作的效果，包括用户没有限定范围时的默认行为： **修复** 会修复全部待处理问题，除非用户只选定其中一部分； **忽略** 需要用户指定范围，并自动修复其余问题，明确忽略全部时则不执行修复； **优化** 会实施全部有充分依据且仍待处理的建议，除非用户只选定其中一部分； **继续** 会展示下一组，或在范围已全部展示时结束审查，并将未实施的优化保留为建议。仍有待处理问题时，说明优化会让这些问题继续处于待处理状态。

结尾菜单不列具体命令语法或带编号的操作用法；项号只出现在问题和建议列表中。最后用一个简短问题询问适用的操作，必要时请用户说明选定的修改项。如果已无需要选择的事项，直接结束，不再提问。下文示例展示不同的结果状态；按对话语言调整其措辞。

### 修改、复审与继续

修复或优化时，加载必要指导，只处理已授权的问题或建议，并执行必要检查。优化须保留现有受支持的行为和契约。操作受阻或检查失败时，说明剩余事项及所需条件，暂停推进。

检查通过后，先复审修改，再继续。已审核内容发生变化时，刷新审核版本，复审此前已审核、但被改动或影响的全部内容，包括意外改动。使用专门的回复，以完整文件块展示更新后的解释和两个维度的判断，与尚未审核的文件分开。保留项号，说明版本切换，必要时更新文件列表和总数。只有复审确认结果，才能将问题标记为已修复，或将建议标记为已完成。

普通分组和专门复审都按以下规则继续：

- **仍有待处理的不合理问题：** 询问要 **修复** 还是 **忽略** ，最后一组也如此；若还有充分依据的优雅性建议，也提供 **优化** 选项。等待用户选择。此时不能选择 **继续** ；单独回复 **优化** 既不授权修复，也不能推进审核。
- **没有待处理问题，但仍有充分依据的优雅性建议：** 询问要 **优化** 还是 **继续** 。等待用户选择。继续会审核下个文件，或在范围已展示完时收尾，并将未选中的建议保留为建议。
- **两者都没有：** 仍有文件则询问是否继续并等待；范围已展示完则直接结束，不再提示。

明确忽略后，如果已无需要修复的问题，就从保存的下一个未审核位置自动继续，或在范围已展示完时结束；如果仍有充分依据的优雅性建议，则先等待选择。保留已忽略的问题和证据缺口，并区分展示完成与问题解决。

## 参考报告

参考以下示例，根据读者调整详略。保留文件总说明、业务修改项、两个有依据的判断和进度；仅在修改项需要展开时使用纵向比较。以下文件和代码仅为示意，不是对某个仓库的审核发现。选定范围包含三个非测试文件。假设删除一条记录后，该记录会脱离其存储 box，任务要求删除后执行 flush，且 flush 错误会传递给调用者。这项持久化契约及脱离存储 box 的机制需要展开说明。

**📄 文件：`l10n/en.json`**

这个文件提供英文界面文案。修改后的标签明确说明操作会删除账号；该文件的所有翻译修改一起审核。

**🔧 1. 明确账号删除按钮的含义**

将“Delete”改为“Delete account”，明确操作对象。 **⚖️ 合理，** 因为标签准确描述了假定的操作； **🎨 优雅，** 因为两个常用英文单词就能清楚传达操作含义。

---

**📄 文件：`lib/item_storage.dart`**

这个文件负责保存和删除记录。这次修改保留存储 box 的引用，使删除记录后仍能刷新这次删除。

**🔧 2. 删除后，仍刷新原来的存储 box**

**⏪ 修改前**

```dart
await item.delete();
await item.box?.flush();
```

删除后，`item.box` 变为 null，因此不会执行 flush。

**⏩ 修改后**

```dart
final originalBox = item.box;
await item.delete();
await originalBox?.flush();
```

先保留 box 引用，删除记录后就能刷新同一个 box。
