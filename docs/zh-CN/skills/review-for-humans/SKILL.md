# 帮助人类审核

帮助人类审阅者理解 PR、分支或本地改动：改了什么、是否合理、实现是否优雅得体，以及哪些地方需要关注。仅在用户明确请求时使用此技能，并加载工作所需的技能与规则。

先只读审查选定范围，再按下述范围与验证要求执行用户所选操作授权的效果。只读审查允许捕获比较、解析现有 Git 对象和运行共享差异链接命令；在获得操作授权前，保持被审查文件与 Git 索引不变。

## 确定审核范围

### 选择比较范围

明确任务预期达到的结果，并按下表选择比较范围。通过可用的只读 Git 或 GitHub 接口，例如 CLI、连接器或已认证的 GitHub 界面，获取修改前后的证据。

| 用户指定的范围 | 比较方式 |
| --- | --- |
| PR | 获取该 PR 的改动文件及比较证据，记录其 base 和 head 的提交 ID。审核这个固定的 PR 版本，并应用下文的文件级查看状态筛选。 |
| 分支，可能指定了比较基准 | 确定被审核分支的最新提交和可靠的比较基准，比较两者的共同祖先与该分支最新提交之间的改动，并固定两个提交 ID。无法可靠确定基准时，询问用户，不擅自假定为 `main`。 |
| 本地改动，或未明确指定范围 | 比较暂存区与当前工作区，使用 `git diff` 或等效证据。 |
| 选定文件 | 在适用的比较范围内筛选这些文件，统计和报告筛选后的范围，而不是整个 PR 或分支。 |

明确指定的 PR 或分支比较不包含本地未提交改动，除非用户要求纳入。

### 审核本地修改

本地默认只审查未暂存改动，以索引为修改前版本。跳过仅存在于暂存区的改动；对于部分暂存的文件，只审查未暂存部分。如果已暂存改动随后在工作区中被撤回，这个相对于索引的撤回也是需要审查的未暂存改动。

用户明确要求包含已暂存改动或采用其他本地比较时，覆盖此默认值。空比较保持为空：不要纳入更早的提交，也不要退而审查已暂存改动或最后一次提交。默认排除未跟踪文件；只有用户明确纳入时，才将其作为新增文件审查。

### 筛选 PR 文件

PR 默认跳过当前已认证 GitHub 查看者标记为已查看的文件。通过可用的已认证只读 GitHub 接口获取完整的文件级状态；GitHub GraphQL 通过 [`PullRequestChangedFile.viewerViewedState`](https://docs.github.com/en/graphql/reference/pulls#pullrequestchangedfile) 暴露这些状态。排除 `VIEWED`；纳入 `UNVIEWED` 和 `DISMISSED`，后者表示文件自上次查看后又有变化。

取完所有分页，并在获取文件列表和状态期间检查 PR 的 base 与 head 未变，确保筛选属于固定的版本。当前已查看状态不能用于确定旧 PR 快照的筛选。PR 批准、评论或之前对话中展示过的文件，都不能证明文件的已查看状态。

用户可以明确要求纳入已审核文件，覆盖这一排除项。如果无法获取所需的查看状态证据，说明缺少的前提条件，暂停依赖这些证据的审核，并询问能否获取该证据，或是否不应用这项筛选、纳入其余符合条件的全部文件。将缺失状态视为未知，不视为 `UNVIEWED`。

### 固定快照与待审文件列表

加载具有不同范围默认值的其他审查指导时，保留本技能选定的比较。保存固定审查快照，包含：

- PR 和分支比较的提交 ID。
- 本地比较的修改前后内容和索引基线。即使明确选定的比较采用其他修改前版本，也要保留该索引基线，以便后续完成操作时核对已有的暂存内容，并保留恢复所需的证据。
- PR 筛选所用的查看者身份与文件级状态。

所有范围都维护与 GitHub Files changed 目录树一致的有序文件列表：在每级目录中，先递归列出各子目录里的改动文件，再列出当前目录直属的文件。能获取 PR 实际的同级顺序时使用该顺序；否则分别按名称排列同级目录和直属文件。例如，`src/z/api.dart` 排在 `src/a.dart` 前面；按 `git diff` 的完整路径排序不能保证这种顺序。

在人类审核报告中跳过测试文件：不生成文件报告，也不计入进度或修改项。先应用范围筛选，再统计数量；被跳过的已查看 PR 文件和仅有已暂存改动的本地文件，同样不生成文件报告，也不计入进度或修改项。这些展示筛选不将修改排除在后续分支提交或其必要检查之外。在展示第一组之前，统计其余文件的数量。简要说明范围和排除项，让读者理解总数的含义。如果没有需要审核的文件，说明情况并结束，不拼凑报告或进度比例。

范围、必要指导或源码证据不可用时，包括没有可用的 `HEAD`、无法取得请求的引用或 PR 证据、必要接口不可用，都要指出缺失的前提及其影响，并暂停依赖它的审查。已知文件即使证据不完整，仍计入总数；在该文件报告中解释缺口，必要时使用证据不足的判断。证据不可用不代表可以编造事实、总数或已完成的评估。

评估选定比较及其影响，必要时阅读相关上下文，同时保留文件筛选和测试排除规则。由选定改动引入、触发或加重的缺陷，即使证据位于未修改的代码中，也属于对应修改项的正式评估。与改动无关的既有问题按下文的顺带发现规则处理。

## 准备动态 diff 链接

### 准备输入

每个被审查文件名都链接到该路径的统一 localhost 差异入口。报告和后续操作所用的固定证据应独立于展示链接保存：本地比较使用审查时固定的修改前内容和该路径当前磁盘上的工作区状态，后者可能已不同于接受判断的快照。提供选定比较实际的修改前提交、已知的修改前 blob，或真实的不存在状态；不要替换成最新索引、`HEAD` 或可变分支名。

使用统一 `local_web` 工具，该工具由 `SmartKit plugin resources` 提供，与受审仓库或 cwd 无关。读取其帮助，了解批次格式和输出契约：

```text
python "<local_web>" --help
python "<local_web>" diff --input "<batch.json>"
```

按仓库和 PR 分批提交，每个批次以工作区根目录作为 `repo`，可带默认 `base` 和 `pr` 上下文，并包含非空 `files` 列表。每个文件提供唯一 `id` 和当前 `path`；`title` 默认取该路径。文件显式指定的 `base` 覆盖批次默认值，否则批次必须提供默认值。CLI 帮助定义精确模式；`local_web` 负责验证、基线解析、GitHub 地址构造和 URL 编码。

本地默认范围使用暂存区模式，在保留审核快照的同时准备链接，让工具固定与本次审核相同的暂存区基线，部分暂存的文件也如此。分支和 PR 比较使用实际的固定修改前提交，或已经掌握的 blob；PR 不能使用可变的暂存区。

每次 PR 审核时，从已取得的 PR 元数据中提供批次级的 `pr.repository`、`pr.number` 和完整、固定的受审 `pr.head`。`repository` 指拥有该 PR 的 GitHub 仓库，不是其源 fork，也不是根据本地 remote 推断的仓库。非 PR 审核省略 `pr`。必要的 PR 上下文不可用时，说明缺少的前提，并暂停依赖它的报告。GitHub 是已接受的展示例外，可能显示远端 PR 版本，而非本地编辑。

### 定位文件与工作区

解析暂存区或提交基线时，通过 `base_path` 提供重命名前的路径；当前 `path` 仍是 GitHub 文件目标。

工具构造指向每个文件的 GitHub Files changed URL，并根据当前 `path` 推导默认文件锚点。Agent 不提供完整的 GitHub URL，也不计算锚点。文件可选的 `github_anchor` 使用已经观察到的片段覆盖默认值，不带开头的 `#`；无法取得时省略，让工具推导锚点。准备文件链接无需另外访问 GitHub 或执行网络查询。

即使不知道是否存在 PR 检出，也使用同一命令。`local_web` 根据提供的 PR head 查找并验证当前检出及其已有的关联 worktree：只有一个匹配时自动绑定，有多个匹配时提供页面供人选择，没有匹配或没有可用的本地比较时，转到生成的 GitHub URL。Agent 提供上下文，不负责枚举、验证或选择 worktree。链接准备和展示仅使用已有 Git 数据；不 fetch、clone、写入 Git 对象、切换检出、创建 worktree 或保存任意修改前字节。

### 使用与打开链接

将返回的每个 `id` 和 `title` 与对应文件匹配，并使用返回的 `markdown` 作为文件名链接。返回的 `url` 与 `markdown` 指向同一个 localhost 差异入口；`local_web` 负责选择查看方式和分派回退。

自包含 URL 携带比较上下文，不依赖签名、注册记录或链接到期时间。一旦绑定，就保持该工作区和固定基线；后续编辑或提交不会触发按 PR head 重新匹配或重新路由。Git 对象缺失或仓库不可用属于错误：链接不备份基线，也不允许退回空内容或替换基线。现有工作区中的删除表示当前侧不存在；重命名需要针对新路径生成链接。

存在可用的本地比较时，`local_web` 先尝试 VS Code。明确不可用或启动失败时，PR 回退到生成的 GitHub 地址，其他范围回退到根据当前本地比较计算的 HTML。自动回退和手动链接的 GitHub 导航都留在当前标签页。派发编辑器请求后，页面尝试关闭自身；若浏览器策略阻止关闭，则保留状态和手动回退控件。手动 HTML 控件直接展示本地比较，不尝试编辑器。CLI 正常返回不能证明差异已展示。

只要引用的工作区和 Git 对象仍然存在，差异 URL 在服务重启后仍可使用；普通预览产物的保留期独立管理。文件名链接不需要固定的修改后快照，但报告示例和审查操作验证仍需要。

### 处理链接不可用的情况

必要的链接生成不可用时，保留诊断，并按共享资源的不可用处理规则暂停依赖它的报告；依赖这些能力的链接保持未完成，不用旧工具或手写地址替代。使用统一工具的帮助恢复服务；报告观察到的导航限制，只有实际观察到打开成功时，才作出相应声明。不只为获得链接而发布仓库修改。

## 围绕文件解决的问题进行说明

需要校准简洁或展开说明、顺带发现或结尾菜单的呈现方式时，参考[报告示例](references/report-examples.md)。这些示例展示下述格式，不增加审查要求。

所有报告中的 emoji 都放在加粗范围之外，保留其旁边文字的强调。强调词语、短语、标识符或标签时，将其外围的分隔符和末尾标点放在加粗范围之外；有意强调整句时，可以保留句子本身的标点。保留代码、标识符和路径中的固有标点。

每个文件以 `📄 **[path](diff-destination)**` 形式开头，使用返回的动态 diff Markdown，并简要说明文件的职责和整体修改。源码链接和相关行号可以作为这个必需文件名链接的补充。用通俗语言解释修改对用户或调用者意味着什么，同时保留影响判断的技术细节。

按照业务问题或人类容易理解的场景划分修改项，优先将相关修改放在一起。只有逻辑上相互独立，或无法用一个简单例子共同解释时，才拆分。方法、diff 块和单个实现步骤本身不足以成为拆分理由。例如，记录尚未完成的工作、拒绝新工作，以及关闭资源前等待，可以合成一个“关闭时安全完成已有工作”的修改项。

顺带的小修改，例如注释拼写错误，可以在文件总说明中提及，也可以省略。每个 l10n 翻译文件作为一个整体修改项说明，不把其中的字符串拆成多个修改项。

严格按 `🔧 **M1** - **<modification title>**` 标记修改项，随后依次为 M2、M3 等，在所有文件和分组中连续编号。在问题列表、建议列表、选择和复审中复用这些以 M 为前缀的 ID。

### 每个修改项都从两个独立维度判断

所有修改项采用同样的思考方式：确认修改前后发生了什么变化、产生什么影响、有哪些证据支持，再分别判断合理性和优雅性。两个维度适用于所有修改，包括修复、新功能、重构、文档和翻译。文字的优雅性侧重表达和组织是否清楚；代码的优雅性侧重机制和结构。调整的是表达篇幅，不是评估的覆盖范围。

每个修改项都使用固定的 ⚖️ 标记合理性、 🎨 标记优雅性，简版修改项也如此。两个判断各自独立成段，直接使用 emoji 加结论，不再重复维度名称。每个维度都要给出明确结论和理由；emoji 区分的是维度，不表示评价是正面还是负面。

- ⚖️ **合理** 。 修改服务于预期任务；行为正确且安全，范围符合任务，现有证据足以支持其成本。
- ⚖️ **不合理** (P1): 实质缺陷、不必要的范围扩张或缺乏依据的成本，使改动不符合任务要求下的合理选择。替换为实际的 P0–P3 严重性，解释证据支持的影响，并给出具体建议及其在相同要求下的优势。只加粗判断词；严重性使用普通 ASCII 括号，后接 ASCII 冒号。更优雅的替代方案、小优化或风格偏好本身不达到这一门槛。
- 🎨 **优雅** 。 修改在恰当的职责或位置解决根本问题，结构清楚，尽量减少不必要的状态、分支和重复。解释哪些选择使其易于理解和维护。
- 🎨 **可改进** 。 行为可以是合理的，但机制或表达带来可以避免的复杂度或重复。指出可以改进的具体结构，在有依据时提出更简单的方案，并解释对维护或理解的好处。区分这些好处与个人风格偏好。
- ⚖️ **证据不足** 。 或 🎨 **证据不足** 。 说明什么阻碍了对该维度的可靠判断，以及哪些证据可以解决问题。区分已确认的事实与假设。一个维度可以有充分依据的结论，而另一个维度仍缺少证据。

修改可以合理但不够优雅。单独的优雅性问题属于可选的改进建议，不触发必须选择修复或忽略的暂停。如果同一结构还造成有证据支持的实质性缺陷、风险或缺乏充分依据的成本，也要在合理性下独立报告该影响；这类不合理问题遵循正常的暂停与修复流程。

只给不合理问题分配 P0–P3，不给纯粹的优雅性建议或风格偏好分级。P0 表示需要立即干预的关键问题，P1 表示需要尽快修正的严重问题，P2 表示普通优先级问题，P3 表示影响较小但值得修正的问题。依据证据支持的后果和触发条件分级，而不是依据代码改动量。

将底层审核发现的重要问题及限定条件带入相应修改项；当规范问题与任务范围问题的区别影响判断时，保留各自依据。通俗解释仍须保留可能改变人类 reviewer 决定的限制。报告实际执行的检查，并与修改作者提供的检查结果区分。

### 选择展示详略

根据读者需要理解什么来选择形式，不依据 diff 行数：一行改动也可能影响异常处理或持久化。两种形式都保留上述两个独立且有理由的判断。

- **简洁形式** ：行为变化直接、影响范围清楚，且没有需要展开的实质风险或取舍时使用。用一个简短的普通段落解释修改前后的行为，不加 emoji 前缀、示例、代码片段、示意场景或固定的修改前后标签。随后先放 ⚖️ 判断段落，再放 🎨 判断段落。
- **展开形式** ：用于复杂机制、重要契约、实质风险或问题、重要取舍或关键证据缺口。先在 ⏪ **修改前** 下解释行为，再在 ⏩ **修改后** 下解释行为，随后依次给出 ⚖️ 和 🎨 判断段落。不必另设“不修改的后果”字段。

展开说明代码改动时，使用保留的审核快照，以项目语言展示简短的修改前后代码。保留能解释机制的条件、状态变化或调用顺序；与判断有关时，也要包含对应的错误或生命周期分支。用通俗语言解释旧代码如何产生原有行为、新代码如何改变它；只说好处或转述 diff，不能解释这层因果关系。简化例子必须能让人看出是示意，保留所比较的行为，并与逐字引用的源代码区分开。代码无助于理解时，例如说明文字组织，可以省略。

使用足以说明问题的最小对照。只有不同的行为或审核发现需要单独解释时，才增加另一个简短例子；同一机制的重复变体只会增加篇幅，无助于理解。保留相关限定和两个维度的判断，让每个例子聚焦于它所支持的决策。

## 展示分组并提供操作

### 分组展示

文件之间用 `---` 分隔，按既定顺序展示完整文件。加入某个文件后，本组修改项达到或超过 10 项，就结束本组。文件不能拆分，单个文件超过 10 项也如此。例如，含 3 项和 8 项的两个文件合为一组，共 11 项；下个文件留到下一次回复。范围结束时，展示最后不足 10 项的一组。

每组以 `---` 和 📊 **审核进度** ： **已展示文件数 / 需要审核的文件数** 结尾，明确说明文件已展示。统计已展示文件数，不统计修改项或已有确定结论的判断。

跨回复保留快照、有序文件列表、每个已展示分组的文件和已审查改动、下一个未审查位置、下一个修改项 ID、判断、问题状态及未完成的优雅性建议。保留每组的记录状态和已验证操作结果，让最终完成能够覆盖之前的分组，包括未记录就继续的分组。

提交分支全部修改时，可能一并提交尚未展示的分组，使本地工作区变为干净状态。保留这些分组固定的修改前后证据，沿保存的列表继续；不要根据新索引重建剩余审查范围，也不要因为修改已经提交就移除文件。重新评估发生变化的内容或影响，同时将此前未展示的文件与已完成的审查区分开。

### 报告顺带发现

在选定审核所需的阅读中，只有现有证据同时证实问题本身及其与选定改动无关时，才报告这个无关的既有问题。这种提醒渠道不授权扩大为全面审计，也不绕过文件筛选和测试排除规则。有待证实的猜测不列入顺带发现。

首次报告观察项时，只在分组结尾的 `📌 **Incidental observations (outside this review's scope)**` 下展示，放在文件块和修改项评估之外。遵循下述结尾章节顺序；为空时省略。使用独立的 **O1** 、 **O2** 等 ID，在整个报告中连续编号；跨分组及专门的修复复审保留其身份和状态，不重复列项或重新编号。

每项顺带发现给出简短标题、源码位置（有可用源码链接时附上）、支持证据及影响、与选定改动的关系，以及具体建议和收益。确认问题此前已经存在，且这次改动没有引入、触发或加重它。首次报告观察项时的源码引用不生成受审文件块，也不要求为额外文件准备 diff 链接。

观察项不增加已审查文件、修改项或进度，并与 **待修复问题** 和 **可选优化** 分开。只作为建议保留的观察项既不阻断推进或完成，也不授权修复或扩大 Viewed 集合。不带限定的 **修复** 、 **优化** 和 **全部忽略** 都不包含 O 项。

明确选择处理某个 O 项时，需要另外确立目标、授权、证据和检查。在将其标为已修复或将后续修改纳入完成操作前，必须按下文执行专门的 O 项复审。除非明确扩大主审查范围，这项后续工作仍与主审查分开；若其修改位于目标分支，则按与其他修改相同的说明和验证要求，纳入分支全部修改的提交。

### 选择操作

面向人类的标签、摘要、操作名称和输入提示使用对话所用的语言。操作名称及说明统一使用该语言，不并列展示另一种语言的名称。按含义理解自然语言选择，不要求用户使用命令语法。

修改项 ID 选择其相关问题或建议。不带限定的 **修复** 、 **优化** 以及明确的 **全部忽略** ，覆盖本报告在对应维度中已经展示且尚未处理的项目，包括之前的分组。选择子集只影响该子集。在菜单中说明适用范围和数量。推进表示从保存的位置展示下一组，或结束已经没有后续文件的范围。

| 操作 | 效果与选择范围 |
| --- | --- |
| **修复** | 修复待处理的不合理问题：未限定时修复全部，否则只修复选定的问题。 |
| **忽略** | 只将选定的问题记录为已忽略，保留其级别和影响。只有一个明确的问题时，无需重复指定 ID；否则询问要忽略哪些，除非用户明确选择全部。其他问题仍待处理。 |
| **优化** | 实施有充分依据、仍待处理的 🎨 **可改进** 建议：未限定时实施全部，否则只实施选定的建议。其他待处理问题不受影响。 |
| **通过并继续** | 按下文完成说明和确认后，提交目标分支全部待提交修改，执行已说明的 PR 发布和 Viewed 记录操作，核验结果后再推进。 |
| **继续** | 推进，不暂存、提交、推送或标记 Viewed。保留尚未发布的修改和未实施的建议。 |

**通过并继续** 与 **继续** 是共享下述推进门槛的同级操作；完成操作另外包含分支提交和适用的 PR 操作。区分三个范围：选定文件及差异决定人类审核范围和进度；目标分支的全部待提交修改决定提交范围；只有实际审核并展示、且符合条件的路径才决定 Viewed 记录范围。因此，提交包含已暂存、未暂存和未跟踪的修改，包括测试、配套文件，以及尚未展示的文件或分组中的修改。纳入提交不能证明这些修改已经审查。纳入前须满足下文的准备和确认要求。

中途的 Viewed 记录覆盖整个当前分组，包括最近展示的复审，以及本次选择明确纳入、此前已展示且符合条件的路径。对只选择个别修改项的请求要先澄清，不能当成整组完成或继续。所有文件都已展示后，将这两个操作称为 **通过并结束** 与 **结束** 。 **通过并结束** 仍提交分支全部修改，并完成所有已展示、已审核分组的 Viewed 记录，包括此前选择 **继续** 的分组。在最终菜单中说明这些范围。覆盖每个分组并复用已经验证完成的步骤；某部分受阻时，完成操作不可用，不能缩小范围。 **结束** 保持 **继续** 的不记录语义。

用户选择完成操作，仅授权选择前已说明的实际效果和范围。本地或分支审核允许执行已说明的本地提交，无需关联 PR，但不提供推送权限。对于已核实的 PR，单独说明完整发布差异和 Viewed 集合，并取得该次推送的授权。完成和继续操作都不正式批准或合并 PR。被忽略的问题仍记为已忽略，不表示已修复或认可。

### 生成结尾菜单

每次结尾都用下表判断完成操作是否可用及其效果，包括普通分组、独立复审、修复／忽略／优化后的菜单、最终分组和中断操作恢复。采用上述完成范围，在没有后续文件时使用最终操作名称。生成结尾前，完成能够推导且已获授权的只读检查来确定状态；用户应选择效果，而不是判断是否需要发布。

两个操作共用相同的推进条件：所有已展示的不合理问题都已修复或明确忽略，审查所需的正确性和版本证据可获得，必要的审查检查和受影响部分的复审已完成，此前已选定的完成操作也已核验完成。可选改进或仅缺少优雅性证据，不阻挡推进。完成操作特有的前提，包括对不影响已审核改动的额外分支内容所需的检查，可以使 **通过并继续** 不可用，而不影响 **继续** ；已选定但未完成的操作则会阻挡两者推进，直到恢复过程核验完成。

| 状态，按优先顺序判断 | 完成状态、效果与可选操作 |
| --- | --- |
| 仍有待处理的不合理问题，包括只修复或忽略了部分问题的情况 | 完成和继续操作都不可用：列明待处理 ID，以及所需的修复或明确忽略。提供 **修复** 、 **忽略** ；仍有充分依据的建议时，也提供 **优化** 。 |
| 缺少审查所需的正确性或版本证据，必要的审查检查未完成或失败，或受影响的审核版本已过时 | 完成和继续操作都不可用：说明缺失的证据、检查或复审及其补救办法。完成已获授权的工作后，再生成菜单。 |
| 已选定的提交、Viewed 或发布操作尚未完成 | 报告已确认、失败和未知的步骤。解决阻碍后，提供同一个完成操作，用于恢复剩余步骤。普通的 **继续** 仍不可用；遵循下文的恢复规则。 |
| 推进已就绪，但无法确定完成操作所需的目标、接口、检查或安全范围 | 完成操作不可用：说明具体前提和补救办法；需要 GitHub 记录或发布时，前提包括经过核实的 GitHub PR 审核目标。 **继续** 可独立选择。 |
| 额外内容尚未确认纳入 | 说明非本次对话引入或来源不明的具体修改；计划发布时，也包括已有的未推送提交。提交或推送前，须取得明确的纳入确认；其他前提均已满足时，可提供 **确认纳入，通过并继续** 这一组合选项，只要选项文字明确指出已说明的额外内容。 **继续** 仍可独立选择。 |
| 完成操作已就绪，没有剩余提交、发布或 Viewed 写入 | 说明已经核实的分支状态和记录结果。并列提供 **通过并继续** 和 **继续** ；前者复用已核验结果并推进，不重复写入。干净分支无需创建空提交。 |
| 本地或分支审核已就绪，仍有待提交修改 | **通过并继续** 暂存全部已说明的分支修改，并通过正常钩子提交，核验提交和剩余状态后推进。 **继续** 直接推进，不提交。无需 PR 或推送。 |
| PR 没有尚未发布的分支修改 | **通过并继续** 核对固定的 PR 版本和查看者，将选定范围内符合条件的已审核路径标为 Viewed，核验每项回读后推进； **继续** 直接推进，不作标记。遵循下文的 PR 记录保护规则。 |
| PR 存在等待发布的分支修改 | **通过并继续** 在需要时提交全部已说明的待提交修改，推送已完整说明并获授权的分支差异，核验生成的 PR 版本，仅将已说明且符合条件的已审核路径标为 Viewed，核验每项回读后推进。 **继续** 保留本地修改，不发布也不标记。提供完成选项前，须先满足下文的发布和记录前提。 |

部分范围已完成记录时，复用已核验完成的步骤，只对剩余工作写入。已就绪的菜单中，仍有充分依据的待实施建议时，追加 **优化** 。本技能的 PR 发布流程要求已知且经过核实的 PR；普通分支或本地比较并不提供远端写入目标。复用已经存在的提交；PR 已包含完整的预期分支状态时，无需进行不必要的推送。

每次结尾都明确交代完成操作，包括修复成功后只剩继续可用的情况。就绪时说明具体效果和范围；适用时说明哪些记录已经完成；否则解释 **通过并继续** 为什么不可用或不适用，并给出下一步补救方式。范围已耗尽时，在该状态说明中使用 **通过并结束** 。不可用或不适用的状态放在 **可用操作** 之外：它是解释性状态，不是可执行选项。

进度之后按顺序使用下列 Markdown 部分，省略空部分：

1. **待修复问题** ：包含之前分组中尚未处理的问题。严格使用 `**M1** (P1): <impact summary>` 格式，替换为实际 ID 和严重性；只加粗 ID，ASCII 括号和冒号保持普通文本。
2. **可选优化** ：包含之前分组中尚未完成且有依据的建议，每项给出 ID、改进方案和收益。
3. 📌 **顺带发现（本次评审范围外）** ：使用上文定义的独立 O 项。
4. **可用操作** ：在列表中从 A 开始，用连续的大写英文字母（`A`、`B`、`C` 等）标记每个可执行选项，即使只有一个继续或恢复选项也要标记。简短描述实际效果，不写执行步骤；说明完整的分支提交范围、额外内容的确认，以及需要时的发布差异和符合条件的 Viewed 集合。每次生成菜单时重新分配字母；这些字母标识当前菜单中的选项，M 和 O ID 则在整个报告中保留各自项目的身份。

以一句简短指令提示用户输入操作字母，例如“请输入操作字母。”没有剩余选择时，直接结束，不再显示输入提示。某种状态的呈现方式需要说明时，参考[结尾示例](references/report-examples.md#example-closings-for-different-results)。

范围已展示完时，收到“继续”也只有在推进条件满足时才结束。用户始终可以明确停止或暂停：按实际情况报告展示进度、未解决或已忽略的问题、证据缺口、尚未提交或发布的修改及未完成操作，不宣称任务成功完成。展示完成不表示问题全部修复，也不表示修改全部提交或发布。

## 执行选定操作

### 理解回复

按最近一次展示的菜单解释操作字母，不区分大小写，再应用该操作已有的范围和授权要求。以 M 为前缀的修改项 ID 和以 O 为前缀的观察项 ID 用于选择项目，而不是菜单操作。继续支持自然语言选择；即使菜单没有列出该操作，只要满足前提并具备授权，也按其含义处理。

所需效果尚未说明或获得明确授权时，先解释并取得选择，再执行写入；历史上仅说明会暂存或标记 Viewed 的“通过”，不提供提交或推送授权。用户在有阻塞时要求推进，简短拒绝，指出阻塞项，并重新生成带字母标记的菜单，提供适用的修复、忽略或补救选择；“继续”从不表示“忽略”。范围或所指菜单含糊、操作字母或项目 ID 无效、要求冲突，或用户只对含糊菜单表示同意时，先澄清；只有前一个问题明确指定操作时，“可以”才授权该操作。根据用户提供的证据重新评估有争议的问题，不把反驳当作忽略。回答问题时，不将提问解释为修改或推进的授权。

### 修复或优化，然后复审

对已获授权的修复或优化，包括单独选定的 O 项修复，加载必要指导，将编辑限制在选定问题、建议或观察项及其必要配套改动内，并运行要求的检查。优化应保留受支持的行为和契约。每当已审查内容发生变化或修复了 O 项时：

1. 成功完成要求的检查，刷新相关修改前后快照，并重新生成或验证差异链接。O 项修复的证据与主审查快照分开保留。对于尚未发布的 PR 改动，同时保留固定的远端版本和预期发布的、已检查的本地内容。
2. 独立复审所有已修改或受影响的先前审查部分，包括意外变化。在专门的回复中展示完整文件块、更新后的说明和两个判断，与尚未展示的文件分开。对于 O 项修复，即使原始观察项位于主审查范围之外，也要独立评估修复后的行为及受影响的依赖。单独展示 O 项复审，包含源码位置、修改前后说明，以及分别给出理由的 ⚖️ 和 🎨 判断；保留其 O ID，不分配 M ID。
3. 保留修改项 ID 和原始分组归属，主审查中每个已展示文件只计数一次，并解释版本变化。除非用户明确扩大范围，O 项复审不增加主审查的文件、修改项、进度或 Viewed 资格。仅在范围实际变化时更新主审查文件列表和总数。只有必要检查和复审确认结果后，才能将问题或 O 项标为已修复、将建议标为已完成；否则保留未解决状态，说明剩余工作。

单独选择 **修复** 、 **忽略** 或 **优化** ，在重新生成菜单并交代完成状态后结束，不自动推进。明确的组合指令授权按顺序执行各步骤，例如修复、检查、单独展示复审、完成已说明的分支提交和 PR 发布、将符合条件的文件标为 Viewed，再推进。已授权步骤继续执行，无需例行重复确认；新发现的额外内容仍须获得明确的纳入确认。发现新问题、检查失败或发生实质性变化时，暂停依赖它们的步骤，并重新生成菜单。有单独授权的优化仍可在问题待处理时执行，但不满足推进条件。

### 准备提交分支全部修改

提供完成选项前，确定将要提交修改的具体仓库、分支和工作区。不能用当前检出的其他分支替代受审分支。通过可用的只读 Git 证据，清点其全部已暂存、未暂存和未跟踪修改，以及拟议推送会发布的所有提交。将分支最新提交、索引条目、工作区内容和适用的未跟踪文件内容作为操作基线，与固定审查快照一并保留。已有提交保持原状，不为了让完成操作产生写入而重新创建提交。

提交包含分支全部待提交修改，不限于当前分组、本次对话的编辑或报告中符合条件的路径。清点测试、必要的配套及生成文件、选定文件范围排除的内容、仅有已暂存的编辑，以及未跟踪的源文件。遵守仓库对忽略文件、敏感文件或临时文件的限制；某项候选修改无法安全纳入时，说明障碍并与用户确定预期范围，不悄悄省略，也不改为只提交某个子集。对于部分暂存文件，比较两部分差异，确定应提交的一致的最终工作区内容；保留原始索引版本用于恢复，并说明工作区取代了哪些已暂存内容。最终内容的冲突未解决时，完成操作受阻。

根据当前对话记录的操作和基线证据判断来源，不根据作者姓名、时间戳、分支名或看起来干净的差异推断。区分本次对话引入的修改、其他地方引入的修改，以及无法确认来源的修改，同文件中混合来源的改动块也要区分。纳入后两类内容前，说明受影响的路径或提交、额外修改的作用及其重要后果。请求用户明确确认将这些具体额外内容纳入提交，以及适用时的发布。内容和效果未变时，原有确认继续有效；笼统认可已审核分组，不能确认尚未说明的额外内容。缺少确认或用户拒绝时，保留修改，让提交分支全部修改的完成操作保持待处理。提供普通继续选项，或请求调整范围；不悄悄退回只提交本次对话的修改。

说明完整提交和任何推送与已展示审查的范围有何不同。同一对话中引入但未进入人类审核范围的修改，虽然无需额外确认来源，仍须清点并执行适用检查。对整个预期提交和发布差异运行要求的检查，包括配套和测试修改，并重新评估它们对已审查内容的影响。差异中包含的每项已授权 O 项修复，都须完成专门复审；O 项修复的检查或复审未完成或失败时，阻断依赖它的完成操作。影响变化时，展示受影响的主审查复审；未展示和已排除文件仍不计入进度或 Viewed 集合。确认额外内容只授权纳入，不证明审核已完成，也不免除必要检查或 O 项复审。

### 提交分支修改

只有完整清点、必要检查、受影响部分的复审、范围说明和所需额外内容确认均已完成，才能执行。整个验证及重试期间，保留选定操作及其基线。

1. 根据准备好的清单和固定审查证据，重新核验目标分支最新提交、索引和工作区。写入前解决状态偏移：刷新清单和检查，复审受影响的已展示内容，并对发生变化或新发现的额外内容或效果重新取得确认。
2. 暂存全部已说明的最终内容，包括适用的新增和删除，并验证完整索引代表预期目录树。保留原始已暂存和未暂存状态的恢复证据。没有剩余待提交差异时，核验并复用已有提交，不创建空提交。
3. 通过正常仓库钩子创建提交。根据预期结果核验生成的提交、父提交和完整目录树，然后检查索引和工作区是否仍有修改。钩子引入的修改须完成适用检查及受影响部分的复审；超出已确认内容的修改还须在后续写入或推进前更新说明并取得确认。命令成功本身不能证明完整完成。
4. 记录已核验的提交和剩余状态。只有全部预期分支修改均已提交，且没有无法解释的残留内容，才算完成。本地或分支审核随后可直接推进，无需 PR 或推送；PR 操作则继续执行下文另行授权的发布和记录步骤。

### 记录已审查的 PR 文件

提供 PR 完成选项前，确立已验证的 GitHub PR 审查目标，以及支持所需查看者、版本和逐路径回读的已认证接口。仍需标记时，该接口还必须能将文件标为 Viewed。PR 必须已包含通过检查和审查的版本；必要时先执行下述发布流程。

Viewed 对应某个 PR 版本中的整个文件。对于选定 Viewed 集合中的每个路径，将其在预期发布的 PR 比较中的完整差异与保留的已展示评估逐一核对。每个改动块都必须被覆盖，包括预期会纳入、且独立于此前已审核修改的额外内容。提供会标记该路径的完成选项前，须通过专门复审展示并评估缺失内容，包含两个判断。保留适用的 M 或 O 身份及原始分组归属，不重复统计文件；对于选定主审查范围之外的路径，O 项复审仍不使其获得 Viewed 资格。纳入确认、检查通过或此前改动块的影响未变，都不能补足缺失的审查覆盖。

无法取得必要的审查覆盖，或需要决定是否调整审查范围时，保持该路径未标记，并说明需要何种审查或范围选择。完成操作不可用；若此前已经选定，则保持待处理。保留其 Viewed 集合和已展示进度，不悄悄移除该路径。发布后，须针对实际 PR 版本再次验证相同的覆盖，再执行记录。

1. 在写入前立即验证查看者身份及固定的 base 和 head，并确认每个选定路径当前的完整 PR 差异与已展示的审查证据一致。
2. 只标记选定完成范围内符合条件、仍等待 Viewed 的已审查路径。
3. 回读每个选定路径的 `viewerViewedState` 和 PR 版本，包括复用已完成标记的路径。推进前，所有选定路径都必须为 `VIEWED`，且记录期间两个提交 ID 都未变化。

版本变化时，需要对受影响部分复审并取得新的选择；将较新版本标为已查看，不能证明它已接受审查。

### 将分支修改发布到受审 PR

使用可用的 Git 和已认证 GitHub 读写接口，例如 CLI、连接器或界面。提供会发布修改的完成选项前，确定具体仓库、PR、源分支、查看者、写入能力、远端 base 和 head，以及完整的待推送提交历史。按上文准备完整分支范围，包括已有的未推送提交和全部待提交修改，并说明该推送将发布的完整差异。对于其中非本次对话引入或来源不明的内容，即使已经在本地提交，也须说明并取得明确确认。发布范围可以超出人类审核范围和 Viewed 集合；纳入发布从不意味着已经审查。无法通过普通推送将完整分支发布到已验证的源分支时，说明所需前提，不暗中变基、强制推送或排除额外提交。

按以下顺序执行选定操作：

1. 核对固定的远端 base 和 head、审核过的修改前后内容及受影响的依赖，以及将要发布的完整差异和提交历史。确认实际发布差异、额外内容的确认及符合条件的已展示路径与已说明的选择一致；核对每个路径的内容和固定的查看者。
2. 需要时，执行并核验上文提交分支全部修改的流程，复用已核验的现有提交。钩子执行后、推送前，重新核验完整的待推送差异；意外变化须完成适用检查、受影响部分的复审及更新后的确认。
3. 正常推送到已核实的 PR 源分支。回读远端 head 和 base，确认预期提交，以及发布的完整差异与经过检查和授权的分支状态一致，且已展示的审查对符合条件的路径仍然有效。
4. 对已说明且符合条件的已展示路径应用上文的 PR 记录保护规则；选定最终累计范围时，也包括该范围。只标记仍待 Viewed 的路径；回读每个选定路径的状态及 PR 版本。全部路径都须在核实过的 base 和 head 上为 `VIEWED`。
5. 确认操作完成，从保存的位置继续，或在范围已展示完时结束。

预期的新 head 需要核对，无需重复已经覆盖的审查。即使额外内容是有意发布的，也须应用上文对每个路径完整审查覆盖的要求。内容、base 或受影响依赖发生意外变化时，复审受影响部分；文本相同本身不能证明影响不变。结果不再代表已授权、已审核的版本时，刷新快照并取得新的选择。发布过程中保留有序文件列表、分组归属、下一个位置、修改项 ID、决策和逐组记录结果。

### 恢复未完成的操作

必要接口不可用，或写入、验证失败时，暂停，不推进，不自动回滚，也不改为 **继续** 或 **结束** 。报告已确认、失败和未知的步骤，包括精确提交、发布状态、分支剩余修改，以及部分暂存或 Viewed 路径，然后按状态表生成结尾状态。

保留完整分支清单及来源判断、纳入确认、选定的发布和 Viewed 范围、分组快照、PR 版本、查看者和恢复位置。恢复中途操作不能悄悄将其 Viewed 集合扩大到最终范围，也不能未经重新评估就纳入新的分支内容。响应丢失后，先检查实际的本地与远端状态，再判断是否发生了写入。恢复就绪后，继续同一个 **通过并继续** 或 **通过并结束** 操作，只描述剩余且有依据的步骤，不重复提交或重做已成功的写入。

只有全部必要回读成功，所选操作才算完成。明确停止可以留下未完成操作，但必须报告该残留状态。成功完成应保留已保存的进度和恢复位置；只有范围实际变化时才修改总数，不要重新应用未暂存或 Viewed 筛选来移除已经展示的文件。
