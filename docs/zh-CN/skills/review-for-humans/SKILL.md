# 帮助人类审核

帮助人类 reviewer 理解改了什么、是否合理，以及哪些地方需要留意。仅在用户要求时使用此 Skill。在用户提供的范围内进行只读审核；只有用户明确选择下文所述的修复操作时，才修改被审核的内容。

加载必要的 Skill 和 Rule 进行审核。人类报告中的标签和操作提示都使用对话要求的回复语言；英文源文档中的标签表示其对应含义。

## 确定审核范围

明确任务预期达到的结果，获取用户提供的修改及其修改前后的证据。固定审核版本，并保留用于展示报告的有序文件列表。所有审核范围的展示顺序都与 GitHub 的 Files changed 目录树一致：在每个目录内，先递归列出各子目录中的改动文件，再列出该目录直属的文件。能获取拉取请求的实际目录树时，采用其中的同级顺序；否则，将同级子目录和直属文件分别按名称排序。例如，`src/z/api.dart` 排在 `src/a.dart` 前面；直接对 `git diff` 中的完整路径排序，无法得到这种顺序。用户只要求审核选定文件时，统计和报告这部分范围，而不是整个拉取请求。

完全跳过测试文件：不审核，也不计入进度或修改项。在展示第一组之前，统计用户提供的范围中其余文件的数量。简要说明范围和排除项，让读者理解总数的含义。如果没有需要审核的文件，说明情况并结束，不拼凑报告或进度比例。

无法获得范围、必要指导或源证据时，说明缺少什么及其影响。暂停依赖这些信息的审核，不编造事实、总数或已经完成的评估。已知文件即使证据不完整，仍计入总数；在该文件的报告中解释缺口，并在必要时给出“证据不足”的评价。

## 围绕文件解决的问题进行说明

每个文件以 **📄 文件：路径** 开头，简要说明文件的职责和整体修改。可获得源链接和相关行号时，一并提供。用通俗语言解释修改对用户或调用者意味着什么，同时保留影响判断的技术细节。

按照业务问题或人类容易理解的场景划分修改项，优先将相关修改放在一起。只有逻辑上相互独立，或无法用一个简单例子共同解释时，才拆分。方法、diff 块和单个实现步骤本身不足以成为拆分理由。例如，记录尚未完成的工作、拒绝新工作，以及关闭资源前等待，可以合成一个“关闭时安全完成已有工作”的修改项。

顺带的小修改，例如注释拼写错误，可以在文件总说明中提及，也可以省略。每个 l10n 翻译文件作为一个整体修改项说明，不把其中的字符串拆成多个修改项。

修改项使用 **🔧 1.** 、 **🔧 2.** 等标签，附上标题，并在同一报告中跨所有文件和继续展示的分组连续编号。

每个修改项纵向依次展示 **⏪ 修改前** 、 **⏩ 修改后** 、 **评价** 。解释前后的行为，无需单列“不改的后果”。优先使用项目语言中的简短实际代码，只保留说明场景所需的部分。用通俗语言解释代码，准确保留所比较的行为。简化例子必须能让人看出是示意，不要让读者误以为是逐字引用的源代码。修改很简单，或代码无助于理解时，可以省略例子，例如注释修正。

每个修改项都要给出有依据的评价，在标签前加上对应的 emoji：

- **✅ 合理：** 修改服务于预期任务，现有证据足以支持其行为和成本。
- **❌ 不合理：** 存在实质性缺陷、不必要的范围扩大，或有证据支持的明显更好方案，使当前修改成为较差的选择。为每个发现标注 P0 至 P3 的问题级别，并解释支持该级别的影响。给出具体建议，并解释为何在相同要求下更好。仅有微小优化或风格偏好，不足以达到这一标准。
- **⚠️ 证据不足：** 说明什么阻碍了可靠判断，以及哪些证据可以解决问题。区分已经确认的行为和假设，不暗示修改已获认可。

P0 表示需要立即干预的严重问题；P1 表示需要尽快修正的重大问题；P2 表示正常优先级的问题；P3 表示影响较小但值得修正的问题。根据有证据支持的后果及其适用条件确定级别，而不是根据代码修改量。例如： **❌ 评价：不合理（P1）。** ，随后说明影响和建议的修复方案。

将底层审核发现的重要问题及限定条件带入相应修改项；当规范问题与任务范围问题的区别影响判断时，保留各自依据。通俗解释仍须保留可能改变人类 reviewer 决定的限制。报告实际执行的检查，并与修改作者提供的检查结果区分。

## 每次展示一组并处理问题

文件之间用 `---` 分隔。按既定顺序加入完整文件，直到本组修改项总数达到或超过 10，再结束本组。一个文件不能拆到多组。如果 A 文件有 3 项，B 文件有 8 项，就一起展示为含 11 项的一组；下个文件从下一次回复开始。单个文件超过 10 项时，仍完整放在一组。范围结束时，展示最后不足 10 项的一组。

每组末尾先展示 `---`，再展示 **📊 审核进度：已展示文件数 / 需要审核文件总数** 。这统计的是已展示的文件，不是修改项，也不表示判断已确定。跨回复保留审核版本、有序文件列表、下一个未审核位置、下一个修改项编号、判断和问题状态。

有待处理的不合理问题时，在进度之后列出 item 编号和问题级别。最后一句提供 **修复** 和 **忽略** 两个选择，然后等待；最后一组也如此。多个 item 待处理时，最后一句必须要求忽略时指定编号；只有一个时无需编号。选择含糊时先澄清，不理解为忽略全部。单纯回复继续不能解决这一选择。

**修复** 授权在适用的权限与约束内修复尚待处理且未被忽略的问题。加载必要指导，将修改限定在解决这些问题上，并执行必要检查。检查通过后，按下文重新审核；只有重新审核确认问题已解决，才标记为已修复。修复受阻或检查失败时，说明剩余问题及所需条件，暂停推进。

**忽略** 保留选定 item 的内容，将其问题及级别记录为已忽略，不表示已修复或认可。如果仍有其他待处理 item，提供剩余的选择并等待。全部处理完后，从保存的下一个未审核位置继续；范围已审核完则结束。

已审核内容发生变化时，刷新审核版本，重新审核此前已审核、但被该变化改动或影响的每一部分，包括原问题之外的改动。以完整文件块展示更新后的解释和判断，使用专门的回复展示复审，与尚未审核的文件分开展示。修复产生了新的内容，值得人类 reviewer 在继续之前单独关注。保留现有 item 编号，明确说明版本切换，必要时重建文件列表和总数。重新审核发现的问题沿用修复或忽略的选择；只有受影响部分均已重新审核，其待处理问题已修复或被明确忽略，才能推进。

没有待处理的不合理问题而仍有文件时，普通分组以 **继续** 提示结尾并等待；收到回复后，从下一个文件开始。修复后的独立复审也采用同样的暂停方式：展示复审结果，提示用户回复 **继续** 并等待，收到回复后再审核剩余文件。忽略则按上文规定自动继续。所有文件均已展示且没有待处理的不合理问题时，直接结束，不再提示继续。区分展示完成与问题解决，保留已忽略的问题和证据缺口。

## 参考报告

参考以下形式，根据用户调整详略。措辞可以灵活，但须保留文件总说明、业务修改项、纵向比较、评价和进度。以下文件和代码仅为示意，不是对某个仓库的审核发现。假设删除一条记录后，该记录会脱离其存储 box，而任务要求删除后执行 flush。选定范围包含以下两个非测试文件。

**📄 文件：`lib/item_storage.dart`**

这个文件负责保存和删除记录。这次修改保留存储 box 的引用，使删除记录后仍能刷新这次删除。

**🔧 1. 删除后，仍刷新原来的存储 box**

**⏪ 修改前**

```dart
await item.delete();
await item.box?.flush();
```

删除后，`item.box` 变为 null，因此不会执行 flush。

**⏩ 修改后**

```dart
final originalBox = item.box;
await item.delete();
await originalBox?.flush();
```

先保留 box 引用，删除记录后就能刷新同一个 box。

**✅ 评价：合理。** 通过较小修改，直接修复承诺的删除行为。flush 失败仍须传递给调用者；flush 不会回滚删除。

---

**📄 文件：`l10n/en.json`**

这个文件提供英文界面文案。修改后的标签明确说明操作会删除账号；该文件的所有翻译修改一起审核。

**🔧 2. 明确账号删除按钮的含义**

**⏪ 修改前**

```json
{"deleteAccount": "Delete"}
```

按钮没有说明会删除什么。

**⏩ 修改后**

```json
{"deleteAccount": "Delete account"}
```

按钮明确指出操作对象。

**✅ 评价：合理。** 文案准确描述了假定的操作，帮助用户在点击前理解它。
