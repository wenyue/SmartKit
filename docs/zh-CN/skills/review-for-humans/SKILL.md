# 帮助人类审核

帮助人类 reviewer 理解改了什么、是否合理，以及哪些地方需要留意。仅在用户要求时使用此 Skill。在用户提供的范围内审核，不修改被审核的内容。

加载必要的 Skill 和 Rule 进行审核。

## 确定审核范围

明确任务预期达到的结果，获取用户提供的修改及其修改前后的证据。固定审核版本，并保留有序的文件列表。遵循用户给出的文件顺序；对于拉取请求，遵循其实际 Files changed 顺序。用户只要求审核选定文件时，统计和报告这部分范围，而不是整个拉取请求。

完全跳过测试文件：不审核，也不计入进度或修改项。在展示第一组之前，统计用户提供的范围中其余文件的数量。简要说明范围和排除项，让读者理解总数的含义。如果没有需要审核的文件，说明情况并结束，不拼凑报告或进度比例。

无法获得范围、顺序、必要指导或源证据时，说明缺少什么及其影响。暂停依赖这些信息的审核，不编造事实、总数或已经完成的评估。已知文件即使证据不完整，仍计入总数；在该文件的报告中解释缺口，并在必要时给出“证据不足”的评价。

## 围绕文件解决的问题进行说明

每个文件先列出路径，简要说明文件的职责和整体修改。可获得源链接和相关行号时，一并提供。用通俗语言解释修改对用户或调用者意味着什么，同时保留影响判断的技术细节。

按照业务问题或人类容易理解的场景划分修改项，优先将相关修改放在一起。只有逻辑上相互独立，或无法用一个简单例子共同解释时，才拆分。方法、diff 块和单个实现步骤本身不足以成为拆分理由。例如，记录尚未完成的工作、拒绝新工作，以及关闭资源前等待，可以合成一个“关闭时安全完成已有工作”的修改项。

顺带的小修改，例如注释拼写错误，可以在文件总说明中提及，也可以省略。每个 l10n 翻译文件作为一个整体修改项说明，不把其中的字符串拆成多个修改项。

每个修改项纵向依次展示**修改前**、**修改后**、**评价**。解释前后的行为，无需单列“不改的后果”。优先使用项目语言中的简短实际代码，只保留说明场景所需的部分。用通俗语言解释代码，准确保留所比较的行为。简化例子必须能让人看出是示意，不要让读者误以为是逐字引用的源代码。修改很简单，或代码无助于理解时，可以省略例子，例如注释修正。

每个修改项都要给出有依据的评价：

- **合理：**修改服务于预期任务，现有证据足以支持其行为和成本。
- **不合理：**存在实质性缺陷、不必要的范围扩大，或有证据支持的明显更好方案，使当前修改成为较差的选择。给出具体建议，并解释为何在相同要求下更好。仅有微小优化或风格偏好，不足以达到这一标准。
- **证据不足：**说明什么阻碍了可靠判断，以及哪些证据可以解决问题。区分已经确认的行为和假设，不暗示修改已获认可。

将底层审核发现的重要问题及限定条件带入相应修改项；当规范问题与任务范围问题的区别影响判断时，保留各自依据。通俗解释仍须保留可能改变人类 reviewer 决定的限制。报告实际执行的检查，并与修改作者提供的检查结果区分。

## 每次展示一组，按用户请求继续

文件之间用 `---` 分隔。按既定顺序加入完整文件，直到本组修改项总数达到或超过 10，再结束本组。一个文件不能拆到多组。如果 A 文件有 3 项，B 文件有 8 项，就一起展示为含 11 项的一组；下个文件从下一次回复开始。单个文件超过 10 项时，仍完整放在一组。范围结束时，展示最后不足 10 项的一组。

每组末尾展示**审核进度：已展示文件数 / 需要审核文件总数**。这统计的是已展示的文件，不是修改项，也不表示每项判断都有确定结论。如果还有文件，在进度之后明确提示用户输入 `继续`，继续审核，然后等待。用户继续时，从下一个文件开始，不重复上一组。全部文件展示完毕时，说明报告已经完成，并保留尚未解决的证据缺口。

跨组保留审核版本、有序文件列表、下一个文件的位置及此前的判断。如果被审核内容发生变化，说明哪些已有解释或判断受到影响，并按新版本更新，再报告该版本的进度。必要时重建文件列表和总数，计入需要重新展示的受影响文件，并明确说明版本切换，避免报告混用多个版本。

## 参考报告

参考以下形式，根据用户调整语言和详略。措辞可以灵活，但须保留文件总说明、业务修改项、纵向比较、评价和进度。以下文件和代码仅为示意，不是对某个仓库的审核发现。假设删除一条记录后，该记录会脱离其存储 box，而任务要求删除后执行 flush。选定范围包含以下两个非测试文件。

**文件：`lib/item_storage.dart`**

这个文件负责保存和删除记录。这次修改保留存储 box 的引用，使删除记录后仍能刷新这次删除。

**修改项 1：删除后，仍刷新原来的存储 box**

**修改前**

```dart
await item.delete();
await item.box?.flush();
```

删除后，`item.box` 变为 null，因此不会执行 flush。

**修改后**

```dart
final originalBox = item.box;
await item.delete();
await originalBox?.flush();
```

先保留 box 引用，删除记录后就能刷新同一个 box。

**评价：合理。**通过较小修改，直接修复承诺的删除行为。flush 失败仍须传递给调用者；flush 不会回滚删除。

---

**文件：`l10n/en.json`**

这个文件提供英文界面文案。修改后的标签明确说明操作会删除账号；该文件的所有翻译修改一起审核。

**修改项 1：明确账号删除按钮的含义**

**修改前**

```json
{"deleteAccount": "Delete"}
```

按钮没有说明会删除什么。

**修改后**

```json
{"deleteAccount": "Delete account"}
```

按钮明确指出操作对象。

**评价：合理。**文案准确描述了假定的操作，帮助用户在点击前理解它。

**审核进度：2/2 个文件已展示。**该选定范围的报告已经完成。

本组尚未结束整个审核时，将完成说明替换为用户语言中的明确继续提示。例如：**审核进度：2/11。**输入 `继续`，继续后面的 review。
