# 帮助人类审核

帮助人类 reviewer 理解 PR 或分支改动：改了什么、是否合理、实现是否优雅且有品味，以及哪些地方需要留意。仅在用户要求时使用此 Skill。先在选定的范围内进行只读审核，再遵循下文的范围和验证规则，仅执行用户所选操作授权的效果。只读审核允许捕获比较内容、解析已有 Git 对象并运行共享 diff 链接命令；在执行下文已获授权的操作前，保持受审文件和 Git 暂存区不变。

加载必要的 Skill 和 Rule 进行审核。

## 确定审核范围

### 选择比较范围

明确任务预期达到的结果，并按下表选择比较范围。通过可用的只读 Git 或 GitHub 接口，例如 CLI、连接器或已认证的 GitHub 界面，获取修改前后的证据。

| 用户指定的范围 | 比较方式 |
| --- | --- |
| PR | 获取该 PR 的改动文件及比较证据，记录其 base 和 head 的提交 ID。审核这个固定的 PR 版本，并应用下文的文件级查看状态筛选。 |
| 分支，可能指定了比较基准 | 确定被审核分支的最新提交和可靠的比较基准，比较两者的共同祖先与该分支最新提交之间的改动，并固定两个提交 ID。无法可靠确定基准时，询问用户，不擅自假定为 `main`。 |
| 本地改动，或未明确指定范围 | 比较暂存区与当前工作区，使用 `git diff` 或等效证据。 |
| 选定文件 | 在适用的比较范围内筛选这些文件，统计和报告筛选后的范围，而不是整个 PR 或分支。 |

明确指定的 PR 或分支比较不包含本地未提交改动，除非用户要求纳入。

### 审核本地修改

本地默认只审核 unstaged 改动，以暂存区内容作为修改前的版本。跳过只有 staged 改动的文件；文件部分暂存时，只审核其中未暂存的部分。如果暂存的修改随后在工作区被撤回，相对暂存区的这次撤回属于需要审核的 unstaged 改动。用户明确要求纳入 staged 改动或采用其他本地比较方式时，覆盖这一默认行为。不纳入此前的提交，选定的比较为空时也不回退到 staged 改动或最后一次提交。除非用户明确要求纳入，否则排除 untracked 文件；明确纳入时，将其作为新增文件审核。

### 筛选 PR 文件

审核 PR 时，默认跳过当前已认证 GitHub 查看者标记为已查看的文件。通过可用的、已认证且只读的 GitHub 接口获取完整的文件级状态；GitHub GraphQL 通过 [`PullRequestChangedFile.viewerViewedState`](https://docs.github.com/en/graphql/reference/pulls#pullrequestchangedfile) 提供这些状态。排除 `VIEWED`；纳入 `UNVIEWED` 和 `DISMISSED`，后者表示文件在上次查看后发生了变化。完成所有分页，并检查获取文件列表和状态期间 PR 的 base 与 head 没有变化，确保筛选对应固定的版本。当前查看状态不能作为旧 PR 快照的筛选依据。PR 批准、评论或此前聊天中展示过的文件，都不能证明文件的查看状态。

用户可以明确要求纳入已审核文件，覆盖这一排除项。如果无法获取所需的查看状态证据，说明缺少的前提条件，暂停依赖这些证据的审核，并询问能否获取该证据，或是否不应用这项筛选、纳入其余符合条件的全部文件。将缺失状态视为未知，不视为 `UNVIEWED`。

### 固定快照与待审文件列表

加载默认范围不同的其他审核指导时，保留本 Skill 已选定的比较范围。如果没有可用的 `HEAD`、无法获取所需引用或 PR 证据，或无法使用必要接口，说明缺少的前提条件，并暂停依赖它们的审核。

固定审核版本，并保留用于展示报告的有序文件列表。记录 PR 和分支比较的提交 ID、本地比较的修改前后内容（包括暂存区基准），以及 PR 筛选所用的查看者身份和文件级状态。即使用户明确选定的比较采用其他修改前版本，也保留本地暂存区基准，以便后续暂存时保留已有暂存内容。所有审核范围的展示顺序都与 GitHub 的 Files changed 目录树一致：在每个目录内，先递归列出各子目录中的改动文件，再列出该目录直属的文件。能获取拉取请求的实际目录树时，采用其中的同级顺序；否则，将同级子目录和直属文件分别按名称排序。例如，`src/z/api.dart` 排在 `src/a.dart` 前面；直接对 `git diff` 中的完整路径排序，无法得到这种顺序。

完全跳过测试文件：不审核，也不计入进度或修改项。先应用范围筛选，再统计数量；被跳过的已查看 PR 文件和只有 staged 改动的本地文件，不生成文件报告，也不计入进度或修改项。在展示第一组之前，统计其余文件的数量。简要说明范围和排除项，让读者理解总数的含义。如果没有需要审核的文件，说明情况并结束，不拼凑报告或进度比例。

无法获得范围、必要指导或源证据时，说明缺少什么及其影响。暂停依赖这些信息的审核，不编造事实、总数或已经完成的评估。已知文件即使证据不完整，仍计入总数；在该文件的报告中解释缺口，并在必要时给出“证据不足”的评价。

评估选定比较及其影响，必要时阅读相关上下文，同时保留文件筛选和测试排除规则。由选定改动引入、触发或加重的缺陷，即使证据位于未修改的代码中，也属于对应修改项的正式评估。与改动无关的既有问题按下文的顺带发现规则处理。

## 准备动态 diff 链接

### 准备输入

每个受审文件的报告都链接到工具为该路径提供的统一 localhost diff 入口。报告和后续操作所用的固定审核证据，与展示链接当前显示的内容分别保留。本地比较始终使用本次审核实际采用的固定修改前内容与该路径当前磁盘上的工作区状态；后续编辑因此可能与已判断的快照不同。提供选定比较实际采用的修改前提交、已经掌握的修改前 blob，或确实不存在的基线；不替换为最新暂存区、`HEAD` 或可变分支名。

使用统一 `local_web` 工具，该工具由 `SmartKit plugin resources` 提供，与受审仓库或 cwd 无关。读取其帮助，了解批次格式和输出契约：

```text
python "<local_web>" --help
python "<local_web>" diff --input "<batch.json>"
```

提交一个批次对象，其中包含共享的 `repo`、可选的默认 `base`、可选的 `pr` 上下文，以及非空的 `files` 列表。以仓库工作区根目录作为 `repo` 查找入口。每个文件提供唯一的 `id` 和当前 `path`；`title` 默认使用该路径。文件显式提供的 `base` 覆盖批次默认值；否则批次必须提供基线。不同仓库或 PR 需要分别提交批次。CLI 帮助拥有准确的格式；`local_web` 负责验证、基线解析、GitHub 地址构造和 URL 编码。

本地默认范围使用暂存区模式，在保留审核快照的同时准备链接，让工具固定与本次审核相同的暂存区基线，部分暂存的文件也如此。分支和 PR 比较使用实际的固定修改前提交，或已经掌握的 blob；PR 不能使用可变的暂存区。

每次 PR 审核时，从已取得的 PR 元数据中提供批次级的 `pr.repository`、`pr.number` 和完整、固定的受审 `pr.head`。`repository` 指拥有该 PR 的 GitHub 仓库，不是其源 fork，也不是根据本地 remote 推断的仓库。非 PR 审核省略 `pr`。必要的 PR 上下文不可用时，说明缺少的前提，并暂停依赖它的报告。GitHub 是已接受的展示例外，可能显示远端 PR 版本，而非本地编辑。

### 定位文件与工作区

解析暂存区或提交基线时，通过 `base_path` 提供重命名前的路径；当前 `path` 仍是 GitHub 文件目标。

工具构造指向每个文件的 GitHub Files changed URL，并根据当前 `path` 推导默认文件锚点。Agent 不提供完整的 GitHub URL，也不计算锚点。文件可选的 `github_anchor` 使用已经观察到的片段覆盖默认值，不带开头的 `#`；无法取得时省略，让工具推导锚点。准备文件链接无需另外访问 GitHub 或执行网络查询。

即使不知道是否存在 PR 检出，也使用同一命令。`local_web` 根据提供的 PR head 查找并验证当前检出及其已有的关联 worktree：只有一个匹配时自动绑定，有多个匹配时提供页面供人选择，没有匹配或没有可用的本地比较时，转到生成的 GitHub URL。Agent 提供上下文，不负责枚举、验证或选择 worktree。链接准备和展示仅使用已有 Git 数据；不 fetch、clone、写入 Git 对象、切换检出、创建 worktree 或保存任意修改前字节。

### 使用与打开链接

将返回的每项 `id` 和 `title` 与对应文件匹配，并使用返回的 `markdown` 作为文件名链接。返回的 `url` 和 `markdown` 指向同一个 localhost diff 入口；`local_web` 负责选择查看器和调度回退。本地 URL 自带比较上下文，没有签名、登记记录或链接到期时间。绑定工作区后，链接始终比较固定基线与该工作区当前磁盘上的目标路径；后续编辑或提交不会触发 PR head 匹配或重新路由。它不备份基线：Git 对象缺失或仓库不可用属于错误，不代表空内容，也不允许替换为其他基线。在仍存在的工作区中删除文件，表示当前一侧不存在，重命名则需要指向新路径的链接。

存在可用的本地比较时，`local_web` 先尝试 VS Code。明确不可用或启动失败时，PR 转到生成的 GitHub 地址，其他情况则根据当前本地比较计算 HTML。自动兜底和手动链接都在当前标签页跳转到 GitHub。编辑器请求发出后，页面尝试自动关闭；浏览器策略阻止关闭时，保留状态提示和手动兜底入口。CLI 正常返回不能证明 diff 已显示。页面内的手动 HTML 控件展示本地比较，不尝试编辑器。只要引用的工作区和 Git 对象仍存在，当前 diff URL 在服务重启后仍可使用；普通预览产物的保留期独立管理。文件名链接无需固定修改后快照，但报告示例和审核操作验证仍需要。

### 处理链接不可用的情况

必要的链接生成不可用时，保留诊断，并按共享资源的不可用处理规则暂停依赖它的报告；依赖这些能力的链接保持未完成，不用旧工具或手写地址替代。使用统一工具的帮助恢复服务；报告观察到的导航限制，只有实际观察到打开成功时，才作出相应声明。不只为获得链接而发布仓库修改。

## 围绕文件解决的问题进行说明

所有报告中的 emoji 都放在加粗范围之外，保留其旁边文字的强调。强调词语、短语、标识符或标签时，将其外围的分隔符和末尾标点放在加粗范围之外；有意强调整句时，可以保留句子本身的标点。保留代码、标识符和路径中的固有标点。

每个文件以 `📄 **[path](diff-destination)**` 形式开头，使用返回的动态 diff Markdown，并简要说明文件的职责和整体修改。源码链接和相关行号可以作为这个必需文件名链接的补充。用通俗语言解释修改对用户或调用者意味着什么，同时保留影响判断的技术细节。

按照业务问题或人类容易理解的场景划分修改项，优先将相关修改放在一起。只有逻辑上相互独立，或无法用一个简单例子共同解释时，才拆分。方法、diff 块和单个实现步骤本身不足以成为拆分理由。例如，记录尚未完成的工作、拒绝新工作，以及关闭资源前等待，可以合成一个“关闭时安全完成已有工作”的修改项。

顺带的小修改，例如注释拼写错误，可以在文件总说明中提及，也可以省略。每个 l10n 翻译文件作为一个整体修改项说明，不把其中的字符串拆成多个修改项。

修改项严格使用 `🔧 **M1** - **<modification title>**` 格式，随后为 M2、M3 等，并在同一报告中跨所有文件和继续展示的分组连续编号。图标和分隔符放在加粗范围之外；问题列表、建议列表、操作选择和复审都使用同一套带 M 前缀的 ID。

### 每个修改项都从两个独立维度判断

所有修改项采用同样的思考方式：确认修改前后发生了什么变化、产生什么影响、有哪些证据支持，再分别判断合理性和优雅性。两个维度适用于所有修改，包括修复、新功能、重构、文档和翻译。文字的优雅性侧重表达和组织是否清楚；代码的优雅性侧重机制和结构。调整的是表达篇幅，不是评估的覆盖范围。

每个修改项都使用固定的 ⚖️ 标记合理性、 🎨 标记优雅性，简版修改项也如此。两个判断各自独立成段，直接使用 emoji 加结论，不再重复维度名称。每个维度都要给出明确结论和理由；emoji 区分的是维度，不表示评价是正面还是负面。

- ⚖️ **合理**。 修改服务于预期任务；行为正确且安全，范围符合任务，现有证据足以支持其成本。
- ⚖️ **不合理** (问题级别): 存在实质性缺陷、不必要的范围扩大或缺乏充分依据的成本，使修改在任务要求下成为较差的选择。将标签中的级别替换为该发现实际的 P0 至 P3 级别，解释有证据支持的影响，并给出具体建议，说明其在相同要求下的优势。仅有更优雅的方案、微小优化或风格偏好，不足以达到这一标准。
- 🎨 **优雅**。 修改在恰当的职责或位置解决根本问题，结构清楚，尽量减少不必要的状态、分支和重复。解释哪些选择使其易于理解和维护。
- 🎨 **可改进**。 行为可以是合理的，但机制或表达带来可以避免的复杂度或重复。指出可以改进的具体结构，在有依据时提出更简单的方案，并解释对维护或理解的好处。区分这些好处与个人风格偏好。
- ⚖️ **证据不足**。 或 🎨 **证据不足**。 说明什么阻碍了对该维度的可靠判断，以及哪些证据可以解决问题。区分已确认的事实与假设。一个维度可以有充分依据的结论，而另一个维度仍缺少证据。

修改可以合理但不够优雅。单独的优雅性问题属于可选的改进建议，不触发必须选择修复或忽略的暂停。如果同一结构还造成有证据支持的实质性缺陷、风险或缺乏充分依据的成本，也要在合理性下独立报告该影响；这类不合理问题遵循正常的暂停与修复流程。

仅为不合理问题标注 P0–P3，纯粹的优雅性建议或风格偏好不标问题级别。P0 表示需要立即干预的严重问题；P1 表示需要尽快修正的重大问题；P2 表示正常优先级的问题；P3 表示影响较小但值得修正的问题。根据有证据支持的后果及其适用条件确定级别，而不是根据代码修改量。例如，使用 ⚖️ **不合理** (P1): 后接影响和建议的修复方案，并将级别替换为该发现的实际级别。只加粗判断词；级别以普通文字放在半角括号内，半角冒号位于括号之后。

将底层审核发现的重要问题及限定条件带入相应修改项；当规范问题与任务范围问题的区别影响判断时，保留各自依据。通俗解释仍须保留可能改变人类 reviewer 决定的限制。报告实际执行的检查，并与修改作者提供的检查结果区分。

### 选择展示详略

行为变化直接、影响范围清楚、没有需要展开的实质性风险或取舍时，采用简版说明。只将修改前后的行为说明合并为一个不带 emoji 前缀的短段落。简版修改项使用纯文字，不举例子，包括代码片段和示意场景，并省略固定的“修改前”“修改后”标签。随后分别用独立的 ⚖️ 判断段落和 🎨 判断段落给出结论与理由。根据读者需要理解的内容判断是否简单，而不是根据 diff 行数：一行修改也可能影响异常处理或持久化。

涉及复杂机制、重要契约、实质性风险或审核发现、重要取舍、关键证据缺口的修改项，需要展开。纵向依次展示 ⏪ **修改前** 、 ⏩ **修改后** 、独立的 ⚖️ 合理性判断段落、独立的 🎨 优雅性判断段落；两个判断都使用 emoji 加结论。解释前后的行为，无需单列“不改的后果”。

展开说明代码改动时，使用保留的审核快照，以项目语言展示简短的修改前后代码。保留能解释机制的条件、状态变化或调用顺序；与判断有关时，也要包含对应的错误或生命周期分支。用通俗语言解释旧代码如何产生原有行为、新代码如何改变它；只说好处或转述 diff，不能解释这层因果关系。简化例子必须能让人看出是示意，保留所比较的行为，并与逐字引用的源代码区分开。代码无助于理解时，例如说明文字组织，可以省略。

使用足以说明问题的最小对照。只有不同的行为或审核发现需要单独解释时，才增加另一个简短例子；同一机制的重复变体只会增加篇幅，无助于理解。保留相关限定和两个维度的判断，让每个例子聚焦于它所支持的决策。

## 每次展示一组并处理操作

### 分组展示

文件之间用 `---` 分隔，按既定顺序展示完整文件。加入某个文件后，本组修改项达到或超过 10 项，就结束本组。文件不能拆分，单个文件超过 10 项也如此。例如，含 3 项和 8 项的两个文件合为一组，共 11 项；下个文件留到下一次回复。范围结束时，展示最后不足 10 项的一组。

每组末尾展示 `---` 和 📊 **审核进度**： **已展示文件数 / 需要审核文件总数** ，明确说明文件已展示。进度统计已展示文件，不统计修改项，也不表示判断已确定。跨回复保留审核版本、有序文件列表、每个已展示组的文件及已审核改动、下一个未审核位置、下一个修改项 ID、判断、问题状态和待处理的优雅性建议。保留每组的记录状态和已核验的操作结果，以便最终完成时涵盖前面的分组，包括此前直接继续、未作记录的组。

### 报告顺带发现

在选定审核所需的阅读中，只有现有证据同时证实问题本身及其与选定改动无关时，才报告这个无关的既有问题。这种提醒渠道不授权扩大为全面审计，也不绕过文件筛选和测试排除规则。有待证实的猜测不列入顺带发现。

只在每组收尾处展示顺带发现，使用 `📌 **Incidental observations (outside this review's scope)**` 标签，放在进度之后、 **可用操作** 之前，位于文件块和修改项评估之外。为空时省略该部分。使用独立的 **O1** 、 **O2** 等 ID，在整个报告中连续编号；跨分组和复审保留其身份和状态，不重复创建或重新编号。

每项顺带发现给出简短标题、源码位置（有可用源码链接时附上）、支持证据及影响、与选定改动的关系，以及具体建议和收益。确认问题此前已经存在，且这次改动没有引入、触发或加重它。这些引用不生成受审文件块，也不要求为额外文件准备 diff 链接。

顺带发现不增加受审文件、修改项或进度，并与 **待修复问题** 和 **可选优化** 分开。它们不阻挡推进或完成，未限定范围的 **修复** 、 **优化** 和 **忽略全部** 都不包含它们。它们不扩大暂存、Viewed 或发布范围。明确选择处理某个 O 项目时，需要单独确定结果、授权、证据和检查；该发现及其后续修改都不自动纳入当前受审范围或完成操作。

### 选择操作

面向人类的标签、摘要、操作名称和问题使用对话所用的语言。操作名称及说明统一使用该语言，不并列展示另一种语言的名称。按含义理解自然语言选择，不要求用户使用命令语法。

修改项 ID 用于选择该修改项中的相关问题或建议。未限定范围的 **修复** 、 **优化** ，以及明确的 **忽略全部** ，仅涵盖本报告已展示、在所选维度仍待处理的项目，包括前面的分组。只选部分项目时，只影响这些项目。在菜单中说明适用范围和数量。推进是指从保存的位置展示下一组，或在范围已展示完时结束。

| 操作 | 效果与选择范围 |
| --- | --- |
| **修复** | 修复待处理的不合理问题：未限定时修复全部，否则只修复选定的问题。 |
| **忽略** | 只将选定的问题记录为已忽略，保留其级别和影响。只有一个明确的问题时，无需重复指定 ID；否则询问要忽略哪些，除非用户明确选择全部。其他问题仍待处理。 |
| **优化** | 实施有充分依据、仍待处理的 🎨 **可改进** 建议：未限定时实施全部，否则只实施选定的建议。其他待处理问题不受影响。 |
| **通过并继续** | 执行下方状态表中适用的完成步骤，核验后再推进。根据已说明的实际效果，可能暂存本地改动、发布已检查的 PR 修复，或将已审核的 PR 文件标为 Viewed。 |
| **继续** | 推进，不暂存、提交、推送或标记 Viewed。保留尚未发布的修改和未实施的建议。 |

**通过并继续** 和 **继续** 是同等地位的并列操作，共用相同的推进条件；完成操作额外包含状态记录步骤及其前提。中途的完成操作涵盖当前整组，包括最近展示的复审版本。需要发布 PR 修改时，所说明的范围也可以涵盖本报告此前已展示且符合条件的路径，以及已获授权、检查和复审通过的决策。用户选择单个修改项时，先澄清，不将其视为整组完成。

全部文件展示完毕时，使用 **通过并结束** 和 **结束** 。它们是同一对操作在报告末尾的形式。 **通过并结束** 涵盖本报告中所有已展示、已审核的分组，包括此前选择 **继续** 的组，并完成这些组剩余的适用记录和发布工作。在最终菜单中明确这个累计范围。复用已经核验完成的步骤，并逐组核对；任何部分受阻，都会使最终完成操作不可用，不能默默缩小其范围。 **结束** 保留 **继续** 的不记录语义。

用户选择完成操作，仅授权选择前已说明的实际效果和范围。完成和继续操作都不正式批准或合并 PR。被忽略的问题仍记为已忽略，不表示已修复或认可。

### 生成结尾菜单

每次收尾都以下表为完成操作的可用性及效果依据：普通分组、专门复审、修复／忽略／优化后的菜单、最终分组，以及中断操作恢复。收尾前，完成为确定状态所需、可推导且已获授权的只读检查；用户应选择操作效果，无需判断是否需要发布。采用上文定义的完成范围，范围已展示完时使用最终名称。

两个操作共用相同的推进条件：所有已展示的不合理问题都已修复或明确忽略，所需正确性和版本证据可获得，必要检查和受影响部分的复审已完成，此前已选定的记录或发布操作也已核验完成。可选改进或仅缺少优雅性证据，不阻挡推进。完成操作特有的前提可以使 **通过并继续** 不可用，而不影响 **继续** ；已选定但未完成的操作则会阻挡两者推进，直到恢复过程核验完成。

| 状态，按优先顺序判断 | 完成状态、效果与可选操作 |
| --- | --- |
| 仍有待处理的不合理问题，包括只修复或忽略了部分问题的情况 | 完成和继续操作都不可用：列明待处理 ID，以及所需的修复或明确忽略。提供 **修复** 、 **忽略** ；仍有充分依据的建议时，也提供 **优化** 。 |
| 缺少正确性或版本证据，必要检查未完成或失败，或受影响的审核版本已过时 | 完成和继续操作都不可用：说明缺失的证据、检查或复审及其补救办法。完成已获授权的工作后，再生成菜单。 |
| 已选定的暂存、Viewed 或发布操作尚未完成 | 报告已确认、失败和未知的步骤。解决阻碍后，提供同一个完成操作，用于恢复剩余步骤。普通的 **继续** 仍不可用；遵循下文的恢复规则。 |
| 推进已就绪，但无法确定完成操作所需的目标、接口或安全范围 | 完成操作不可用：说明具体前提和补救办法；需要 GitHub 记录或发布时，前提包括经过核实的 GitHub PR 审核目标。 **继续** 可独立选择。 |
| 本地或 PR 完成操作已就绪，没有剩余暂存、发布或 Viewed 写入 | 说明哪些内容已核验为已暂存或 Viewed。并列提供 **通过并继续** 和 **继续** ；前者复用已核验结果并推进，不重复写入。依赖该结果前，重新核验当前状态。 |
| 本地审核已就绪，仍有待暂存的已审核差异 | **通过并继续** 只暂存选定完成范围内剩余的已审核差异，并核验暂存区和工作区； **继续** 直接推进，不暂存。遵循下文的本地记录保护规则。 |
| 没有关联 PR、已就绪的分支比较 | 完成操作不适用，因为该比较没有记录或发布目标。提供 **继续** ；不虚构远端写入目标。 |
| PR 与检查、审核过的版本一致，且没有尚未发布的已审核修改 | **通过并继续** 核对固定的 PR 版本和查看者，将选定范围内符合条件的已审核路径标为 Viewed，核验每项回读后推进； **继续** 直接推进，不作标记。遵循下文的 PR 记录保护规则。 |
| PR 的本地修改已经授权、检查和复审，等待发布 | **通过并继续** 仅在需要时提交并推送已说明范围内的决策所对应的修改，核对生成的 PR 版本，将已说明且符合条件的已审核路径标为 Viewed，核验每项回读后推进； **继续** 保留本地修改，不发布也不标记。提供完成选项前，须先满足下文的发布和记录前提。 |

部分范围已完成记录时，复用已核验完成的步骤，只对剩余工作写入。已就绪的菜单中，仍有充分依据的待实施建议时，追加 **优化** 。发布要求已知且经过核实的 PR；普通分支或本地比较并不提供这个目标。PR 已包含审核过的版本时，完成操作无需创建空提交或进行不必要的推送。

每次收尾都要明确交代完成操作：就绪时，提供具体效果和范围；记录已完成时，明确说明；否则，说明 **通过并继续** 暂不可用或不适用，并给出具体原因和下一步补救办法。不可用或不适用的状态放在 **可用操作** 列表之外，作为状态说明，不作为可执行选项。范围已展示完时，该状态说明使用 **通过并结束** 。修复成功后仅能继续的情况，也要交代上述状态。

进度之后，用 Markdown 依次分开展示 **待修复问题** 、 **可选优化** 、 **顺带发现（本次评审范围外）** 和 **可用操作** ，省略为空的部分。待处理问题严格使用 `**M1** (P1): <impact summary>` 格式，替换为实际 ID 和级别；只加粗 ID，半角括号和冒号保持普通文字。按 ID、改进方案和收益列出有充分依据的建议，并纳入前面各组仍待处理的问题和建议。用简短列表描述每个可用操作的实际效果，不列命令语法或带编号的用法；需要时，包含准确的发布差异和符合条件的 Viewed 路径集合。最后用一个简短问题询问；已无需要选择的事项时，直接结束，不再提问。

范围已展示完时，收到“继续”也只有在推进条件满足时才结束。分支范围已展示完、状态就绪且没有建议时，解释完成操作不适用的原因后，可以直接结束，不再询问。用户始终可以明确停止或暂停：按实际情况报告展示进度、未解决或已忽略的问题、证据缺口、尚未发布的修改及未完成操作，不宣称任务成功完成。展示完成不表示问题全部修复，也不表示修改全部发布。

### 理解回复并复审修改

按用户选择的含义执行，即使菜单没有列出该操作，也须满足其前提并具备授权。所需效果尚未说明或获得明确授权时，先解释并取得选择，再执行写入；历史上仅说明会暂存或标记 Viewed 的“通过”，不提供提交或推送授权。用户在有阻塞时要求推进，简短拒绝，指出阻塞项，并询问适用的修复、忽略或补救选择；“继续”从不表示“忽略”。范围含糊、ID 无效、要求冲突，或用户只对含糊菜单表示同意时，先澄清；只有前一个问题明确指定操作时，“可以”才授权该操作。根据用户提供的证据重新评估有争议的问题，不把反驳当作忽略。回答问题时，不将提问解释为修改或推进的授权。

修复或优化已获授权时，加载必要指导，只修改选中的问题或建议及其必要配套内容，并运行必要检查。优化保留受支持的行为和契约。审核过的内容发生变化时，先使必要检查全部通过，刷新审核快照，并重新生成或重新核验其 diff 链接，再独立复审此前已审核、但被修改或影响的全部内容，包括意外改动。使用专门的回复，以完整文件块展示更新后的解释和两个维度的判断，与尚未审核的文件分开。保留修改项 ID 和原分组归属，每个已展示文件只计数一次；说明版本切换，只因实际范围变化才更新文件列表和总数。PR 的修改尚未发布时，同时保留固定的远端版本，以及经过检查、预期发布的本地内容。只有复审确认结果，才能将问题标记为已修复，或将建议标记为已完成。

单独选择 **修复** 、 **忽略** 或 **优化** ，在重新生成菜单并交代完成状态后结束，不自动推进。明确的组合指令授权按顺序执行各步骤，例如修复、检查、单独展示复审、发布限定范围的修复并标记 Viewed，再推进。已授权步骤继续执行，无需例行重复确认；发现新问题、检查失败或发生实质性变化时，暂停依赖它们的步骤，并重新生成菜单。有单独授权的优化仍可在问题待处理时执行，但不满足推进条件。

### 记录选定完成范围的状态

本地审核中，跨组保留每个已展示组的修改前后内容、原始暂存区条目和已核验的暂存结果。执行完成操作前，将当前工作区内容和相关暂存区条目与这些快照核对，计入此前已核验的任务暂存，并保存当前完整暂存区作为写入基准。确定选定范围内仍未暂存的已审核差异；最终完成操作包括此前直接继续的组。只暂存这些剩余差异；整文件暂存会带入未展示或已排除的修改时，使用限定范围的补丁。保留该差异之外的已有暂存内容，包括部分暂存文件中的无关修改，并保持工作区不变。验证写入后的暂存区等于写入基准加上且仅加上该差异，其他所有条目不变，工作区仍与快照一致。保留已核验结果，使后续完成操作可以复用，无需重复应用已暂存修改。快照过时或无法安全分离差异时，刷新并展示受影响的审核内容，在暂存前取得新的选择。本地完成操作不提供提交或推送授权。

PR 审核中，提供完成选项前，先确定经过核实的 GitHub PR 审核目标，以及能够回读所需查看者、版本和逐路径状态的已认证接口；仍需标记时，该接口还须能够将文件标为 Viewed。检查、审核过的版本必须已在 PR 中；必要时先执行下文的发布流程。写入前立即核对查看者身份和固定的 base、head，只标记选定完成范围内符合条件且尚待 Viewed 的已审核路径，再回读每个选定路径的 `viewerViewedState` 和 PR 版本，包括复用既有标记结果的路径。全部选定路径都须为 `VIEWED`，两个提交 ID 在记录期间也须保持不变，才能推进。版本变化时，需要复审受影响部分并取得新的选择；将更新后的版本标为已查看，不能证明它已经审核。

### 完成操作需要时发布已审核的 PR 修改

使用可用的 Git 和已认证 GitHub 读写接口，例如 CLI、连接器或界面。提供会发布修改的完成选项前，确定具体仓库、PR、源分支、查看者、写入能力，以及归属清楚的发布范围。只纳入本报告中明确授权、必要检查及复审已通过的决策所对应的修改，包括必要的配套、生成和测试修改；测试仍不计入报告。保留无关的暂存区和工作区修改，排除无关的未推送提交、其他未展示改动及版本不明的文件。无法安全分离要推送的提交历史或差异时，说明所需前提，不暗中变基或强制推送。

按以下顺序执行选定操作：

1. 核对固定的远端 base 和 head、审核过的修改前后内容及受影响的依赖，以及将要发布的完整差异和提交历史。确认实际发布的差异及符合条件的已展示路径与已说明的选择一致；核对每个路径的内容和固定的查看者。
2. 需要时，暂存并通过正常仓库钩子创建仅含授权范围的提交，保留授权差异之外的原有暂存内容和工作区。核对生成的提交及剩余本地状态；钩子引入的修改须在发布前完成检查及受影响部分的复审。
3. 正常推送到已核实的 PR 源分支。回读远端 head 和 base，确认预期提交，以及完整比较结果和影响与检查、复审过的决策一致。
4. 对已说明且符合条件的已展示路径应用上文的 PR 记录保护规则；选定最终累计范围时，也包括该范围。只标记仍待 Viewed 的路径；回读每个选定路径的状态及 PR 版本。全部路径都须在核实过的 base 和 head 上为 `VIEWED`。
5. 确认操作完成，从保存的位置继续，或在范围已展示完时结束。

预期的新 head 需要核对，不需要重做整个审核。内容、base 或受影响依赖发生意外变化时，复审受影响部分；文本相同本身不能证明影响不变。结果不再代表已授权、已审核的版本时，刷新快照并取得新的选择。发布过程中保留有序文件列表、分组归属、下一个位置、修改项 ID、决策和逐组记录结果。

### 恢复未完成的操作
