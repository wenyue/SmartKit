# 面向人类的审查

帮助用户理解每项改动，并形成两个判断：改动是否合理，实现是否优雅。先只读审查所选比较，再执行用户选择的操作。采集证据和准备 diff 链接属于审查；修改被审查文件或 Git 状态，需要相应操作的授权。

每次提问都提供具体选项，并使用对话语言解释各自效果，包括范围问题、工作区创建或同步、补救措施和收尾菜单。建议依次用 **A**、**B**、**C** 等大写字母标记，方便选择。使用字母时，按最新菜单解释，不区分大小写；接受含义明确的自然语言选择，包括对已明确说明的操作表示同意。M 和 O 编号用于选择条目，而非操作。澄清有歧义的回答；提问和异议不构成操作授权。

下文的格式是推荐的表达方式：emoji、标签、强调、分隔符和版式可根据读者调整。必要证据、两个判断、稳定的 M/O 编号、分组与进度统计、操作含义、授权及验证要求仍具有约束力。

## 确定比较范围

| 请求范围 | 审查证据 |
| --- | --- |
| PR | 确认 PR 及其源仓库和分支。完成工作区检查后，固定 PR 的 base 和 head，并应用下述 Viewed 筛选。 |
| 分支 | 固定分支顶端提交，以及它与可靠确定的比较基准之间的 merge-base。基准不明确时询问用户，不要假定为 `main`。 |
| 本地改动，或未明确指定范围 | 比较暂存区与工作树：仅审查未暂存改动。 |
| 指定文件 | 将适用的比较范围筛选到这些文件。 |

明确指定 PR 或分支比较时，除非用户要求，否则不包含本地未提交改动。遵守明确选择的历史版本。应用默认范围不同的其他审查指导时，保留已选范围。

### 本地比较的默认范围

跳过仅已暂存的编辑，对部分暂存的文件只审查其未暂存部分。在工作树中撤销已暂存内容，仍属于相对于暂存区的未暂存改动。只有用户明确要求时，才将未跟踪文件作为新增文件纳入。明确选择其他本地比较方式时，覆盖这些默认值；比较结果为空就保持为空。

### 检查审查工作区

每次 PR 审查前，依次确认当前工作区的仓库、已检出分支和提交。在筛选或展示文件前解决分支和版本选择，让本地审查链接打开用户预期要编辑的工作区。

使用当前权威 PR 元数据确认 PR 所属仓库、源仓库或 fork、源分支和目标提交。明确选择的历史版本仍是目标；本地跟踪数据无法证明 PR 当前的 head。

有可用 Git 工作区时，运行共享的只读检查，即使当前检出已经使用 PR 分支也一样。从已加载的 SmartKit 资源中解析 `local_web`，按其帮助准备输入并读取结果：

```text
python "<local_web>" --help
python "<local_web>" diff --inspect --input "<context.json>"
```

提供已验证的 PR 上下文。读取 `current` 获取所提供检出的信息，读取 `worktrees` 获取匹配的备选工作树；备选列表为空，不能说明当前仓库的身份。分别使用每项观察的 `repository_status`、`branch_status` 和版本 `status` 作出下述决定。提交相同不能证明分支匹配，仓库相关也不能证明源分支身份。命令只观察所提供的目标，不证明远端数据是否最新，也不执行检出或同步。

报告当前工作区的路径、仓库对应关系、分支、提交，以及 `changes` 中已暂存、未暂存、未跟踪和冲突路径。选择或修改任何备选工作区前，使用同一检查。保留部分暂存、重命名来源和冲突之间的区别；这份清单是观察结果，不是恢复快照，也不能证明检出安全。未知或不可用的证据不能视为干净或最新状态。报告诊断信息，仅将独立可用的证据用于它能支持的决定；让依赖缺失证据的审查保持待处理，或提供已有独立验证依据的固定比较。下述固定快照选项仅适用于 PR，且要求已有固定比较所需的证据。

1. **仓库。** 确认当前检出是否属于 PR 所属仓库或已验证的源仓库。两者均不匹配时，提供以下选择：使用可用且已验证的工作区；从已验证的仓库和目标授权创建工作区；审查固定 PR 快照；或取消。保持无关检出不变。身份未知时，先补足证据，或选择已有独立验证依据的固定比较，再继续。
2. **分支。** 在相关仓库中，验证已检出分支是否对应 PR 的源分支和源仓库。本地别名可通过已验证的跟踪关系满足要求；应说明该映射。即使处于目标提交，另一分支或 detached HEAD 仍需用户选择。询问是否在当前工作区检出 PR 分支，说明安全方案及适用的替代选项：选择已有且已验证的工作树、创建隔离工作树、审查固定快照，或取消。发现其他匹配工作树不能静默替用户作出选择。若该分支已在其他位置检出，应提供使用该工作树或其他安全方案的选项，而不是强制重复检出。
3. **版本。** 选择或准备好对应分支和工作区后，将其 `HEAD` 与已验证的审查目标比较。不一致时，按下表提供选择，询问是否将该工作区同步到确切的目标提交。批准检出本身不授权同步；只有既有授权明确涵盖相同具体效果时，才可复用。

| 选定工作区的版本 | 选择 |
| --- | --- |
| 提交相同 | 直接继续，无需询问同步。若实时链接会显示本地改动，应说明这些改动。 |
| 落后 | 提供以下选择：按具体、安全的方案同步到确切目标；不同步而审查固定 PR 快照；或取消。 |
| 领先或分叉 | 说明本地提交；分叉时也说明目标独有的提交。询问是否同步到确切目标，说明保留本地工作和提交的方案；方案中尚未解决的选择需要单独决定。同时提供以下选项：保留本地版本，为固定审查使用实时链接；使用固定 PR 快照链接；或取消。保留的实时链接展示有差异的本地版本，而非固定的已审查内容；应说明这一区别。 |
| 未知 | 说明缺失的证据。提供可行的证据获取方式、已验证的固定 PR 比较，或取消。 |

检出或同步前，说明工作区、目标分支和提交、方法、受影响提交，以及如何保留已暂存、未暂存和未跟踪工作。取得对这些具体效果的授权；两种操作均不授权未说明的历史变更或发布。获得创建授权后，使用 [create-worktree](../create-worktree/SKILL.md)，传入用户选择的干净模式和已验证的不可变基准。

获授权的检出、创建或同步完成后，使用选定工作区路径重新运行检查，在审查或准备实时链接前验证结果及本地工作的保留情况。刷新 PR base/head 和 Viewed 证据，重新评估已变化的目标。中断后先检查实际结果再重试；在完成验证、用户明确改选受支持的固定审查或取消之前，审查保持待处理。保留已验证的工作区、分支映射、目标提交和选定的链接模式。[工作区示例](references/report-examples.md#pr-workspace-decisions)展示了分别选择检出和同步的方式。

检查命令要求 PR 上下文。仅审查分支时，通过只读 Git 检查当前检出和已注册的关联工作树。在权威远端已指定或可可靠确定时，与其比较；缺少目标时询问用户，不要臆造上游。应用上述相关版本、工作保留、授权和验证要求。没有可用的展示工作区时，提供授权创建、改选范围或取消的选项。有意选择本地分支或本地未暂存改动进行审查时，无需远端同步。

### 筛选文件并保留快照

对 PR，获取当前已认证 GitHub 查看者完整的文件级 Viewed 状态。排除 `VIEWED`，纳入 `UNVIEWED` 和 `DISMISSED`。完成分页，并验证获取过程中 base 和 head 保持不变。审批、评论和先前对话中的展示都不能证明 Viewed 状态，当前状态也不能建立历史快照的筛选结果。明确要求纳入已查看文件时，覆盖该筛选。所需状态不可用时暂停，并提供获取状态或不筛选而审查所有其他符合条件文件的选择。

测试文件不进入文件报告、修改项计数或进度。先应用指定文件、Viewed 和本地范围筛选，再计数。这些筛选影响报告，不影响后续整分支提交或其检查的范围。

按 GitHub Files changed 的目录树排列文件：递归列出子目录中的改动文件，再列出当前目录的直接文件。能观察到同级顺序时沿用，否则分别按名称排序同级目录和直接文件。因此，`src/z/api.dart` 排在 `src/a.dart` 前。

保留固定的修改前后证据、固定的比较提交、有序文件清单，以及 PR 查看者和筛选证据。本地比较还要保留原始暂存区基准，即使用户选择了其他修改前版本，以便完成操作时清点已有暂存工作。展示第一组前说明范围和排除项。如果没有剩余文件，直接说明并结束，不虚构报告或进度比例。

所需范围或源证据不可用时，指出缺口并暂停依赖它的审查。已知文件即使证据不完整，也保留在总数中，对受影响的判断报告证据不足。所选改动引入、触发或加剧的缺陷应在对应修改项中评估，即使证据位于未改动代码。无关的既有问题按下述 O 类观察处理。

## 准备文件名链接

每个被审查文件的文件名链接都使用共享工具，输入遵循其帮助：

```text
python "<local_web>" diff --input "<batch.json>"
```

根据保留的比较证据准备链接：本地暂存区比较的链接与审查快照一并采集；分支和 PR 比较使用固定的修改前提交、已有 blob 或真实的不存在状态。按帮助要求提供固定的被审查 PR head、其他 PR 元数据以及重命名路径。

对 PR，明确选择历史目标、选择固定比较或源身份不可用时，设置 `view="snapshot"`，并提供所需固定证据。PR 链接指向本地文件时，设置 `view="worktree"`，并将 `repo` 设为前置检查已验证的工作区，包括当前检出或选定的本地分支别名。绑定这一确切路径，不将工作区选择留给自动发现。仅审查分支时，提供已验证的展示工作区，不提供 PR 上下文。

使用返回的 ID 将返回的 Markdown 与文件对应。即使实时链接或 GitHub 展示更新的内容，审查证据和 Viewed 资格仍绑定已评估的固定版本。

链接准备失败时，报告诊断信息并暂停依赖它的报告；解决问题时保留所选比较和模式。仅生成链接不能证明编辑器已展示内容。

## 解释每个文件

使用[报告示例](references/report-examples.md)校准解释、观察和菜单的表达。每个完整文件块都提供带链接的文件名，简述文件职责和总体改动。推荐以 `📄 **[path](diff-destination)**` 开头。用普通语言解释对用户或调用者的影响，保留影响判断的技术细节。

按改动解决的问题或场景划分修改项。相关实现步骤放在一起；只有改动彼此独立或无法用一个简单说明解释时才拆分。一个本地化文件算一个修改项。附带的小改动可放在概述中，也可省略。

为修改项分配跨文件和分组连续的 M 编号，在发现、建议、选择和复审中保留。推荐标签为 `🔧 **M1** - **<title>**`；emoji 和周边标点通常放在粗体之外更易读。保留代码和路径自身的标点。

### 将更多审查投入用于优雅性

主审查 Agent 应在优雅性上投入比合理性更多的审查精力。专门检查相关的周边实现、受影响的调用者，以及附近或同类的实现模式，使判断覆盖改动与上下文的契合程度，而不只关注 diff。利用单元测试和集成测试证据聚焦合理性检查，同时仍核对任务完成情况、受支持的行为、既定契约和严重后果。

对于有实质意义的设计选择，存在可信的更简单或更直接的替代方案时，将其与当前结构比较，判断当前结构的收益是否值得其复杂度。 **优雅** 的结论应基于已检查的上下文和适用的方案比较；没有可信替代方案时，上下文也可以支持保留当前结构。根据改动调整投入：直接明了的编辑无需虚构替代方案，深入检查也不必产生更长的解释。

### 给出两个独立判断

每个修改项都要给出两个判断，各自包含明确结论和理由。代码、文字和翻译都适用。建议分别成段，用 ⚖️ 表示合理性、🎨 表示优雅性；emoji 后通常无需重复维度名称。

| 判断 | 依据 |
| --- | --- |
| ⚖️ **合理** 。 | 改动服务于任务，在受支持的行为和既定契约内正确，符合范围，其成本和风险有任务及证据支持。 |
| ⚖️ **不合理** (P1): | 证据表明存在实质缺陷、不必要的范围或不合理成本。解释影响，并给出具体修正建议及其收益。使用实际的 P0–P3 严重级别。 |
| 🎨 **优雅** 。 | 职责和结构清晰，表达易读，接口自然且一致地表达用途，抽象、状态、分支、重复和防御措施都值得其成本。新增代码与附近或同类实现保持一致；偏离惯例时有合理依据。 |
| 🎨 **需要改进** 。 | 证据表明存在实质且可避免的理解或维护负担，并有依据充分的更简单或更一致的做法，其收益值得承担改动成本。说明具体负担、拟议改动及收益。推进前必须优化，或明确接受保留。 |
| 🎨 **可选改进** 。 | 当前实现已达到结构质量要求，但有依据的调整能带来具体收益，值得承担其改动成本。说明有限的收益，并保持其可选性质。 |
| ⚖️ **证据不足**。或 🎨 **证据不足**。 | 指出该维度缺少什么证据以及如何补足。另一个维度仍可得出有依据的判断。 |

对报告中的改进建议采用比内部检查更严格的筛选：省略个人偏好、琐碎或收益很小的润色。将同一根本负担的证据和补救措施合并说明，避免产生许多细碎建议。只报告值得实施的改动；没有发现这类改动也是有效结果，但每个修改项仍须给出必要的两个判断。

在优雅性维度评估防御措施的增加和删除。优先依赖已建立的不变量和边界保证，避免重复检查或推测性的兜底；增加防御措施需要有具体目的，足以证明其复杂度值得承担。仅仅缺少额外保护不构成不合理，除非证据指出了可信的触发条件和可能造成的严重后果。正常受支持的行为和承诺的失败处理仍属于正确性义务。

合理的改动也可能有必须处理的优雅性问题。保持两个判断独立：有依据的结构问题需要优化或明确接受保留，未达到该门槛但值得实施的调整仍为可选项。风格对齐以观察到的附近或同类实现为依据，而非审查者偏好的惯例。另有证据支持的合理性缺陷仍须修复或明确忽略。只对不合理发现分配严重级别：P0 为关键问题，需立即处理；P1 为严重问题，需尽快修正；P2 为普通优先级；P3 为影响较低但值得修正的问题。依据后果和受影响条件判断。

保留底层审查中的实质发现及限定条件，包括任务和规范方面的问题。区分实际执行的检查与作者报告的结果。

### 选择解释深度

行为直接、范围清楚且没有实质风险或权衡时，通常适合 **简洁** 解释：一个简短的前后变化段落，再给出两个判断。一般无需例子、代码片段、emoji 前缀或修改前后标签。

复杂机制、重要契约、实质发现或权衡，以及关键证据缺口，适合 **展开** 解释。一种实用版式是先 ⏪ **修改前**，再 ⏩ **修改后**，然后给出两个判断。对代码，从保留的证据中展示最小而有用的前后片段，并解释它们如何产生所比较的行为。保留相关错误、状态或生命周期条件。清楚标明示意性简化并保持其行为；代码不能帮助理解时省略。一行 diff 也可能需要展开。

## 分组展示并维护进度

在某个文件使本组修改项数达到至少 10 时结束该组；不要拆分文件。范围结束时展示最后不足一组的内容。在收尾中给出本组结论与累计进度，明确表示需审查文件中已经展示的数量；进度不代表完成操作或 Viewed 记录已经完成。建议用 `---` 分隔完整文件块和收尾，并将计数和总数加粗，便于浏览。

跨回复保留分组成员、已审查改动、下一位置和 M 编号、判断、发现的处理决定、必须处理的优雅性问题及其优化或保留决定、可选建议，以及各组已验证的完成结果。主审查中的每个文件只计一次。整分支提交可能在文件尚未全部展示前就使工作树变干净；继续根据保留证据展示未见分组，不要从新暂存区重建范围。只有范围实际变化时才更新总数。

### 单独处理顺带观察

在必要阅读中，只有证据既能证明一个无关既有问题确实存在，又能证明所选改动没有引入、触发或加剧它时，才报告该问题。这不授权扩大审计范围。

为观察分配连续的 **O1**、**O2** 等编号。最初只在分组收尾中单独、明确标为范围外的部分展示，包含标题、源位置或链接、证据与影响、它与所选改动的独立关系，以及建议和收益。推荐标签为 `📌 **Incidental observations (outside this review's scope)**`。

O 条目不增加主审查文件数、修改项、进度或 Viewed 资格。仅作为建议时，它既不阻止推进，也不授权修复。未限定范围的修复、优化、忽略全部和接受全部操作不包含 O 条目。选定的 O 修复需要单独确定结果、授权、检查和专门复审；除非用户明确扩大主范围，否则保持独立。

## 提供操作

| 操作 | 效果 |
| --- | --- |
| **修复** | 修复选定的待处理不合理发现；未限定范围时，选择所有已展示且未解决的不合理发现，包括之前分组。 |
| **忽略** | 只将选定的不合理发现标记为已忽略，保留严重级别和影响。若存在多个可能条目，除非用户明确选择全部，否则澄清选择。 |
| **优化** | 实现选定的必须处理或可选的 🎨 改进；未限定范围时，选择所有已展示且未完成的优雅性改进，包括之前分组。待处理不合理发现仍保持待处理。 |
| **接受保留** | 在说明负担和拟议补救方案后，明确保留选定的必须处理的优雅性问题。将判断和取舍保留为已接受，不标记为已优化。若存在多个可能条目，除非用户明确选择全部，否则澄清选择。这既不忽略不合理发现，也不授权编辑。 |
| **通过并继续** | 完成必要的整分支提交和已说明的 PR 发布，将符合条件的 PR 文件记录为 Viewed，验证完成后再推进。 |
| **继续** | 不暂存、不提交、不推送，也不标记 Viewed，直接推进。保留改动、判断、保留决定和可选建议。 |

按对话语言本地化操作名称和说明。M 编号将操作限定到条目，不代表选择整组完成。推进到保存的下一组；全部文件展示后，使用 **通过并结束** 和 **结束**。

区分以下三个范围：

| 范围 | 包含内容 |
| --- | --- |
| **审查和进度** | 选定、符合条件且实际展示的文件和差异。 |
| **提交和发布** | 分支全部待提交改动；推送时还包括完整的待发布提交祖先链，须满足下述准备和确认要求。 |
| **Viewed** | 当前组符合条件且已审查的文件，以及中途完成操作中明确纳入的先前文件。最终的 **通过并结束** 覆盖所有已展示并审查的分组，包括通过 **继续** 推进的分组。 |

纳入提交或推送不等于已经审查。本地或分支审查无需 PR，也不授予推送权限。PR 完成操作要求已验证的 PR；发布还需要对已说明的发布差异取得明确授权。两种推进操作都不批准或合并 PR；已忽略的发现仍是已忽略。

### 判断哪些操作已就绪

两种推进操作都要求：所有已展示的不合理发现均已修复或明确忽略，所有已展示的必须处理的优雅性问题均已优化并复审或明确接受保留，正确性与版本证据可用，必要审查检查通过，受影响部分的复审已完成，且任何先前选定的完成操作都已充分验证。这些要求也覆盖之前分组的未解决条目。仅有可选改进或缺少优雅性证据，不阻止推进；没有依据的优雅性疑虑不能成为必须处理的问题。

提供完成选项前，为其实际效果执行可推导的只读准备。按以下优先顺序处理：

| 状态 | 菜单 |
| --- | --- |
| 有待处理的不合理发现 | 提供修复、忽略；如果还有必须处理的优雅性问题，同时提供有依据的优化和接受保留。解释两种推进操作为何都不可用。 |
| 必须处理的优雅性问题尚未解决 | 针对明确的条目提供优化和接受保留。如果同时还有不合理发现，加入相应的修复或忽略选项；接受保留优雅性问题不能解决不合理发现。解释两种推进操作为何都不可用。 |
| 缺少正确性或版本证据、审查检查失败或未完成，或审查已过时 | 说明缺口及补救方式；先完成已授权工作，再提供推进选项。 |
| 选定的提交、推送或 Viewed 操作尚未完成 | 保留该选择，就绪后直接恢复已授权的剩余步骤，无需例行重新确认。若效果变化需要新的决定，针对同一个完成操作提供该决定；普通继续不能绕过它。 |
| 推进已就绪，但完成操作的目标、接口、检查或安全范围不可用 | 说明具体前提。继续仍可用。额外分支内容的检查只有影响审查时才阻止继续。 |
| 额外内容需要确认纳入 | 说明该内容；其他前提都就绪时，提供确认并完成的组合选项，同时提供继续。 |
| 完成操作已就绪 | 提供实际剩余的提交、推送和 Viewed 效果，同时提供继续。复用已验证完成的工作，不创建空提交或进行不必要的推送。 |

本地或分支审查就绪后，完成操作会提交待提交改动并验证。PR 就绪后，完成操作会在需要且获授权时发布审查改动，再将符合条件的文件记录为 Viewed；不需要提交或发布时，提供仅记录 Viewed 的通过选项。说明将复用的任何已验证结果。只要仍有有依据的建议，就加入优化选项。

每次收尾都说明完成操作是否就绪，包括修复后或专门复审的收尾。说明待处理不合理发现的编号、严重级别及影响，包括之前分组的发现。单独展示尚未解决的必须处理的优雅性问题，列出编号、具体负担、补救方案和收益；保留明确的接受决定及其取舍、可选建议，以及单独的 O 类观察。适用时披露完整提交范围、额外内容确认、发布差异以及 Viewed 集合。明确区分不可用操作和可执行选项。

一种实用的收尾版式是结论与进度、相关检查及限制、具体决定与可用操作。emoji、简短标签和字母选项有助于浏览。简单的继续问题通常无需编号；多个决定或后续引用则可能需要编号块。建议可紧贴选项，理由需要解释时也可用单独的 ➡️ 段落。直接引用已经说明的范围，避免重复菜单或要求作出同一个选择。[收尾示例](references/report-examples.md#example-closings-for-different-results)展示了这些表达选择及不同的就绪状态。

已授权工作就绪后直接继续。审查和完成操作均已结束且没有待决定事项时，报告结果，不再要求选择。

用户在受阻时要求推进，应说明待处理编号或前提，并重新生成可用菜单；继续从不等于忽略或接受保留。问题和争议发现需要回答或重新评估，不自动推进。用户始终可以明确停止或暂停：报告已展示进度，以及未解决的发现、证据、改动、发布或操作，不宣称工作已经完成。

## 修复并复审

将已授权的修复或优化限定在选定条目及必要支持改动内；优化保留受支持的行为和契约。被审查内容变化后，或任何 O 条目修复后：

1. 成功完成必要检查，刷新修改前后证据和链接。对尚未发布的 PR 改动，同时保留固定的远端版本和经检查、准备发布的本地内容；O 证据单独保留。
2. 独立复审已变化或受影响的已审查部分，包括意外改动。在专门回复中展示完整更新后的文件块及两个判断，与尚未展示的文件分开。对 O 修复，在专门的 O 复审中评估行为及受影响依赖，给出源位置、前后解释和两个有理由的判断。
3. 保留原始 M/O 编号和分组成员，不重复计数文件。O 复审不产生主进度或 Viewed 资格。只有检查和复审确认结果后，才将修复或优化标记为完成。接受保留的决定仅对相同的已评估内容和效果有效；两者变化时重新评估该决定。

单次修复、忽略、优化或接受保留以更新菜单结束，不推进。单独接受保留不会改变被审查内容，无需对内容重新复审。明确的复合请求授权其有序效果，包括编辑后先完成专门复审，再执行完成操作和推进；继续执行这些已授权步骤，无需例行再次确认。新发现、检查失败、效果变化或新发现的额外内容会暂停依赖它的步骤。单独授权的优化可在仍有发现时进行，但推进仍要求满足上文所有适用条件。

## 准备完成操作

对于没有本次审查所产生的未发布改动、且没有尚未完成的已选提交或发布操作的 PR，通过可以在不提交或推送的情况下核验固定的远端 PR 版本并记录 Viewed。通过只读检查确认，包括子模块检出差异在内的无关本地差异，不会影响固定审查差异及其依赖，也不会使逐文件的完整审查覆盖失效；保留这些差异。它们的存在本身不要求发布或确认纳入。本次审查产生的未发布改动，包括修复和优化，必须先进入已验证的 PR 版本，才能记录 Viewed；尚未完成的已选提交或发布操作仍须保留完整范围并完成剩余步骤。

### 清点整个分支

完成操作包含提交或推送时，确认准确的仓库、分支和工作树。清点所有已暂存、未暂存和未跟踪改动，以及拟议推送会发布的每个已有提交。保留分支顶端、暂存区、工作树和适用的未跟踪内容，作为恢复证据。

完成操作中的提交包含整个分支的待提交状态，包括测试、支持或生成文件、仅已暂存改动，以及未展示或被排除的文件。遵守仓库对敏感、被忽略或临时文件的限制；与用户解决不安全的纳入问题，不要悄悄缩小提交范围。对于部分暂存，确定一致的最终工作树内容，说明它取代了哪些暂存内容，并保留原始暂存区。未解决的内容冲突阻止完成。

根据本次对话记录的操作和基准确定来源，包括同一文件中来源混合的代码块。对于在其他地方产生或来源未知的改动，说明具体路径或提交、行为和实质效果，并在提交或发布前取得明确纳入确认。已有确认适用于相同内容和效果；对已审查分组的一般认可不覆盖未说明的额外内容。没有确认或用户拒绝时，保留改动，让整分支完成操作保持待处理；提供继续或调整范围，不自动改成更小的提交。

说明提交和推送范围与已展示审查及 Viewed 范围的差异。同一对话产生的额外内容需要清点和检查，但不需要额外的来源同意。对完整拟提交或发布范围运行必要检查，评估对已展示审查的影响，并在需要时完成专门复审，包括每一项选定的 O 修复。纳入同意不能替代审查或检查。

### 准备 PR 发布和 Viewed 记录

提供 PR 完成选项前，验证 PR 所属仓库、源分支与远端、查看者、当前 base/head，以及实际写入操作和回读所需的可用接口。涉及发布时，还要验证待发布提交祖先链，并将完整推送差异与 Viewed 集合分开说明，包括已有未推送提交。除下述 review 提交的 amend 情况外，发布要求普通推送；说明任何缺失的前提。完成操作不授权变基或排除提交。

Viewed 覆盖 PR 某个版本上的整个文件。提供标记某路径的选项前，将其完整的拟发布 PR 差异与保留的已展示评估比较。对每个尚未覆盖的改动块进行专门复审并给出两个判断，即使它是已获准纳入的独立额外内容。保留编号、原始分组和进度。O 复审不会让原本不符合条件的路径获得资格。

如果覆盖范围缺少证据或需要范围决定，让路径保持未标记，完成操作保持不可用或待处理。保留选定的 Viewed 集合，不要靠丢弃路径来完成。检查通过、纳入同意以及先前改动块未变化，都不能补足缺失的覆盖。

## 执行完成操作并验证

只执行所选操作已说明且获授权的效果。复用已验证的提交、推送和 Viewed 结果，不重复写入。

在整个完成过程中，预期的新 head 需要验证，不必重复已经覆盖的审查。内容、base 或受影响依赖发生意外变化时，复审受影响部分；仅凭文本相等无法证明效果未变。结果不再代表获授权的已审查版本时，刷新证据并取得新选择。标记较新版本不能证明它已被审查。

### 1. 重新验证所选效果

将审查证据、适用的远端 base/head 及相关本地状态，与准备好的状态比较。提交或发布时，纳入分支顶端、暂存区、工作树和待发布提交祖先链。发生偏移时刷新清单，运行适用检查并复审受影响部分。将要提交或发布的额外内容发生变化或新增时，需要重新确认纳入。

### 2. 需要时提交

暂存已说明的完整最终内容，并将暂存区与预期文件树核对。已记录的审查操作能确认 HEAD 是本次审查的修复或优化提交，且当前分支和任何推送目标均不是 `master` 或 `main` 时，使用 `git commit --amend`；否则新建提交。

运行正常钩子，然后验证提交、父提交、完整文件树、暂存区及剩余工作树状态。钩子产生的改动需要适用检查和受影响部分复审；超出已确认内容的改动还需要更新同意。提交所有预期改动，不留下无法解释的残余。本地或分支完成操作此时可以推进。

### 3. 获得授权且需要时发布

钩子执行后重新验证完整待发布差异。替换已发布的 review 提交时，使用 `--force-with-lease=<ref>:<verified-old-remote-SHA>` 推送到已验证的源引用；否则普通推送。远端变化或推送被拒绝时暂停。

回读 base/head 和完整已发布差异。确认提交符合预期、内容经过检查，且已展示评估仍有效。

### 4. 在已验证的 PR 版本上记录 Viewed

在实际 PR 版本上验证查看者和两个提交 ID，确认选定集合中每条路径都已完整覆盖。只将符合条件且仍待记录的选定路径标为 Viewed。回读每条选定路径，包括复用的结果，以及 PR 版本。全部路径都必须是 `VIEWED`，且记录期间 base/head 保持不变。

### 5. 推进或结束

确认已验证的结果，从保存的位置继续。最终完成涵盖所有已展示分组，包括此前未记录而直接推进的分组。

### 恢复未完成操作

写入、接口或验证失败时暂停，不推进、不自动回滚，也不改用继续或结束。报告已确认、失败和未知的效果，包括提交、推送状态、剩余改动、部分暂存和 Viewed 路径。

保留清单、来源确认、固定证据、选定的发布和 Viewed 范围、查看者与版本、分组状态及恢复位置。响应丢失后先检查实际本地和远端状态，再重试。就绪后，只恢复同一个完成操作的缺失步骤；不要悄悄加入内容、扩大中途选定的 Viewed 集合或重复成功写入。

完成要求所有必要回读都成功。明确停止可以留下残余工作，但必须报告。成功恢复后保留进度，不要重新应用筛选来删除已展示的文件。
