# 报告格式

[Skill 入口](../SKILL.md)负责评估、发现、身份、进度、动作标签及决定。本参考文档负责如何呈现这些内容：范围、文件块、解释深度、收尾和菜单。普通、补充、修复及选定 O 项报告共享此布局。入口中的情景示例展示其用法；其中虚构的路径、源码、检查和结果都不构成执行证据。

## 确定报告范围

说明读者即将评估什么。普通报告引言标识分组；补充报告引言标识额外交付覆盖；修复报告引言点明选定的原始 M/O 项，并关联其配套改动。补审和修复覆盖应与尚未展示的主分组分开。

每个已评估文件使用一个文件块，在首个文件块前、各文件块之间及收尾前各放一条水平线。文件标题为 📄，后接 `local_web` 返回的完整仓库相对文件名链接，加粗且保持原样。简短概览可以说明文件职责或伴随改动。文件名就是差异链接；只有读者需要其他独立证据时才增加链接。

````markdown
<report scope and original-item relationship, when needed>

---

📄 **[<full/repository-relative/path>](<returned-url>)**

M1 · <one natural sentence explaining the change and why it matters>

---

📄 **[<another/full/path>](<returned-url>)**

**M2** · **<detailed change title>**

> ⚖️ ❌ **Unreasonable** · **P2** · <defect and user or caller consequence>\
> 🎨 ❌ **Needs improvement** · <design problem and remedy>
>
> ⏪ <earlier implementation>
>
> ```<language>
> <relevant actual earlier code>
> ```
>
> ⏩ <changed implementation>
>
> ```<language>
> <relevant actual changed code>
> ```

---

<result, unresolved decisions, warnings, and accepted trade-offs>

<actual checks, re-review coverage, and evidence limits>

📊 **Reviewed 7 / 42 files, with 10 modifications.**

<state-appropriate choices or remaining authorized work>
````

此处展示的进度行属于普通主分组。补审和修复报告说明各自覆盖范围；有必要时，说明已保存的主进度不变，不增加已审查主文件或修改项数。

## 按所需深度解释修改

直接明了、没有可操作问题、值得实施的可选改进或实质不确定性的修改，使用简洁形式：`M1 · <change and purpose>`。普通 ID、中点和自然句放在同一行，不加单独标题、加粗、引用块、判断图标或代码块。单个此类修改只需要文件标题和该句。简洁项与详细项可共存于同一文件；两者都要完成两个维度的完整评估。

可操作发现、值得实施的可选改进、实质不确定性，或读者需要理解的重要机制，使用详细形式。将加粗 ID 和加粗标题放在同一非缩进行，以普通中点分隔。下方像骨架那样，将两个判断及前后证据对齐放入同一 Markdown 引用块。条目间使用普通段落间距。

每个判断包含维度图标、结论，以及一句说明原因和后果或取舍的话。两个判断行用 Markdown 硬换行连接。只有实际缺陷才在维度图标后紧接 ❌，严重性放在不合理行。结构缺陷在合理性行说明用户或调用者影响，在优雅性行说明设计问题，共用一个条目和一个修复方案。具体替代方案决定判断时，应点明它。

使用简洁的真实前后代码片段，保留理解改动所需的错误、状态或生命周期上下文。⏪、⏩ 说明和代码围栏与判断放在同一引用块内。短改动可用行内代码作证据。示意简化需明确标注。修复证据比较修复前后的内容，不用原先固定的 PR 比较替代。

修复或优化后，已解决的直接改动可转成简洁项。重要设计选择、契约变化、新增或新揭示的风险，以及用户要求的解释，仍需详细呈现。选定项的当前判断在其详细项中给出；判断相同的简洁项，可在收尾用一句话统一说明。解释变化的理由，并保留尚未解决的决定。

## 保留身份和可见覆盖

修复报告展示每个已改非测试文件，包括配套文件。测试按仓库分类出现在验证证据中。简洁呈现不缩小完整修复或受影响上下文的评估范围。

保留既有条目的 ID，并仅在负责解释它的文件下展示一次。需单独解释的配套修改使用入口连续序列中的下一个未分配 M ID；在引言中将其关联到原始修复。例如，分配过 M1–M10 后，一次修复可在三个文件中包含 M2、M11、M12，主进度仍不变。对 M2 的引用用于说明关系，不创建另一个编号条目。没有独立条目的伴随改动可使用简短文件概览。

选定 O 项工作保留所选 O ID，用文件概览说明配套改动；这些改动既不产生新的 O 观察，也不产生 M 项。详细 O 项使用相同的双维判断和证据布局。任何由此产生的发现，都归到负责的选定项下报告。

顺带 O 项放在来源文件的 M 项之后。只有 O 项的文件使用相同标题及已验证源码链接，位于主文件块之后。如果不适合归于单个文件，就将观察放在文件块之后，并在观察前及收尾前放置水平线。纳入入口要求的证据、影响、独立性及建议或收益；若有判断行，使用相同图标与严重性约定。放置位置不改变主进度、交付或 Viewed 资格。

## 以结果和下一项决定收尾

按以下顺序保留四部分，省略空类别：

1. **结果与决定。** 说明分组结论或修复的实际完成状态。列出待处理不合理项 ID、严重性与影响，保留的取舍，以及待选的可选方案和收益。简洁修复项尚未展示的当前判断，在这里给出。用 ⚠️ 单独总结实质不确定性，包含对应条目 ID、观察到的风险和未明背景。没有可操作发现，不代表每项改动都优雅或没有不确定性。
2. **证据与限制。** 说明实际执行的检查、结果及实质缺口。修复报告需指出全部已改非测试文件及受影响的此前已审上下文的覆盖，并提供验证记录和可用日志。区分编辑成功与必要检查不可用或复审未完成；后两者使依赖的补救仍未完成。测试仍是证据，作者报告的检查须与实际执行的检查区分。
3. **进度或覆盖。** 主分组仅按报告语言展示累计已审文件比例及实际主修改项数。补充、修复或选定 O 项工作单独说明覆盖，并保留已保存的主总数和位置。
4. **选择或剩余授权工作。** 按入口适用菜单展示具体 ID、效果及下一位置。如果已选交付，保留该待完成意图并使用对应决策表。没有新决定时，说明并继续授权工作，不再询问通过。前提不可用且没有可选补救时，说明限制，不虚构动作选项。

## 统一呈现选择

选择、标签、推荐、顺序和范围来自入口及阶段表。使用 Markdown 无序列表，每个选项占一个列表项，字母连续大写，项间不留空行。依次使用 `- `、字母、简短加粗动作标签、加粗外的可选推荐、冒号及具体效果。只加粗动作标签。

以下模式展示标点和间距，并不规定某份报告的动作：

```markdown
- A. **Pass** (recommended): Prepare and complete applicable delivery, then review the next group.
- B. **Continue**: Review the next group without delivery.
```

中文使用全角 `．` 和 `：`，加粗标签两侧留空格，`（推荐）` 放在加粗外。Pass 译为 `通过`，Continue 译为 `继续`，Finish 译为 `结束`；其他动作标签保留对应含义。

```markdown
- A． **通过** （推荐）：准备并完成适用的交付，然后审阅下一组。
- B． **继续** ：从下一组开始只读审阅。
```

工作区菜单使用相同呈现方式。范围结束时按入口动作语义使用结束，而非继续。

## 发送前检查报告

确认完整路径链接匹配已评估版本，每个必要文件均可见。检查 ID 稳定、每项仅独立出现一次、简洁项没有重复标题或引用块，以及详细项对齐判断与真实证据。检查 O 项位置、准确的修复状态和检查结果、额外覆盖不改变主进度、不确定性警告可见，以及菜单的标点、范围、推荐和效果。
