# 报告格式

[Skill 入口](../SKILL.md)负责评估、发现、身份、进度、动作标签及决定。本参考文档负责如何呈现这些内容：范围、文件块、解释深度、收尾和菜单。普通、补充、修复及选定 O 项报告共享此布局。入口中的情景示例展示其用法；其中虚构的路径、源码、检查和结果都不构成执行证据。

## 确定报告范围

首个普通分组先交代审阅对象、比较范围、纳入审阅的文件数和适用的排除条件，并说明哪些测试文件提供了行为证据。写明所选工作区或固定快照模式。说明与本次审阅相关且已核实的环境就绪情况和 Git 状态。若另行准备了工作区，也根据核实结果说明原检出目录的保留情况。

在首个文件块之前，用报告语言添加独立的 Markdown 二级章节「改动概览」。讲清原来遇到了什么具体问题、这次改了什么，以及用户或调用方预期会得到什么结果，让第一次接触项目的读者也能理解。用日常用语交代必要的背景，把这些信息串起来。自然段、无序列表或编号列表都可以，选择最容易把事情说清楚的形式。审查发现放在收尾总结。

首组的 `<REPORT_INTRODUCTION>` 采用以下结构。

```markdown
<REVIEW_SCOPE_AND_WORKSPACE>

## <CHANGE_OVERVIEW_HEADING>

<CHANGE_OVERVIEW>
```

后续普通报告引言标识分组。补充报告引言标识额外交付覆盖。修复报告引言点明选定的原始 M/O 项，并关联其配套改动。补审和修复覆盖应与尚未展示的主分组分开。

每个已评估文件使用一个文件块，在首个文件块前、各文件块之间及收尾前各放一条水平线。展示已评估的差异时，文件标题以 📄 开头，后接加粗的完整仓库相对文件名链接。使用 `local_web` 时，保留它返回的原始 Markdown。使用入口所述的固定快照替代方式时，保留同样的完整文件名标签，链接到已核实的该文件固定版本比较。文本文件在链接后加中点和 `+N / −N`，显示评估版本中已核实的新增和删除行数。二进制文件差异和只有源码链接的标题省略计数。简短概览可以说明文件职责或伴随改动。

提到其他文件、其中定义的符号或负责的行为时，在提到它的文字上附上已核实的差异或源码链接。描述整个文件或跨文件流程时，文件级链接即可。使用当前查看器支持的链接格式。在 Windows 下用 Markdown 按路径链接本地源码文件时，链接目标的第一个字符就是盘符字母，如 `[label](D:/project/src/task.dart)`。核实链接中绝对路径实际指向的文件。SmartKit 生成的差异链接目标保持原样。

按报告语言填写占位内容。[完整分组示例](../examples/review-group.md) 展示了首组开头、标题、结论和进度的写法。

````markdown
<REPORT_INTRODUCTION>

---

📄 **[<PATH_1>](<URL_1>)** · `+1 / −1`

**M1** · Add | <NEW_CAPABILITY_AND_PURPOSE>

---

📄 **[<PATH_2>](<URL_2>)** · `+9 / −4`

**M2** · Modify | <CHANGED_BEHAVIOR>

> ❌ ⚖️ **<VERDICT>** · **P2** · <TRIGGER_AND_IMPACT>
>
> 💡 <REMEDY>

**M3** · Delete | <REMOVED_ENTRY_POINT>

> <REASON_AND_CALLER_IMPACT>

---

<RESULT_AND_DECISIONS>

<EVIDENCE_AND_LIMITS>

📊 **<MAIN_PROGRESS>**

<CHOICES_OR_AUTHORIZED_WORK>
````

这里的进度行用于普通主分组。补审和修复报告单独说明各自的覆盖范围，必要时交代已保存的主进度。两者都不增加主审查的文件数或改动项数。

## 按每项改动的类型说明

每个条目的标题只加粗编号。改动项在编号后用报告语言写明类型和具体摘要。中文使用「新增」「修改」「删除」，例如「 **M2** · 修改｜重试失败的上传」。先说清这一项讲的是哪个行为、入口、职责或契约，再对照本次评估的版本，按它的实际变化定类型。需要时沿调用方找到另一个路径下的对应实现。同一文件可以包含多种改动。报告修复或优化时，比较本轮操作开始前和完成后的实际内容。

| 类型 | 应向读者说明什么 |
| --- | --- |
| **新增** | 说清新增了什么、用来做什么。指出谁会用到它，或它解决了什么问题。 |
| **修改** | 说清原有的行为或职责，以及具体改了什么。可以直接陈述。把前后并列更容易看清影响时，用 ⏪ 写具体的旧行为，用 ⏩ 写与其对应的新行为。 |
| **删除** | 说明删掉了什么、为什么删，以及对现有调用方的实质影响。有替代方式时，说清它能满足哪些用法，受影响的调用方还需要做什么。 |

新增和删除直接陈述。用需求、调用情况或差异中的证据支撑理由。只能确定效果时，就写实际效果。只有理由不明会影响判断时，才指出还缺什么依据。标题下如有正文或判词，放在同一个 Markdown 引用块里。使用箭头时，在各箭头后直接写说明。条目之间按普通段落留空行。

### 选择读者需要的说明深度

先评估合理性和优雅性，再决定写多细。三种改动类型都适用下面四种写法。用户仅指定审阅哪个文件时，按普通审阅的条件选择写法。

- **速览** 。改动很小、有充分依据判断它合理且优雅，并且标题能讲清该类型需要交代的信息时，只写标题即可。例如，「 **M6** · 修改｜将大小单位从 KB 改为 KiB，与界面按 1,024 字节换算的数值一致」就是完整的一项。
- **常规说明** 。标题需要补充背景时，写清有助于理解改动的原因、机制或影响。如果调用方依赖的保证能解释为什么这样改，也一并说明。
- **问题详述** 。评估发现缺陷、值得做的可选改进或实质不确定性时，把它写在该条目标题下。只交代理解这项发现所需的改动背景。行为缺陷先写触发条件和用户或调用方能观察到的结果，再解释原因和修法。结构缺陷说明违反的约定、对调用方或维护者的影响及修法。可选改进说明现有负担、改法和收益。实质不确定项说明已知事实、哪项判断受缺失证据影响，以及什么证据能定论。
- **按问详解** 。用户明确要求解释某个文件或条目时，直接回答所问，用一个具体例子讲到足以解答为止。展开已报告的改动时，沿用原标题，包括编号和类型，并保留仍然适用的发现。如果用户问的正是这项发现，在回答里把它讲清一次即可。

每项说明都应能单独读懂。修改是为修复旧缺陷时，可以用一个简单的触发条件和结果把差别讲清楚。有助于理解时，展示简短的实际代码、用图表示路径或状态，或给出足以让读者看懂修法的建议代码。节选保留相关的状态、错误和生命周期信息。简化示意和建议代码标明用途。陌生术语在首次出现时解释。引用界面文案时沿用被审版本实际显示的文字，转述用普通文字。

只把缺陷、值得做的可选改进或实质不确定性作为判词展示。每个问题在相应维度下解释一次。缺陷用 ❌ ⚖️ 或 ❌ 🎨 开头并注明严重级别。用 ❌ 🎨 **需要改进** 展示的结构缺陷，仍按入口的规则归为不合理项。值得做的可选改进用 🎨 **可选改进** ， **不确定** 的判断用 ⚠️ ⚖️ 或 ⚠️ 🎨。具体补救方法或消除不确定性所需的证据，前面只放 💡 图标。

## 保留身份和可见覆盖

修复报告展示每个已改非测试文件，包括配套文件。测试按仓库分类出现在验证证据中。简洁呈现不缩小完整修复或受影响上下文的评估范围。

保留既有条目的 ID，并仅在负责解释它的文件下展示一次。需单独解释的配套改动使用入口连续序列中的下一个未分配 M ID；在引言中将其关联到原始修复。例如，分配过 M1–M10 后，一次修复可在三个文件中包含 M2、M11、M12，主进度仍不变。对 M2 的引用用于说明关系，不创建另一个编号条目。没有独立条目的伴随改动可使用简短文件概览。

处理选定的 O 项时，保留所选 O 编号，在文件概览中说明配套改动。配套改动既不产生新的 O 观察，也不产生 M 项。在所选 O 编号下标明已实施改动的类型，解释该改动，并写明由此发现的问题。

附带观察保留 O 编号和标题，省略改动类型。将它放在来源文件的 M 项之后。只有 O 项的文件使用相同标题及已验证源码链接，位于主文件块之后。如果不适合归于单个文件，就将观察放在文件块之后，并在观察前及收尾前放置水平线。纳入入口要求的证据、影响、独立性及建议或收益；若有判断行，使用相同图标与严重性约定。放置位置不改变主进度、交付或 Viewed 资格。

## 以结果和下一项决定收尾

按以下顺序保留四部分，省略空类别：

1. **结果与决定。** 说明分组结论或修复的实际完成状态。列出待处理不合理项 ID、严重性与影响，保留的取舍，以及待选的可选方案和收益。用 ⚠️ 单独总结实质不确定性，包含对应条目 ID、观察到的风险和未明背景。
2. **证据与限制。** 说明实际执行的检查、结果及实质缺口。报告测试覆盖缺口时，核对已有用例及其准备步骤，指出具体哪个条件或操作顺序还没测到。修复报告需指出全部已改非测试文件及受影响的此前已审上下文的覆盖，并提供验证记录和可用日志。区分编辑成功与必要检查不可用或复审未完成；后两者使依赖的补救仍未完成。测试仍是证据，作者报告的检查须与实际执行的检查区分。
3. **进度或覆盖。** 主分组仅按报告语言展示累计已审文件比例及已展示的主审查改动项数。补充、修复或选定 O 项工作单独说明覆盖，并保留已保存的主总数和位置。
4. **选择或剩余授权工作。** 按入口适用菜单展示具体 ID、效果及下一位置。如果已选交付，保留该待完成意图并使用对应决策表。没有新决定时，说明并继续授权工作，不再询问通过。前提不可用且没有可选补救时，说明限制，不虚构动作选项。

## 统一呈现选择

选择、标签、推荐、顺序和范围来自入口及阶段表。使用 Markdown 无序列表，每个选项占一个列表项，字母连续大写，项间不留空行。依次使用 `- `、字母、简短加粗动作标签、加粗外的可选推荐、冒号及具体效果。只加粗动作标签。

以下模式展示标点和间距，并不规定某份报告的动作：

```markdown
- A. **Pass** (recommended): Prepare and complete applicable delivery, then review the next group.
- B. **Continue**: Review the next group without delivery.
```

中文使用全角 `．` 和 `：`，加粗标签两侧留空格，`（推荐）` 放在加粗外。Pass 译为 `通过`，Continue 译为 `继续`，Finish 译为 `结束`；其他动作标签保留对应含义。

```markdown
- A． **通过** （推荐）：准备并完成适用的交付，然后审阅下一组。
- B． **继续** ：从下一组开始只读审阅。
```

工作区菜单使用相同呈现方式。范围结束时按入口动作语义使用结束，而非继续。

## 发送前检查报告

确认首组把独立的「改动概览」放在已核实的审阅范围和工作区信息之后、首个文件块的分隔线之前。检查概览是否解释了为什么需要这次改动。站在刚接触项目的读者角度，逐项读一遍，再把每项发现的首句单独读一遍。行为问题的触发条件或结果如果需要读者先懂内部状态名、存储操作或项目术语，就重写首句。用日常用语说清具体操作或情况，以及用户或调用方能观察到的结果。把确切的技术条件和原因放到后面的解释里，并简短说明陌生术语。核对加引号的界面文案是否与实际显示一致。

核对文件计数、链接目标与评估版本。确认每个必要文件有可用链接，提及其他文件中的界面、调用方或责任方时，在相应文字上附链接。对照实际改动核对每项编号和类型。读一遍新增项和删除项，看是否讲清理由和对调用方的影响。再检查每处前后对比是否有具体对应项。确认每项改动只出现一次，判词跟在解释之后。检查 O 项位置、修复状态和检查结果、额外覆盖是否维持原有主进度、不确定性警告是否可见，以及菜单的标点、范围、推荐和效果。
