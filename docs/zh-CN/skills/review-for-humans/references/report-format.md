# 报告格式

[Skill 入口](../SKILL.md)负责评估、发现、身份、进度、动作标签及决定。本参考文档负责如何呈现这些内容：范围、文件块、解释深度、收尾和菜单。普通、补充、修复及选定 O 项报告共享此布局。入口中的情景示例展示其用法；其中虚构的路径、源码、检查和结果都不构成执行证据。

## 确定报告范围

首个普通分组先交代审阅对象、比较范围、纳入审阅的文件数和适用的排除条件，并说明哪些测试文件提供了行为证据。写明所选工作区或固定快照模式。说明与本次审阅相关且已核实的环境就绪情况和 Git 状态。若另行准备了工作区，也根据核实结果说明原检出目录的保留情况。

在首个文件块之前，用报告语言添加独立的 Markdown 二级章节「改动概览」。讲清原来遇到了什么具体问题、这次改了什么，以及用户或调用方预期会得到什么结果，让第一次接触项目的读者也能理解。用日常用语交代必要的背景，把这些信息串起来。自然段、无序列表或编号列表都可以，选择最容易把事情说清楚的形式。审查发现放在收尾总结。

首组的 `<REPORT_INTRODUCTION>` 采用以下结构。

```markdown
<REVIEW_SCOPE_AND_WORKSPACE>

## <CHANGE_OVERVIEW_HEADING>

<CHANGE_OVERVIEW>
```

后续普通报告引言标识分组。补充报告引言标识额外交付覆盖。修复报告引言点明选定的原始 M/O 项，并关联其配套改动。补审和修复覆盖应与尚未展示的主分组分开。

每个已评估文件使用一个文件块，在首个文件块前、各文件块之间及收尾前各放一条水平线。展示已评估的差异时，文件标题以 📄 开头，后接 `local_web` 返回的完整仓库相对文件名链接，加粗且保持原样。文本文件在链接后加中点和 `+N / −N`，显示评估版本中已核实的新增和删除行数。二进制文件差异和只有源码链接的标题省略计数。简短概览可以说明文件职责或伴随改动。

提到其他文件、其中定义的符号或负责的行为时，在提到它的文字上附上已核实的差异或源码链接。描述整个文件或跨文件流程时，文件级链接即可。使用当前查看器支持的链接格式。在 Windows 下用 Markdown 按路径链接本地源码文件时，链接目标的第一个字符就是盘符字母，如 `[label](D:/project/src/task.dart)`。核实链接中绝对路径实际指向的文件。SmartKit 生成的差异链接目标保持原样。

按报告语言填写占位内容。[完整分组示例](../examples/review-group.md) 展示了首组开头、标题、结论和进度的写法。

````markdown
<REPORT_INTRODUCTION>

---

📄 **[<PATH_1>](<URL_1>)** · `+1 / −1`

**M1** · **<TITLE_1>**

> ⏪ <PRIOR_BEHAVIOR_1>
>
> ⏩ <CHANGED_BEHAVIOR_1>

---

📄 **[<PATH_2>](<URL_2>)** · `+9 / −4`

**M2** · **<TITLE_2>**

> ⏪ <PRIOR_BEHAVIOR_2>
>
> ```<LANGUAGE>
> <PRIOR_CODE>
> ```
>
> ⏩ <CHANGED_BEHAVIOR_2>
>
> ```<LANGUAGE>
> <CHANGED_CODE>
> ```
>
> ❌ ⚖️ **<VERDICT>** · **P2** · <FINDING>
>
> 💡 <REMEDY>

---

<RESULT_AND_DECISIONS>

<EVIDENCE_AND_LIMITS>

📊 **<MAIN_PROGRESS>**

<CHOICES_OR_AUTHORIZED_WORK>
````

此处展示的进度行属于普通主分组。补审和修复报告说明各自覆盖范围；有必要时，说明已保存的主进度不变，不增加已审查主文件或修改项数。

## 按所需深度解释修改

将加粗 ID 和加粗标题放在同一非缩进行，以普通中点分隔。下方使用一个 Markdown 引用块，先用 ⏪ 说明以前的行为以及促使改动的具体问题或限制，再用 ⏩ 说明改了什么、如何满足这项需要。图标后直接写正文。如果原来的行为已经依靠某项必要保证来实现，就交代这项保证和提出改动的原因。

给每项补足背景，让首次接触项目的读者也能单独读懂。行为有变化时，在前后对比中解释用户或调用方能观察到的影响。涉及行为的发现，首句用日常用语交代触发情况和用户或调用方看到或收到的结果。紧接着说明确切的技术条件和原因。术语第一次出现时就解释。引用界面文案时，使用被审版本实际显示的文字。转述时用平实的话表达，省去引号。

对于直接明了的修改，如果没有可操作发现、值得实施的可选改进或实质不确定性，每个图标后写一个自然句即可。遇到这些发现和读者需要理解的重要机制时，详细说明。代码有助于说明行为时，在相应说明旁展示简洁的真实片段，保留必要的错误、状态或生命周期上下文。示意简化需明确标注。修复报告比较修复前后的内容。条目间使用普通段落间距。

在 ⏩ 之后，只展示可操作发现、值得实施的可选改进或实质不确定性。每个问题只写一次，放在相应的评估维度，说明具体原因以及可观察的影响或取舍。示例有助于理解触发条件或后果时，举一个例子。实际缺陷以 ❌ ⚖️ 或 ❌ 🎨 开头，并标明严重性。用 ❌ 🎨 **需要改进** 展示的结构缺陷，仍按入口的规则分类为不合理项。条目中的 **不确定** 判断以 ⚠️ ⚖️ 或 ⚠️ 🎨 开头。具体补救方法或消除不确定性所需的证据，前面只放 💡 图标。这些段落保留在同一引用块内。

修复或优化后沿用同一条目布局。仍需展示尚未解决的可操作发现、实质不确定性或重要的设计选择。

## 保留身份和可见覆盖

修复报告展示每个已改非测试文件，包括配套文件。测试按仓库分类出现在验证证据中。简洁呈现不缩小完整修复或受影响上下文的评估范围。

保留既有条目的 ID，并仅在负责解释它的文件下展示一次。需单独解释的配套修改使用入口连续序列中的下一个未分配 M ID；在引言中将其关联到原始修复。例如，分配过 M1–M10 后，一次修复可在三个文件中包含 M2、M11、M12，主进度仍不变。对 M2 的引用用于说明关系，不创建另一个编号条目。没有独立条目的伴随改动可使用简短文件概览。

选定 O 项工作保留所选 O ID，用文件概览说明配套改动；这些改动既不产生新的 O 观察，也不产生 M 项。使用相同的前后说明布局，将由此产生的发现放在负责的选定项下。

顺带 O 项放在来源文件的 M 项之后。只有 O 项的文件使用相同标题及已验证源码链接，位于主文件块之后。如果不适合归于单个文件，就将观察放在文件块之后，并在观察前及收尾前放置水平线。纳入入口要求的证据、影响、独立性及建议或收益；若有判断行，使用相同图标与严重性约定。放置位置不改变主进度、交付或 Viewed 资格。

## 以结果和下一项决定收尾

按以下顺序保留四部分，省略空类别：

1. **结果与决定。** 说明分组结论或修复的实际完成状态。列出待处理不合理项 ID、严重性与影响，保留的取舍，以及待选的可选方案和收益。用 ⚠️ 单独总结实质不确定性，包含对应条目 ID、观察到的风险和未明背景。
2. **证据与限制。** 说明实际执行的检查、结果及实质缺口。报告测试覆盖缺口时，核对已有用例及其准备步骤，指出具体哪个条件或操作顺序还没测到。修复报告需指出全部已改非测试文件及受影响的此前已审上下文的覆盖，并提供验证记录和可用日志。区分编辑成功与必要检查不可用或复审未完成；后两者使依赖的补救仍未完成。测试仍是证据，作者报告的检查须与实际执行的检查区分。
3. **进度或覆盖。** 主分组仅按报告语言展示累计已审文件比例及实际主修改项数。补充、修复或选定 O 项工作单独说明覆盖，并保留已保存的主总数和位置。
4. **选择或剩余授权工作。** 按入口适用菜单展示具体 ID、效果及下一位置。如果已选交付，保留该待完成意图并使用对应决策表。没有新决定时，说明并继续授权工作，不再询问通过。前提不可用且没有可选补救时，说明限制，不虚构动作选项。

## 统一呈现选择

选择、标签、推荐、顺序和范围来自入口及阶段表。使用 Markdown 无序列表，每个选项占一个列表项，字母连续大写，项间不留空行。依次使用 `- `、字母、简短加粗动作标签、加粗外的可选推荐、冒号及具体效果。只加粗动作标签。

以下模式展示标点和间距，并不规定某份报告的动作：

```markdown
- A. **Pass** (recommended): Prepare and complete applicable delivery, then review the next group.
- B. **Continue**: Review the next group without delivery.
```

中文使用全角 `．` 和 `：`，加粗标签两侧留空格，`（推荐）` 放在加粗外。Pass 译为 `通过`，Continue 译为 `继续`，Finish 译为 `结束`；其他动作标签保留对应含义。

```markdown
- A． **通过** （推荐）：准备并完成适用的交付，然后审阅下一组。
- B． **继续** ：从下一组开始只读审阅。
```

工作区菜单使用相同呈现方式。范围结束时按入口动作语义使用结束，而非继续。

## 发送前检查报告

确认首组把独立的「改动概览」放在已核实的审阅范围和工作区信息之后、首个文件块的分隔线之前。检查概览是否解释了为什么需要这次改动。站在刚接触项目的读者角度，逐项读一遍，再把每项发现的首句单独读一遍。行为问题的触发条件或结果如果需要读者先懂内部状态名、存储操作或项目术语，就重写首句。用日常用语说清具体操作或情况，以及用户或调用方能观察到的结果。把确切的技术条件和原因放到后面的解释里，并简短说明陌生术语。核对加引号的界面文案是否与实际显示一致。

检查文件计数与链接目标是否对应已评估版本。确认每个必要文件有可用链接，提到其他文件中的界面、调用方或负责这项行为的代码时，在相应文字上附链接。核对 ID 稳定、每项仅单独出现一次、判断在对比之后、每个问题只解释一次。检查 O 项位置、准确的修复状态和检查结果、额外覆盖不改变主进度、不确定性警告可见，以及菜单的标点、范围、推荐和效果。
