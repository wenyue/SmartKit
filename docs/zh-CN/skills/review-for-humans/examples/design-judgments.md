# 不同证据下的设计判断

这些虚构摘录展示单项判断及其对下一步决定的影响。完整条目和报告按[报告格式](../references/report-format.md)编排。

## 何时可以去掉额外的结果包装

一个服务的 `stop()` 必须在重复调用时返回同一个 Future，包括清理回调里的重入调用。PR 新增一个 completer，使清理开始前就有可用的返回值。审查者核实，即使互斥锁空闲，它也总会推迟执行回调，因此 `stop()` 可以在任何重入发生前缓存互斥锁返回的 Future，并在每次调用时返回它。这些证据支持行为判为 **合理** ，也支持将移除额外的完成状态管理列为 **可选改进** 。如果回调可以在调用时立即执行，等调用返回后才缓存 Future 就会留下重入窗口。

## 何时值得新增适配器边界

两个配置读取方唯一共用的加载步骤是调用第三方加载器。它的固定接口接收当前 schema 的文件，并返回通过校验的配置。应用仍支持按上一版 schema 保存的文件，因此新增一个应用侧适配器，在调用加载器前转换旧文件。检查确认两个读取方得到的配置和错误处理行为都与此前一致。兼容要求支持 **合理** 的判断。共用适配器也可以判为 **优雅** ，因为在加载器内部转换需要扩大第三方库的 schema 契约，在两个读取方各自转换则会重复映射逻辑。如果所有受支持的输入都已采用当前 schema，而适配器只是转发调用，直接调用加载器可以列为 **可选改进** 。

## 何时不确定性会影响下一步决定

解析器开始拒绝旧版本曾接受的值。新增测试证明了拒绝行为，受支持的输入策略仍未确定。将合理性判为 **不确定** ，指出缺失的策略决定和可能的兼容影响，等到正确性依据明确后再推进。

在另一次审查中，M12 增加了隐式上下文，同时保留了已核实的回调顺序和错误处理。源码和检查确认了受支持的行为，采用这套额外机制的理由仍不明确。通过已选定，其他交付前提均已满足。

> ⚖️ **合理** · 改动后的路径保留了已确认的回调顺序和失败行为。\
> 🎨 **不确定** · 隐式上下文让回调归属更难追踪，判断能否安全简化所需的设计约束仍然缺失。

⚠️ M12 的回调归属更难追踪，隐式上下文的必要性仍未核实。保留该警告，继续已选交付。
