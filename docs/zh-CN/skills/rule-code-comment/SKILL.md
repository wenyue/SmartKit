# 代码注释

用注释帮助读者理解、使用或维护代码。除非目标另有规定，默认读者熟悉语言和框架，但不了解这份实现。

## 判断什么值得注释

满足明确的覆盖要求。选择覆盖范围和信息时，综合权衡以下问题：

- 这段代码有什么用途，实际由谁使用或共享？即使只有一个调用者，也要认真考虑共享和外部使用的契约。
- 契约或行为有多复杂，还有什么不清楚？解释名称、类型、签名和代码未能充分传达的重要调用者义务、不变量、生命周期约束和边界情况。
- 这段说明如何融入可比较的本地代码？将注释的有无、风格、详略和视觉协调性视为判断阅读体验的依据。

这些因素没有固定优先级，本地惯例不能单独决定答案。公开可见本身不要求添加注释，简单直接的本地代码也可能不需要。添加或省略一条注释，不必意味着相邻代码的选择有误。

## 让说明有代码事实依据

依据当前实现及其所属契约确定事实。如果不确定性可能改变注释或其验证，就扩展证据范围。

如果实现与契约不一致，在授权范围内解决冲突，或报告冲突及其所有者。如实描述实际行为；注释不能把预期契约写成已经实现的行为。

## 将信息放在读者需要的位置

无论注释出现在何处，都按用途区分：

- API 文档解释调用者契约。
- 实现注释在代码旁解释局部原因、约束和权衡。
- 更广泛的概念放在负责它们的文档中。

先选择有用的目标位置，再确定修改权限。对超出任务范围的修正或移动提出建议。只有含义已在获授权的目标位置得到安全保留时，才能删除原说明。

## 编写和维护有用的文字

先说明具体职责或行为，再解释影响正确使用的重要约束。根据读者需要选择相关义务和理由。较长的说明可以通过阐明重要关系体现价值；简短的分节标签即使没有提供隐藏知识，也能帮助读者找到连贯的内容。

使用自然、准确、普通的语言。省略泛泛的赞美、逐行叙述、冗余名称和编辑历史。

遵循目标的文档语言、语法和明确格式要求。观察到的习惯可以影响表达，但不会因此成为要求。没有适用惯例时，使用已有的原生注释机制。

修正或删除过时和冗余的文字，同时保留仍然有效的含义，包括代码或其他负责承载说明的内容已表达清楚的含义。完整保留必需的机器指令、生成标记、协议令牌、机器可读形式和外部固定措辞。

沿相关路径把结果与代码一起阅读，检查其有用性、直接性和准确性。需要了解信息和语气选择的对比时，可以参阅可选的
[注释判断示例](references/examples.md)。示例给出了理解选择所需的上下文，不提供政策、规定格式或关于目标的事实。

## 在任务范围内工作

确定位置、所有者，以及审查或编辑权限。完成已授权的注释编辑，并使相关注释与独立获授权的代码修改保持一致。仅开展注释工作不授予修改代码、名称、类型或结构的权限。仅评估的工作保持文件和结构不变。

对于受管理或生成的内容，在编辑前确定规范编辑路径，以及其效果和必需输出的权限。

在普通工作中，使用父任务的验证和交付流程。应用本 Rule 不会额外增加单独的注释审计、报告或子代理流程。

对于应请求开展的评估，按上述覆盖和证据指导覆盖请求的边界。在准确位置报告可采取行动的缺失、误导、过时或冗余注释。说明其有实质影响的含义或冲突，以及支配判断的证据；必要时纳入建议的移动或结构修正及其所有者。无发现结论仅适用于已评估的边界。

对于专门的注释工作，运行相关、可用且由所有者支持的检查，包括获授权目标和受管理输出的每项必需检查。当适度增加的检查能实质提高对修改或潜在回归的信心时，补充这些检查。完成时，各所有者负责的要求必须得到保留，必需检查必须通过；必需检查失败或不可用时，工作仍未完成。

对于专门的工作，简明交付已覆盖位置、重要决策和证据、实际验证结果以及剩余限制。包括覆盖不完整、未经测试的目标或路径、不确定性、受阻动作、所有权冲突和范围外建议。

如果无法确定必要证据、必需资源、所有权、目标要求、访问条件或权限，报告确切缺口，暂停依赖它的动作和结论。在所属工作流允许时，继续独立且已授权的工作。
