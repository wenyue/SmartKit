# 代码注释

强度：`Default`

适用范围：跨语言开发或审查中受影响的代码注释和文档注释，以及用户要求的相关评估或维护。

## 选择有用的信息

满足明确的覆盖要求；否则，依据用途、实际使用和共享边界、契约及行为复杂度、名称、类型、签名和代码已经解释的内容，以及可比本地注释的有无、风格、详略和视觉连贯性来判断覆盖。综合权衡这些因素，不设固定优先级，也不预设本地实践决定答案。

解释原本不够清楚的重要调用方义务、不变量、生命周期约束和边界情况。即使只有一个调用方，也应认真审视共享和外部使用的契约。公开可见性本身不要求注释，清楚直白的局部代码也可以不写注释。决定添加或省略一条注释，无需先证明相邻代码的选择有误。

## 确定含义与位置

每项判断都应依据当前实现及其所属契约。若不确定性可能影响注释或验证，就扩大证据范围。实现与契约冲突时，在获准范围内解决，或报告冲突及其负责人；如实描述实际行为，不得把预期契约写成已经实现的行为。

无论出现在何处，都按用途区分 API 文档与实现注释。API 文档解释调用方契约。局部理由、约束和取舍应靠近实现，更广泛的概念应放在其所属文档中。先选择有用的位置，再确定修改权限。对范围外的修正或迁移提出建议；只有原有解释的含义已在获准位置得到妥善表达，才能删除原文。

## 面向有经验的同事写作

除非目标另有规定，假定读者了解语言和框架，但不了解当前实现。先说明具体职责或行为，再解释正确使用时的重要约束。依据读者需要选择相关义务与理由，控制详略。较长的说明可以澄清重要关系；简洁的分节标签即使不提供隐藏知识，也可以帮助读者找到连贯的代码部分。

使用自然、准确、平实的语言。省略笼统赞美、逐行复述、重复名称和编辑历史。遵守目标的文档语言、语法和明确格式要求。观察到的习惯可供表达参考，但不因此成为要求；没有适用约定时，采用语言已有的常规注释机制。

修正或移除过时、冗余的文字，同时保留仍然有效的含义，包括代码或其他所属载体中已经清楚表达的内容。保持必需的机器指令、生成标记、协议标记、机器可读形式和外部规定的措辞不变。沿相关路径，将结果与代码对照阅读，确认其有用、直接、准确。可选的[对照示例](references/examples.md)展示信息选择和表达方式，不提供政策、规定格式或目标事实。

## 在任务内应用并完成

明确任务的位置、负责人，以及审查或编辑权限。完成获准的注释编辑，使相关注释与另行获准的代码变更保持一致。注释工作本身不授权修改代码、名称、类型或结构；仅评估的工作保持文件和结构不变。对于受管理或生成的内容，在编辑前确定规范编辑路径，以及相应效果和必需输出的权限。

普通工作使用主任务的验证和交接，不另起注释审计、报告或子 Agent 流程。对于用户要求的评估，依据上述覆盖和证据政策，覆盖请求指定的范围。针对缺失、误导、过时或冗余的注释，在准确位置报告可采取行动的发现，说明其重要含义或冲突及依据。必要时给出迁移或结构修正建议及其负责人。无发现的结论仅适用于已评估范围。

专项工作应运行相关、可用且由所属方支持的检查，包括获准目标和受管理输出的全部必要检查。当适度补充检查能够实质提高对变更或可能回归的信心时，再添加检查。完成时应保留所属要求；必要检查失败或不可用，工作就仍未完成。简洁交接覆盖位置、重要决定及证据、实际验证结果，以及任何未完成覆盖、未验证目标或路径、不确定性、受阻操作、归属冲突或范围外建议。

无法确定必要证据、必需资源、归属、目标要求、访问条件或权限时，报告准确缺口，暂停依赖它的操作与结论。在所属工作流程允许的范围内继续独立且获准的工作。
