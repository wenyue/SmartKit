# 代码注释

用注释帮助读者理解、使用或维护代码。除非目标另有规定，应面向了解语言和框架、但不熟悉此实现的读者编写。

## 确定任务和修改所有者

确定位置、所有者，以及审查或编辑权限。完成已授权的注释修改，并在代码变更另行获授权时保持相关注释一致。单独的注释工作不授权修改代码、名称、类型或结构；仅评估工作保持文件和结构不变。

对于受管理或生成的内容，在编辑前确定规范修改路径，以及对其影响和必要输出的权限。

## 判断什么值得注释

满足明确的覆盖要求。决定覆盖范围和信息取舍时，综合考虑以下问题：

- 代码做什么，谁实际使用或共享它？即使只有一个调用者，也要认真对待共享和对外消费的契约。
- 契约或行为有多复杂，什么仍不清楚？解释名称、类型、签名和代码未充分表达的重要调用义务、不变量、生命周期约束及边界情况。
- 解释与同类本地代码如何配合？将注释的存在与缺失、风格、细节和视觉一致性，作为阅读体验的证据。

这些因素没有固定优先级；本地惯例不能单独决定答案。public 可见性本身不要求注释，直白的局部代码也可能不需要。增加或省略注释，不必意味着相邻选择有误。

对于影响调用者决定的失败，在 API 文档中解释失败条件、契约通过原生类型、类别或标识承诺的稳定识别方式，以及失败后的重要状态。覆盖返回和抛出的失败，包括有意跨越边界传播的失败。应用前述覆盖判断，不罗列偶发的底层失败，也不重复已经清楚的契约。

## 让解释以代码为依据

通过当前实现及其所属契约确定事实。当不确定性可能改变注释或验证方式时，扩展证据。

实现和契约不一致时，在授权范围内解决冲突，或报告冲突及其所有者。如实描述实际行为；注释不能把预期契约说成已经实现的事实。

## 将信息放在读者需要的位置

无论现有注释放在哪里，都按读者需求选择目的地：

| 信息 | 所属位置 |
| --- | --- |
| 调用义务和可观察行为 | API 文档 |
| 局部原因、约束和取舍 | 代码旁的实现注释 |
| 更广泛的概念 | 其所属文档 |

先选择有用的目的地，再确定修改权限。对于超出任务范围的修正或移动，给出建议。只有含义已在获授权的目的地安全表达后，才能删除原解释。

## 编写并维护有用的文字

先写具体职责或行为，再说明正确使用的重要约束。按读者需求分配细节：较长说明可以阐明重要关系，而简短的章节标签即使不增加隐含知识，也能帮助读者找到完整部分。

使用自然、准确、普通的语言。省略泛泛赞美、逐行复述、冗余名称和编辑历史。

遵循目标的文档语言、语法和明确格式要求。观察到的习惯可影响表达，但不因此成为要求。没有适用约定时，使用成熟的原生注释机制。

纠正或删除过时和冗余文字，同时保留仍有效的含义，包括已经在代码或其他所属载体中清楚表达的含义。保留必要的机器指令、生成标记、协议标记、机器可读形式和外部固定措辞。

沿相关路径，将结果与代码一起阅读，检查是否有用、直接、准确。需要比较信息取舍和口吻时，可选读 [注释判断样例](references/examples.md)。其中明示的背景帮助理解选择；样例不提供策略、规定格式或目标事实。

## 按任务规模验证并报告

普通工作使用父任务的验证和交接。应用本 Rule 不增加独立注释审计、报告或子 Agent 流程。用户要求的评估和专门注释工作，适用以下完成要求。

### 用户要求的评估

按前述覆盖与证据指导评估请求范围。在精确位置报告可行动的缺失、误导、过时或冗余注释。解释其重要含义或冲突及依据；适用时，包含推荐移动、结构修正及所有者。无发现的结论只适用于已评估范围。

### 专门注释工作

专门注释工作应运行相关、可用且由所有者支持的检查，包括授权目标和受管理输出的全部必要检查。若能显著提高对变化或可能回归的信心，增加适度检查。完成要求保留所属要求且必要检查通过；必要检查失败或不可用时，工作仍未完成。

专门工作应简洁交接覆盖位置、重要决定和证据、实际验证结果及剩余限制。说明未完整覆盖、未测试目标或路径、不确定性、受阻行动、所有权冲突，以及超范围建议。

### 缺失前提

必要证据、必需资源、所有权、目标要求、访问权限或授权无法建立时，报告准确缺口并暂停依赖的行动与结论。在所属工作流允许的范围内，继续独立且获授权的工作。
