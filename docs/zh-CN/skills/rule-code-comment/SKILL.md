# 代码注释

为将要调用或修改代码的人写注释。项目另有指定时，以指定的读者为准。默认读者熟悉语言和框架，第一次接触这段实现。

## 判断读者需要知道什么

从名称、类型、实现和现有文档出发，想想读者接下来会怎么做。读者会不会以不安全的方式重试、删掉一项看似多余的检查，或把有意接受的限制当成待修复问题？如果补充某个事实能改变这个判断，就把它讲清楚。现有说明已经足够时，直接沿用。

遵守明确的文档要求。其余情况综合考虑代码的用途和使用者、契约的复杂程度，以及阅读同类代码的体验。即使存储接口只有一个调用者，也可能需要仔细说明重试义务。公开的 getter 也可以通过名称和实现把行为说清楚。参考邻近注释的风格和详略，按读者的需要决定覆盖范围，按当前任务决定编辑位置。

在实现、修复和审查时，顺带判断是否需要注释。用户提出或确认行为时，想想后来的人看不到这段对话还能知道什么。如果修复或审查纠正依赖一个不明显的不变量、框架保证或设计决定，而维护者容易改掉相关实现，就在代码旁说明经核实的依据。已有说明充分时可以沿用，包括解释临时简化的注释。

## 核实实际行为

阅读相关代码路径及负责定义行为的契约。进一步核实会影响说明内容或验证方式的疑点。如果实现与契约不一致，如实说明差异，并在授权范围内解决或报告给责任方。直接在注释中承诺预期行为会掩盖这个差异。

用实际实现和相关契约解释不直观的取舍。写明行为、经核实的保留理由、适用范围和重要的剩余风险。理由不明时如实说明。说明或依赖某个已明确接受的决定时，查看相关注释及其引用的决定，核实是否确实已被接受。已接受的缺陷仍有后果，长期取舍可以延续，无需编造替换期限。

审查时沿用相同的范围。明确接受且仍符合原决定的后果无需另列修复项。新证据、条件变化或超出接受范围的影响应根据实际情况评估。

## 把说明放在负责的位置

在 API 文档中说明调用者义务及可观察的保证。纳入调用者需要据此采取行动的重要不变量、生命周期义务和边界情况。某种失败会影响调用者的选择时，说明何时发生、契约提供了哪些稳定识别方式，以及失败后留下的状态或部分结果。返回错误、抛出异常，以及从其他层有意传播的失败都适用。只承诺契约支持的错误类型、类别或标识。

把实现的原因、约束和取舍放在维护者可能改动的代码旁。更广泛的概念放在负责解释它的文档中。一项决定可以同时影响调用者和维护者。分别提供各自需要的解释，并复用归属位置上已有的充分说明。

先确定任务授权编辑的位置。完成已授权的注释改动，并与另行获授权的相关代码改动保持一致。修改行为、名称、类型或结构需要单独的代码改动授权。对于受管理或生成的内容，确定规范修改路径，以及对相应影响和必要输出的权限。超出授权范围的移动或修正应作为建议提出，并指出责任方。

## 编写并整体修订注释

默认采用 Google 风格，用平实的语言解释代码。先说明职责或行为，再交代正确使用或维护所需的内容。使用项目要求的文档语言、语法和格式。项目没有相应约定时，使用语言原生的注释方式。有具体用途时才使用已有约定的标记，例如用 `TODO` 记录明确的后续事项。

详略由读者的需要决定。简短的段落标签能帮助读者在长函数中找到一段完整操作。恢复算法可能需要几句说明，解释为什么某个处理顺序能防止数据丢失。省略泛泛赞美、名称复述、逐行叙述和编辑历史，直接说明必要事实。省略本项目工单和 PR 的引用，包括编号和链接。仓库内的决策文档、外部标准或第三方工单可以提供背景，注释本身应足以让读者理解。

修改注释时，对照当前代码阅读整个受影响的注释块。把改动融入上下文，合并相关说明，并修正或删去过时或重复的文字。删掉一段说明前，确认仍有效的含义已经在负责的代码或文档中清楚表达。保留必要的机器指令、生成标记、协议标记、机器可读形式和外部固定措辞。

如果重构编辑、移动、合并或删除了注释，确认仍然生效的取舍及其理由现在由哪段代码或哪份文档负责。理由可能随重构丢失时，就把说明带到该位置。

每次编辑注释后，对照相关代码路径阅读结果，检查说明是否准确、有用。需要参考详略选择和放置方式时，可以阅读[注释判断示例](references/examples.md)。

## 按任务范围验证

日常代码改动沿用原任务的检查和交接。审计、报告或委派的需要由原任务决定。

用户要求评估时，以只读方式覆盖请求范围。精确指出值得处理的注释遗漏，以及误导、过时或重复的说明。解释后果和依据，并指出建议移动注释或修正结构时应由谁负责。无发现的结论只覆盖实际评估的范围。

专门编辑注释时，运行相关且由所有者支持的检查，包括授权源码和受管理输出所需的全部检查。额外检查应能明显提高信心或发现可能的回归。报告覆盖位置、重要决定和依据、实际检查结果，以及仍有疑问、未经测试或超出授权范围的工作。目标要求得到保留且必要检查通过后，任务才算完成。

如果缺少证据、所有权信息、权限、目标要求、访问能力、必需资源或检查，指出具体缺口。暂停依赖该条件的操作和结论，继续独立且获授权的工作。必要检查失败或不可用时，报告验证未完成。
