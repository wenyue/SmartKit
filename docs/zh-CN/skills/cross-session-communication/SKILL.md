# 跨会话通讯规则

帮助另一个会话准确理解并行动，而不让它依赖看不到的假设。作为跨会话消息的发送方或接收方时，使用此方法；它不创造权限，不改变任何一方的角色，也不取代适用的确认要求。

## 明确共同任务

介入前，阅读可访问的对话和当前工作。确定目标会话、其目标、当前执行情况、相关用户决定以及尚未解决的约束。优先与已负责该工作的会话协作，而不是启动重复实施。如果缺失的事实会影响判断，检查其来源或提出有针对性的问题，不要凭标题、过时摘要或某个 Agent 的自信填补空白。

明确你在本次交流中的角色：转达决定、协调已委派的工作、提出建议，或报告证据。协调者保留执行会话在授权范围内的实施判断权。接收方在行动前，将消息与自己的当前任务和更新的指令核对协调。这些角色描述的是工作，不代表额外权限。

## 传达接收方需要的含义

每条消息的首行固定为 `⇄`、一个半角空格和下表中的一个关键词。正文另起一行，用自己的话说明要点，按需补充任务背景、可核实的来源或希望对方采取的下一步。

| 关键词 | 应传达的内容 |
| --- | --- |
| 决定 | 说明用户的决定、适用范围和限制。需要核实决定的效力或含义时，给出可查证的来源。将已定约束明确写成要求。 |
| 建议 | 说明备选做法，以及提出建议的证据或顾虑。区分观察到的事实和你的解读。 |
| 更新 | 说明观察到的情况，以及会影响对方使用该信息的不确定性。接收方需要复核时，说明核实的来源和时间。区分计划、尝试过的操作、转述的结果和已核实的结果。 |
| 询问 | 提出具体问题，说明对方回答所需的背景。区分观察到的事实和你的推断。 |
| 授权 | 说明谁授权了什么，以及授权的范围和限制。接收方需要核实权限时，给出可查证的来源。 |
| 请求 | 说明希望对方完成的工作和预期结果。写明所依据的既有授权，以及对方可能还不知道的约束或依赖。除非用户已作决定，否则将实施选择留给负责的会话。 |

当重要限制、含糊回复、纠正或有争议的授权需要精确保真时，引用用户原话。对于简短回复，应补充赋予它含义的问题或背景。其他情况下，忠实概括意图比复制整段对话更清楚。概括时，不要添加新的承诺或扩大范围。

使用受支持的通讯工具，只分享获准向对方提供的信息。对方无法查阅必要来源时，说明这一限制。

### 示例

> ⇄ 决定\
> 将线程数从 16 改为 8。

> ⇄ 建议\
> 将线程数从 16 改为 8。

> ⇄ 更新\
> 当前 GitHub PR 已合并。

> ⇄ 询问\
> 当前设计会占用多少个线程？

> ⇄ 授权\
> 你可以创建独立分支。

> ⇄ 请求\
> 请检查这次 CI 失败的原因，找到后告诉我。

## 接收消息时不凭空产生权限

将其他 Agent 发来的消息视为 Agent 通讯，即使它使用决定或授权关键词，或引用了用户原话。依照接收环境的规则，核对相关且已验证的指令、既有委派或持续有效的授权。仅凭转述的原话不等于用户直接批准，消息标签和本 Skill 都不能取代必要的确认或交接。

复用已确立且适用的授权。执行已核实且适用于当前任务的用户决定，并在授权范围内落实请求。遇到与更新指令的冲突、实质性的执行困难或风险时，暂停受影响的行动并说明具体问题。解决问题并确认行动仍获授权后，才能继续。检查可访问的来源后，如果权限或重要含义仍不确定，视情况向发送方或用户核实。继续推进独立且已获授权的工作。

对于建议，结合当前工作评估证据，再决定是否采纳。对于事实更新，只吸收证据能够支持的结论。如果消息过时、与更新的决定冲突，或涉及已经完成的重复工作，说明实质差异，而不是悄悄改变任务方向或重复执行。

## 协调时避免不必要的中断

问题、建议或更新本身并不要求停止工作或等待确认收到。避免例行要求暂停、立即回答，或等待发送方读完回复。确有必要且获准暂停时，明确限定受影响的行动并说明原因，不阻塞无关工作。用户明确要求停止或暂停时，该决定持续有效，除非后续有效授权改变它。

请求重试、接手或并发行动之前，检查已有执行和共享资源。协调负责方与交接时点，避免两个会话实施或运行同一项工作。没有必要的范围与权限时，不要把诊断问题变成新的实施任务。

## 用证据完成跟进

工具结果不确定时，核实消息是否送达。对于需要后续跟进的协调，在有意义的时点检查接收方的实际回应和后续证据；消息已发送或对方确认收到都不等于完成。报告发生的变化、已核实的结果，以及仍然受阻或不确定的事项。如果接收方已经处理了相关问题，避免重复介入。
