# 代码设计目标

强度：`Default`

适用范围：跨语言的代码编写、修改和审查，涵盖归属、边界、清晰度、局部一致性、状态完整性、依赖、抽象、诊断和文档。

## 归属与 API

- 每项行为、状态、不变量和生命周期都要有一个明确的所有者。
- 所有者内部的逻辑应与所有者保持内聚；只有确实存在复用或边界时才移动逻辑。
- 公共接口应保持精简，并对应稳定的产品或领域能力。
- 测试和调用需求通过所属契约解决，不要仅为方便而扩大 API、移动所有者内部逻辑或增加间接层。

## 清晰度与抽象

- 修改代码前，先查看目标文件及附近实现中是否有类似逻辑。除非更具体的 Rule 或明确批准的设计要求
  有意采用不同做法，否则沿用既有的命名、结构、控制流、API 风格。
- 通过命名、类型和结构，让职责、有效状态和主要决策路径可以在局部理解。
- 在契约或控制流中清楚呈现副作用、失败方式、重试、后备行为和生命周期转换。
- 只有抽象能表达真实概念、保护不变量，或在降低维护成本的同时消除有意义的重复时，
  才引入它。
- 不要引入会模糊归属，或只服务于一个简单用法的辅助函数、适配器和通用层。

## 诊断与抑制

- 不要在配置层面屏蔽编译器、分析器或 linter 的诊断。只有在解决诊断会破坏已批准的设计，或导致
  明显更差的结果时，才能在行内或整个文件中屏蔽。每次屏蔽前，都要说明具体诊断、影响范围和必要性，
  并取得用户明确确认；笼统授权或以前的授权不能用于之后的屏蔽。

## 状态与依赖

- 从创建到清理，状态变更和生命周期转换都应当容易预测。
- 在异步工作和回调中维持正确的依赖生命周期。
- 每个代码单元只接收自身需要的能力，并明确依赖方向和跨层边界。
- 通过可见的所有者提供依赖，并按照该归属放置状态。

## 文档

- 综合权衡注释用途、代码实际的共享程度和使用边界、行为或契约复杂度、信息价值，以及附近可比的代码，
  决定是否编写注释、采用哪类注释和写到什么详细程度。附近注释的有无、风格、详细程度和视觉协调性
  都应有实际分量，但任何因素都没有固定优先级，局部惯例也不是默认答案。有充分依据的判断可以支持
  添加或省略注释，无需先证明附近代码有错。
- 遵守明确规定且适用的文档语法和格式要求；将这些要求与观察到的习惯区分开，后者是上述判断的参考。
- 重点关注共享接口和供外部使用的接口的文档。根据实际契约判断：即使只有一个调用者，也可能承担共享
  契约；语言层面的 public 可见性本身不要求必须编写文档，简单局部函数也无需一律补齐。对于名称、
  类型和签名未清楚表达的重要调用约束和行为，应予以说明，包括相关不变量、生命周期义务、外部要求
  和边界情况。
- 按用途而非位置区分 API 文档与内部注释：前者说明调用契约，后者帮助读者理解实现。内部注释应简短，
  理解需要时再补充细节。它们可以解释原因、约束或取舍，也可以在有助于阅读和视觉组织时，用简短标题
  划分逻辑段落，无论位于函数内部还是外部。有用的分段标题不必揭示隐藏知识。
- 随代码变化维护注释的准确性和价值，更新或删除过时、冗余的文字。适度使用分段标题，保持代码阅读连贯。
  避免逐行复述代码、重复名称和记录修改历史；设计不清楚时，直接改进设计，不要用解释掩盖问题。
