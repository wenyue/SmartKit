# 代码设计目标

强度：`Default`

适用范围：跨语言的代码编写、修改和审查，涵盖归属、边界、清晰度、局部一致性、状态完整性、依赖、抽象、失败处理、诊断和文档。

## 归属与 API

- 每项行为、状态、不变量和生命周期都要有一个明确的所有者。
- 所有者内部的逻辑应与所有者保持内聚；只有确实存在复用或边界时才移动逻辑。
- 公共接口应保持精简，并对应稳定的产品或领域能力。
- 测试和调用需求通过所属契约解决，不要仅为方便而扩大 API、移动所有者内部逻辑或增加间接层。

## 清晰度与抽象

- 修改代码前，先查看目标文件及附近实现中是否有类似逻辑。除非更具体的 Rule 或明确批准的设计要求
  有意采用不同做法，否则沿用既有的命名、结构、控制流、API 风格。
- 通过命名、类型和结构，让职责、有效状态和主要决策路径可以在局部理解。
- 在契约或控制流中清楚呈现副作用、失败方式、重试、后备行为和生命周期转换。
- 只有抽象能表达真实概念、保护不变量，或在降低维护成本的同时消除有意义的重复时，
  才引入它。
- 不要引入会模糊归属，或只服务于一个简单用法的辅助函数、适配器和通用层。

## 诊断与抑制

- 不要在配置层面屏蔽编译器、分析器或 linter 的诊断。只有在解决诊断会破坏已批准的设计，或导致
  明显更差的结果时，才能在行内或整个文件中屏蔽。每次屏蔽前，都要说明具体诊断、影响范围和必要性，
  并取得用户明确确认；笼统授权或以前的授权不能用于之后的屏蔽。

## 状态与依赖

- 从创建到清理，状态变更和生命周期转换都应当容易预测。
- 在异步工作和回调中维持正确的依赖生命周期。
- 每个代码单元只接收自身需要的能力，并明确依赖方向和跨层边界。
- 通过可见的所有者提供依赖，并按照该归属放置状态。

## 失败处理

- 根据操作承诺判断成功、正常拒绝或缺失、契约内失败和程序契约违反，不以表达形式、发生频率或能否重试判断。
  保留失败结果和部分副作用；仅捕获失败或恢复未来可用性，不能证明使用默认值或报告成功合理。
  恢复必须履行承诺，或达到已接受的降级或部分完成结果。
- 不会失败的操作应保持直接；失败机制由语言和项目契约负责。只为调用方决策引入稳定区分，必要转换由所属边界完成。
  契约要求封闭业务失败分类时，穷尽处理；开放协议显式处理未知结果，保留失败和有用原因，不将附带失败伪装成业务拒绝。
- 生产所需的校验、控制流、副作用和不变量，应独立于可能关闭的检查而生效。程序契约违反与正常否定结果保持可区分。
- 只为自身负责的恢复、清理、补偿、契约要求的转换或最终处理而介入失败；否则按已接受契约传播，包括从库移交给调用方。
  每个独立发起的操作都应有最终负责人，每条异步或脱离调用链的路径都应明确完成、失败和生命周期归属。
  保证所有路径上应负责的清理，包括取消和中断。
- 消费失败或委托报告后，仍承担状态、清理、重试和反馈责任。保留可观察的未解决结果、残留副作用、已有且有用的原因和诊断，
  直到最终处理，并区分原始失败与恢复、清理或补偿失败。
- 恢复需要有效结果状态、可行且有界的动作，以及产生相应副作用的权限。重试必须能解决原因，并在完整路径上安全，
  其中包括部分不可逆副作用及必要的幂等性或补偿。在确立具体损失的权限和有效结果状态前，保留重要数据或唯一副本。
- 在理解数据语法和含义的边界校验数据，区分无效内容与 I/O 失败。受支持的持久化数据损坏恢复，
  必须避免重复读取时发生相同失败；不受支持或失败的恢复仍保留失败结果。
- 每个需要报告的事件都应有最终报告负责人，允许互补的诊断和受众反馈，但传播过程不重复报告事件。
  根据影响、运行预期和所需响应判断严重程度；具体级别和告警由项目负责。
  失败通道或恢复结果中的任何一项，都不能单独决定严重程度；已恢复事件仍可能值得调查。
  提供有用的上下文、影响和处置情况，排除凭据和不必要的隐私数据。
- 根据实际能力和权限分配补救责任，专业修复交给具备相应能力的角色。区分产品反馈与维护者诊断，
  即使用户无法修复，也说明重要损失或不可用情况；存在可行行动或受支持的升级处理途径时予以提供。
  补救行动的完成、失败和中途停止都应有负责人，并通过适合受众和运行环境的渠道保持可观察。
- 代码、类型和引用契约未清楚表达重要含义时，解释调用方义务和恢复依据，尤其是数据损失权限与重试安全。
- 根据这些原则及代码和契约证据，判断是否需要开展失败处理工作。仅沿用明确既有的传播策略时，无需单独启动流程。
  需要编写或实质修改失败路径，或选择失败契约、恢复、重试、数据损失、最终处理或补救策略时，
  使用 [handle-operation-failure](../skills/handle-operation-failure/SKILL.md)。专项失败处理评估、诊断或设计也使用该 Skill。

## 文档

- 随代码变化维护注释的准确性和价值，更新或删除过时、冗余的文字。
- 遵循目标的文档语言、语法和明确的格式要求。
- 满足明确适用的注释覆盖要求。除此之外，综合权衡用途、实际使用与共享边界、行为及契约复杂度、
  名称、类型、签名或代码尚未清楚表达的信息，以及附近可比代码的注释有无、风格、详细程度和视觉协调性，
  决定是否需要注释。各因素没有固定优先级，局部惯例也不是默认答案；有依据时可以添加或省略注释，
  无需先证明附近代码有错。
- 重要的调用方义务、不变量、生命周期约束或边界情况尚不清楚时，可以据此判断需要注释。
  即使只有一个调用方，也要认真考虑共享和供外部使用的契约；仅凭 public 可见性不要求注释覆盖。
  没有明确要求时，简单且含义清楚的局部代码可以不写注释。
- 日常注释需求仅根据上述标准和代码或契约证据判断，先解决会影响判断的重要证据缺口。
  确定需要编写或实质修改后，使用 [write-code-comment](../skills/write-code-comment/SKILL.md)。
  对于专项代码注释或文档注释的评估、审查、补全、整理或迁移，也使用该 Skill。
