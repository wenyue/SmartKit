# 指令治理

强度：`Mandatory`

所有 SmartKit Skill 都在已安装的 SmartKit 核心治理下运行。以 `rule-<domain>` 命名的规则导向 Skill
是通过原生 Skill 发现机制提供的 Rule，在入口中声明默认 `Strength`。
Rule 文件与规则导向 Skill 属于同一类政策；它们约束相关工作，而不作为任务工作流参与竞争。

## Rule 的适用性与加载

根据原生发现机制中的描述和当前任务，在作出相关决策前加载适用 Rule。无法确定是否适用时，先阅读 Rule。
每项要求都在其规定的条件满足时生效，显式调用时也一样；调用不会改变这些条件。
无论强度如何，适用 Rule 都必须加载；加载本身不会启动独立任务、要求单独交付物或扩大权限。

上下文中已有完整且适用的 Rule 或引用内容，且没有证据表明其变化或过时会影响当前决策时，
即可视为满足加载和阅读要求。补充缺失内容，包括压缩上下文后丢失的内容；出现上述证据时，
重新读取受影响的内容。明确要求重新读取或检查的指令仍须遵守。

在作出依赖配套引用内容的决策前，先加载该 Rule 自身负责的必要引用内容。所需 Rule 或引用内容不可用时，
说明缺失内容并停止依赖它的工作；无关工作可以依据已有指令继续。

## 强度等级

- `Mandatory`：必须遵守，除非更高优先级的指令另有要求。
- `Default`：默认遵守，除非具有决定权的直接指令或政策要求不同结果，或明确的任务替代要求
  根据下文“任务型 Skill 组合”的规则胜出。
- `Advisory`：可根据任务情况酌情采用。

Rule 自身负责的规范性引用内容继承入口的默认强度，不受引用所在章节影响，也可以显式覆盖该强度。
应用这些要求时，同时遵守入口中的相关条件和例外。由独立所有者负责的政策保留自身契约；链接到示例材料不会使其成为规范性政策。

在 Rule 入口或其自身负责的规范性引用文档中，每项要求采用所在章节或上级章节中最近的 `Strength` 声明；
均无声明时，采用该文档的默认强度。章节声明写在 Markdown 标题后的第一个非空行，例如 ``Strength: `Mandatory` ``，
可使用上述任一等级。章节包含其子章节，范围止于下一个同级或更高级标题之前，或文件末尾。

章节强度不改变 Rule 的适用性和归属；标题深度不增加优先级。

## 优先级

直接指令的权威由当前智能体宿主定义。所有适用 Rule 和 Skill 中互不冲突的要求都要执行。
仅对冲突条款按下述方式比较；胜出的条款不会使其他适用要求失效。真实冲突仍无法分出高低时，
只进行确认冲突所需的只读调查，然后停止受影响的有副作用操作，并请用户决定。任何判定结果
都仍须满足独立的权限要求。

封装形式、名称、始终加载或条件加载、交付顺序，以及显式调用都不赋予优先级。
智能体宿主选择器只决定是否激活，不影响优先级。

对于 Rule、规则导向 Skill 和任务型 Skill，都根据规范来源及其含义由谁负责，确定其项目或插件归属。
仅将插件制品安装或复制到项目中，不会使其变成项目所有。来自外部本身不会增加新的优先级层级。

冲突的政策要求依次比较：

1. 实际生效强度：`Mandatory` > `Default` > `Advisory`。
2. 相同强度时的归属：项目 > 插件。
3. 强度和归属都相同时，比较针对同一决策的要求具体性。

只有根据条件或约束对象，有证据确认一项要求的适用情形严格包含于另一项要求的适用情形时，
前者才算更具体。路径限制可以确立这种关系；文件大小、标题深度或“专项”标签不能。
交叉约束或仅部分重叠的情形不能确立具体性高低。比较的是发生冲突的要求，不是整个文件或全局层级。

## 任务型 Skill 组合

任务型 Skill 在直接指令和按上述规则确定的适用政策要求内执行。
这些比较不会使任务型 Skill 获得 Rule 的 Strength 声明。

- 遵守 `Mandatory` 政策。任务的归属或具体性不能覆盖它。
- 遵守 `Default` 政策，除非任务型 Skill 为当前任务中由它负责的决策明确规定了有意采用的替代要求。
  这样的替代要求可以参与比较，无须特殊的覆盖元数据。按上述规则，先比较它与 Default 要求的归属，
  再比较针对该决策的要求具体性。只有胜出的替代要求才能取代发生冲突的 Default 条款；真实冲突仍
  无法分出高低时，同样停止并请用户决定。遗漏、示例、附带的工具选择、便利性、发现机制和调用都
  不能确立替代要求。覆盖后仍须满足 Mandatory 以及其他仍具有决定权的要求。
- 根据任务情况酌情采用 `Advisory` 指导，不将其视为对工作流的绝对否决。

任务方法发生冲突时，项目所有的 Skill 优先于插件所有的 Skill。归属相同时，只有一个任务型 Skill
的受支持任务情形——由其触发条件和负责的结果确定——严格包含于另一个 Skill 的对应情形时，
前者才算更具体。名称、较长的文本或“专项”标签不能确立这种关系。胜出者只决定发生冲突的方法；
仍无法分出高低时，采用相同的安全处理方式。

项目可以通过明确委托，在委托的结果范围内选择插件中的专项 Skill。
必须保留项目约束和委托的权限限制。

## 冲突警告

- 正常执行中如果发现语义冲突——同一组已证实事实下，一个动作或结果无法同时满足两项适用要求——
  应在面向用户的工作报告中发出警告，但不另做冲突审计或预检。
- 只使用可以向用户披露的信息，指出冲突的要求及其来源，说明优先级判定，并解释已经采取的行动或
  需要用户作出的决定。
