# 工作区政策

选择能在保留已有工作的前提下推进任务的工作区。保持所有权清楚：链接 worktree 中可以同时存在
从源检出继承的修改和当前任务的修改，携带这些修改不会改变它们原有的归属。

## 保留现有工作

保留当前检出和每个链接 worktree 中已有的暂存、未暂存和未跟踪工作。选择非破坏性的路径；
如果没有这样的路径，停止并请求指示。

当已有工作和任务修改位于同一文件时，只有能区分二者，并验证结果保留了已有修改，才可继续。
共享文件本身可以接受；无法区分的修改要求停止并请求指示。

## 工作区与提交权限

### 选择工作位置

如果能够保留现有状态，且用户、Harness、适用 Skill 和并行工作均不要求隔离，则使用当前检出。
当必须隔离或需要隔离来保护现有状态时，使用 `create-worktree`。该 Skill 负责工作区选择和就绪判断。

### 确定哪些内容可以提交

除非用户已授权提交，或满足下文的检查点权限，否则让任务修改保持未提交状态。

收到并重新核验 `create-worktree` 的就绪结果后，负责该任务的工作流可以在该确切 worktree 中，
通过正常仓库提交钩子创建仅包含任务范围内容的检查点提交，无需另行授权。就绪的 worktree 中仍可能
包含继承的源修改；检查点权限只覆盖任务范围。按照原有归属处理继承的工作，不要把 worktree 中的
所有内容都当作当前任务拥有的可提交内容。

后续 Agent 只有在已接受的工作流明确标识了确切 worktree 和基线，且当前 Git 证据证明其间的
每个提交和每项本地修改都属于同一范围时，才可继续使用这项检查点权限。存在歧义时停止新增提交。

## Git 远端写入

只有用户明确请求了相应结果，才执行改变远端状态的 Git 操作。本地提交权限本身不授权远端写入。

只读 Git 远端查询仍须满足普通工具和网络授权；本 Rule 不为它们增加明确请求这一条件。
