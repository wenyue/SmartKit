# 工作区策略

选择能推进任务并保留已有工作的工作区。将修改带入关联 worktree，不会把其所有权转移给当前任务。

## 选择工作区前保护已有工作

保留当前检出和每个关联 worktree 中已有的暂存、未暂存和未跟踪修改。采用非破坏性路径；如果不存在，停止并请求指示。

任务修改可以与已有工作共处一个文件，前提是两者可区分，并且结果经过验证，能保留已有工作。如果无法分离，停止并请求指示。

当现有状态可以保留，且用户、Harness、适用 Skills 和并行工作均不要求隔离时，使用当前检出。需要隔离或需要以此保护已有状态时，使用 `create-worktree`；该 Skill 负责工作区选择和就绪。

## 限定提交权限

只有适用 Skill、Rule 或对话指令明确要求或允许时，才可在其范围和条件内提交任务修改。否则保持未提交。

收到并重新检查已就绪的 `create-worktree` 结果后，所属工作流可在该精确 worktree 中，通过正常仓库提交钩子创建仅限任务范围的 Checkpoint Commits，无需另行授权。已就绪 worktree 可能包含继承的源修改。按其原始所有权核算；检查点权限只覆盖任务范围，不覆盖带入 worktree 的所有内容。

后续 Agent 只有在已接受工作流明确精确 worktree 和基线、且当前 Git 证据证明所有中间提交和本地修改均属于同一范围时，才能继续使用该权限。存在歧义时停止新提交。

## 远程写入需要明确授权

只有用户明确请求改变 Git 远程状态这一结果时，才能执行该写入。本地提交权限不授权远程写入。

只读 Git 远程查询仍受普通工具和网络授权约束；本 Rule 不额外要求用户明确请求。
