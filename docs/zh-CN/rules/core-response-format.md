# 回复格式

本 Rule 仅适用于向人类用户呈现的最终回复。先选择这项工作需要报告的内容，再用下面的约定让回复便于浏览。

## 语言

使用简体中文，除非用户明确要求其他语言。

## 工作汇报

- 实现类工作应列出主要修改文件，并用一到两句话概括变更。
- 审查应先按严重程度列出发现，尽可能附上文件和行号。
- 计划和设计说明应明确重要取舍。

## 回复标签

非微小回复使用正文内标签。选择对本次回复有用的标签，省略空标签；很小的回复使用普通文字。最终回复不使用 Markdown 标题。按需使用列表、表格、粗体或强调，以及代码块。

| 标签 | 用途 |
| --- | --- |
| `🎯` | 用户的目标。 |
| `⚠️` | 重要风险、约束、前置条件或假设。 |
| `✅` | 已完成的结果、主要修改文件和简短变更说明。 |
| `❌` | 失败或阻塞，以及继续所需的条件。 |
| `🤖` | 一个需要用户回答的问题、一小组选项，或附带执行询问的具体后续建议。 |

推荐顺序：`🎯 → ⚠️ → ✅ or ❌ → 🤖`。审查报告必须以发现开头时，省略目标前言；推荐顺序不能把发现移到可选背景之后。

## 标签规则

每个带标签的段落都以图标开头，图标及其对应文字放在同一段。使用 `🎯` 时，将它放在最前面，且只陈述目标。`⚠️` 只用于有意义的信息，最多三项。带标签的回复报告结果时，必须在 `✅` 和 `❌` 中二选一。

### 需要用户选择时

需要用户输入，或提出尚待用户选择的后续建议时，使用 `🤖`。提出行动建议时，询问是否执行。执行仍受既有授权和当前工作流约束；已经授权的必要工作应直接完成，无须再次确认。

重要且未解决的 `⚠️` 需要采取行动时，在 `🤖` 下建议具体后续步骤。如果缺少事实，无法提出可靠建议，就询问所需的具体信息。仅供知悉或已经解决的注意事项，无须附带后续建议。

将 `🤖` 放在最后，询问信息后结束回复。
