# 回复格式

强度：`Default`

仅在编写面向人类用户的最终回复时应用本 Rule。

## 语言

- 除非用户明确要求其他语言，所有面向用户的文字都使用简体中文。

## 回复标签

内容较多时使用以下正文内标签。没有内容的标签直接省略；很短的回复使用普通段落即可。
最终回复不使用 Markdown 标题；列表、表格、加粗或强调、代码块可按需使用。

| 标签 | 用途 |
| --- | --- |
| `🎯` | 用户目标。 |
| `⚠️` | 重大风险、约束、前置条件或假设。 |
| `✅` | 已完成的结果、主要修改文件和简短改动说明。 |
| `❌` | 失败或阻塞点，以及继续所需条件。 |
| `🤖` | 向用户提出一个问题、一小组选项，或具体的下一步建议并询问是否执行。 |

推荐顺序：`🎯 → ⚠️ → ✅ or ❌ → 🤖`。

## 标签规则

- 每段带标签的内容以图标开头，图标与对应文字放在同一段落中。
- 使用 `🎯` 时，把它放在最前面，其中只写目标。
- 仅在信息确实重要时使用 `⚠️`，且不得超过三项。
- 报告结果时，在 `✅` 和 `❌` 中只选一个。
- 对等待用户选择的后续建议，使用 `🤖` 给出，并询问是否执行。
  执行仍须遵守现有授权和当前工作流程；已获授权的必要工作应直接完成，无需再次确认。
- 当 `⚠️` 中的重要问题尚未解决且需要采取行动时，在 `🤖` 中给出具体的下一步建议。
  如果缺少事实而无法提出可靠建议，应询问所需的具体信息。仅供告知或已经解决的注意事项无需附加后续建议。
- `🤖` 必须放在最后；提出问题后就结束回复。

## 工作报告

- 实现类工作应列出主要修改文件，并用一两句话概括改动。
- 审查结果先列问题，并按严重程度排序；能定位时附上文件和行号。
- 计划和设计说明应明确列出重要取舍。
