# 第三方 Skill 政策

强度：`Mandatory`

适用范围：SmartKit 对第三方插件或外部来源提供的 Skill 施加的行为约束。

## 工单颗粒度

当 `$smartkit:to-tickets` 起草工单时：

- 赋予每个内聚的“示踪弹”式切片足够的工作量，使其值得独立实施和审查；同时将范围控制在当前前沿
  LLM Agent 能借助可用工具、在一个全新上下文内可靠理解、实施、验证和修复的程度。以这种能力作为
  校准点：上下文限制是实际容量边界，而不是把本可从容容纳的工作拆碎的理由。
- 当工单边界能够带来独立且有意义的验收、有用的并行执行、所有权或风险的实质分离、能力或上下文
  边界，或扩展—收缩迁移所需的绿色边界时，再设置该边界。
- 将附带或局部的前置重构放在第一个使用它的工单中。只有当前置重构可独立复用、后续多个工单都
  需要、存在实质风险或超出可靠的能力或上下文边界时，才将其单独设为工单。
- 在提交草案供审批前，从两个方向重新平衡：合并过小或紧密耦合的相邻候选工单，并拆分超出前沿
  Agent 可靠能力的候选工单。每个工单都有连贯的范围和彼此不同的验收标准，且每条边界都有上述因素
  支撑时，才算完成。保留该 Skill 的展示和发布协议，不新增 `Why separate` 输出字段。

## 工件语言

- `$smartkit:wait-what` 重新表述消息时，使用简体中文编写重新表述的内容。
- 第三方 Skill 创建或编辑 `CONTEXT.md` 时，每个规范术语都写成
  `**{English term}（{Simplified Chinese term}）**:`。新增或重命名时，同时处理两个规范名称。
- 上下文文档中的术语只能用于解释或说明直接用户沟通中的语言。这些引用使用普通正文样式，不要仅因
  它们是术语而添加特殊格式。除非独立的已接受来源确立了相同含义，否则不要把上下文文档中的定义或
  名称带入 Rule、Skill、契约、代码、测试、schema、配置、验证或 Acceptance 输入。如果原文或作者
  独立地为了对比或强调而强调某次引用，则保留该强调，但不叠加标记。代码、命令、标识符和字面量语法
  不适用这一要求。
- 第三方 Skill 在 `docs/adr/` 下编写 ADR 时，使用英文。
