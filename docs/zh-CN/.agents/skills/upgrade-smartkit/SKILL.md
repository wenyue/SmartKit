# 升级 SmartKit

准备版本变更，并明确已有项目需要什么。发布版本标识插件，本身不要求再次运行 setup。将必要迁移声明与简洁项目指令保持一致。

本项目本地 Skill 维护 SmartKit 仓库。评估以提案结束；获授权升级按下列顺序执行。发布、安装、提交和推送各自需要授权。

## 1. 确定基线、目标和发布范围

检查工作树、索引、根 [VERSION](../../../../../VERSION) 及已有版本修改。保留无关工作和已接受目标。修改发布输入前，解决请求版本的重要不确定性。

通过仓库发布记录或已验证发布标签确定上一个已发布版本，并解析其提交。将该版本与完整预期新发布比较，包括暂存和未暂存修改。当前 `HEAD`、本地版本修改或看起来最新的标签，都不能单独证明项目正在使用什么版本。基线未知时，在判断无需迁移前报告缺失证据。

保留已知基线和目标身份、完整发布范围及已有工作记录，供后续检查区分本任务修改。

## 2. 判断已有项目需要什么

沿 [setup 所有权](../../../skills/setup-project-agents/references/ownership.md)、目录、蓝图、项目配置 schema、入口模板和 setup 行为追踪完整发布差异。相关项目决定有助解释契约时，通过仓库文档约定发现它们。文件名或蓝图指纹变化是调查线索，不是迁移决定。

变化影响已有 setup 的要求、生成结果或阅读契约时，要求迁移。明确已初始化项目会保留什么状态，以及为何该状态不符合新契约。

| 变化 | 评估方式 |
| --- | --- |
| 实质蓝图要求、不兼容配置格式、必要的 `AGENTS.md` 加载，或不兼容的项目定义 Agent 配置 | 确定已有项目状态必须发生的变化。 |
| 蓝图拼写错误 | 有效的已有输出仍可能可用；仅文本差异不要求迁移。 |
| 新共享 Skill 或新可用模型 | 两者本身均不要求迁移。完整 setup 负责日常评估 Agent 模型和推理设置；此处判断必要的配置契约变化。 |

对每项相关发布变化，说明是否需要迁移，或为何仍可使用，并给出具体项目后果。通过所属源或针对性检查解决不确定兼容性。只有覆盖整个发布，才算完成决定；版本不一致不是充分证据。

## 3. 维护必要迁移指令

编辑记录前，阅读 [迁移指南](../../../skills/setup-project-agents/references/migrations.md) 和 [目录](../../../../../setup-assets/catalog/migrations.json)。决定行动前，阅读适用版本指南。概览负责适用性和发现，目录将每个必要迁移版本关联到独立指南。

需要迁移时，一起新增或协调目标发布的声明及 `skills/setup-project-agents/references/migrations/<version>.md`。将声明的 `guide` 设为 `references/migrations/<version>.md`；指令保留在该文件中，不向概览增加版本条目。

面向升级受影响项目的 Agent 编写：哪些项目状态受影响、必须改变什么、怎样识别完成。只有确实影响升级成功时，才包括前提、顺序约束或手动源修改。setup 或被调用 writer 已提供执行细节时，引用所属指令。排除仅内部变化，以及该 Agent 无需关注的变化。仅有 changelog 无法让必要行动可执行，也不能揭示缺失的项目决定。

### 保留历史并协调未发布版本

保留必要的已发布迁移身份和历史，让项目可以跳过版本，在一次 setup 中满足全部适用变化。阅读更早的适用条目；解释依赖和已被替代的行动，不要求安装每个中间插件版本。

编辑已有目标版本条目前，确定它属于同一未发布版本。与已发布条目冲突时，需要发布决定，不能悄然替换。

按当前决定协调该未发布条目。仍需迁移时更新声明和指南；不再需要时，在已接受范围内移除过时草稿声明和指南。保留已发布历史及独立所有的修改。所有权或权限未解决时，不得删除，并须在继续准备发布前报告。

不需要迁移且没有过时草稿时，保持目录、概览和指南不变，并报告原因。无关版本提升不需要空指南。

## 4. 从规范版本同步

目标和迁移决定明确后，更新根 `VERSION`，并在仓库根目录运行所属同步器：

```bash
python scripts/sync_plugin_version.py
```

通过其当前接口和输出确定同步的清单及目录字段，不维护第二份清单。审查改变路径，保留无关字段和已有修改。失败时先检查实际部分结果和原因，再重试；只协调本任务修改。失败不证明没有文件发生变化。

## 5. 验证并交接

以不修改文件的方式检查版本一致性：

```bash
python scripts/sync_plugin_version.py --check
```

运行 [CI](../../../../../.github/workflows/test.yml) 定义的适用所有者检查；声明或指南改变时，包括迁移验证和测试。确认声明指向匹配指南、迁移版本符合发布版本、早期必要条目和文件仍可用。修改第一方 Skill 参考资料时，遵循项目翻译策略。

对照已发布基线和已有工作记录，审查完整差异。运行 `git diff <comparison-point> --check`，也覆盖新文件。源修改、同步字段和迁移决定必须一致；同步器通过不能抵消其他必要检查失败。

报告基线和目标、改变路径、是否需要迁移及原因、适用指南条目和验证结果。完成仅表明仓库发布输入一致且经过检查，不表明已发布，也不表明任何项目记录的 setup 版本已推进。
