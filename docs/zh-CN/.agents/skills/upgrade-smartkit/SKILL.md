# 升级 SmartKit

准备 SmartKit 版本变更，并明确判断现有项目是否需要迁移。发布版本号用于标识插件；仅凭版本号变化，不能要求项目重新执行 setup。必要的迁移声明及其简短项目指引应一并维护。

这个项目技能用于维护 SmartKit 仓库。评估请求以提案结束；已获授权的版本升级则按以下步骤执行。发布、安装、提交和推送各自仍需相应授权。

## 1. 确定正在准备的发布版本

检查工作区和暂存区、根目录的 [VERSION](../../../../../VERSION)，以及已有版本改动。保留无关工作和已经确定的目标版本。在修改发布输入前，明确请求的目标版本，并解决与之有关的重大不确定性。

根据仓库发布记录或经过验证的发布标签，确定上一个已发布版本及其提交。以该发布版本作为比较基线，将计划纳入新版本的暂存和未暂存改动都计入目标范围。当前 `HEAD`、本地版本编辑，或看起来最新的标签，都不足以单独证明项目正在使用哪个发布版本。如果无法确定基线，应先报告缺少的证据，再判断是否无需迁移。

明确基线、目标版本和发布范围后再继续。保留它们的标识和已有改动记录，以便后续验证区分本次编辑与先前工作。

## 2. 判断现有项目 setup 是否必须改变

将基线与计划发布的完整内容进行比较。通过 [setup 所有权](../../../skills/setup-project-agents/references/ownership.md)、目录、蓝图、项目配置 schema、入口模板和 setup 行为，追踪相关改动。如果相关项目决策能解释预期契约，则按本仓库的文档约定读取这些决策。文件名或蓝图指纹变化只是需要调查的信号，本身不构成迁移判断。

当变化影响现有项目 setup 应遵守的要求、生成结果或读取契约时，要求迁移。检查已经初始化的项目会保留什么，以及保留这些内容为何会违反新契约。相关变化包括蓝图的实质要求、配置格式不兼容、必须调整的 `AGENTS.md` 加载方式，以及不兼容的项目自定义 Agent 配置。

例如，纠正蓝图中的错别字后，原本有效的项目产物仍然可用；增加必须遵守的加载条件，则可能使原产物不完整。新增共享技能或新模型可用，本身都不要求项目迁移。项目 Agent 的模型与思考设置的常规评估由完整 setup 负责；这里的发布评估关注配置契约是否必须改变，而不是新模型是否更合适。

对每项相关发布改动，都要判断是要求迁移，还是无需迁移仍可使用，并说明具体的项目影响。不确定是否兼容时，向所属源文件或针对性检查取证；版本不一致本身不构成证据。只有判断覆盖完整发布范围后，这一步才算完成。

## 3. 只维护必要的迁移指引

修改迁移记录前，读取 [setup 迁移指引](../../../skills/setup-project-agents/references/migrations.md) 和 [迁移目录](../../../../../setup-assets/catalog/migrations.json)。指引说明适用条件，以及如何在 `skills/setup-project-agents/references/migrations/` 下查找独立的版本指引；目录记录每次必要迁移的发布版本和指引文件。确定迁移动作前，读取每份适用的版本指引。

需要迁移时，将目标版本声明和一份 `skills/setup-project-agents/references/migrations/<version>.md` 文件作为一项完整改动添加。声明的 `guide` 为 `references/migrations/<version>.md`；迁移说明保留在该文件中，不在总览中添加版本条目。

为负责升级受影响项目的 Agent 编写简短指引。仅写入会影响其升级判断或必需操作的变化：指出受影响的项目状态、必须改变的内容，以及如何确认完成。只有影响升级成功时，才写入前置条件、执行顺序限制或手动修改源文件的要求。省略仅涉及内部的变化，以及无需该 Agent 留意的变化。对于 setup 或被调用写作器已提供的执行细节，应引用其所属指引。动作应足够具体，让 setup 能执行，或能指出缺少哪项项目决策；仅有变更日志不够。

保留必要迁移的历史，让跳过多个版本的项目能通过一次 setup 满足全部适用要求。编写新条目时，读取之前适用的条目；说明依赖关系或已被替代的动作，使项目不必逐个安装中间插件版本。保持已发布迁移的标识稳定。修改现有目标版本条目前，先确认它属于同一个尚未发布的版本；如与已发布条目冲突，应作为发布决策处理，不能悄悄替换。

对于同一未发布版本已有的条目，应根据当前迁移判断调整，而不是重复添加。如果仍需迁移，更新该条目及其版本指引。如果该版本已无需迁移，在已接受的编辑范围内，删除过时的草稿声明及版本指引。保留已发布历史和独立所有者的编辑；所有权或权限未解决时，必须暂停这项删除，并在继续发布准备前报告。

如果无需迁移，也没有过时的草稿条目，保持目录、总览和版本指引不变。报告原因；无关的版本提升不需要空的迁移文件。

## 4. 推进权威版本并同步

确定目标版本和迁移判断后，将根版本更新为已接受的目标，并从仓库根目录运行现有同步器：

```bash
python scripts/sync_plugin_version.py
```

哪些清单和目录版本字段跟随 `VERSION`，由同步器负责；使用它的当前接口，不在这里维护第二份列表。检查它改动的路径，保留所有无关字段和已有编辑。如果执行失败，先检查实际的部分结果和原因，再重试。只协调本任务的改动；命令失败不代表没有文件发生变化。

## 5. 验证并交付发布输入

执行不修改文件的版本检查：

```bash
python scripts/sync_plugin_version.py --check
```

运行 [CI](../../../../../.github/workflows/test.yml) 中适用的所有者检查；如果声明或指引有变化，还要运行迁移验证和测试。确认每项声明都能定位到对应版本指引，迁移版本符合目标发布版本，且之前的必要条目及文件仍然可用。对修改过的第一方技能引用文件，遵循项目翻译流程。

结合确定的基线和已有工作记录，检查完整差异。使用 `git diff <comparison-point> --check` 检查空白问题，检查范围包括新文件，并确认源文件改动、同步后的版本字段与迁移判断一致。即使版本同步器报告成功，必需检查失败仍属于未完成工作。

报告基线和目标、改动路径、是否要求项目迁移及原因、适用指引条目和验证结果。完成意味着仓库发布输入一致且经过检查；不意味着已经发布新版本，也不意味着任何项目的 setup 版本记录已经推进。
