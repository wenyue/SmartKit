# 编写共享 Rule 和 Skill

编写在所支持的各个项目中都有依据的指导。难点在于判断：哪些含义能随工件一起迁移，哪些事实只属于某个目标环境。

本 Skill 为一个共享工件确认资格，将编写与审查委托给
[`write-rules-and-skills`](../../../skills/write-rules-and-skills/SKILL.md)，并依据其可移植性义务核对返回的证据。编写与审查机制由该公共工作流负责。

## 1. 确定哪些内容可以共享

仅当请求恰好涉及一个可跨项目使用的 SmartKit Rule 或 Skill，且其共享所有者与独立来源有依据时，才继续。将有用的本地指令视为共享政策或方法之前，先确定谁拥有其含义，以及它声明支持哪些环境。

调用公共工作流前，先处理超出这一范围的请求：

| 请求 | 路由 |
| --- | --- |
| 项目本地工件、Setup Authoring Blueprint，或其他已明确不属于共享范围的请求 | 转交给有依据的所有者。 |
| 同时需要 Rule 和 Skill | 为 `split` 返回分别针对 Rule 和 Skill 的请求。 |
| `environment-owned` | 指明当前所有者，不返回 Candidate。 |
| 所有权存在歧义、不相容或尚未解决 | 通过公共路径返回 `NEEDS_INPUT`，说明缺失的选择、相关证据、决策所有者和实质后果。 |

### 区分可移植含义与目标事实

对工件依赖的每项事实，确定其所有者、来源、适用性和限制。只有跨项目所有者与独立来源支持这种用途时，才能将其作为可移植含义。现有 Candidate 文本是需要审视的主张，不能证明自身的权威性。

假设一项已接受的共享要求是：报告完成之前，运行各项目要求的检查。某个源项目使用 `npm test`。它成功运行，只能支持该目标的检查路径，不能证明所有项目都应使用这个命令。将已接受的要求写入共享工件，同时把这个命令保留为其受支持范围内的目标事实。

同样的区分也适用于源项目政策、仓库布局、打包与发现、宿主注入、工具可用性，以及其他 Agent 转述的信息。这些内容可以帮助定位或支持证据，但没有一项能单独确立可移植含义。项目与宿主指令仍在各自范围内约束当前工作，却不会为 Candidate 增加可移植含义或权限。

## 2. 准备公共编写输入

向公共工作流提供编写和评估这个具体工件所需的知识。将以下关注点整理成一致的输入。义务命名应足够一致，使审查和交付时可以追踪；选择适合任务的表达方式，无须强制使用义务 ID 或记录模式。

### 明确预期契约及其依据

说明已接受的结果、非目标、安全边界、退出条件和交付要求。对每项继承或新增的义务，说明要保留、修改、添加、移动还是退役。这些是 Author 必须传递的含义，而不是从旧文档复制的提纲。

在这些含义之外，还要明确：

- **Candidate 的位置：**共享所有者、适用性、来源、确切资源及其存在要求，以及预期的公共加载、发现、分发和 Skill 接口路径。
- **支撑它的证据：**每个来源及其发现路径、它支持的事实、代表的范围，以及仅限其源项目的限制。
- **它使用的依赖：**所有直接和传递依赖的 Rule、Skill、工具、模式、环境能力或宿主行为；每项依赖的所有者、所需行为、使用者、有依据的共享所有者或目标所有者路径，以及可用、不可用和使用失败时的可观察结果。
- **验收边界：**验证和完成职责、已接受的权限与效果、评估它们所需的证据，以及可观察的通过、阻塞和失败条件。

沿依赖一直追踪到其使用者。工具存在于编写机器上，并不证明其他项目也能使用它；仅仅写出依赖名称，也不说明 Agent 如何到达它。在交付依赖这些内容的工作前，先解决每条实质路径及其失败行为。

### 根据真正重要的差异选择目标

提供最小的非空代表性目标集合，覆盖适用性、依赖、权限、执行、观察、恢复和退出方面每个实质不同的衔接点。衔接点是可能改变工件能否工作或如何工作的差异。项目名称或目录布局不同，本身不足以构成这样的差异。

例如，两个项目若提供相同且受支持的检查接口，可能覆盖的是同一种情况。若工件声明支持某个缺少必需能力的项目，这个项目就体现了不同的边界：Agent 必须识别限制，并按规定退出。再增加一个成功项目，无法证明这种行为。应根据这类差异选择案例；移除一个目标后，所有实质衔接点仍得到覆盖，这个目标就是冗余的。

对每个衔接点，明确相关目标事实、使用的义务和依赖、权限、关键成功和终止路径、恢复与中途停止、预期观察结果，以及证据特征。要求公共 Correctness 视角同时覆盖：

- **可移植语义权威：**共享所有权、适用性、合格证据、完整依赖路径，以及不存在仅在源项目成立却被当作执行依据的假设。
- **代表性行为：**每个实质衔接点、关键路径和退出条件。

说明证据必须证明什么。把命令、Reviewer 身份、案例选择、验证选择、可选 Runner 的使用和判断留给公共工作流。代表性目标是一项覆盖承诺，本身并不要求执行它。需要时补齐适用的验证和代表性运行输入，并要求最终关闭义务的证据指明最终 Candidate 指纹。

### 将目标访问与 Candidate 编辑分开

为公共 Author brief 及公共任务单独进行的冻结提供已接受的权限和效果。Candidate 修改仅限于其确切资源；请求移动时，要为写入范围冻结保留两个端点。本 Skill 提供合格输入，由公共工作流按自身契约冻结权限。

每项代表性目标读取或执行效果都需要单独、确切的授权。将这些效果与 Candidate 资源分开：目标授权不授予 Candidate 修改权限，Candidate 修改权限也不授予目标访问或执行权限。通过公共工作流解决适用的运行边界，不另造私有授权类别或第二套执行协议。

### 交付已闭合的输入

当每项实质事实、路径、权限、通过条件和完成义务都有一个有依据的答案，且预期工作符合这些权限时，输入才算准备就绪。将其保留在 Agent 上下文中。若缺少实质答案，在调用前返回公共 `NEEDS_INPUT` 结果，并说明尚未解决的事项。

将这份已闭合的输入原样传给公共工作流，等待其结果。使用公共工作流的编写、审查拓扑与身份、验证、可选 Runner 证据和判断机制，不在此修改或重建它们。

重写本 Skill 时，整个运行由 Author 开始编写前的公共和私有契约支配。修改后的文本仅在后续调用中生效。

## 3. 完成可移植性交付

将公共工作流实际返回的内容，与共享工件必须证明的事项逐一核对。在 Agent 上下文中维护临时关闭记录，覆盖每项已接受的含义、证据来源、依赖、代表性衔接点、验证职责和完成义务。

只能依据绑定到当前 Candidate 指纹的可观察公共输出关闭义务：

- Author 的语义变更摘要；
- 选定的审查拓扑，以及每个专业视角的最终结果；
- 自动化验证结果，以及存在时的 Runner 证据；
- 剩余风险、最终指纹和终止结果。

当一项输出明确覆盖一整组义务时，它可以关闭这组义务。Reviewer 的隐藏推理、假定的证据选择或人为制造的轨迹，都不能补足缺失证据。这份记录只承载控制和交付事实，不是 Candidate 内容、语义权威、额外审查或新的公共结果。

**可移植性成功同时要求公共 `COMPLETE`，以及最终 Candidate 指纹上的每项义务都已关闭。**如果公共 `COMPLETE` 缺少必要的可移植性证据，它仍是公共结果，但不足以证明可移植性成功。让无依据的义务保持未关闭，并准确说明缺少哪些绑定指纹的输出。

保留公共交付及其 `COMPLETE`、`NEEDS_INPUT` 或 `BLOCKED` 结果。附上完整记录，逐项说明义务、关闭其通过条件的可观察输出，或使其保持未关闭的缺口。只有公共输出展示了代表性目标证据，且通过条件需要它时，才将它纳入记录。

保持这份记录的临时性质。不创建私有 Candidate 副本、工作流报告或永久夹具。本 Skill 不授予发布、安装、提交、推送、发版或其他下游效果的权限。
