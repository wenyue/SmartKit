# 升级第三方 Skill

升级本仓库登记的外部 Skill，同时保留已接受的本地行为。
核心比较包含三个方面：上游改了什么、我们的补丁要保留什么，以及哪些使用方依赖最终指令。
补丁顺利应用，只回答了这项比较中的机械问题。

这是一个项目本地维护 Skill。评估请求授权调查和提出方案；升级请求还授权在已接受范围内执行已就绪的实施。
两者都不会自动扩展为发布结果或将其安装到用户环境。

## 明确升级边界

阅读 [Skill 注册表](../../../skills/registry.json)中的外部来源条目、[锁文件](../../../vendor/external-skills.lock.json)中的对应记录，以及列出的补丁文件。
以锁文件解析出的 commit 作为已安装内容的上游基线；仅有配置的标签或分支名称，不能确定实际字节内容。
选择工作区和比较基点前，检查 Git 状态和托管输出，识别已有工作。

注册表和补丁是输入；分发的 Skill 目录、许可证和锁文件由[外部 Skill 更新器](../../../scripts/update_external_skills.py)派生。
通过这些归属方维护适配，不直接编辑生成的快照。

确定请求涉及的来源、目标修订和预期结果。对照当前上游发布记录和仓库内容核实目标，区分正式发布与尚未发布的分支工作。
记录解析出的目标 commit，用于比较和后续验证。请求未指定目标时，推荐一个受支持的版本或修订，并解释发布版本稳定性与所需未发布变更之间具有实质影响的选择。
缺少或无法核实基线或目标证据时，升级就缺乏依据；说明缺口，仅继续不依赖该证据的调查。

更新器的 `--source` 选择整个上游仓库，而非单个 Skill。确定该来源修订影响的每个已选 Skill。
如果用户只要求升级一个 Skill，说明无法避免的扩大更新，并在实施前解决其范围问题。

## 比较人们实际会使用的结果

阅读发布说明，比较所有已选 Skill 及其自有资源的新旧上游目录。
沿着变化的引用和受影响的使用方调查，直到能确定拟议结果仍可正常使用。
根据实际差异决定调查方向；无关的上游功能不会仅因存在就需要开展采用工作。

对每个受到实质影响的 Skill，厘清以下关系：

| 关注点 | 证据与决策 |
| --- | --- |
| 工作流行为 | 比较触发条件、必需步骤、审批与停止条件、委派和副作用。识别新指令在哪些地方改变了已接受的行为，或与适用的项目、共享指导冲突。 |
| 本地适配 | 结合旧上游和当前应用后的内容，理解每个补丁的预期结果，再定位其在目标版本中的对应部分。判断它能否原样应用、是否需要调整上下文、上游是否已满足其要求，或是否需要行为决策。 |
| 选择与发现 | 逐项核对重命名、移动、删除和新增必需的 Skill 或资源。追踪调用方、路由引用、注册表条目和公开暴露；新的上游 Skill 属于单独的采用选择。 |
| 文档与依赖 | 检查受影响的模板、术语表名称、链接、脚本、命令、工具、Harness 能力和外部服务。在依赖新路径前，明确迁移工作及其可用性。 |
| 来源与执行 | 审查相关许可证或署名变化、来源身份，以及新增的可执行或网络行为。差异引入额外访问权限、凭证、持续费用或信任要求时，说明这些要求。 |

仅上下文变化且已接受的结果仍然成立时，可以直接调整补丁，无需询问。
如果上游现已提供该结果，应先证明等价，再移除冗余补丁。
如果新工作流使旧适配失效或不兼容，就明确提出这一选择；为让更新器通过而悄悄删除补丁，会丢失它原本要保留的行为。

例如，上游重命名术语表格式并开始只查找新文件名时，仅修复补丁路径还不够。
找出仍使用旧名称的项目指针、模板和现有文档，在升级使用方前确定其迁移或受支持的兼容方案。
同样，上游删除 Skill 时，需要决定如何处理受支持的调用方和公开入口，不能只删除注册表中的一行。

每个已选 Skill 和补丁都已交代清楚、受影响的依赖都有受支持的使用路径、剩余选择已明确时，评估才完成。
在对话中概括实质变化及其证据；注册表、锁文件和补丁继续作为持久的来源记录。

## 修改前解决选择

说明来源及基线到目标的变化、预期收益、受影响的文件与使用方、补丁处理方式、迁移工作、验证和恢复方案。
根据差异大小调整说明篇幅。区分已证实的事实与可能改变决策的不确定假设。

只询问无法从现有资料恢复、且会实质影响结果的选择或事实。
典型情况包括采用或停用公开 Skill、改变其名称或激活方式、改变本地适配的预期行为、接受新的服务或权限要求，或扩展到使用方迁移。
将相关问题合并，给出具体选项及其后果。有证据支持时推荐方案，并在执行依赖该决定的变更前等待用户作出决定。

复用已有决策和授权。不要把保持行为不变的常规补丁修复变成又一次审批节点。
如果用户仅要求分析，交付具体方案和所需决策后停止。对于已授权的升级，在已接受范围、须保留的行为、前提条件和检查都明确后继续执行。

## 通过负责的更新器实施

通过 Git 证据或隔离工作区保留升级前的输入和已记录输出，使本任务的变更可恢复，同时不丢弃已有工作。
更新前处理托管输出与记录之间的偏差：保留它，确定归属和意图，把已接受的变化表达在对应补丁中；只有这些工作已被安全保留，才恢复相应的已记录输出。
归属或保留方式不清楚时，暂停受影响的更新并请求指引。

修改注册表中的修订及任何已接受的选择或路径变化；针对解析出的目标调整有序补丁，同时保留已接受本地差异以外的上游措辞。
保留许可证和版权声明。通过仓库中负责相应内容的机制执行任何已授权的公开暴露或使用方变更；移除契约时，须一并处理受影响的调用方、文档和检查。

在仓库根目录更新选定来源：

```bash
python scripts/update_external_skills.py --update --source <owner/repository>
```

使用注册表中的实际来源 ID。必要时通过 `--help` 确认当前 CLI。
省略 `--source` 会处理所有配置来源；仅在确实需要该范围时使用。
删除整个来源需要规划完整更新，因为删除后的 ID 不再被 `--source` 接受。
从保留的来源中移除某个已选 Skill，会使更新器删除其托管目标目录。

更新器先在暂存区应用并验证补丁，再将 Skill、许可证和锁文件一起安装。
补丁冲突会保留原先安装的输出；调用更新器前修改的输入仍需审查。
重试前先调查失败原因。若报告事务或回滚失败，检查实际文件和保存的 Git 证据，不要假定恢复已成功。

## 验证应用后的结果

完整阅读发生变化的 Skill 及其必需资源，追踪受影响的调用路径。
确认预期的补丁行为、发现机制、文档约定和依赖能够协同工作。
对于变化的可执行行为，运行相应的受支持检查；无法验证行为时，报告具体缺口，不把文字自洽当作运行时证据。

以非修改性的检查模式运行更新器：

```bash
python scripts/update_external_skills.py --check --source <owner/repository>
```

更新和检查都会解析上游来源，可能需要网络访问；`--check` 不是离线锁文件检查。
核对生成的锁文件 commit 是否与已审查目标一致。目标移动或新发现的差异都需要重新评估。
将报告的补丁改动比例作为本地维护负担的信号，不能将其当作适配正确的证明。

按照当前归属方和 [CI 配置](../../../.github/workflows/test.yml)运行适用的清单、Rule 交付、翻译及仓库检查。
项目翻译政策适用时，同步镜像。对照已接受范围检查每个变化或删除的路径、生成输出、许可证和锁文件条目，包括选定来源之外的意外变化。
运行 `git diff <comparison-point> --check`，并覆盖新建且未跟踪的文件。

完成要求包括：已审查修订已安装到仓库快照中，已接受的本地行为与受影响的使用方一致协调，所有必需检查通过，已有工作得到保留。
报告来源与修订变化、采用或停用的条目、重要的补丁与迁移决策、验证证据，以及任何未解决的限制。
区分已完成的仓库升级与下游发布或安装；后者仍受各自授权约束。
