# 编写项目创作蓝图

编写能将已接受意图转化为有用项目 Rules 和 Skills 的蓝图集。每份蓝图描述一个未来目标：读者的工作、塑造内容的项目证据、重要内容及其演化方式。公共 `write-rules-and-skills` Skill 编写和审查每个未来 Candidate。同一组蓝图输入既支持独立调用 writer，也支持由 Setup 使用。

蓝图提供语义要求、任务特定的验收条件，以及已接受的固定来源。为开放选择提供具体方向，将组织表达及普通推理留给未来 Author。该 Author 在调用权限内发现并确认项目证据；调用方可以提供已接受输入。如果顺序影响行为，就包含未来目标必须教授的流程。调用调度、脚本机制和重试仍由 runtime 所有者负责。

写作前阅读检出源权威的 `writing-for-agents`。下列顺序约束本次编写，不是每份蓝图的提纲。

## 1. 确定目标与写作权限

从已接受用户决定和适用项目记录还原结果，再对照治理契约、目标所有者来源及可观察行为确认。确定所有权和来源，防止已有示例意外成为要求。使用旧蓝图和目标发现意图、遗漏和回归，但不假定其设计正确。仅为适用指令或可访问范围内的具体问题扩大调查。

为每个必要目标确定读者、目的、触发条件、Rule 或 Skill 类型、精确路径及所有者。赋予独立职责，将策略、流程和事实留给适当所有者。仅在已接受意图要求时新增目标。修订时，交代每项改变行为的义务应保留、改变、新增、淘汰还是排除在范围外；没有依据的处置仍是未解决事项。

起草前固定精确蓝图及配套资源路径，以及创建、替换、删除或移动操作。每项都需要同时覆盖路径和操作的权限；已有授权足够时复用。可见性、目录条目和文件系统访问，不确立语义或写入权限。保留无关路径和独立所有的表面。

完整目标集、职责及授权操作明确后继续。否则使用下文停止条件。

## 2. 给未来 Author 有用的方向

从未来读者的决定出发编写。Rule 将适用条件连接到必要或有优先级的行为，以及重要例外。Skill 解释结果和实现它的选择或必要顺序。在影响行为之处明确权限、验证、结果和停止，并将条件与例外放在其含义旁。

对目标的每个实质部分，连接以下内容：

- 读者需要完成什么；
- 哪些项目证据决定内容；
- 什么值得强调或排除。

指出有用来源方向和所有者，例如已声明检查、生成器映射、架构决定或实现关系，并解释它们解决什么。泛泛要求检查仓库，不能支持内容决定；项目事实必须来自合格证据，而非示例命令或猜测的布局。

例如，Tools 蓝图可以将 Author 引向生成器、输入输出映射和受支持检查，使未来 Rule 解释何时必须再生成、如何验证一致，以及缺失何种权限会阻塞它。列出全部已安装工具反而会掩盖这个任务。蓝图可以指导调查，而不预选命令或标题。

当 Author 能识别必要含义、找到决定项目特定形式的事实，并在不虚构事实或权限的前提下选择相关细节，方向就足够。结构和措辞保持开放，除非它们承载已接受的行为契约。

对于 Skill 蓝图，`description` 就是目标 Skill 的描述，原样复制到目标。蓝图是编写输入，没有自身的发现触发条件。按公共 writer 的元数据约定提供目标 `agents/openai.yaml` 界面字段和打包图标。仓库特定的选择与执行细节放在目标正文中。每个固定值或资源只存储一份，并通过 writer 的固定内容接口声明来源到目标的约束。对选定元数据字段要求一致，同时保留独立字段和项目补充；只有完整字节均固定的资源才要求整个文件一致。

将目标资源与蓝图自身的编写指令区分开，并在可用输入包中包含声明及其引用的每个来源。公共 writer 冻结并验证已接受的固定内容；Setup 和其他调用方提供相同输入，不另设编写协议。

## 3. 解释刷新时应改变什么

每份蓝图都需要符合内容的刷新偏好，混合内容也应分别处理。全部重写或全部保留，都不能作为普遍默认。

| 内容 | 刷新方向 |
| --- | --- |
| 工具和代码结构事实 | 重新核对权威配置、已记录所有权或实现关系。更新变化事实，移除被推翻主张；蓝图本身不必发生变化。 |
| 流程和持久上下文 | 保留适用决定、义务和理由。找出足以支持修订的需求、职责或受支持行为变化；若只有措辞可能不同，保留合理文字。 |
| 混合内容 | 区分稳定义务和变化事实，例如验证职责及项目命令。刷新事实，不丢失职责，也不保留过时命令。 |

结合当前目标与新的合格证据。保留有效项目补充及义务，包括条件和例外。已有文字是意图证据，不是争议主张的证明；通过负责所有者和已接受权限解决冲突。新蓝图不授权抹除项目决定。

解释哪些证据支持每类改变，什么必须保留。没有相关变化或缺陷时保留合理内容；有依据修订时保持一致，不堆积重复。这些偏好指导内容，不规定调用频率、脚本或替代公开 writer。

每份蓝图都能通过预期变化来源、稳定含义和修订证据，区分有用刷新与无谓重写后，才继续。

## 4. 界定未来写作任务

说明未来 Author 需要的证据，以及如何在调用权限内发现和确认它：带所有者及来源的项目事实、已有目标和相关补充、已接受要求，以及用于发现回归的材料。调用方可提供证据，但交接不完整时，应先进行获授权发现，而非立即以缺少输入停止。

让 Author 根据合格证据选择普通文件、接口和实现细节。超出已接受权限的重要选择需要用户输入。说明发现后仍无依据的事实为何阻碍产出可用目标。

写作前确定未来 Author 的精确 Candidate 和可写路径、允许的创建、替换、删除和移动操作、必要验证，以及其他权限或外部影响。使用获授权目标位置，明确每项必要操作的授权；已有授权足够时复用。生成或检查产物，不授权修改活动目标。

定义任务特定的验收条件和必要交接证据。公共 writer 负责 Author 与 Reviewer 角色、Candidate 版本、审查顺序和终止结果；蓝图通过该工作流提供要求。将完成产物的运行时结果与编写完成区分开。缺少权限、重要事实无依据或重要选择未解决时，通过 writer 停止依赖这些条件的编写工作，不另设状态表或集成授权。

未来 Author 能识别范围、发现职责、可用结果和停止条件，无需假定其他工作流的授权或输入时，本步骤完成。

## 5. 检查整体并交付

对照已接受意图和相邻所有者审查整个集合。每个必要目标和改变行为的义务，都需要有依据的处置；每项未来操作都必须符合授权。交接前解决所有权重叠和重要歧义。

针对每份蓝图追踪有代表性的正常、异常和证据不足案例，包括不经 Setup 的使用。包括证据未变的重复运行、项目事实变化，以及已有有效项目补充。检查指导是否支持保留合理内容、纠正过时事实和保护项目意图，并指出证据及缺失事实导致的停止。这些案例检验指导，不创建通用内容 schema，也不声称穷尽覆盖。对于目标运行时结果协议，确保条件可区分、重叠有明确优先级，并且没有重要缺口。检查固定声明是否对应预期目标路径和完整来源包、保留独立字段，并与目标行为一致。

运行适用、由所有者支持的确定性检查，不使用修复模式。只有合格所有者证据证明没有适用检查时，才使用 `NOT_REQUIRED`。完成要求检查通过，或得到有依据的该结果，同时完成集合审查。必要检查失败或不可访问时不能完成；保留证据并报告未解决条件。

交付精确蓝图路径和所有者、支持结果、检查及结果、保留约束，以及不确定或未测试表面。将交接留在蓝图之外。本轮仅修改获授权蓝图及其配套资源：不编写未来目标或共享 SmartKit 产物，也不调用未来目标写作或后续集成。不执行翻译、安装、发布、提交或推送；它们仍是独立任务。

## 输入不足以支持工作时停止

所需证据或验证在授权内不可访问、合格证据无法确立必要事实，或重要选择超出已接受权限时，停止依赖这些条件的工作。

对于访问或上下文缺口，说明准确需要、为何授权发现未能解决、负责所有者或解决条件，以及贸然继续的后果。说明重新运行所需权限和可观察条件。对于决定，给出所有者、选择、证据和后果。

只有缺失输入和重试权限均确立后，才能恢复；已有接受授权可能覆盖该重试。声称完成前，重新核查受影响的证据。
