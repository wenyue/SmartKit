# 编写 Setup Authoring Blueprint

为已接受的意图所要求的未来项目 Rule 或 Skill 编写完整的蓝图集合。
`setup-assets/blueprints/**` 下的每份蓝图规定一个目标：它必须表达的含义、编写它所需的项目证据，
以及未来 Author 的权限和验收条件。

蓝图**仅用于判断**：它为有能力的 Author 提供作出这些决策所需的知识，将常规表述和推理留给 Author。
项目证据提供项目事实；setup 和公共 writer 提供生成机制。如果未来目标中的某个流程顺序会影响目标行为，
这个必要流程仍应写入蓝图。

起草前，读取并应用当前 checkout 中具有权威性的 `writing-for-agents`。

## 确立蓝图集合

从请求的结果和当前权威证据出发：已接受的用户决策、Issues、Specs、ADRs、治理契约、目标所有者资料，
以及可观察的目标行为。确定每项来源的所有者和出处。既有蓝图和目标有助于发现遗漏与回退，
但不能证明旧设计完整或正确。只有适用指令或具体问题需要时，才在获准访问范围内进一步调查。

确定每个必要目标的目的、执行者、触发条件、确切路径、Rule 或 Skill 类型，以及所有者。
让每个目标的职责都能独立说明。政策、流程和事实继续归现有所有者负责；只有已接受的意图要求时，才新增目标。

修订既有集合时，为每项会改变行为的义务确定保留、变更、新增、退役或非目标的处置。
缺乏依据的处置仍是未解决的决策，不能据此丢弃该义务。

写入前确定蓝图路径。每项创建、替换、删除或移动操作，都需要覆盖其确切路径和操作的授权。
现有会话授权若已覆盖这两项，就复用该授权；否则在受影响的写入之前停止。
仓库可见性、目录条目和写入权限，都不能确立语义权威或授予操作权限。保留无关路径和独立归属的内容。

## 规定未来目标

从未来目标读者的任务出发：读者必须识别什么、决定什么、执行什么，或在什么情况下停止？
对于 Rule，将受治理条件与其要求或优先选择的结果，以及重要例外联系起来。
对于 Skill，说明预期结果，以及达到该结果所需的选择或流程。过程导向的目标必须保留必要顺序。

说明已接受的含义，以及将决定其项目特定形式的证据。将条件与其结果、例外和可观察依据放在一起。
当权限、验证、结果和停止条件会影响目标行为时，明确规定它们。
为未来 Author 提供表达该行为所需的知识，不要规定文档模板，也不要叙述其写作过程。

例如，假设已接受的项目政策要求生成内容与其规范输入保持同步。
Tools 蓝图可以要求未来 Rule 指明哪些更改需要同步、如何检查一致性，以及缺少必要权限时怎么办。
仓库脚本及其所有者提供实际命令和生成路径；setup 决定何时编写和注册该 Rule。
蓝图承载同步义务及表达它所需的事实，不猜测命令，也不重复 setup 的执行步骤。

本节只纳入会改变受支持目标含义或目标读者决策的细节。
setup 的发现、调度、重试和生成机制仍由相应运行时所有者负责。当职责边界不明确时，读取
[setup 所有权](../../../skills/setup-project-agents/references/ownership.md)以了解目标所有权，
并读取[生成编写](../../../skills/setup-project-agents/references/generated-authoring.md)以了解 setup 与公共 writer 的分工。

## 为未来 Author 提供所需输入

规定 setup 必须提供哪些目标仓库证据，包括理解这些证据所需的来源所有者和出处。
区分已接受的要求与作为回归证据提供的既有内容。对于随项目变化的事实，指明如何用合格项目证据确定它们。
蓝图必须让编写工作无需捏造项目事实或授权即可进行。

确定未来 Author 的确切 Candidate 和可写路径、允许的创建、替换、删除和移动操作、
其他权限或外部效果，以及必要验证。明确每项操作的授权；已接受的权限可能已经覆盖多项操作。
检查或生成文件并不授权修改实际目标。声明蓝图 ready 之前，必须核对每项必要操作。

说明未来编写运行支持的结果，以及返回这些结果的可观察条件。这些结果描述 Author 能否产出可接受的工件；
要将它们与该工件使用时所治理的结果区分开。规定哪些权限缺失、不受支持的事实或实质性歧义会让 Author 停止，
以及交接必须包含什么证据。这些验收条件补充公共 writer 的结果契约，不替代它的工作流，也不授予 setup 操作权限。

## 验证完整集合

对照已接受的意图和相邻所有者审阅完整集合。确认每个必要目标和每项会改变行为的义务都有已接受的处置，
每项未来 Author 操作都符合其授权，且每份蓝图都提供了目标所需的含义与证据。
交接前解决所有权冲突和实质性歧义。

对于已声明的有限结果协议，检查条件能否区分、可能同时成立的条件是否有明确优先顺序，以及是否仍有实质性缺口。
对于开放的项目情境，沿决策标准推演有代表性的正常、异常和证据不足案例。
指明每项结论背后的证据，以及哪些事实缺失必须停止编写。这些推演用于检验实用性，不声称覆盖每一种可能的项目。
修复发现的缺口，不要把示例变成通用字段模式。

运行每项适用、由所有者支持的确定性非修复检查。只有合格的所有者证据证明没有此类检查适用时，
才记录 `NOT_REQUIRED`。完成既需要上述蓝图审阅，也需要检查通过，或有依据地得到这一无需检查的结果。
检查失败尚未解决时，不能完成；保留失败证据并报告未解决事项。

## 交接或停止本次运行

以下结果属于当前蓝图编写运行，与蓝图内部规定的结果分开：

| 结果 | 条件 |
| --- | --- |
| `ACCESS_REQUIRED` | 必要证据或验证在授权范围内无法访问。 |
| `CONTEXT_REQUIRED` | 已有访问权限，但合格证据无法提供必要事实。 |
| `HUMAN_DECISION_REQUIRED` | 实质性选择超出已接受的权限。 |

对于缺少访问权限或上下文，报告确切需求、获准探索为何无法满足它、可以解决问题的所有者或条件、其后果，
以及新运行所需的权限和可观察条件。对于决策，指出其所有者、当前可选项、证据和后果。
只有缺失输入和重试权限均已确立后，才能在一次新运行中恢复；已接受的权限可能已经覆盖重试。

完成时，返回确切的蓝图路径和所有者、受支持结果、检查及结果、保留约束，以及不确定或未测试的部分。
将这份交接说明与蓝图分开。向负责下游生成和 setup 执行的 `setup-project-agents` 交付 ready 输入，但不调用它。

本次运行只更改获准修改的蓝图，不生成未来目标或共享 SmartKit 工件，
也不执行翻译、安装、发布、提交或推送。
