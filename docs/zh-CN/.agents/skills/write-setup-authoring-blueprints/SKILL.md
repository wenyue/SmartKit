# 编写项目创作蓝图

编写所需的蓝图集合，将已接受的意图转化为有用的项目 Rules 和 Skills。每份蓝图描述一个未来目标：帮助读者完成什么工作、哪些项目证据决定其形式、哪些内容重要，以及这些内容应如何随后续更新演进。蓝图支持通过公共编写流程独立编写。

蓝图 **仅提供判断依据** 。为未来 Author 提供明确要求和具体选择方向，将组织表达和一般推理留给 Author。Author 在本次调用的权限内主动发现并核实项目证据；调用方可以提供已接受输入。公共编写流程负责 Candidate 编写和审查。未来目标需要教授的流程，在顺序影响行为时应写入蓝图；调用调度、脚本机制和重试归运行时所有者负责。

编写前阅读当前检出中具有权威性的 `writing-for-agents`。本次蓝图编写遵循以下步骤；这些步骤不是蓝图本身的模板。

## 1. 确定目标与编写权限

从已接受的用户决定和适用项目记录中恢复预期结果，再依据治理契约、目标所有者资料和可观察行为核实。明确来源的所有权和出处，避免既有示例悄然成为要求。利用既有蓝图和目标发现有用意图、遗漏和回归；文件存在不代表旧设计正确。只有为满足适用指令或回答具体问题时，才在可用访问权限内扩大调查。

对每个必要目标，确定读者、目的、触发条件、Rule 或 Skill 类型、确切路径和所有者。让它承担独立职责，并将策略、流程和事实留给各自所有者。只有已接受意图要求时，才增加目标。修订时，将每项改变行为的义务明确处置为保留、变更、新增、停用或范围外；没有依据的处置属于待解决决定，不是删除义务的许可。

起草前固定蓝图路径和操作。每项创建、替换、删除或移动都需要覆盖确切路径及操作的权限；已有授权同时覆盖两者时直接复用。可见性、目录条目和文件系统访问权限不提供语义或写入权威。保留无关路径及独立所有者的内容。完整目标集合、职责和获准蓝图操作明确后继续；缺少输入时按下文停止条件处理。

## 2. 给 Author 可用的创作方向

从未来读者需要作出的决定出发编写。Rule 必须把适用条件与必需行为或优先选择关联起来，并说明改变结果的例外。Skill 必须解释预期结果，以及达成结果所需的选择或必要顺序。权限、验证、结果和停止条件影响目标行为时予以明确。条件与例外应紧邻它们限定的含义。

对目标的每个主要部分，连接三件事：读者需要完成什么、哪些项目证据决定内容，以及哪些信息应突出或排除。指出有用的来源方向及其所有者，例如项目声明的检查命令、生成器映射、架构决定或实现关系。解释每项来源能解决什么问题，不只要求 Author“查看仓库”或“记录工具”。依赖项目的事实来自经过核实的项目证据，不来自示例命令或猜测的仓库布局。

例如，Tools 蓝图可能需要帮助读者保持生成输出同步。引导 Author 查看项目声明的生成器、输入输出映射和受支持的检查。让最终指引重点说明哪些源文件变化需要重新生成、如何验证一致性，以及缺少哪些权限会阻止执行。列出所有已安装工具会掩盖这些判断。蓝图可以明确这种方向，而不在项目证据具备前选择命令，也不规定未来 Rule 的标题结构。

当 Author 能识别必要含义、取得决定项目特定表达形式的事实，并在不虚构事实或权限的情况下选择相关细节时，蓝图才足够具体。除非承载已接受的行为契约，否则将文档结构和措辞留给 Author 决定。

## 3. 让后续更新对这类内容有用

在每份蓝图中定义更新偏好。按内容用途选择偏好，混合目标的不同部分可以采用不同偏好。全部重写或全部保留，都不适合作为所有蓝图的统一默认策略。

| 内容 | 蓝图应如何指导 Author |
| --- | --- |
| 工具和代码结构事实 | 重新核对确立这些事实的配置、所有权文档或实现关系。更新变化的事实，删除被证据否定的说法；即使蓝图未变，频繁更新也可能合适。 |
| 流程和长期上下文 | 保留仍然适用的决定、义务及其理由。指出哪些要求、职责或受支持行为的变化足以支持修订。仅有措辞变化时，保留有用且稳定的表达。 |
| 两者混合 | 区分各个部分，例如稳定的验证义务与不断变化的项目命令。更新事实时不丢失义务，也不因为周围策略稳定就保留过时命令。 |

结合当前目标与新取得的合格项目证据。保留有效的项目补充和义务，包括条件与例外。既有文本是意图证据，不足以证明有争议的说法仍然有效；通过负责的所有者和已接受权限解决冲突。较新的蓝图同样不构成抹去项目决定的普遍理由。

解释什么证据支持各类变化，以及哪些内容应在变化中保留。更新标准未发现相关变化或缺陷时，保留正确内容；有依据修订时，使最终指引准确、一致，不累积重复内容。这些标准指导内容判断，不定义调用频率、脚本行为，也不替代公共编写流程。

每份蓝图都应充分具体地说明预期变化来源、稳定含义和修订证据，足以区分有用更新与无必要重写，之后才能继续。

## 4. 界定未来编写任务的范围

说明未来 Author 需要哪些证据，以及如何在本次调用权限内取得并核实这些证据：带所有权和来源信息的项目事实、既有目标及相关项目补充，以及与回归检测材料明确区分的已接受要求。调用方可以提供这些输入，但交接中缺少它们时，应先主动调查，而不是立即因缺少输入停止。让 Author 根据合格证据确定普通的文件、接口和实现选择；只有超出已接受权限的重大选择才需要用户输入。解释授权范围内调查后仍无依据的事实如何影响产出目标的能力。

写入前确定该 Author 的确切 Candidate 和可写路径、允许的创建、替换、删除和移动操作、必需验证，以及其他权限或外部效果。使用本次调用授权的目的位置。明确每项必要操作的授权，已有权限足够时予以复用。生成或查看工件不授予修改实际目标的权限。

定义可观察的验收条件及交接必须携带的证据。区分未来编写运行支持的结果，与完成后的 Rule 或 Skill 在使用时规定的结果。缺少权限、关键事实无依据或重大选择未解决时，必须停止依赖这些条件的编写。这些条件补充公共编写流程的结果契约，既不取代其工作流，也不授权下游集成效果。

未来 Author 无需假定授权或其他工作流提供的输入，便能识别范围、证据发现职责、可用结果和停止条件时，本步骤完成。

## 5. 检查完整集合并交付

对照已接受意图及相邻所有者审查完整蓝图集合。每个必要目标和改变行为的义务都需要有依据的处置，每项未来操作都必须符合授权。交接前解决所有权重叠或重大歧义。

用有代表性的正常、异常和证据不足情形逐一走查蓝图。包括证据未变时重复执行、项目事实变化、已有有效项目补充三种情形。确认指引在相应情况下支持保留正确内容、修正过时事实和保留项目意图。指出每项结论的证据，以及缺少事实时必须在哪里停止编写。这些示例用于检验指引，不成为通用字段 schema，也不代表穷尽覆盖。有限结果协议还需检查条件可区分、重叠条件有明确优先级，并且没有实质性缺口。

以非修复模式运行全部适用的所有者支持确定性检查。只有合格所有者证据表明没有适用检查时，才使用 `NOT_REQUIRED`。完成要求检查通过，或具备上述有依据的结果，并完成完整集合审查。必需检查失败或无法访问时不能宣告完成；保留失败证据并报告未解决条件。

交付确切蓝图路径及所有者、支持的结果、检查及结果、保留约束，以及不确定或未测试表面。交接说明放在蓝图之外。结果支持通过公共编写流程独立编写。未来目标编写和下游集成仍是由各自所属工作流负责的独立任务；本次蓝图编写运行不调用这两类任务。只修改获准蓝图：不产出未来目标或共享 SmartKit 工件，不执行翻译、安装、发布、提交或推送。

## 输入不足以支持工作时停止

以下结果用于当前蓝图编写运行，与蓝图内部描述的任何结果契约相互独立：

| 结果 | 条件 |
| --- | --- |
| `ACCESS_REQUIRED` | 必要证据或验证无法在授权范围内访问。 |
| `CONTEXT_REQUIRED` | 已授权访问，但合格证据无法确立必要事实。 |
| `HUMAN_DECISION_REQUIRED` | 重大选择超出已接受权限。 |

缺少访问权限或上下文时，指出确切需求、授权内调查未能解决它的原因、负责的所有者或解决条件，以及缺少该条件时继续的后果。说明新一轮运行所需的权限和可观察条件。需要决定时，说明决定所有者、可选方案、支持证据和后果。缺少的输入与重试权限确立后，只在新一轮运行中恢复；已有授权可以覆盖该次重试。
