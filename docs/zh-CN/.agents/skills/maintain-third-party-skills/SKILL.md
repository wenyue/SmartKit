# 维护第三方技能

通过同一条维护路径引导首次接入和升级：评估所选上游技能会让使用方如何行动，确定必要的本地适配，再生成并验证仓库快照。在决定改变之前保留已接受的本地行为。主动调查风险和重要取舍，无需等用户指出，再给出有依据的建议。补丁能够顺利应用，只能证明机械层面的兼容性。

这是一个项目级维护技能。评估请求授权调查和提出方案；添加或升级技能的请求还授权在已接受范围内实施准备就绪的变更。两者都不会自动授权发布结果或将其安装到用户环境。

## 确定维护边界

阅读[技能注册表](../../../skills/registry.json)中的外部来源条目、[锁文件](../../../vendor/external-skills.lock.json) 中已有的对应记录，以及列出的补丁文件。在选择工作区和比较基准前，检查 Git 状态、已安装技能的目标目录和受管理输出中的已有工作。确定请求中的每个技能适用哪一种起点：

| 起点 | 所需证据与审查 |
| --- | --- |
| 从新来源首次接入 | 此时本来就没有已安装基线。确定来源身份、已审查的目标提交、所选技能及其完整行为、许可证、依赖和本地集成方式。 |
| 从已有来源新增技能 | 将新技能按首次接入进行审查。对于该来源中已有的所选技能，使用来源记录中的基线，并将来源修订的任何变化作为这些技能的升级进行评估。 |
| 升级已安装技能 | 使用锁文件中解析后的提交作为已安装上游版本的基线；仅凭配置的标签或分支名无法确定实际内容。结合该基线和当前本地适配比较目标版本。 |

对于确实新增的来源或技能，没有锁记录是正常情况。如果已有安装内容缺失来源记录或来源无法核实，则需要调查；将其当作首次接入，会绕过证明替换合理所需的基线和保留措施。修改受影响内容前先补齐这一缺口。

注册表和补丁是输入；分发的技能目录、许可证和锁文件由[外部技能更新器](../../../scripts/update_external_skills.py) 生成。通过这些负责的输入维护适配，不要直接编辑生成的快照。

明确请求涉及的来源、所选技能、目标修订和预期结果。依据当前上游发布记录和仓库内容核实目标，区分正式发布与尚未发布的分支内容。记录解析后的目标提交，用于审查及后续验证。如果请求没有指定目标，推荐有依据的发布版本或修订，说明发布版本的稳定性与所需未发布变更之间的重要取舍。如果目标证据缺失或无法核实，则不能采用该目标；说明缺口，只继续不依赖它的调查。

注册表中的修订和更新器的 `--source` 都作用于整个上游仓库，而非单个技能。确定该来源修订影响的所有已选技能。从已有来源新增技能时，使用的是同一个修订；如果新增技能需要更新的修订，应评估它对所有已选技能的影响。说明无法避免的扩大更新范围，并在实施前确定该范围。

## 主动发现影响采用决策的因素

首次接入时，完整阅读目标修订中的所选技能及其所属资源。追踪必需的引用、脚本、资产和其他技能依赖，确定所选内容正常运行需要什么。区分用户目标所需的能力与可选分支，明确使用方如何在具备相应前提时使用每个受支持分支。候选技能的简介或近期变更日志无法证明将要引入的完整行为。

升级时，阅读发布说明，比较所有已选技能及其所属资源的旧版和目标上游目录。明确现有本地补丁为何存在，以及目标版本是否提供了等效结果。将审查重点放在变化的行为及其依赖上，同时保留变更范围之外的必要保障。

无论哪种情况，都应沿着受影响的指令检查本地规则、技能、调用方和工具。利用这些关系发现风险和有益的简化机会。仅当上游内部冲突或歧义实质上妨碍本地采用时才处理它们；无关的上游功能不应仅因存在就成为采用工作。

对每个新增选取或发生实质变化的技能，调查其后果：

| 关注点 | 哪些因素可能改变决策 |
| --- | --- |
| 行为与组合 | 新增或变化的触发条件、义务、停止条件、委派和副作用可能改变已接受的行为。结合适用规则、原生发现元数据和实际依赖一起阅读，再判断是否缺失能力或存在不兼容。 |
| 本地适配 | 新增时，确定与仓库协同所需的最小本地差异。升级时，根据旧版上游及当前应用后的内容确定每个补丁的目的，再在目标版本中寻找对应实现。区分上下文修复、上游的等效实现和预期行为变更。 |
| 选择与重叠 | 将拟议能力与本地已有能力比较，说明所选内容是补充、重复还是替代。沿调用方、注册表和公开入口追踪新增、重命名、移动、移除和新增必需条目。选取范围变化会影响能力覆盖范围及维护成本。 |
| 依赖与迁移 | 检查所选内容需要或升级所改变的文档约定、模板、链接、脚本、命令、工具和 Harness 能力。所选目录之外的依赖需要受支持的交付或访问路径；即使补丁可以应用，格式重命名仍可能使调用方或现有文档无法使用。 |
| 来源与影响 | 检查来源身份、许可证和署名要求，以及引入的可执行或网络行为。揭示额外的访问、凭据、服务、持续费用或信任要求。 |

只有适用条款无法在同一决策中同时满足时，才判定为冲突。引用双方的准确来源位置、适用条件、触发场景及后果；提出修复前先应用既有优先级规则。针对不同阶段的指令可以并存。同样，没有明确写出技能名称不等于缺少能力：应检查适用规则和原生发现机制是否已经提供所需路径。区分有依据的静态解读与实际观察到的调用行为，指出会影响决策的不确定性。

按照使用方依赖的结果和必要保障评估替代方案，包括已接受的授权、验证和恢复边界。仅有步骤差异不足以证明需要保留两个技能。说明替代方案覆盖哪些能力、还有哪些不支持，以及这些缺口是否值得通过小幅集成、保留独立能力或推迟采用来处理。计入保留旧协议的维护成本；保留必要保障，无需搬入已经不再服务于这些保障的步骤。

根据需要改变的职责选择各项适配的负责方。为了与合理的上游设计配合，本地调用方或规则可能需要修改；只有已接受的本地差异必须保留在引入的技能中时，才应通过补丁实现。增加补丁负担前先比较这些选项。仅修复上下文的补丁可以在已有授权范围内推进。只有确认补丁原本保障的结果已由别处提供，或移除补丁已获授权，才能淘汰它；仅为让更新器通过而丢弃补丁，会失去它原本要保留的行为。

对于拟议的淘汰或替代，追踪剩余使用方及其假设：引用、公开入口、术语、协议、文档和检查。区分该决策必需的清理与周边工作流的可选简化。如果旧依赖正是这些工作流复杂的原因，建议范围明确的后续工作；实质性的范围扩大仍由用户决定。

所有已选技能和补丁都已交代清楚、受影响的使用方与依赖都有可行路径或明确缺口，且重要风险和取舍已解释清楚时，评估才算准备就绪。将证据保留在对话中；注册表、锁文件和补丁仍是长期来源记录。

## 推荐方案并确定重要取舍

先说明推荐的采用范围及其如何服务于用户目标。明确来源、新增选取内容或基线到目标的变化、收益、重要风险、受影响的使用方、补丁处置、迁移工作，以及拟议的验证和恢复方式。优先说明可能改变决策的后果，无需给每个文件或每一项差异相同的篇幅。

对每个尚未解决的重要选择，给出可行方案、各自的取舍和有依据的建议。说明建议依据的证据及假设。如果缺失证据可能推翻建议，应尽量自行取得；无法取得时，指出缺口、下一项有用调查或需要用户提供的准确信息。不要用开放式征求方向代替 Agent 能够自行完成的分析。

当选择会改变已接受的范围或行为时，应询问并等待，再执行依赖该选择的变更，例如采用或淘汰公开技能、改变名称或激活方式、接受新的服务或权限要求，或扩大使用方迁移。复用用户已经给出的决定和授权；保留已接受结果的常规修复无需新增审批关卡。对于仅分析的请求，以具体方案和剩余决策结束。对于已授权的新增或升级，在已接受的范围、行为、前提和检查都明确后继续执行。

## 通过负责的更新器实施

通过 Git 证据或隔离工作区保留原始输入及记录中的输出，以便恢复任务变更而不丢弃已有工作。更新前处理受管理输出的偏离：先保留偏离内容，确定其归属和意图，将已接受变更表达为负责的补丁，然后在相关工作已安全保留的前提下，仅恢复对应的记录输出。同时检查拟议的新目标路径；已有目录是需要查明和协调的事实，并不代表可以覆盖它。如果归属或保留方式不清楚，暂停受影响的更新并请求指示。

对于新来源，将来源声明、已审查修订、许可证声明和所选技能加入注册表。对于已有来源，只修改已接受的修订、选取范围或路径。根据当前注册表和更新器校验确定准确字段、命名约束以及受支持的来源和许可证形式，不另行发明一套 schema。确认所选名称和目标路径能与第一方及其他外部技能共存。

依据解析后的目标创建或调整有序补丁，保留已接受的本地差异之外的上游措辞。本地调用元数据和打包资产需要适配时，将这些适配保留在补丁中。保留许可证和版权声明。通过仓库中相应的负责机制修改已授权的公开入口、README 介绍和使用方，让新条目与其他第三方技能保持一致。移除一个契约也包括处理其受影响的调用方、文档和检查。

在仓库根目录更新选定来源：

```bash
python scripts/update_external_skills.py --update --source <owner/repository>
```

使用注册表中的实际来源 ID，新声明且尚无旧锁记录的来源也适用。必要时用 `--help` 确认当前 CLI。指定来源的操作通过已有锁记录保留其他已配置来源；这些来源缺失锁记录属于需要解决的前提缺口，不能因此悄悄扩大更新范围。省略 `--source` 会处理所有已配置来源；仅在确实需要该范围时使用。移除整个来源需要规划完整更新，因为已移除的 ID 不再被 `--source` 接受。从保留的来源中移除某个已选技能，会使更新器删除其受管理的目标目录。

更新器将选定 Skill 复制到暂存区，对不含 NUL 字节的 UTF-8 资源将 CRLF 规范化为 LF，再应用补丁，并在记录最终哈希前再次规范化补丁输出。编写补丁时，以规范化后的文本为基准。二进制资源和上游检出目录保持原样；转换会保留其他空白，包括 Markdown 硬换行。文本许可证采用相同的 LF 表示。仓库 Git 属性对 Skill 目录树和许可证禁用换行转换，确保其记录的字节在不同宿主换行设置下保持一致，即使不透明资源使用了文本文件后缀。

更新器先暂存并验证补丁，再一起安装技能、许可证和锁文件。补丁冲突会保留之前安装的输出；调用更新器之前修改的输入仍需审查。重试前先调查失败原因。如果报告事务或回滚失败，应检查实际文件和保存的 Git 证据，不要假定恢复已经成功。

## 验证应用后的结果

完整阅读新增或发生变化的技能及其必需资源，追踪受影响的调用路径。确认预期的补丁行为、发现机制、文档约定和依赖能够协同工作。对于新增或变化的可执行行为，运行相关受支持检查；如果无法验证行为，应报告具体缺口，不要把文本自洽当作运行时证据。

运行更新器的非修改检查模式：

```bash
python scripts/update_external_skills.py --check --source <owner/repository>
```

更新和检查都会解析上游来源，可能需要网络访问；`--check` 不是离线查看锁文件。将结果锁文件中的提交与已审查目标比较。目标发生移动或出现新差异时，必须重新评估。将报告的补丁范围视为本地维护负担的信号，不要把它当作适配正确的证明。

按照当前负责机制和 [CI 配置](../../../.github/workflows/test.yml)运行适用的清单、规则交付、翻译和仓库检查。项目翻译政策适用时同步镜像。对照已接受范围检查每个变化或移除的路径、生成输出、许可证和锁文件条目，包括选定来源之外的意外变更。运行 `git diff <comparison-point> --check`，同时覆盖新增的未跟踪文件。

完成维护要求已审查的选取内容和修订安装到仓库快照中、已接受的本地行为与受影响使用方保持协调、全部必需检查通过，并保留已有工作。报告来源和修订变化、采用或淘汰的条目、重要补丁与迁移决策、验证证据及任何尚未解决的限制。区分已完成的仓库维护与下游发布或安装，后两者保留各自的授权要求。
