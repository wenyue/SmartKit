# 契约

## 目的与证据

对于独立创建或修订 `.agents/rules/contracts.md` 的请求，使用 `write-rules-and-skills` 编写一份归目标仓库所有、标题为 `Contracts` 的 Rule，规定什么样的变更才有效。

根据已接受请求和当前证据确立目标仓库。Author 主动发现并核实相关目标证据：入口指引和适用 Rules；已接受的 Issues、Specs 和 ADRs；API、模式、事件、领域模型、实现和行为测试；以及注册表、同步器、清单、包、加载器和文档路径中的所有权与交付关系。复用调用方提供的合格证据，直接发现缺失事实；调用方无需事先准备证据包。按所有者和来源评定资料。既有 Rule 文本是保留和回归证据，不是设计权威；可见性、历史文本、机器本地状态和写入访问权限不授予权威。

将每项义务分类为保留、变更、新增、停用或非目标。变更、新增、停用、例外和兼容要求都需要已接受意图与合格证据。否则保留受支持行为；若其处置会改变结果，则停止。

## 需要确立的策略

对每项有证据支持的策略，明确触发条件、可观察结果、确切例外、优先级和决策所有者，并覆盖最接近边界的包含与排除情形。涵盖：

- **消费者契约：** 状态、兼容性、生命周期、并发、取消、迁移、持久化和清理。
- **规范所有权：** 输入所有者，以及修改该输入分别对转换、适配器、传输、安装和交付造成的影响。
- **托管状态：** 对已拥有的文件、结构化字段、摘要和托管配置的声明、保留、冲突、替换和停用。
- **文档：** 公开材料与贡献者材料、规范语言与派生语言各自的权威和暴露边界。
- **评估：** 结构、可执行和自然语言评估的边界，以及使既有结论失效的证据变化。
- **契约演进：** 实现、文档、测试、验证、持久化状态和调用方的连贯变更；仅在当前正确性需要时保留兼容和恢复。
- **分发：** 交付方向、硬依赖、可见性和公开／私有暴露边界。

已安装的 SmartKit 治理决定 Rule 的优先级。触发、适用性、结果、例外、优先级、所有权、保留或停用方面的实质性分歧需要决策；不受支持的事实不能用于选择策略或悄然省略策略。

工具和 Skills 保留命令发现、准备、变更、同步、测试和验证流程。结构所有者保留放置建议。只有省略会改变策略时，才纳入可从当前所有者获取的事实；清单、实现步骤和通用架构指引不增加契约含义。

## 更新重点

将已接受的项目契约及其理由视为长期有效的内容。通过 API 和 schema 定义、行为测试、交付边界及已接受的架构决定，重新核对其当前所有者。这些来源证实义务、受支持例外、所有权边界或兼容性决定发生变化时，才修改 Rule；仅有新的措辞偏好不足以成为重写理由。

重点说明会影响结果的包含和排除情形，例如某项变化是否保留消费者契约，还是需要迁移。保留仍然有效的项目补充和例外。义务变化时，替换受影响的定义并协调相邻引用，不同时保留两个版本。含义未变化时，保留完整的既有 Rule。

## 编写边界与验收

Author 可以查看目标证据，运行所有者支持的只读或非修复检查，并在本次请求授权的 Candidate 根目录下创建或替换 `.agents/rules/contracts.md`。写入前，通过公共 writer 确定该根目录、确切路径和操作。不要求固定的暂存目录。删除、移动、写入实际目标、无关变更和外部效果都需要单独的已接受授权。

公共 writer 负责编写、审查和终止结果。本 Rule 的验收要求每个受支持的判别条件、义务和受影响表面都有证据支持的策略结果：每个受支持输入都无需虚构事实便能选出恰好一个结果。必要检查必须通过；省略检查需要有证据证明其不适用。

在 writer 交接中说明目标及证据所有者、义务处置、检查结果、保留约束，以及不确定或未测试表面。对于尚未解决的访问、证据或授权缺口，指出阻塞项、所有者、后果和继续所需的条件。交接必须能由调用方独立使用，且不授予下游安装、发布、提交或推送权限。
