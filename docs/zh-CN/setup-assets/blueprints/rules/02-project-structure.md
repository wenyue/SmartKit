# 项目结构

强度：`Advisory`

适用范围：关于目标仓库结构、放置位置、职责和导航建议的 Setup Authoring Contract。

## 契约框架

当 `setup-project-agents` 请求 `.agents/rules/02-project-structure.md` 时，编写且仅编写这一项
由目标仓库所有、标题为 `Project Structure` 的 Advisory Rule。它在更具体或 Mandatory 的有效性
政策生效之后，对位置、职责接缝或导航入口的受支持选项进行排序。它不确立所有权，不准许依赖，
也不改变交付、安装或暴露政策。

依据目标仓库的所有者和来源，判定已接受意图与证据是否合格。相关证据包括入口指引和更具体的
Rule；已接受的 Issue、Spec 和 ADR；调用方、import、使用方、测试、schema、注册表、generator、
运行时入口以及规范文档路径。目录名、命名、共置关系、package 边界和仅限本机的状态只是线索，
并非权威依据。现有目标 Rule 是回归证据，而非设计权威。

将每项继承或拟议建议分类为保留、更改、新增、退役或非目标。更改、新增、退役受支持的建议，
或为其设定例外，都需要已接受意图和合格证据；否则应予以保留或停止。

## 必备建议

每项建议都必须用其适用谓词、排序结果、证据所有者以及任何明确例外，回答一个真实存在的竞争
选择。保留以下各项中所有已有证据支持的映射：

- 当一个使用方保有作出决定所需的上下文，并使政策、实现和测试保持内聚时，采用本地放置；
- 当独立使用方需要一项稳定决定，或多个副本会造成跨所有者耦合时，采用既有共享接缝；
- 对于适配上游意图而不决定该意图的表征，采用面向使用方的边界；
- 对于重复出现的下游政策或机制，采用最早具备足够上下文的既有所有者，但上移会抹去选择所需
  上下文时除外；以及
- 采用能通向所属规范源且不重复清单的规范导航入口。

例外应说明其范围、适用谓词和原因。所有权、规范源、依赖、生成、安装、交付、暴露和验证方面
的硬性政策仍归其 Mandatory 所有者负责。排除 package 导览、缓存布局、通用分层、臆测性架构、
设置或编写过程，以及不会改变任何受支持选择的建议。

## Author 权限与终态结果

未来的 Author 可以检查目标证据，运行所有者支持的只读或非修复性检查，并使用
`setup-project-agents` 提供的请求根目录，仅创建或替换
`GENERATED/.agents/rules/02-project-structure.md`。它不得删除或移动该 Candidate，不得写入实际目标、
变更无关状态，也不得在没有另行获得已接受授权的情况下产生外部效果。

只返回以下一个终态结果；首个匹配的判定条件优先：

1. 当在授权范围内无法访问必要证据或验证时，返回 `ACCESS_REQUIRED`。
2. 当具备访问权限，但无法从合格证据中发现某项必要事实时，返回 `CONTEXT_REQUIRED`。
3. 当合格证据支持实质不同的排序，或所需所有者、例外、义务处置、操作或效果缺少已接受授权时，
   返回 `HUMAN_DECISION_REQUIRED`。
4. 当某项检查仍未通过，或某个受支持选择、义务、操作或边界缺少一项有证据支持的结果或权限时，
   返回 `VALIDATION_FAILED`。
5. 当每项建议都回答一个受支持选择、每项受支持输入都选定一个可观察结果、没有任何结论依赖
   不受支持的项目事实，并且所有适用且由所有者支持的确定性检查均通过或被记录为
   `NOT_REQUIRED` 时，返回 `READY`。

每次停止都应说明阻塞项、所有者、后果以及重新尝试的条件。`READY` 应报告 Candidate、目标所有者
和证据所有者、义务处置、检查、保留的约束，以及不确定或未经测试的表面。它只能作为
`setup-project-agents` 的输入，不授予任何下游生成、安装、发布、提交或推送权限。
