# 结构

## 目的与证据

对于独立创建或修订 `.agents/rules/structure.md` 的请求，使用 `write-rules-and-skills` 编写一份归目标仓库所有、标题为 `Structure` 的 Rule。它依据适用策略和已安装的 SmartKit 治理，对位置、职责边界或导航入口的有效选择排序。所有权、依赖许可、交付、安装和暴露仍归相应策略所有者负责。

根据已接受请求和当前证据确立目标仓库。Author 主动发现并核实相关目标证据：入口指引和适用 Rules；已接受的 Issues、Specs 和 ADRs；调用方、导入、消费者、测试、模式、注册表、生成器、运行时入口和规范文档路径。复用调用方提供的合格证据，直接发现缺失事实；调用方无需事先准备证据包。按所有者和来源评定资料。名称、共同放置、目录与包边界和机器本地状态只是线索，不是权威；既有 Rule 文本是回归证据，不是设计权威。

将每条建议分类为保留、变更、新增、停用或非目标。变更、新增、停用和例外需要已接受意图与合格证据；否则保留受支持建议或停止。

## 需要指导的选择

每条建议都解决一个真实的竞争选择。说明其条件、排序结果和证据所有者，并说明任何例外的范围、判别条件和理由。保留有证据支持、倾向以下选择的建议：

- 当一个消费者保有决定性上下文，且能让策略、实现和测试保持内聚时，优先 **局部性** 。
- 当独立消费者需要一个稳定决策，或重复副本造成跨所有者耦合时，优先 **既有共享边界** 。
- 对适配上游意图而不决定上游意图的表示，优先放在 **面向消费者的边界** 。
- 对下游重复的策略或机制，优先交给 **最早具备充分上下文的既有所有者** ，前提是上移仍保留作出选择所需的上下文。
- 优先使用能引向所属来源、且不重复维护清单的 **规范导航入口** 。

相关政策的所有者保留所有权、规范来源、依赖、生成、安装、交付、暴露和验证策略。建议应针对受支持选择；包结构导览、缓存布局、通用分层、推测性架构，以及配置或编写流程都不属于本 Rule。

## 更新重点

项目结构变化时，重新查看调用者、消费者、依赖边界和规范导航入口。根据有代表性的实现和测试中的具体关系，说明新行为应放在哪里，以及何时有理由共享。目录移动可能只需要更新指针，不改变原有职责或放置原则。

证据仍然有效时，保留已接受的排序建议及其理由；职责、消费者或已接受的架构决定发生变化并使原建议失效时，再修订排序。保留仍然描述受支持选择的项目补充。结果应继续是一份决策指南，更新受影响的事实，不让每次更新变成目录清单或重述未变化的指引。

## 编写边界与验收

Author 可以查看目标证据，运行所有者支持的只读或非修复检查，并在本次请求授权的 Candidate 根目录下创建或替换 `.agents/rules/structure.md`。写入前，通过公共 writer 确定该根目录、确切路径和操作。不要求固定的暂存目录。删除、移动、写入实际目标、无关变更和外部效果都需要单独的已接受授权。

公共 writer 负责编写、审查和终止结果。本 Rule 的验收要求每条建议都解决一个受支持选择：每个受支持输入都无需虚构事实便能选出一个可观察结果，且每项义务和边界仍有证据支持。必要检查必须通过；省略检查需要有证据证明其不适用。

在 writer 交接中说明目标及证据所有者、义务处置、检查结果、保留约束，以及不确定或未测试表面。对于尚未解决的访问、证据或授权缺口，指出阻塞项、所有者、后果和继续所需的条件。交接必须能由调用方独立使用，且不授予下游生成、安装、发布、提交或推送权限。
