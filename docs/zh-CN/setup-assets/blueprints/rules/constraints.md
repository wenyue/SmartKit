# 约束

## 用途与证据

对于独立创建或修订 `.agents/rules/constraints.md` 的请求，使用 `write-rules-and-skills` 生成一条归目标项目所有、标题为 `Constraints` 的 Rule。向 Agent 提供选择实现方式或运行工具前需要了解的项目专有约束、例外和入口条件。已安装的共享政策与现有项目所有者保留各自含义；这条 Rule 提供项目额外规定的决策。

从已接受的请求确定目标。检查其入口指引、现有 Rules 与相关 Skills、已接受的 Issues 和 ADR、模式与接口、配置、生成器、准备和验证所有者，以及有代表性的实现和测试。按所有者和来源确认各项证据。现有指令可以揭示项目意图和回归风险；仅凭当前代码不能授权改变这些意图。已有 Wiki 可以帮助定位来源、解释关系，但重要主张必须向其规范所有者核实。没有 Wiki 时，编写流程仍须可用。

合并早期 Rules 时，阅读其完整内容，包括当前项目补充、例外以及已有目标文件。逐项说明每个重要义务的去向：保留在本文件中、已由其他所有者负责且具有可用加载路径、依据已接受意图有意修改或退役，或尚未解决。写入前解决缺乏依据的处置；结果更短不能成为丢失约束的理由。

## 需要指导的决策

包含会影响 Agent 选择的项目专有含义：

- **行为与演进：** 已接受的兼容性、持久化、生命周期、并发、取消、恢复和清理义务，包括受支持的例外以及决策所有者。
- **放置位置：** 在不同产品所有者、局部与共享实现、使用方适配或既定扩展边界之间作出选择。以职责和实际使用方为依据，不做目录导览，也不提供泛化的分层建议。
- **规范来源与交付：** 哪些改动需要生成或同步使用方，哪些独立所有或已交付的表面必须保持分离，以及如何确认已接受的结果。
- **执行与验收：** 重要的工作目录或运行时要求、项目专有的效果限制、必需的验证证据，以及触发现有准备、验证或维护能力的条件。

共享政策或现有所有者已提供其他内容时，只写项目额外的要求或例外。能力指针说明适用的触发条件和必需结果；命令、执行顺序、恢复方式和详细成功标准留给该能力。尤其应由准备和变更集验证 Skills 拥有各自执行流程。保留它们在项目中的激活条件，不复述操作过程。

将持久有效的已接受决策及理由保留在 ADR 中，术语交给其领域所有者，确定性机制交给脚本，条件性政策交给适用的所有者。架构解释、模块与依赖关系图、运行流程、工具原理和故障排查背景应放在项目知识文档中，包括项目采用时的 `openwiki/`。本次编写任务不生成这些知识文档。即使跳过 Wiki 检索或 Wiki 不可用，必需政策仍应在相关决策前可达；Wiki 摘要不会成为政策权威。

使用能够承载这些决策和必要指针的最小完整 Rule。不要为了模仿已退役的 Tools、Contracts 和 Structure 文件而填充标题、拼接它们，或为显得完整而重述共享政策。

## 更新重点

含义仍然正确时，保留有效的项目决策、条件、例外和有用表述。对照当前所有者重新检查发生变化的接口、源所有权、工具要求、生成关系、验证义务和 Skill 入口条件。更新受影响的事实，不复制其所有者的完整流程。

新接受的决策或已证明的重复可以成为修订依据；新蓝图指纹或措辞偏好本身不能。保留项目专项 Skills、自定义脚本、ADR 和无关 Rules。某项职责已有权威归属时，保留该归属及充分的到达路径，不在这条 Rule 中建立另一份定义。

## 编写边界与验收

Author 可以检查目标证据、运行所有者支持的只读或非修复检查，并在本请求授权的 Candidate 根目录下创建或替换 `.agents/rules/constraints.md`。通过公共 writer 确定根目录、精确路径和操作。源退役、其他文件修改、真实目标写入和下游效果，仍由各自另行授权的所有者负责。只读访问早期 Rules 提供的是证据，不是删除权限。

公共 writer 拥有编写、审查和终态结果。验收要求每项重要的项目义务都有受支持的处置和可达所有者；每个纳入的条件都必须导向可用的决策，并完整保留例外。按项目适用范围检查有代表性的行为、放置位置、工具执行、验证和证据不足场景。确认没有 Wiki 时 Rule 仍然充分，且不重复两个执行型 Skills。必需检查必须通过；省略检查需要证据证明其不适用。

在交接中提供证据所有者、义务处置、检查结果、保留的项目补充和约束，以及未解决或未测试的表面。指出任何阻止完成的证据缺失、权限缺失或所有者修正。交接必须可独立使用，不授予本 Candidate 之外的生成、安装、退役、发布、提交或推送权限。
