# 项目契约

强度：`Mandatory`

范围：跨 API、能力所有权、安装、文档、评估、契约演进、分发、硬依赖和暴露边界的持久变更有效性策略所对应的 Setup Authoring Contract。

## 目的与证据

当 `setup-project-agents` 请求生成 `.agents/rules/01-project-contracts.md` 时，Author 编写一份归目标仓库所有、标题为 `Project Contracts` 的 Mandatory Rule。只要变更涉及本范围中的事项，它就规定该变更满足什么条件才有效。

Setup 必须提供相关目标证据：入口指引和更窄范围的 Rules；已接受的 Issues、Specs 和 ADRs；API、模式、事件、领域模型、实现和行为测试；以及注册表、同步器、清单、包、加载器和文档路径中的所有权与交付关系。按所有者和来源评定资料。既有 Rule 文本是保留和回归证据，不是设计权威；可见性、历史文本、机器本地状态和写入访问权限不授予权威。

将每项义务分类为保留、变更、新增、停用或非目标。变更、新增、停用、例外和兼容要求都需要已接受意图与合格证据。否则保留受支持行为；若其处置会改变结果，则停止。

## 需要确立的策略

对每项有证据支持的策略，明确触发条件、可观察结果、确切例外、优先级和决策所有者，并覆盖最接近边界的包含与排除情形。涵盖：

- **消费者契约：**状态、兼容性、生命周期、并发、取消、迁移、持久化和清理。
- **规范所有权：**输入所有者，以及修改该输入分别对转换、适配器、传输、安装和交付造成的影响。
- **托管状态：**对已拥有的文件、结构化字段、摘要和 setup 托管状态的声明、保留、冲突、替换和停用。
- **文档：**公开材料与贡献者材料、规范语言与派生语言各自的权威和暴露边界。
- **评估：**结构、可执行和自然语言评估的边界，以及使既有结论失效的证据变化。
- **契约演进：**实现、文档、测试、验证、持久化状态和调用方的连贯变更；仅在当前正确性需要时保留兼容和恢复。
- **分发：**交付方向、硬依赖、可见性和公开／私有暴露边界。

范围最窄的当前权威决定受支持冲突的处理。触发、适用性、结果、例外、优先级、所有权、保留或停用方面的实质性分歧需要决策；不受支持的事实不能用于选择策略或悄然省略策略。

工具和 Skills 保留命令发现、setup、变更、同步、测试和验证流程。结构所有者保留放置建议。只有省略会改变策略时，才纳入可从当前所有者获取的事实；清单、实现步骤和通用架构指引不增加契约含义。

## Author 边界与结果

Author 可以查看目标证据，运行所有者支持的只读或非修复检查，并在 setup 的请求根目录下创建或替换 `GENERATED/.agents/rules/01-project-contracts.md`。删除、移动、写入实际目标、无关变更和外部效果都需要单独的已接受授权。

首个适用条件决定唯一的编写结果：

| 结果 | 判别条件 |
| --- | --- |
| `ACCESS_REQUIRED` | 必要证据或验证在授权范围内无法访问。 |
| `CONTEXT_REQUIRED` | 已有访问权限，但无法从合格证据中发现必要事实。 |
| `HUMAN_DECISION_REQUIRED` | 仍存在实质性策略分歧，或必要的操作、效果、所有者、比较点、例外或义务处置缺少已接受授权。 |
| `VALIDATION_FAILED` | 必要检查失败，或受支持条件、义务、受影响表面或 Author 操作缺少有证据支持的结果或授权。 |
| `READY` | 每项必要映射均已具备，每个受支持输入都无需虚构事实便能选出恰好一个可观察策略结果，且所有适用的确定性检查均通过或有证据支持记为 `NOT_REQUIRED`。 |

停止时指出阻塞项、所有者、后果和重新尝试的条件。就绪交接说明 Candidate、目标及证据所有者、义务处置、检查、保留约束，以及不确定或未测试表面。它是 `setup-project-agents` 的输入，不授予下游安装、发布、提交或推送权限。
