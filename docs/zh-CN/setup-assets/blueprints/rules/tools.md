# 工具

## 目的与证据

对于独立创建或修订 `.agents/rules/tools.md` 的请求，使用 `write-rules-and-skills` 编写一份归目标仓库所有、标题为 `Tools` 的 Rule。

根据已接受请求和当前证据确立目标仓库。Author 主动发现并核实相关目标证据：入口指引、清单和运行时要求、仓库脚本及其当前帮助、任务运行器和 CI、Git 状态、既有 Rules 和 Skills，以及已接受的 Issues、Specs 或 ADRs。复用调用方提供的合格证据，直接发现缺失事实；调用方无需事先准备证据包。按所有者和来源评定每项资料。已接受的项目意图具有决定权；既有 Rule 文本提供保留和回归证据。将义务分类为保留、变更、新增、停用或非目标；除非已接受意图要求变更或停用，否则保留受支持策略。可见性和访问权限不授予权威。

## 需要确立的策略

Rule 将每个会影响结果的条件与其要求的结果关联起来：

- **调用：** 决定工具能否正常工作的工作目录和运行时要求。
- **同步：** 规范来源的变更、所需同步、受支持的只读漂移检查，以及需要审查的生成效果。
- **变更：** 每项操作所需的权限，以及缺少权限时允许采用的只读、限定范围、试运行或停止结果。
- **验证：** 从声明的比较点出发核对完整变更，包括已跟踪、已暂存、未暂存和未跟踪状态、生成效果、受影响表面，以及每项适用的非修复检查。
- **交接：** 当既有 Skill 负责某项工作时，明确它的可观察触发条件和有界结果。

每次交接都必须遵守被调用 Skill 的调用条件和权限。环境准备的条件是：新建 linked worktree 的首次使用、有证据表明当前任务所需环境前提缺失或过时，或用户明确请求准备。前提满足时，普通实现和检查使用现有环境。仅位于 linked worktree 中或缓存准备记录失效，并不能确立准备需要；缓存有效性只决定在已有充分理由的调用中能否复用证据。

API、能力、生成来源、交付、安装、依赖、契约演进和放置策略仍归既有所有者负责。脚本保留确定性机制，Skills 保留流程。只有省略会改变策略结果时，才纳入可从当前所有者获取的事实；清单、命令目录、快照和调用方编排留给这些所有者。

## 更新重点

每次更新都重新核对运行时要求、工具入口、生成器所有权和 CI 选择条件。根据当前清单、脚本帮助和 CI 任务，确定哪些变化需要同步或验证。即使蓝图没有变化，也要及时修正已变化的事实；保留仍然适用的项目特定条件和权限边界。

重点说明贡献者运行工具前需要作出的判断：正确的根目录、受影响的输入和输出、受支持的检查，以及检查结果要求的操作。稳定策略的含义仍然准确时，保留原有措辞。替换过时映射，不再追加相互竞争的操作配方；证据没有表明需要修正时，保留完整的原有 Rule。

## 编写边界与验收

Author 可以查看目标证据，运行所有者支持的只读或非修复检查，并在本次请求授权的 Candidate 根目录下创建或替换 `.agents/rules/tools.md`。写入前，通过公共 writer 确定该根目录、确切路径和操作。不要求固定的暂存目录。删除、移动、写入实际目标、无关变更和外部效果都需要单独的已接受授权。

公共 writer 负责编写、审查和终止结果。本 Rule 的验收要求每项必要映射和受影响表面都有证据支持的结果：每个受支持的判别条件都无需虚构事实便能选出一个可观察策略结果，且每条纳入的确切命令都受其当前所有者支持。必要检查必须通过；省略检查需要有证据证明其不适用。

在 writer 交接中说明目标及证据所有者、义务处置、检查结果、保留约束，以及不确定或未测试表面。对于尚未解决的访问、证据或授权缺口，指出阻塞项、所有者、后果和继续所需的条件。交接必须能由调用方独立使用，且不授予下游生成、安装、发布、提交或推送权限。
