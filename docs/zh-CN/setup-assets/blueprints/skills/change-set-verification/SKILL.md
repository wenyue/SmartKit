# 变更集验证

## 目标含义

当 `setup-project-agents` 请求
`GENERATED/.agents/skills/change-set-verification/SKILL.md` 时，编写这一个由目标仓库所有、
由模型调用的 Skill。其执行者是负责验证内在一致且已完成的变更集的 Agent，包括目标仓库的
`change-set-verifier`；其触发条件是交接前出现已完成的实现检查点。在产生新的已完成检查点之前，
活跃的实现或调试工作仍归其当前责任方所有。

目标 frontmatter 使用 `name: change-set-verification`，省略
`disable-model-invocation`，并让 `description` 表明已完成检查点这一触发条件和验证结果。把完整的
运行时契约保留在唯一的 `SKILL.md` 中；实时仓库责任方继续拥有确定性命令和映射。

使用已接受的项目意图，以及经目标仓库责任方和来源限定的证据。相关证据包括项目 Rule 和 Skill；
已接受的任务和比较点；版本控制状态；清单、锁文件、工具链声明、仓库脚本及其当前帮助信息；测试布局
和 CI 配置；以及生成源、依赖项和直接测试的责任方。现有目标 Skill 是保留行为和回归验证的证据，
而不是设计权威。除非已接受的意图更改或淘汰其行为，否则保留其受支持行为；可见性、可执行性、
写入权限或 Future Author 权限均不向 Candidate 授予运行时许可。

## 必需的运行时契约

### 选择、影响与安全

要求该 Skill：

- 根据已接受的任务上下文和当前仓库状态，确定预期变更集和比较点，并计入其生产代码、测试、配置、
  配套文件、生成影响以及已跟踪、已暂存、未暂存和未跟踪状态；
- 保留 `HEAD`、索引、无关工作和用户自有文件，同时仅规范化所选的项目自有源文件，并且只通过已声明
  的责任方更改生成输出；
- 将变更集映射到当前责任方所支持的最小充分 formatter、静态检查、测试、构建、运行时和 diff 完整性
  验证面；只有当依赖关系、共享契约、生成接口、工具限制、fixer 修改、缺失的测试归属或未解决的范围
  会使更窄的证据不可靠时才扩大范围，绝不只是为了发现或修复既有问题；以及
- 按范围保真度、修改边界、诊断质量和最终证据的可信度，选择有效的仓库工具、原生工具或 MCP 工具。
  应指向实时责任方，而不是缓存命令清单或可从当前配置或帮助信息恢复的值。

Candidate 的运行时影响授权是穷尽性的：它可以运行由责任方支持的证据生成型检查，但这些检查所声明的
输出必须限于责任方声明的项目路径；它也只能使用责任方支持的 formatter，或仅针对已知机械诊断或
已接受机械迁移而获准的自动 fixer，对所选项目自有源文件进行规范化。它只能通过已声明的责任方更新
生成输出。每项修改和一次性检查输出都必须限定范围并报告。保留 `HEAD`、索引、无关工作、用户自有
文件以及此授权之外的一切影响。所需影响不可用时，在该影响发生前返回 `inconclusive`。尝试产生或
观察到此授权之外的影响属于安全违规：停止进一步影响、保留相关证据，并在诊断路由之前返回 `failed`。

### 流程孤岛

只要求执行能够保护状态和证据的顺序：

1. 在发生修改前，确定检查点、所选范围、归属、前置条件和必需验证面。
2. 适用时，对所选的项目自有源文件运行责任方支持的 formatter。仅针对已知机械诊断或已接受的机械
   迁移，在每个检查点上以最小受支持范围运行一次已授权的自动 fixer。必要时重新格式化，并将工具
   修改的每个文件加入所选变更集。
3. 从所得状态开始，先运行最小且受支持的非修改性静态检查，再运行直接归属的测试，之后只运行由已
   证实的风险或归属所选择的更广验证面。每个不同验证面只运行一次，除非后续修改使其证据失效。
4. 将剩余语义诊断及准确证据交回实现责任方。实现责任方的任何修改都会创建一个新检查点，并从当前
   仓库状态重新开始验证。

如果活跃 Harness 能保留各自的选择器和证据，互不依赖的非修改性检查可以并发运行。对修改敏感的检查
以及生成输出的消费者仍应保持顺序。当某个所选失败可能早于当前变更时，只针对该失败验证面使用可信
基线进行分类，并且基线工作不得超出分类所需范围。

### 可选的确定性选择器

只有当经限定的证据证明责任方工具无法表达必需且重复的确定性选择或聚合，并且来自授权来源的已接受
输入提供脚本准确的 Candidate 相对路径和目标责任方时，Candidate 才能包含一个辅助脚本。Future
Author 可以验证并使用这两个值，但不能选择它们。缺少授权、授权有歧义或授权与责任方不匹配时，须在
写入任何 Candidate 前以 `HUMAN_DECISION_REQUIRED` 停止；glob、目录级授权或运行时选择的路径均
不充分。Candidate 应规定准确的输入和输出 schema、允许的文件系统和进程影响、失败行为、责任方支持
的运行时、代表性和边界校验，以及责任方工具取代它时的移除要求。该脚本实现已经确定的映射；不得选择
策略、范围、归属、权限、扩大范围或结论。脚本失败时，报告其准确调用和错误并停止；修正需要新的、
经过审查的 Candidate。

### 可观察结果与退出

针对每个所选验证面，报告责任方支持的调用、范围、选择理由、`passed`、`failed`、`inconclusive` 或
`not applicable` 结果，以及所有剩余缺口。还要报告每次规范化调用及其修改、重复执行及其原因、语义
诊断和未测试的验证面。

应用上述安全违规防护后，只返回一个总体结果；按顺序采用首个为真的判别条件：

1. 当可信且完整的证据诊断出实现责任方必须对检查点作出的语义更改时，返回
   `semantic_fix_required`。报告并发出现的机制故障或证据缺口，但它们不能取代这一结果。
2. 未确定需要语义修复，且可信证据表明所需机制、工具或运行时失败时，返回 `failed`。
3. 两个在先结果均未确定，且必需证据、归属、前置条件、比较点、仓库状态或基线分类不充分时，返回
   `inconclusive`。
4. 只有当每个必需验证面均通过、每项所选修改均有明确归属并包含在已验证变更集中，且不存在必需
   证据缺口时，才返回 `passed`。

退出时保留已观察到的状态和证据。该 Skill 不负责业务实现、语义修复、工作树创建或集成、依赖安装、
Agent 同步、Git 历史修改、交付或破坏性清理。它只能执行上述所选的项目自有规范化和证据生成型检查；
任何其他修改或外部影响都需要另行获得已接受的授权，否则须在产生该影响前返回 `inconclusive`。

## Future Author 授权

Future Author 可以检查经限定的目标证据、运行责任方支持的只读或非修复性检查，并且只能创建或替换
`GENERATED/.agents/skills/change-set-verification/SKILL.md`，以及已接受输入按上述要求授予准确路径
和责任方的单个可选脚本。Author 不得删除或移动文件，不得写入实时目标或修改无关的目标状态。除下述
Acceptance 授权之外，Author 无权产生外部影响。创建 Candidate 不会把 Author 的权限转移到 Candidate
的运行时授权中。

## 编写证明与 Acceptance 授权

证明是证据依赖图，而非实现顺序：

- **Machine 证据：**使用责任方支持的确定性非修复检查，校验完整 Candidate 的结构、frontmatter、
  引用、路径以及任何脚本。
- **Quality 和 Correctness Review：**根据经限定的证据，审查调用方式、范围、影响授权、检查映射、
  顺序、扩大范围、基线分类、结果优先级、脚本例外、退出和交接。**Review PASS**要求解决每一项不受
  支持或有歧义的映射。
- **Acceptance 屏障：**Acceptance 要求同一 Candidate 的 Machine 证据以及 Quality 和 Correctness
  Review PASS。达到 PASS 时，冻结 Candidate 的指纹、受保护目标状态（`HEAD`、索引、无关状态和
  用户自有状态），以及授予 Acceptance 修改权限的准确路径和预期影响。任何其他 Review 结果都须在
  Acceptance 前停止。
- **Acceptance 证据：**在一个有代表性且内在一致、已完成的变更集，以及一个安全且适用的失败或停止
  路径上实际运行 Candidate。证明规范化范围、必需检查、结论优先级、报告以及无关仓库状态得到保留。
- **最终边界：**Acceptance 后，根据 Review PASS 指纹重新检查 Candidate 和受保护目标状态，并将
  每项获授权的可修改路径变更与冻结的 Acceptance 影响计划逐一核对。记录预期且已授权的变更，不将
  其视为漂移；任何其他变更都会使 Review 和 Acceptance 失效。记录准确调用、修改、诊断、初始和
  最终状态以及未测试的验证面。

本契约仅向 Acceptance 授予上述 Candidate 运行时影响，并且这些影响仅限目标仓库中已识别的代表性
变更集，且只有经限定的目标责任方允许时方可执行。在执行前后记录准确的目标、所选文件、调用、预期
影响和观察到的影响。此授权不包括依赖安装、历史修改、交付、破坏性清理以及任何无关仓库影响或外部
影响。如果必需的 Acceptance 影响超出此授权，或缺少目标责任方的授权，须在执行前以
`HUMAN_DECISION_REQUIRED` 停止；Future Author 的写入权限不能为其授权。

只返回一个编写结果；按顺序采用首个匹配的判别条件：

1. 必需证据或校验在授权范围内不可访问时，返回 `ACCESS_REQUIRED`。
2. 可以访问，但无法从经限定的证据中发现某项必要事实时，返回 `CONTEXT_REQUIRED`。
3. 经限定的证据允许存在实质不同的语义，或者必需的归属、比较点、许可、影响、例外或淘汰没有获得
   已接受的授权时，返回 `HUMAN_DECISION_REQUIRED`。
4. 校验仍然失败，或任何必需的运行时输入缺少一个受支持的可观察结果时，返回 `VALIDATION_FAILED`。
5. 只有当最终边界证明经过审查和 Acceptance 的 Candidate 未发生变化、包含每项必需义务、将每个
   受支持的运行时输入映射到恰好一个结果，并且所有适用检查均通过或记录为 `NOT_REQUIRED` 时，才返回
   `READY`。

每次停止都要报告阻碍、责任方、后果和全新尝试的条件。`READY` 报告准确的 Candidate 路径、证据
责任方、保留、更改、新增、淘汰和非目标处置、检查、Review 和 Acceptance 证据以及未测试验证面。
它只作为 `setup-project-agents` 的就绪输入，不授予任何下游生成、安装、发布、commit 或 push 权限。
