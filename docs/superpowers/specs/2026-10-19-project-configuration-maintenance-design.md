# 项目配置库维护设计

日期：2026-10-19

状态：已按确认范围实现并通过本地验证，尚未发布。

## 目标与已确认范围

让用户把个人项目 Agent 配置保存在独立于业务仓库的个人私有 GitHub 仓库中，由一个配置库服务多个项目。日常在业务项目的聊天中发起维护，Agent 根据业务项目的真实上下文修改配置库中的源，再应用回该项目。

配置范围包括项目指令、Rules、Skills 及其必要支持文件、自定义 Agents、MCP 声明和项目级宿主设置。全局宿主配置、凭据和机器运行状态保留在各自原有位置。术语见[SmartKit 词汇表](../../../contexts/smartkit/GLOSSARY.md)，源权威决定见[ADR 0020](../../adr/0020-author-project-configuration-in-a-personal-repository.md)。

## 编写源与项目绑定

面向用户提供三种完整维护模式：

- 项目共享：项目内的当前 canonical 输入继续作为编写源，随业务仓库共享。
- 仅本机：项目内的当前 canonical 输入继续作为编写源，通过 Git 本地排除规则保留在本机，不需要 GitHub。
- 独立配置仓库：所选个人私有配置库条目是编写源；业务项目保留应用结果和本机状态，并通过 Git 本地排除规则避免纳入业务仓库。setup 和维护 Skill 均先更新该编写源。

绑定项目的受管配置编写先解析此来源，再向既有公开作者流程提供业务项目证据和源输出位置。宿主发现仍使用业务项目中经过验证的应用结果。绑定的变更属于项目本机引导操作，不由配置正文反向覆盖。

项目内 `.agents/config.json` 增加可选的 `maintenance` 声明。三种用户模式分别记录为 `local`、`local-only` 和 `repository`；已有 `local` 保留项目共享含义，不自动改为仅本机。配置库模式还包含 GitHub 仓库标识、分支和项目条目标识。仓库分支在绑定时确认，不猜测默认分支。每个条目管理一个项目的配置，第一版使用独立条目，不引入跨条目的继承合并机制。个人配置的排除使用 Git 的 `info/exclude`，不修改共享 `.gitignore`，也不自动取消已有文件的 Git 跟踪。

本机的持久源库工作副本位置由用户级状态解析。绑定不携带其他机器的绝对路径。源库工作副本可能包含尚未推送的唯一内容，必须按源材料保存，不能进入有过期删除生命周期的临时产物缓存。

下发配置按声明的文件、章节或结构化字段应用。目标的绑定、`setupVersion`、所有权记录和运行状态由其原有 owner 管理，不作为源库配置正文整文件覆盖。宿主适配文件、索引和共享插件交付内容继续通过既有 owner 生成或同步。

## 首次 setup

首次 setup 与升级在 Skill 中分别给出入口、所需输入、步骤和完成条件；共享底层检查和应用机制。

1. 检查项目现状、既有配置和所有权，识别全新项目、已有但缺失成功基线的项目。
2. 一次性呈现项目共享、仅本机和独立配置仓库三种完整选择。
3. 选择配置库维护时，支持连接已有个人私有 GitHub 仓库，或按用户明确指定的身份和名称创建新私有仓库；后续项目可复用该仓库。
4. 配置库模式下选择已有条目，或为当前项目建立新条目。建立条目时保留当前有效配置及其独立所有权，只有经识别和接受的个人配置进入源库。新机器连接已有条目时先比较目标现状。
5. 写入所选模式；配置库模式下准备可用的持久源库工作副本。依据业务项目上下文，在对应编写源完成配置评估和编写。
6. 按所选模式验证、应用，并报告本机 setup 与源库同步的实际结果。

个人配置的本机 Git 排除应避免将其加入业务仓库；已经被业务 Git 跟踪的文件不能靠排除规则隐藏，必须保留其既有归属并在涉及接管时展示真实差异。

## 升级

- 根据现有初始化和成功版本记录判断升级需求，不把缺少维护方式误判为全新项目。
- 旧项目首次升级到这项能力时，若尚无维护方式记录，补问一次并保存选择；后续升级沿用记录。
- 没有成功版本基线的已有项目保留所有权与内容，按原合同建立基线，不猜测历史版本。
- 汇总全部适用迁移，检查业务项目及源配置。配置库模式下先在源库完成需要的配置修订，再应用目标。
- 用户明确要求切换维护方式时，执行差异检查与源迁移；普通升级保持已选方式。
- 保留 CodeGraph 准备、完整配置评估、作者流程、私有会话及失败恢复的既有要求。局部同步仍只承担其原有范围，不因名称相近而获得隐含的 full setup 或发布权限。

## 维护 Skill

新增一个明确调用的 `maintain-project-config` Skill，提供检查、维护并同步、显式采纳目标修改三个入口；setup 承担初始化、绑定以及升级。

“维护并同步项目配置”在配置库模式下包含：

1. 读取绑定，检查目标、源库工作副本、Git 分支和未完成状态，保留已有 staged、unstaged 和 untracked 工作。
2. 获取源库更新并使所选分支安全收敛；有冲突或无法验证源状态时先解决该条件。
3. 根据业务项目证据和本次维护目标修改源配置，通过适用的公开编写流程保持 Rules、Skills 的作者与审查责任。
4. 验证源配置并预览目标变化；发现目标侧未采纳的修改时，保护双方内容并展示差异。
5. 通过现有所有权边界应用并核验目标；需要完整 setup 的变更走对应升级流程。
6. 仅提交本次维护的范围，并正常推送到所选分支。提交钩子改变源内容时，重新核验它与已应用内容的一致性后再发布。
7. 依据实际 Git 结果确认目标提交已到达远端，报告应用内容、源提交和目标完成状态。

用户明确调用“维护并同步”表示请求本次正常提交与推送。普通项目编辑不会因此获得向配置库远端写入的授权。第一版按明确调用执行，不增加启动时自动获取或自动应用。

## 显式采纳目标修改

当业务项目中的副本与源配置不同，普通维护展示差异并保留双方内容。

用户可明确选择“采纳目标修改到源库”。该操作核对最后应用内容、当前源内容和目标修改，只将用户接受的文件或字段变更写入源库，再走验证、应用、范围提交和正常推送。初次导入与后续采纳共用来源和所有权保护；未经选择的目标内容继续保留其原有归属。

## Git 访问与失败边界

个人私有配置库使用经验证可用的用户 GitHub/Git 访问方式，认证材料保持在原有凭据管理位置。现有公共第三方 Skill 快照的隔离抓取合同维持不变；个人源库访问作为独立入口实现。

不假设配置库 Git 操作、目标应用和 setup 清理能够组成一个跨仓库原子事务。分别报告：

- 源工作副本更新、编辑、验证和本次范围提交的状态；
- 目标应用、原有 full setup 完成条件和实际 `setupVersion`；
- 远端推送及目标提交是否已保存。

`setupVersion` 继续表示最近一次实际成功的本机 full setup。维护、推送和普通局部同步不单独推进它。若本机 full setup 已成功而稍后的 push 失败，新本机版本仍准确；外层维护报告“本机已完成、远端同步未完成”，不宣称整项维护完成。

推送失败或远端前进时保留本地提交及已应用目标，先查明原操作结果，再进行受保护的重试或冲突处理。目标应用、清理或版本写入失败时遵守各自现有恢复合同，并准确报告已发生的部分结果。恢复不覆盖其他项目或已有用户工作。

## 实现边界

- 重整 `setup-project-agents` 的首次 setup、升级及相应引用，保留局部同步的独立合同。
- 新增维护 Skill；Git、绑定和源库配置读写的共享机制由 setup 与新 Skill 共同使用，并放在声明、打包的共享运行时边界。setup 继续拥有蓝图评估和宿主适配语义。
- 扩展现有项目配置 schema 与解析器，区分可迁移配置、目标绑定及本机执行状态，保持现有未绑定项目可读取。
- 复用并扩展来源记录、范围提交、所有权、差异预览和目标验证机制，避免创建第二套相互覆盖的目标管理器。
- 按实际新增公开入口更新插件声明、英文与中文 README；first-party Skill 变更同步中文镜像。
- 按实际合同变化评估必要迁移及发布版本，使用本仓库对应的维护流程，不猜测已有项目的成功基线。

## 验收

1. 首次本地维护与首次配置库维护分别完成；后者覆盖创建新私有仓库、接入现有库，以及多个项目复用一个库。
2. 旧项目只补问一次维护方式，升级保留已选方式、既有工作与适用迁移顺序。
3. 在不同本机路径连接同一源条目，恢复同一配置，同时保留各自绑定、成功基线和运行状态。
4. Rules、Skills、自定义 Agents、MCP 和项目级宿主设置均按已声明范围应用，独立字段与内容保留。
5. 外置模式的 setup 和后续受管配置编写均解析正确源位置，使用业务项目证据；日常维护只包含本次授权范围。
6. 目标手改得到保留并能被显式采纳；冲突和未归属内容不会被静默覆盖。
7. 校验、应用、提交钩子、清理、版本写入、推送与远端并发失败均报告真实状态，并能基于保存的证据继续恢复。
8. 本地工作完整性、范围提交和正常推送得到验证；完整维护只在远端保存确认后成功。
9. 实际 owner 检查、受影响测试、镜像与插件交付检查，以及相应 diff whitespace 检查全部通过。
